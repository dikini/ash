Forwarding capability evidence

The previous lesson made a client choose Equal<Int> directly from the source that defines it. A larger program may not want every client to depend on that source. It may place a smaller public boundary in front of several libraries and let clients depend on that boundary instead.

Such a boundary is called a facade. An Ash facade can re-export public names, but equality behavior needs more than names. The implementation owner, facade, and client form a route: the owner publishes an implementation fact, the facade authorizes that fact for its dependents, and the client selects it. We can observe what each hop contributes without writing another equality implementation.

Begin with the same equality.ash source used in the previous lesson:

pub interface Equal<A> {
    equal : (A, A) -> Bool
}

pub impl Equal<Int> {
    equal (left, right) = left == right
}

pub same : (A, A) -> Bool where Equal<A>
same pair = equal pair

This source still owns the Equal interface, its Int implementation, and the constrained same definition. The facade will not copy any of those declarations.

What do public names carry?

First read names_only_facade.ash, which contains one public targeted import:

pub import equality (Equal, equal, same)

The import makes the three selected names available in the facade and stages them for its public summary. A later client reaches the original declarations through those spellings: re-export preserves each defining identity rather than creating a forwarding declaration. But ordinary name items select no implementation facts. These are separate rules in Ash’s imports and namespaces.

Use that facade from 02-names-only.ash:

import names_only_facade (same)

main : Unit -> Bool
main () = same((21, 21))

Before running it, follow the name route. The client imports same from the facade, and the facade publicly imported same from the equality owner. The call can therefore reach the constrained definition. Now ask a different question: which source item selected Equal<Int> implementation evidence for this client?

Run the entry from this lesson’s src directory:

Ash exits with status 1 and writes this message on standard error.

Typing the integer pair fixes the call’s requirement to Equal<Int>, but no implementation item supplied a candidate. The diagnostic places its sole primary label on the same call. Its related labels identify the client’s import and the original same and Equal declarations in equality.ash. There is no facade-owned copy to identify, and the unselected implementation is not exposed. The constraint-selection rules make an eligible concrete obligation with no available source constraint.unsatisfied.

Forward the implementation route

capability_facade.ash differs by one import item:

pub import equality (Equal, equal, same, impl Equal)

impl Equal binds no source name. In this public import, it selects the equality owner’s public Equal facts and adds their authorization routes to the facade’s public implementation closure. The route retains its hop back to the defining source and preserves the original implementation identity. The facade still contains no interface, function, or implementation body.

The client must select the route that the facade made public:

import capability_facade (same, impl Equal)

main : Unit -> Bool
main () = same((21, 21))

Trace the implementation route from this client through the facade to equality.ash. Which item authorizes each hop, and which complete requirement does the integer pair create? Predict the comparison’s boolean, then run it:

ash 01-forwarded.ash

Ash reports:

true : Bool

The result comes from the original method’s 21 == 21 comparison. same receives that method and returns its answer; the facade adds no calculation.

There are two explicit implementation items. The public item in the facade authorizes the route for later dependents. The private item in the client selects that authorized fact into the client’s effective implementation environment. Ordinary typing fixes Equal<Int>, the route leads to the original implementation, and its method compares the two integers.

This routing is static. A public import does not construct a runtime facade object, register an implementation, or arrange dynamic dispatch. After Ash validates the selected route, it lowers evidence to ordinary Core functions and applications. The evaluator performs no runtime interface lookup.

The source adds one import hop and an explicit selector at each boundary that forwards or consumes the capability. The invariant is visible in source: names and implementation authorization travel through independent items. The facade gains a stable public boundary without duplicating the interface, constrained function, implementation identity, or method body.

Practice: inspect each hop

Start each task with fresh copies in a scratch directory. For tasks one, two, and four, copy equality.ash, capability_facade.ash, and 01-forwarded.ash together. For task three, copy equality.ash, names_only_facade.ash, and 02-names-only.ash instead.

  1. Remove impl Equal only from capability_facade.ash, leaving the client selector in place. Predict whether the failure occurs while resolving the import or while satisfying the call, then run it. This is a different boundary from the lesson’s name-only client.
  2. Remove impl Equal only from 01-forwarded.ash. Predict whether the facade’s public authorization is enough for this call, then check and explain the observation through the two imports.
  3. Add the ordinary name Equal to 02-names-only.ash’s import. Predict what the call requires and what the new item supplies, then run it and explain the message’s labels.
  4. Change pub import to import in capability_facade.ash. Identify which facts remain usable inside that facade. Predict what its client can import, then check your prediction.

Both facades contain a single import line, and neither copies a declaration; what differed was whether impl Equal rode the public boundary and was selected again at the client.
