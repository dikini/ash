Resource definitions, typing, surface forms, and Core

Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes

This study is experimental evidence under DN-0036. The type schemas, grammar, and transitions below are comparison inputs, not accepted Ash syntax or normative semantics. Incomplete contracts cannot authorize an implementation slice.

Method and current boundary

Always follow the types. Start with a resource type definition, check its provider and associated effect interface and handlers, then derive the typing of a resource instance. A proposed spelling needs that account before becoming an implementation target.

Current resource typing and syntax provide the baseline: the initializer is checked before introducing the fresh identity; the acquired body receives a handle, exact sealed authority, and an interpreter. Current Ash supports only cell and native_buffer, with compiler-defined contracts. This study proposes library-defined resource types. It must preserve the distinction between ordinary effect interpretation and authority to create or complete a resource.

Use current effects and handlers where their types suffice. Effects declare parameterized operation interfaces; handlers check implementations against those operation types. A resource type adds the relationship between that interface, provider state, initialization, unique identity, access, and completion. A matching set of method names is insufficient to establish that relationship.

Declaration and instance

The first declaration spelling is a module declaration. It creates an opaque resource family; it is not a data declaration followed by an ordinary impl. Fields and clauses end at line boundaries, following current declarations. The following is the complete assembly shape, with operation bodies supplied by the Ash library author:

pub resource Connection<R> {
input OpenConfig
state Native.ConnectionState<R>
result Provider.Scope<OpenError, CloseError, T> for <T>
provider ConnectionProvider<R>
effect ConnectionOps<R>
interpret Native.Connection<R>
acquire config => perform Native.Connection<R>.open config
finish state => perform Native.Connection<R>.close state
handlers state {
diagnostic db => resume (ForeignError (perform Native.Connection<R>.diagnostic state))
}
}

pub resource Statement<S, C> {
input (Connection<C>, SqlText)
state Native.StatementState<S, C>
result Provider.Scope<PrepareError, FinalizeError, T> for <T>
provider StatementProvider<S, C>
effect StatementOps<S, C>
interpret Native.Statement<S, C>
acquire input => match input {
(db, SqlText(sql)) => perform Native.Statement<S, C>.prepare (Provider.state_of db, sql)
}
finish state => perform Native.Statement<S, C>.finalize state
handlers state {
bind_int operand => match operand {
(stmt, index, value) => match (perform Native.Statement<S, C>.bind_int (state, index, value)) {
Native.Ok(()) => resume (Ok ())
Native.Err(error) => resume (Err (ForeignError error))
}
}
step stmt => match (perform Native.Statement<S, C>.step state) {
Native.Row => resume Row
Native.Done => resume Done
Native.StepError(error) => resume (StepError (ForeignError error))
}
column_int operand => match operand {
(stmt, index) => match (perform Native.Statement<S, C>.column_int (state, index)) {
Native.Ok(value) => resume (Ok value)
Native.Err(error) => resume (Err (ForeignError error))
}
}
}
}

The two state families are public opaque native nominal families of kinds ConnectionState : Type -> Type and StatementState : Type -> Type -> Type. Their internal constructors are absent from every source-visible constructor channel. Acquired state tokens are made only by registered native operations under their unpublished guards. Acquire and Finish constructors are ordinary data and provide no guard or capability by themselves; controlled template checking and runtime postcondition tokens are required even if a client constructs a Consumed value.

NativeFailure stores the exact native result code and a copied diagnostic as independent UTF-8 String. Input/protocol faults map the safe adapter's structured failure before native use. Native column-kind rejection is ColumnTypeMismatch; a failed native conversion is ConversionFailure. Actual SQLite allocation failure retains NativeFailure with its native code; AllocationFailure is reserved and unused by this adapter. These wrappers keep the error families distinct without duplicate constructor names in the registered module.

The selected codec admits bounded packed Bytes and String and produces independent copies from native diagnostics and columns. The initial MoreBytes/EmptyBytes family is absent from the manifest and source re-exports. String generally permits NUL, as specified below. The selected adapter rejects embedded NUL in paths, SQL and bound TEXT. InMemory supplies the native :memory: filename. Returned TEXT uses its explicit byte length, preserves embedded NUL and requires valid UTF-8 without replacement; malformed native TEXT produces a conversion failure. These are selected adapter contracts, not restrictions on all String values.

Empty BlobBytes is a BLOB, empty TextValue is TEXT, and NullBytes and NullText denote SQL null in their respective result families. Empty payloads do not become null through a null host slice pointer. Source error mapping adds only the library protocol cases shown above.

Both TEXT operations borrow the tuple's state operand at position 0 and return independent data; they add no acquisition or completion authority.

Their later retained/view variants need separate declared relations, not a changed meaning for these copying calls.

Provider.state_of is a general controlled primitive. Descriptor admission supplies a sealed determination relation StateAccess<Q,State> from an exact resource access type to its exact associated state type. Its method has type Q -> State, using current determined-interface typing. Thus in the statement acquire template Provider.state_of db : Native.ConnectionState<C>. The primitive can run only in provider contexts, borrows a live scope's state, and cannot complete or transfer that owner. Its result retains C and cannot leave the provider context. Runtime dispatch uses the admitted resource definition and activation IDs, never nominal spellings. A new library receives this relation from its own resource descriptor without changes to the primitive's code. Finisher capability checks still permit completion of the current owned state only, excluding an outer state obtained this way.

Generated provider handler entry independently authenticates the resource access operands against its instance before executing the source clause. It retains typed operand positions from the associated signature, including tuple fields; ordinary source handler overrides retain existing checking and precedence. Native borrowed calls then need only the state token and raw operands. This avoids a cyclic native signature mentioning library handles and avoids passing redundant client handles to the adapter.

ConnectionProvider<R> and StatementProvider<S,C> are source-declared interfaces. Their methods have the associated operation names and value types, with the exact associated effect row on the result arrow. For example, StatementProvider<S,C>.bind_int has value type (Statement<S,C>, Int, Int) -> Result<Unit> ! {StatementOps<S,C>}. The resource association seals these interfaces against ordinary impl and with construction. Declaration admission rejects an existing implementation, another resource association or a missing/mismatched method. The association generates checked forwarding evidence at acquisition, following the current cell convention, rather than requiring the library to implement construction authority in an ordinary interface equation.

Methods enter the module's existing term namespace. A collision uses ordinary duplicate-name rejection, including two associated interfaces with the same method spelling in one module. Authors can use distinct operation names or separate modules; targeted imports already permit term aliases. No special type-qualified method lookup is added. The first SQLite module's diagnostic, bind_int, step and column_int are distinct.

Handler template answer and row instantiation

Declaration checking allocates a fresh hidden answer binder A of kind Type and a distinct hidden row binder rho of kind EffectRow before checking the actual operation clauses. These identities belong to the defining ProviderTemplateId and cannot alias a source answer parameter, a formal resource parameter, or another template's hidden binders. The canonical associated operation op_i : P_i -> Q_i determines the pattern type P_i and resume input Q_i. Every clause produces A; its owned resume produces A with the shared handler output Omega. The declared resource operand type is not A.

A template retains its checked direct clause-demand relation D(sigma,c) and its relation to the full client continuation row epsilon as separate facts. Here sigma is the authenticated kind-preserving substitution of formal arguments and selected evidence. The input c is independently reconstructed from the actual owned captures, their completion obligations and the surviving interpreter context, using current capture, discard and completion rules. A scalar epsilon and sigma alone do not determine discard's close demands. When c is not yet known, the template retains authenticated conditional equations for those demands; it does not assert a concrete close row. D_sigma is shorthand only for capture-independent cases.

D(sigma,c) includes resume argument evaluation and all other direct clause work, including native requests, checked helper latent demands and admitted close execution. Its derivation suppresses shared outputs of the properly owned internal resumes within the relevant direct-demand analysis, preserves their argument demands, and applies ordinary exact nested-handler removals. It does not replace nested handlers' own output checks. The full epsilon is the actual handled body's outward remainder at the generated ordinary exact handler boundary, derived by current exact removal, not an arbitrary row supplied by the provider. The outer shared output must satisfy the least ordinary principal union Omega = D(sigma,c) union epsilon and agree with the independently reconstructed ordinary least-output equations of the actual handler graph. This equality is checked, not assumed to linearize every nested row equation. All known members, tail identities and lacks constraints follow current row algebra.

The hidden rho may occur as an ordinary Core tail only in a recorded residual realization of that relation. Let K be the exact known-member set of D(sigma,c) after substitution and canonical coalescing. After deriving Omega, derive r by exact removal from Omega of every member of K; no removal searches an unconstrained tail. The instantiation relation is rho -> r, with r = Omega remove K and Omega = K union r. Thus rho denotes this normalized residual, not epsilon. An open r retains Omega's exact tail identity and every existing lacks fact, including the justified exclusions of K. For a closed r there is no tail constraint to retain. Recomposition uses ordinary row formation/substitution and must equal Omega, including tail identity and accumulated lacks facts. Replacing rho with epsilon without deriving and checking this relation is invalid; kind agreement alone is insufficient. If the authenticated relation establishes epsilon = r, the same row value is a valid replacement. This occurs, for example, when D is empty, or when D is closed and its known members are disjoint from epsilon. Replacement validity depends on the row equations and constraints, not on the row value's origin.

The exclusions of K in the residual template's own tail describe this internal normalization relation; they assert nothing about absence of K from the full client continuation. Authority for D comes from checked actual clause Core, authenticated operation, helper and evidence facts, and independently reconstructed c where completion depends on capture. Authority for epsilon comes from the checked actual body and exact handler boundary. Authority for r and its lacks facts comes from the independently checked union and exact removals. Neither EffectRow construction, draft metadata, matching names, nor a public-summary assertion supplies those proofs. Ordinary instantiation must still check all additional retained template lacks constraints, occurs checks, kinds and scope identities.

A single ordinary open row does not encode an unresolved equation between distinct direct-demand and continuation tails. Until the existing algebra can establish their relationship, the generic template retains the D(sigma,c)/epsilon/Omega relation and the actual clause row-replay inputs as an authenticated internal recipe. This recipe is conditional template validation, not a new source row syntax, a qualified ordinary type scheme, or proof that provisional Core already satisfies ordinary handler row equations. Specialization resolves that recipe with checked actual arguments and reconstructed c, computes the existing principal union and any residual realization, and solves and checks each handler's distinct shared-output equations through the retained typed graph. It instantiates admitted Core and its authenticated facts; it does not re-elaborate provider source or resolved bodies. Every resulting ordinary exact Handler then undergoes ordinary independent validation, including least output, resume argument/result/row, structural scope, capture and completion. If the current union is nonprincipal, specialization reports that ordinary ambiguity without adding lacks facts. A representation that cannot yet retain an otherwise principal recipe is an explicit implementation frontier, not a new language rejection or a global closed-row requirement.

The authenticated body-free summary must preserve the defining template identity, formal kinds and hidden-binder roles/identities, exact operation and resume contracts, D(sigma,c) or its checked demand recipe, the full-continuation-to-output relation, residual normalization and any additional row constraints, and relevant evidence, owner, capture/control and origin facts. Conditional completion contracts must identify the actual capture and surviving-interpreter facts needed to establish c; scalar effect rows cannot stand in for them. Executable linkage separately supplies the corresponding checked template graph, per-handler output and owner/root relations, and row-replay inputs. Independent admission compares these contracts with the defining checked context; copies or invented summaries cannot create authority. Native demands in D remain present in Omega until the separately admitted interpretation discharges the exact native instance. This row normalization neither authorizes native interpretation nor removes capture/control obligations.

Handler row recipe authentication

The retained recipe is an equation graph reconstructed from the actual typed clause graph, not caller-authored equations or a D/Omega match claim. Each real HandlerId, including nested handlers, has a distinct internal shared-output unknown Omega_h. Its actual owned ResumeIds refer to that unknown only through their authenticated handler/owner and clause-root relation. Unknowns with equal row values remain distinct identities. Ordinary child equations preserve resume arguments, callable/request demands, exact handler removal and all other current row operations. Direct-demand analysis suppresses only resume outputs whose handlers belong to the relevant analysis root's owned-handler set, as current least-output reconstruction does. An enclosing resume occurring in a nested handler's body remains an input from its enclosing Omega_h when checking that nested handler; it is not globally suppressed or treated as that nested handler's resume.

Independent template checking reconstructs those handler sets, actual clause roots and structural pattern/resume scopes. It checks canonical signatures, ordinary stored callable/request rows and authenticated imported selections, all non-row metadata, answer/input types, single consumption and phase authority. It reconstructs c-dependent demand equations and verifies that every deferred row position belongs to these actual equations. Builder ranges only delimit replay; they do not authorize deferred positions, handler identities or capture assumptions. Any row relation not independently derivable from the actual graph and canonical context rejects. D may therefore be a checked expression over formal row arguments and c, rather than an asserted literal.

At specialization, substitute authenticated kinded formal/evidence facts into those reconstructed equations and independently reconstruct c from the actual capture/completion and surviving-interpreter facts. Derive epsilon from the real outer handler body, and compute the outer candidate Omega using existing union/removal. Evaluate and check every retained node equation and every Omega_h against that handler's ordinary least-output reconstruction, with each actual ResumeId receiving its own handler's solved output. Recompute all affected resumes and descendants, including nested handler clauses; an outer range replay that keeps other resumes unchanged is insufficient. Check the outer candidate against the reconstructed outer least output rather than assuming the D(sigma,c) union epsilon form replaces those equations. Unresolved c-dependent obligations remain conditional until the actual facts establish them; none may survive admission to ordinary Core. No unresolved recipe, unchecked row hole or added tail exclusion survives that boundary. Ordinary independent handler validation is final: every handler result row equals its reconstructed least output, and all resume, scope, capture/completion and metadata checks pass.

Public summary retains authenticated conditional row contracts/known inputs for client checking; linked code carries the exact equation/root correspondence and must authenticate against that defining summary/context. An unpublished source draft may retain this information without Core admission. Independent generic template admission must prove this correspondence, not just construct the recipe. Closed D is an initial realization, not a P-1/source admission rule.

Required handler row evidence

  • D={H}, epsilon={H,K}: Omega={H,K}, r={K}.

  • D={H}, epsilon={H,K|eta}, with existing eta lacks H,K: Omega is unchanged; r={K|eta} retains both exclusions.

  • D={H}, epsilon={K|eta}, with an existing H exclusion: add H and preserve eta. Without H in epsilon's known set or eta's established exclusions, this is ordinary ambiguous union, not a new candidate rejection.

  • D={|delta}, epsilon={H}, with delta already lacking H: Omega={H|delta}. Refusal merely because D is open remains an implementation frontier.

  • With D empty, authenticated epsilon = r is a valid rho replacement. Also check a closed disjoint D/epsilon pair for which epsilon = r. Reject unchecked epsilon-to-rho replacement when overlap makes epsilon differ from r; do not reject an authenticated equal row value based on its origin.

  • A provider clause can contain the ordinary nested handler:

    handle({ let ignored = perform H.op (); resume () }) with H {
  op x => resume ()
}

    The first resume belongs to the outer provider clause and the second to H's clause. With outer epsilon={H,J} and D={}, outer output and its resume row are {H,J}; the nested handler output and its own resume row are {J}. Check both least-output equations and every node row. Keeping the nested resume's provisional empty row during outer replay is stale, not evidence that the nested handler has no outward demand.

  • Distinct actual owned captures or surviving interpreter contexts with the same sigma and scalar epsilon must derive their own c and close rows under existing rules. Reject forged c, erased close demands or asserted independent discard rows; unknown c remains conditional until specialized facts settle it.

  • Reject distinct unsolved tails, unjustified or forged exclusions, wrong exact effect arguments, hidden row identity collisions/occurs checks, mutated D/r/Omega with coherent row metadata, mismatched nested handler/resume/root identities, stale nested resume or descendant rows, and dropped native demand.

  • Specialization must work without provider-body replay. Preserve caller work and reject without publication on any failed relation.

State and native authority

The machine owns a nonduplicable native guard separately from source values. Native.ConnectionState<R> and Native.StatementState<S,C> are opaque, non-owning state tokens usable only in checked provider contexts. Connection<R> and Statement<S,C> are different opaque client access tokens. Neither token contains a source address or owns release. State tokens cannot become ordinary client results, captures, evidence fields or stored data. Provider templates may capture the state token for their owned handler and completion code; their scope and authority remain tied to that resource instance.

Ordinary local aliases of a state token inside its direct controlled computation preserve the same lineage. For example, let held = state followed by the permitted finisher on held does not create a second owner. Each alias remains subject to the phase's operation roles and the same completion capability; consuming that capability prevents subsequent native access through every alias, including after a retained outcome. This permits non-owning token aliases, not callable or storage transport of state or duplication of the native guard.

Acquisition has a controlled Acquire<State, InitError> result. Native code places a successful owner under the machine's unpublished guard before a state token can be delivered to the acquire template. A terminal successful branch publishes that guard once; a terminal failed branch publishes no access. There is no source publish function. Pure data preparation, error mapping and total matches are permitted, but each successful acquire path must return exactly the guarded state produced by its registered acquiring operation. Duplicating, discarding, replacing or fabricating native ownership rejects at declaration checking; local aliases do not alter which guard the returning path publishes.

The finish context has one controlled completion capability, analogous to the single-use resume capability. Every returning path must invoke exactly one registered finisher for its state. Finisher replies authenticate Consumed or Retained; returning an independently constructed report cannot manufacture that postcondition. The guard remains machine-owned until consumption or quarantine. Calling a finisher twice, calling it from an ordinary client, or using a state token after consumption rejects. Handler clauses may invoke only borrowed state operations, never acquiring or finishing ones. These are new provider checking obligations, not consequences of an ordinary function arrow.

Layout and publication

Witnesses describe a private native serialization, not a C ABI for arbitrary Ash data. Admitted rules are:

Payload Encoding and natural alignment
Unit Zero bytes, alignment 1.
Bool One byte 0/1, alignment 1.
Int Eight-byte signed two's-complement little-endian integer, alignment 8; values outside signed-64-bit range refuse allocation. Ash integers elsewhere retain arbitrary precision.
Bytes Eight-byte unsigned little-endian byte-count header followed by the exact packed contents, alignment 8. Arbitrary byte values are preserved.
String The same checked byte-count header followed by exact UTF-8 contents, alignment 8. Count bytes rather than characters; preserve NUL and reject invalid UTF-8 on decoding.
Ref<A,T> Two private unsigned 64-bit little-endian owner/object identities, alignment 8; the target payload T is not recursively inlined.
Tuple Fields in source order, each preceded by checked padding to its natural alignment; maximum field alignment, or 1 for an empty tuple. No trailing padding.
Ordinary nominal data Sole-constructor payload omits a tag; multiple constructors store a checked unsigned 32-bit little-endian zero-based defining-order tag. Encode the selected constructor's entire optional semantic payload as one child, aligned after the tag. No trailing padding. Natural alignment is the maximum over all alternatives' payload alignments, with base 1 and minimum 4 when tagged. The by-value nominal layout graph must be acyclic.

Layout dictionaries are finite graphs keyed by type/layout IDs; a reference edge does not expand its target layout. By-value recursive nominal types are unsupported, even when one input value happens to be acyclic. Packed Bytes and String have dedicated dynamic-length codecs; the earlier registered-list representation is not part of this selected fragment. The header contributes eight bytes even for empty payloads. Check host-size conversion, header-plus-length arithmetic and object extent before reservation or read. These widths and byte orders describe private arena serialization, not the representation of evaluator packed values or a C ABI for arbitrary Ash values. Acyclic admitted ordinary values encode recursively, duplicating ordinary shared inline fields. Arena reference fields preserve their object identities and never copy target payloads. State tokens, resource access families, functions, evidence and arbitrary native opaque families have no derived payload layout. A capturing closure may still live in ordinary storage and retain an arena reference. A closure-as-payload rejection is a layout limitation, not evidence of owner-escape checking.

Aggregate alignment belongs to the type dictionary, not the selected value. An absent constructor payload has alignment 1. A constructor with several declared fields has one tuple payload, as in ordinary Ash; encoding does not flatten that tuple across the constructor boundary. For example, a tagged (Bool,Int,Bool) payload stores its tag at bytes 0--3, padding at 4--7, and its tuple child at byte 8, with fields at offsets 8, 16 and 24. Its extent is 25 and alignment 8; the same sole-constructor payload has extent 17. Decoding advances by each field's actual extent, including dynamic contents, then aligns the next field. The containing field or next object separately aligns its start; no aggregate extent is rounded to its natural alignment.

The alignment operand is zero or a power of two at least the natural alignment and no greater than 64. Unsupported alignment, value conversion and all arithmetic checks precede reservation. For cursor c, size n and admitted alignment a, compute start = align_up(c,a) and end = start+n with checked arithmetic; require end <= payload_bytes and an available object record. Padding is zero-initialized and counts against payload capacity. Unit has zero encoded extent but an explicit stronger alignment may still advance the cursor through padding. Distinct Unit objects always consume distinct records. Metadata does not count as payload bytes.

Native initialization and reserved reference/result metadata, including checked codec conversion and evaluator result admission, complete before publication. Preparing a native store may reserve unpublished scratch and a candidate key; it does not change counters. Admission failure drops that preparation. The synchronous final commit publishes initialized bytes and one record before the already-admitted result enters evaluator control. No fallible conversion follows native publication. A failed conversion, initializer or runtime admission publishes no reference and leaves the cursor/object count unchanged. Writes to an unpublished reservation cannot touch earlier objects. If initialization fails after writing the reservation, roll back its cursor/record and dispose partial temporary state; do not publish a partially initialized object. Published objects never move or mutate. Zero-sized allocations still get distinct object IDs/records, preventing address coincidence from becoming identity.

For M-03, a B object containing (refA, refB) loads to an ordinary tuple with field-sensitive summaries. Selecting refA yields A only, so it can survive B while A remains live. Returning the entire tuple, B ref, or a closure capturing B still rejects. Independent Core validation rederives store/load relations from the registered contracts and checked operands.

Ref tokens retain owner/object identity and no ownership keepalive; they cannot extend their source arena's lifetime. Aliases preserve object identity and allocate no payload. Immutable persistent structures may share refs arbitrarily while their owners remain live. Unbinding an alias performs no individual free. Bulk completion frees the arena once, including unreachable objects; it does not trace roots or scan destructors. Immutable construction has no forward-reference publication, so cyclic shared graphs remain a named construction question rather than an admitted test result.

Deep copy is explicit source code with an explicit output type. For example, copy_node<A> : (Arena<A>, Ref<A,Node>) -> Node ! {StorageOps<A,Node>} loads the reference-free node. A shared pair of A-node refs can become a pair of ordinary Nodes through two loads, or two independently allocated B nodes plus a B pair. Its output type names Node/recipient-B references rather than A references. Source signatures retain every exact source/read and recipient/store effect and provider/layout requirement. This avoids assuming a nonexistent EraseRefs<T> type function or calling a shallow T -> T conversion independent. The first deep-copy routines duplicate shared payloads and record allocations, bytes copied and duplicate work. General cyclic copying and preserving sharing through an identity map require another bounded contract. Shallow load/copy continues to retain any reference fields and fails the corresponding escape test.

Completion and M-01 through M-06

No object/ref binding owns a completion action. cleanup supplies separately checked ordinary actions, which may capture refs and request the exact storage instances. Their contracts and interpreter requirements follow current cleanup analysis, extended to the generated family handlers. All such inner actions run while their arena storage and selected interpreter remain live, before the synchronous arena finisher reclaims payload/table storage.

Capture moves the arena owner, native state, exact instantiated handlers, layout dictionaries and pending action obligations together. Resume restores them without reallocation or duplication. Owned discard runs admitted inner actions, then consumes the arena state once; it cannot skip an outside required action or discard a running action/finisher. Internal teardown uses safe native destruction without executing source cleanup as recovery. Divergence retains its ordinary lack of eventual-release guarantee.

M-01 records exact layouts, payload/object limits, alignment and rollback. M-02 observes one node payload through aliases, a shared persistent structure and a capturing closure called twice; escaping that closure rejects. M-03 uses the store/load relation for its safe outer projection and inward-store rejection. M-04 compares explicit independent and shallow copies, including recipient-B storage and declared sharing duplication. M-05 repeats scratch scopes and checks payload/table reclamation, while owner-plus-object packaging and counting an owner past scope reject. M-06 retains an action reading arena-backed data and checks normal/capture/resume/owned-discard order against actual native events. None of these checks runs stale pointers as a negative test.

Resource type definition

This general schema explains the candidate roles. P-1 selects controlled publication without a source publish function and controlled lifecycle replies as specified above; alternatives in this study are not additional authoring features admitted by that slice.

The declaration and instance occupy different source positions. A resource type definition introduces a family Q<r, alpha>. Its formal identity parameter r has kind Type; alpha denotes any other ordered parameters with declared kinds. The family has the corresponding function kind ending in Type. At an instance, r is replaced by a fresh rigid identity R. Other parameters come from the surrounding typing environment and ordinary inference.

The proposed value type of a bound resource access is Q<R, alpha>. Its values are non-owning handles; the lexical scope owns completion. A declaration must identify its provider implementation P and connect the following types and contracts under the same parameter environment:

Component Required typed relationship
Initializer A value type I<alpha> known before the new identity exists.
Provider state A private representation State<r, alpha> with declared retained dependencies and owned completion.
Acquisition Code accepting I<alpha> and producing either guarded State<r, alpha> or an initialization error. Failed acquisition publishes no handle or authority.
Publication Controlled construction of Q<r, alpha> from acquired state, with its exact authority. The handle is access, not ownership of the state.
Effect interface Declared operation types whose resource operands and results refer to the appropriate Q<r, alpha> and associated types.
Handlers Clauses checked against those instantiated operation types under the provider state and current resume rules. Their outward effects remain explicit.
Completion Code consuming owned state or retaining it with a failed-completion report, according to its declared postcondition. It cannot silently duplicate ownership.
Scope result A specified type family F<T, alpha> for a body result T and acquisition/completion reports, with no reference to the closing identity.

I, State, and F are type templates in the definition, not identifiers injected into client code. The definition must resolve actual declarations and check their kinds and signatures. Initializer, acquisition, publication, handler, and completion effects also belong to that contract.

For example, the following are internal provider contract shapes at one fresh identity, written as type notation rather than proposed declaration syntax:

acquire : I<alpha> -> AcquireResult<State<R, alpha>, InitError<alpha>> ! epsilon_acquire
publish : State<R, alpha> -> Q<R, alpha> ! epsilon_publish
finish  : State<R, alpha> -> FinishResult<State<R, alpha>, CloseError<alpha>> ! epsilon_finish

AcquireResult distinguishes acquired state from failure; unpublished partial state remains guarded. FinishResult distinguishes consumed state from retained state after refusal. These owned states belong to establishment and completion, not transportable client results. Publication borrows the owned state to construct access; it does not consume or transfer the scope's owner.

These signatures do not by themselves prove ownership or foreign memory safety. Their controlled calling positions, construction authority, state usage, and postconditions require checking rules. Current ordinary rank-1 functions and interface evidence do not establish them. A declaration with an arbitrary publish function cannot claim authority merely because its result type matches. The experiment must specify which obligations Ash checks, which need trusted primitives, and which remain explicit assumptions about foreign code.

A handler also has a precise checking context. For an associated operation op : D<R, alpha> -> B<R, alpha>, its clause pattern binds D<R, alpha> and its resume capability accepts B<R, alpha>. The clause must produce the shared handled result type with the declared outward row, following current handler checking. Q<R, alpha> is the resource operand type, not the handler's type.

Imports must preserve the resource family's defining identity, parameter kinds, provider association, operation identities, construction authority, and result contract. Copying a type or effect declaration cannot recreate resource construction authority. Provider declaration syntax and public-summary encoding remain to be designed around these obligations.

Instance typing and lexical lifetime

Let Q be a resource family with an admitted definition and inferred outer parameters alpha. The initializer checks as I<alpha> in the preceding environment.
