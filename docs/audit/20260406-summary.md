# Ash audit summary — 2026-04-06

## Scope

This note summarizes the current executable state of Ash as of 2026-04-06, with emphasis on:

- whether Ash can load, parse, lower, type-check, and execute workflows
- the current state of capabilities, policies, authority, and runtime constraints
- what looks production-usable today versus what remains partial or explicitly incomplete

This is an implementation-oriented audit summary, not a claim that the entire language/spec surface is complete.

## Executive summary

Short answer:

- Yes, Ash can currently load, parse, lower, type-check, and execute workflows through a real engine pipeline.
- Yes, Ash has a real capability system, not just placeholders.
- Yes, it now has meaningful runtime supervision and retained-completion support.
- No, it is not yet accurate to say the full language/runtime/provider story is complete.

The most accurate top-level characterization is:

- parse: yes
- lower to core IR: yes
- type-check: yes, for the supported path
- execute: yes, including stateful runtime execution
- CLI run path: yes
- canonical entry workflow bootstrap path: yes
- capabilities: real and usable, but uneven by provider/domain
- supervision/runtime observation: materially stronger after TASK-405 through TASK-412
- still incomplete: full provider closure, full retained-payload parity, and broader semantics/runtime closure

## 2. What looks production-usable now vs not yet

### 2.1 Things that look solid enough to build on now

#### a. Parse/check/execute core workflow path

These look real enough to build on for internal or controlled usage:

- `Engine::parse`
- `Engine::check`
- `Engine::execute`
- `Engine::run`

This is a real engine pipeline, not a placeholder.

#### b. CLI for supported workflows

The CLI `ash run` path looks usable for:

- workflows that match the current supported path
- especially canonical entry workflows or known-good ordinary workflows

It should not be assumed that every historical or reference example in the repo will run unchanged.

#### c. Built-in stdio and filesystem capabilities

These look usable now for internal or controlled workflows:

- stdio capability path
- filesystem capability path

Use with ordinary care around file-access policy and constraints.

#### d. Capability governance mechanics

These appear real and operationally meaningful:

- missing provider failure
- authority checks
- policy deny / require approval / transform
- runtime constraint enforcement
- receive policy enforcement on sources

#### e. Spawn supervision lifecycle

These appear to be real runtime facilities now:

- control links
- pause/resume/kill/check-health
- retained completion records
- completion wait API

This is one of the strongest runtime areas after recent work.

### 2.2 Things to use with explicit caution

#### a. Parallel semantics (`par`)

`Par` clearly executes, but the runtime should not yet be described as proving full semantic closure for:

- cumulative aggregation
- exact multi-carrier provenance/effects interpretation
- strongest formal concurrency correspondence claims

Use it, but keep documentation honest and conservative.

#### b. Retained completion payloads

The runtime now retains:

- outcome class
- terminal result
- conservative effects
- terminal-visible obligations
- runtime-owned provenance
- wait surface

That is operationally useful, but it is still best described as retained runtime observation rather than full exact semantic `CompletionPayload` transport.

#### c. Entry bootstrap path

The canonical entry path looks trustworthy for workflows designed to that contract, but it is still a narrow and opinionated application entry model.

### 2.3 Things that should not yet be represented as production-complete

#### a. Built-in HTTP capability support

This is explicitly not complete.

`with_http_capabilities(...)` still yields a configuration error in the builder path.

#### b. “All examples / all language surfaces are production-ready”

That would be inaccurate. The README itself warns that some larger reference examples are not expected to run unchanged in the current CLI path.

#### c. Fully hardened security boundary

Capabilities + policy + constraints are real, but Ash should not yet be marketed as:

- a hardened sandbox
- a fully closed enforcement perimeter
- a finished production security product

#### d. Full semantic/runtime closure

Still open:

- exact cumulative carriers
- exact effect/provenance transport
- full `CompletionPayload` parity
- broader runtime cleanup/alignment items

### 2.4 Honest production statement

A fair current statement would be:

> Ash is now a real executable workflow engine with a meaningful governed runtime. It looks usable for controlled/internal systems and evolving product workflows. It should not yet be represented as fully closed, fully provider-complete, or fully hardened.

## 3. Concrete walkthroughs: source -> parse -> check -> execute -> capability/policy behavior

### 3.1 Walkthrough A: ordinary workflow execution

Conceptual source:

- a normal workflow file
- no special entry bootstrap required
- returns a value

#### Pipeline

1. Read source
   - CLI or engine reads `.ash` file contents.

2. Parse
   - `Engine::parse(source)`
   - uses `ash_parser`
   - produces a surface `WorkflowDef`
   - lowers it into `ash_core::Workflow`
   - caches the surface definition for type-checking

3. Type check
   - `Engine::check(&workflow)`
   - retrieves cached `WorkflowDef`
   - converts parameter annotations into typeck types
   - runs `ash_typeck::type_check_workflow(...)`
   - fails with `EngineError::Type` if invalid

4. Execute
   - `Engine::execute(&workflow).await`
   - calls into `ash-interp`
   - interpreter executes the lowered core workflow
   - returns `Result<Value, ExecError>`

5. CLI output
   - CLI formats the result
   - prints it or emits JSON depending on flags
   - optional timeout / trace wrapping may apply

#### What this proves

Ash is not parse-only. It has a real load -> parse -> lower -> check -> execute chain.

### 3.2 Walkthrough B: canonical entry workflow

Current canonical entry model is more opinionated.

Expected shape:

- workflow name must be `main`
- return type must be exactly `Result<(), RuntimeError>`
- parameters must be capability-typed

Approximate current style:

```ash
use result::Result
use runtime::RuntimeError
use runtime::Args

workflow main(args: cap Args) -> Result<(), RuntimeError> {
  observe Args 0 as _;
  done;
}
```

#### Pipeline

1. Build engine
   - CLI builds an `Engine` using stdio, fs, and runtime argument providers.
   - when args are passed, CLI creates providers like `Args:0`, `Args:1`, etc.

2. Load runtime stdlib
   - `bootstrap_entry_source` loads the narrow runtime stdlib registry for supported entry imports.

3. Validate entry prelude
   - `parse_entry_source` accepts the narrow leading `use` prelude and validates imports.

4. Parse entry workflow
   - engine parses the workflow source.

5. Type check
   - `Engine::check` runs as usual.

6. Verify entry contract
   - `verify_entry_workflow` ensures:
     - name is `main`
     - return type is `Result<(), RuntimeError>`
     - each parameter is a capability type

7. Build input bindings
   - `entry_input_bindings` maps capability-typed params into execution bindings.

8. Execute
   - engine executes the workflow with or without input bindings depending on signature.

9. Derive exit code
   - if return value is `Err(RuntimeError { exit_code = N, ... })`, bootstrap returns `N`
   - otherwise returns `0`

#### What this proves

Ash has a real application entrypoint path, not just a low-level interpreter hook.

### 3.3 Walkthrough C: capability-governed execution

This is the important path for understanding capability maturity.

Imagine a workflow that does one or more of:

- observe a capability
- send or set to a capability
- receive from a stream source
- run under a role / policy / constraint environment

#### Runtime path

1. Provider registration
   - `EngineBuilder` constructs providers:
     - built-in stdio if enabled
     - built-in fs if enabled
     - custom providers supplied by the embedding app
   - these are adapted into interpreter-compatible providers
   - they are stored in `RuntimeState`

2. Workflow executes a capability-sensitive form
   - interpreter reaches forms like:
     - `Observe`
     - `Act`
     - `Set`
     - `Send`
     - `Receive`

3. Capability/provider resolution
   - runtime attempts to resolve the provider
   - if missing: `ExecError::CapabilityNotAvailable(...)`

4. Effect compatibility check
   - providers declare effect levels
   - runtime distinguishes observation-capable vs action-capable use

5. Authority check
   - if role runtime / role context is in play, capability use can be checked against role authority
   - if role lacks the needed grant, operation is denied

6. Constraint enforcement
   - if the capability grant carries constraints, runtime checks them against actual operation args
   - examples include:
     - path constraints
     - host constraints
     - permission constraints like `read` / `write` / `spawn` / `kill`
   - on violation, runtime returns a constraint-related failure

7. Policy evaluation
   - capability policy layer evaluates the operation in context
   - depending on policy:
     - `Permit`: operation proceeds
     - `Deny`: runtime errors
     - `RequireApproval`: runtime blocks in approval state
     - `Transform`: runtime rewrites/masks/replaces value and continues

8. Execute provider action / observation
   - if allowed, provider observe/execute runs

9. Return or continue workflow
   - observed value may bind into context
   - action result may be returned or propagated forward

#### What this proves

Capabilities are not just provider lookup. They are mediated by:

- provider existence
- effect compatibility
- authority
- policy
- constraints

## 4. State of capabilities: direct answer

If the question is: “What is the current state of capabilities?” the shortest accurate answer is:

- materially real
- already useful
- more advanced than a toy/provider mock layer
- still uneven across built-in provider domains, with built-in HTTP notably incomplete

### 4.1 Capability system components currently present

Ash currently has real machinery for:

- capability providers
- effect levels on providers
- capability lookup and failure behavior
- role/authority checks
- capability policy evaluation
- approval gating
- runtime constraint enforcement
- stream and behavior capability subsystems

### 4.2 What happens when a capability is missing?

Missing capabilities fail explicitly via:

- `ExecError::CapabilityNotAvailable(...)`

This is an explicit fail-closed behavior in the sense that operations do not silently no-op.

### 4.3 What built-in capability support exists?

Current engine builder supports:

- `with_stdio_capabilities()`
- `with_fs_capabilities()`
- `with_custom_provider(...)`

Important caveat:

- `with_http_capabilities(...)` is still not implemented as a working built-in path
- current behavior is an explicit configuration error
- recommended workaround is custom providers

### 4.4 What policy capabilities exist?

Capability policy layer supports:

- input vs output policy distinction
- observe / receive / set / send operation classes
- pattern matching over capabilities/channels
- decisions:
  - permit
  - deny
  - require approval
  - transform

Transforms include forms like:

- masking fields
- filtering
- replacing values

This is a substantial runtime policy layer, not a parser-only feature.

### 4.5 What role/authority mechanics exist?

Runtime supports:

- role context
- authority checks for capabilities
- role pending/discharged obligations
- capability grants
- runtime constraint checks against grants

This separates:

- capability exists
from
- actor/role is allowed to use it

### 4.6 What constraint enforcement exists?

Constraint enforcement is one of the stronger practical pieces.

Current runtime constraint areas include:

- paths
- hosts
- ports
- permissions like `read`, `write`, `spawn`, `kill`

So capability access can be fenced by grant-level constraints, not just binary provider presence.

### 4.7 Stream and behavior capability surfaces

Ash also has separate subsystems for:

- behavior providers
- stream providers / stream context

That matters because not all effectful workflow operations are plain provider observe/act calls.

Behavior support includes things like:

- sampled state
- settable behavior providers
- change detection

Stream support includes:

- blocking / non-blocking / timeout receive
- wildcard fallback
- control mailbox handling
- policy checks over receive sources

## 5. Strongest current areas

The strongest current areas appear to be:

- engine parse/check/execute pipeline
- CLI run path
- stdio/fs/custom provider integration
- stream receive execution
- policy/authority/constraint enforcement
- supervision/control links
- retained completion observation and waiting

## 6. Medium-confidence but still-evolving areas

The following are real, but still evolving and should be described conservatively:

- entry bootstrap ergonomics as the long-term application model
- richer semantic parity for retained completion
- `par`’s full formal/runtime correspondence story

---

## 7. Clearly not done yet

The following remain clearly incomplete or intentionally unresolved:

- built-in HTTP capability path
- “all examples run unchanged” claim
- full semantic/runtime closure
- any claim of final hardened security sandboxing

---

## 8. Bottom-line assessment

Current Ash is best described as:

- a real parse/check/execute workflow engine
- with a functioning interpreter and runtime
- with a meaningful capability + policy + authority system
- with increasingly strong runtime supervision and completion observation
- but still mid-flight on full provider coverage and full semantics/runtime closure

In direct response to the original questions:

### Can it load, compile, and execute workflows?

Yes.

More precisely, it can:

- read workflow source
- parse it
- lower it to core IR
- type-check it
- execute it through a runtime interpreter
- run canonical entry workflows through the engine/CLI bootstrap path
- execute workflows with capabilities, policies, streams, behaviors, and supervision features

### What is the state of capabilities?

Capabilities are real and already useful.

They include:

- providers
- effect levels
- authority checks
- policy decisions
- approval flow
- runtime constraints
- stream/behavior capability surfaces

The capability system is materially more advanced than a toy mock layer, but it is still uneven across built-in provider domains, with built-in HTTP still notably incomplete.
