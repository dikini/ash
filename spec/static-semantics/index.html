Static Semantics

Development specification · ash-lang 67c79dd

OverviewLexical StructureSyntaxName ResolutionStatic SemanticsElaborationDynamic Semantics

Ash has Int, Bool, Unit, String, Bytes, rigid type variables, structural tuples, parameterized nominal algebraic data types, unary functions, and effect rows. A tuple contains at least two element types. A function has a value domain and a computation codomain A ! epsilon, where A is a value type and epsilon is an effect row. Source kinds contain Type, EffectRow, and right-associative function kinds, subject to the binder restrictions below.

Type equality is one shared rule. Int, Bool, Unit, String and Bytes equal themselves; tuples, term functions and their computation codomains, and unary type applications compare structurally; type variables compare by binder identity; nominal constructors compare by stable declaration identity. Equal spelling or constructor shape does not make two nominal declarations equal. Interface requirements are constraints rather than monotypes. They do not participate in monotype equality or ordinary unification. Effect rows are computation requirements rather than interface requirements and never select implementation evidence.

The typing environment GAMMA maps resolved BinderId identities to rank-1 constrained schemes. Interface methods do not have binder identities. The immutable method registry MU instead maps each resolved MethodId to its owning InterfaceId, ordered interface parameters, optional determinant positions, ordered method-local parameters, declared method value type, declaration order, and provenance. A constrained scheme has three fields:

ConstrainedScheme =
    ordered outer (TypeVariableId, Kind) parameters
    ordered interface requirements
    source value type

The outer parameters quantify only the value type and the types within the requirements. Looking up a scheme replaces every quantified parameter with a fresh inference variable of the same fixed kind, instantiates the value type, and creates one evidence obligation for each requirement in source order. A scheme with no requirements has the ordinary forall parameters. type behavior. Rigid variables from annotations never unify with a different type.

One registry method has a distinct method scheme under its owning interface parameter vector:

MethodScheme = forall method_parameters. method_value_type

The interface parameters remain free relative to this scheme and are owned by the enclosing interface. A method scheme never enters GAMMA, and no source occurrence can name it without instantiating every method parameter.

The immutable effect registry PHI maps every accessible EffectId to its ordered fixed-kinded parameters, ordered operations, visibility, and provenance. Each operation record contains its stable OperationId, spelling, and one pure value-function type. PHI authenticates operation typing; it is not a provider environment or handler registry.

The judgment GAMMA |- expression ⇒ A ! epsilon synthesizes a value type and effect row, while GAMMA |- expression ⇐ A ! epsilon checks an expression against an expected computation type. These judgments also consult the fixed method registry MU and record pending requirements on the exact constrained-term occurrences that create them. The ordinary rules omit MU, PHI, and that structural output. The interface section defines the distinct method-occurrence rule, and the selection section defines how a definition closes the pending requirements.

Kinds, monotypes, and schemes

Four environments determine value-type kinds, and PHI determines effect instance formation:

  • DELTA maps every in-scope resolved TypeVariableId to exactly one declared kind;
  • OMEGA maps every live InferenceVariableId to exactly one fixed kind;
  • XI maps every accessible NominalTypeId to its constructor kind; and
  • IOTA maps every accessible InterfaceId to its nonempty ordered canonical parameter records and optional ordered determinant positions.

A nominal declared with ordered parameter kinds kind_1 through kind_n has the constructor kind obtained by the right fold kind_1 -> ... -> kind_n -> Type. The declaration's ordered parameter records are authoritative; any retained nominal-kind cache must equal this derivation. Imported nominal and interface kinds come from authenticated body-free summary facts and retain their defining identities.

A newtype representation is one monotype template under its declaration's ordered parameter environment. The fully applied template must synthesize Type; this check adds no kind inference or higher-rank representation. A representation may contain primitives, parameters, structural tuples, functions with computation codomains, ordinary nominals, and other newtype nominals under the ordinary scope and kind rules. Kinding a computation codomain checks every nested effect instance, including effect arguments that contain a newtype identity.

After every module-level ordinary constructor payload and newtype representation is kind-correct, static nominal admission constructs the directed graph whose vertices are the module-level newtype declarations and whose edges are newtype identities occurring anywhere in another representation. The directed graph containing only newtype representation edges must be acyclic. Traversal follows declaration and structural type order; the first closing edge owns newtype.recursive-representation. Its primary label identifies the rejected representation occurrence, and its related labels identify the declarations that complete the cycle. An ordinary data declaration ends this graph traversal even if its payload refers back to the originating newtype.

A local newtype uses the same representation-kind check under its own parameters and enclosing lexical type parameters. Its nominal kind depends only on its declared parameter vector. Sequential scope rules out self and forward representation references, so local declarations add no cycle pass.

The total synthesis judgment DELTA; OMEGA; XI |- monotype => kind assigns a kind to every well-formed monotype. PHI is an ambient input used when synthesis reaches a computation codomain; the ordinary judgment omits it. all_type means that each listed monotype synthesizes Type under the supplied environments. The last two rules are owning checks: ordinary value positions require Type, while an interface constraint requires one complete argument per declared interface parameter and the corresponding kind at every position. Arity is checked before any positional kind.

kind-synthesis

An unsaturated nominal constructor synthesizes its derived function kind. A partial application synthesizes its residual kind. Either form is valid when the owning rule accepts that kind. Resolution represents an ordinary named application as repeated unary Apply(function_type, argument_type) nodes, folded from left to right. Equality, substitution, unification, occurs checks, implementation matching, summary authentication, and validation use this structural and injective form. Both the function and argument are immediate strict subterms of an application.

Resource-family checking facts retain their complete ordered Type/Row vectors. Their original declaration identities determine argument kinds and arity. These metadata facts do not authorize nonbuiltin provider instantiation or native lifecycle execution, and add no Row argument to ordinary nominal, interface or effect declarations.

Constructor payloads, global and method value types, pattern and term-binder types, source expression types, entry results, and ordinary Core value annotations use K-Value-Type. Requirements, method obligations, implementation heads and prerequisites, and evidence goals use K-Interface-Argument. An interface constraint has no monotype kind of its own. An interface parameter without an annotation has kind Type, which recovers the predecessor behavior at that argument position.

A scheme is distinct from a monotype and has no ordinary kind. It has the form forall (A_1 : kind_1) ... (A_n : kind_n). body, with distinct binders and a body accepted by K-Value-Type under the extended DELTA. A scheme cannot occur as a type-application argument, tuple element, term-function domain or codomain, term-binder type, or any other source monotype. A method scheme remains separate in MU; the elaboration specification defines its sole authenticated compiler-generated Core evidence position.

EffectRow is valid as a complete global or eligible generalized-local kind. Resource-family metadata preserves its ordered Type/Row argument kinds. EffectRow cannot occur within a written function-kind annotation. Ordinary nominal, interface, implementation, effect and method parameter lists admit only their existing ordinary kinds. A row tail must resolve to an in-scope EffectRow binder. A row variable cannot occur in an ordinary value position, ordinary nominal, interface or effect argument, or pattern.

Every omitted declaration kind annotation and every binder introduced by an omitted implementation binder list is fixed to Type. An omitted global list discovers ordinary free type variables and effect-row-tail variables in their shared first-occurrence order. A name occurring only in ordinary type positions has kind Type; one occurring only as an effect-row tail has kind EffectRow; using the same name in both roles is invalid. Ash does not infer a function kind from use. This is the current phase-dependent language constraint, not a commitment against a later bounded declaration-local inference rule.

Computation types and effect rows

An effect instance is one stable EffectId plus a complete ordered vector of type arguments. Its arguments must match the declaration's arity and positional kinds. Two instances are equal only when their identities and all zonked arguments are structurally equal. An effect row is an unordered idempotent set of exact instances with at most one open tail. Source order does not affect row equality or handler order. Rendering orders known members canonically by exact identity and structural arguments; that presentation order has no semantic effect.

The following rules form effect instances, rows, and computation types. distinct_exact compares the resolved identity and all zonked arguments. lacks(R) is the set of instances known absent from the row variable R.

effect-row-formation

WF-Effect-Instance checks arity before positional kinds. The row rules reject a repeated written member as effect.duplicate, even though inferred row operations coalesce equal members. WF-Open-Effect-Row records that every written known member is absent from its tail. WF-Computation keeps rows out of ordinary value positions.

Row equality ignores known-member order and multiplicity after inference. Open rows are equal only when their known sets, tail identity, and accumulated lacks facts are equal after substitution. Type substitution descends through every effect argument. Row substitution replaces a tail only with a row of kind EffectRow, unions the replacement's known members with the enclosing known members, and preserves all accumulated lacks facts. It rejects an occurs check or any replacement containing an instance forbidden by those facts.

Row unification is kind-preserving first-order unification: it succeeds exactly when a substitution makes both rows equal without violating an occurs check or lacks fact. It aligns known members by exact instance identity and structurally unifies their arguments. It never equates distinct effect identities or invents a lacks fact.

Write epsilon_1 union epsilon_2 for partial inferred union. It coalesces equal known members. It succeeds for closed rows, and may retain one open tail only when substitution has made the tails identical or closed the other tail and every added known member is already absent from the retained tail. Two distinct unsolved tails, or a member not known absent from a retained tail, produce effect.row-union-ambiguous. An expected row may supply an existing lacks fact; union never strengthens a tail merely to make the operation succeed. Schemes retain no qualified row-union or membership constraints.

Effect weakening permits a computation inferred as A ! epsilon_1 to check as A ! epsilon_2 when every requirement of epsilon_1 is present in epsilon_2 under the same tail constraints. Synthesis retains the least row established by the expression rules; weakening applies only while checking against an expected computation. Exact removal epsilon remove E removes only an explicitly established exact instance. Thus {E | R} remove E = {| R}; removing a different instance from a closed row is missing, and searching an unconstrained open tail is ambiguous. No rule removes an effect by spelling or API shape. Rows have no semantic order or multiplicity, effect subtyping or masking, or implicit removal. Weakening is a checking relation; it does not change a synthesized least row.

Hook scopes use the distinct partial relation scope_discharge(epsilon, H). It removes H when explicitly present. If H is absent from the known members, it leaves a closed row unchanged, or leaves an open row unchanged only when its tail already lacks H. Otherwise discharge is ambiguous. This relation adds no lacks fact and does not relax ordinary handler admission or exact removal.

Let delta denote the exact canonical private DefaultAlloc instance. Every Source value-function arrow expands its codomain row by idempotent union with {delta}, including nested arrows. Thus omitted rows and written ! {} include allocation, and written ! {E} includes allocation and E. A written row still attaches only to its own computation codomain. For example, A -> B -> C ! {E} has allocation at both calls and E at the second call; A -> (B -> C) ! {E} has E at the first call and allocation at both.

The outer pure arrow of an effect operation declaration remains its required operation shape. Value-function types nested in its domain or result receive ordinary expansion. Host/control leaves retain their actual complete rows. This expansion infers no unrelated omitted effects and hides no observable provider effect. Core has no implicit defaults.

Row lifting for existing expression rules

The expression rules below use one row-lifting convention where they retain a predecessor judgment without an explicit row. A variable lookup, code-only constructor/intrinsic value, or known immediate literal has row {}. Persistent construction adds the canonical allocation requirement to its strict-child rows; this includes tuples, nominal records, buffers, large integers and materialized ordinary function records. Potentially large arithmetic carries that requirement even when a particular result is immediate. Erased newtype conversions add no allocation. Generated wrappers allocate only when lowered to ordinary Function. An ordinary strict form with evaluated expression children e_1 through e_n otherwise has the partial union of their rows, accumulated in the existing left-to-right checking order. A match has the scrutinee row unioned with every arm-body row. A block has every initializer row unioned with its remainder row. A checking judgment also requires the synthesized row to weaken to the expected row. The value-type, pattern, coverage, and interface-obligation premises remain unchanged.

Thus every later displayed GAMMA |- e ⇒ A abbreviates GAMMA |- e ⇒ A ! effects(e), and every GAMMA |- e ⇐ A abbreviates checking against the computation expected at that site. The convention does not apply to application, operation request, handler, or resume; their row equations are stated explicitly. Partial union failure is effect.row-union-ambiguous. Union records requirements and does not license evaluation reordering.

Tuples and constructors

Tuple elements synthesize from left to right. A constructor declaration under Owner<A_1, ..., A_n> contributes a scheme quantified over those declaration parameters and their declared kinds. The payload and fully applied owner both have kind Type; a data constructor has this checked rank-1 term scheme rather than a separate constructor kind. Instantiating a nullary constructor produces the applied owner type. Instantiating a payload constructor produces an ordinary unary term function from its substituted semantic payload to that owner. Multiple declared fields form one tuple payload.

data-typing

The constructor premises consult the immutable registry produced by name resolution. T-Newtype-Constructor defines explicit wrapping and does not make the representation and nominal types equal. Every constructor application then follows T-Apply; it does not have a special call rule.

Functions and application

An anonymous function checks only when an expected function type supplies its parameter and computation result. Evaluating the function creates its record and actual captures once in the selected region, adding {delta}. The body row remains latent; calling the stored function uses the caller's allocation selection for fresh body construction. Lookup, copying and type instantiation do not recreate or relocate the record. Application first synthesizes the function, then checks the argument against its domain, and unions both strict-child rows with that latent row.

function-typing

T-Effectful-Function-Check preserves the existing pattern and coverage checks. T-Effectful-Apply preserves strict evaluation order even though its effect row is unordered. Any partial union failure follows the row-algebra rule above.

An anonymous function normally checks from an expected function type. The one additional synthesis site is an unannotated local binding whose initializer is syntactically an anonymous function. That site allocates fresh inference variables for the domain and codomain, checks the function, and applies the local-generalization rule below. An anonymous function in any other synthesis position is rejected with type.function-needs-context. The parameter position is a pattern. Two or more syntactic parameters form one tuple pattern and consume one tuple domain. Because an anonymous or operational function has no alternate clauses, exhaustive([pattern], domain) requires its singleton domain pattern to be irrefutable under the same usefulness analysis as a local binding. The bindings returned by pattern checking, rather than one distinguished binder, extend the function body environment.

Patterns, matches, and coverage

The judgment pattern ⇐ type => bindings checks a pattern against an expected type and returns its typed binders. Wildcards return no binders. Boolean and unit patterns require their corresponding primitive types. Tuple patterns require equal tuple arity. A constructor pattern must belong to the expected nominal type and must agree with the constructor's payload shape. Pattern binders are pairwise distinct.

An accessible newtype constructor pattern has exactly one subpattern, checks that subpattern against the substituted representation, and explicitly unwraps the nominal value. It is irrefutable for its owner. The constructor remains unavailable through an opaque or hidden source route, and no pattern matches a representation value as though it had the nominal type.

A match synthesizes its scrutinee once, checks every arm pattern against that type, and gives the resulting bindings only to that arm body. All arm bodies have one type. The typed usefulness relation over closed nominal sums, tuples, Bool, Unit, binders, and wildcards must find each arm useful and must find no witness outside all arms. A useless arm is rejected with coverage.redundant-case; a remaining witness is reported with coverage.non-exhaustive.

For a local or imported transparent ordinary nominal, coverage uses its complete constructor family. For a transparent newtype, coverage treats its sole constructor as complete without requiring a runtime tag test. An imported opaque or hidden nominal has no accessible constructor pattern and is not treated as an empty sum. A binder or wildcard can cover such a value without inspecting its representation.

match-typing

A match has at least one arm. T-Match-Synthesize obtains its result type from the first arm and checks every later arm against that type. T-Match-Check propagates a result type supplied by the surrounding context to every arm, including the first. This admits anonymous functions and other checking-only forms in all arms when their context supplies a type.

Blocks

Block bindings are checked from left to right. An annotated initializer checks against its annotation. An unannotated initializer must synthesize its binding type. The new pattern bindings are available only in the remainder. A block can synthesize from its result or check by passing an expected type to its result.

block-typing

generalize_local quantifies unsolved inference variables only when pattern is one binder and initializer is syntactically an anonymous function. It excludes inference variables free in GAMMA and preserves each selected variable's fixed kind. Every other unannotated binding keeps the inferred monotype, including an application that returns a function. An annotation checks a monotype and introduces no type parameters. A use of a generalized local binder instantiates its scheme as in T-Variable.

The first three rules synthesize a block type. The last three rules check a block, carrying the expected type through its bindings to the result. Every binding checks its complete pattern, requires that singleton pattern to cover the initializer type, and extends the remainder with all returned bindings. The checking rules overlap with T-Check-Inferred when the result synthesizes, but also admit a result that itself needs an expected type, such as an anonymous function. The semicolons in the binding conclusions separate semantic fields. They do not add semicolon punctuation to Ash source.

Local nominal scope

A local newtype checks its remainder with its rigid nominal and unary constructor in scope. Construction, irrefutable pattern matching, and representation substitution use the same rules as module newtype. No representation interface evidence transfers to the local nominal.

At each declaration boundary, the compiler zonks the outward computation and rejects a local identity in its value type, effect row, generalized scheme, or requirements. Traversal includes function domains and codomains, tuple members, nominal applications, effect arguments, and row structure. Solving an inference variable in a preceding or enclosing binding must not carry the identity outside the declaration's scope either, even when the block returns Unit. If later constraint improvement solves an outward inference variable, its solution must satisfy the same boundary before checked publication. This check does not change ordinary unification, improvement, or evidence-selection order.

In the following rules, n is the resolved lexical nominal identity, P its ordered parameters, and R its representation template. Extending XI with n(P) = R also makes its constructor scheme available. outward includes the zonked result computation, any outward scheme or requirement, and the zonked types of bindings that preceded the declaration. The semicolons separate semantic fields and add no source punctuation.

Inference and rank-1 restrictions

Inference variables are compiler facts, not source types. Each inference variable is registered in OMEGA with one fixed monomorphic kind before it enters a type. Instantiating an outer scheme copies the corresponding declared binder kind. Unification compares primitive and nominal identities, descends structurally and injectively through unary applications, tuples, term functions, computation codomains, and effect arguments, and checks kinds before solving a variable. Row unification additionally applies the exact row algebra and lacks constraints above. It may solve a higher-kinded inference variable with a constructor or partial application of the same kind. It cannot infer a kind, change the variable's registered kind, synthesize a type lambda, abstract over mismatched application arguments, or recover a missing or conflicting registry entry.

The occurs check visits both children of every unary application, each computation row, and every effect argument, and rejects a solution containing the variable being solved with type.infinite. While checking one complete module, typing accumulates the substitution THETA and records each allocated inference variable's causal origin in allocation order. Successful module checking requires every allocated inference variable to occur in the domain of THETA. Otherwise typing selects the first unsolved identity in allocation order and reports type.ambiguous at its retained causal origin. This check includes discarded expressions and unused initializers. Every value-type and row inference variable must be solved or generalized. Zonking removes every inference variable before a checked summary, linked fact, or Core program is retained.

Global type parameters and generalized local parameters are rigid within their definitions. A recursive self-use receives the same rigid arguments rather than a fresh instantiation. A recursive call that would require a distinct instantiation is rejected with type.polymorphic-recursion. Local recursive annotations introduce no type parameters and remain monomorphic.

There are no source-denotable nested schemes or polymorphic function domains. Generalization occurs only at global signatures and eligible local function bindings. An eligible local may generalize inference variables of any fixed monomorphic kind, but the variables remain outer scheme binders and the scheme body must have kind Type. Source expressions cannot provide explicit type arguments. Method schemes remain registry facts that each occurrence instantiates; they do not make a polymorphic value available to source typing. Global signatures may explicitly quantify complete EffectRow binders, and the omitted global binder list discovers their first row-tail occurrences along with ordinary type occurrences. Eligible local anonymous-function bindings may generalize row variables not free in GAMMA, preserving their lacks facts. Other local bindings remain monomorphic.

Local nominal identities are rigid constants and are never generalized. Eligible local functions may quantify unrelated inference variables under the existing rules; that quantification cannot hide a nominal identity or create an inferred local requirement.

Recursive block groups

Let GAMMA_R map every member of one nonempty recursive group to its required declared monotype. All members enter the type environment before any initializer is checked, and the same environment applies to the block remainder.

The initialization-safety judgment admits a direct anonymous function. It also admits a data member when the initializer is rooted at a fully applied constructor of the declared nominal type. A recursive occurrence under that root may pass only through constructor or tuple construction, or occur in an anonymous function body where evaluation delays it. A subtree with no recursive occurrence may be any well-typed expression. An ordinary call, primitive, match, or block cannot force or transport a recursive occurrence.

Source foreign declarations

A foreign library is passive. It has exactly one profile, "x86_64-unknown-linux-gnu", and zero or more symbols. Each symbol has a nonempty NUL-free native link name and a closed source function type. Unsupported profiles and signatures reject statically. The declaration has no representation, operand, status, owner, host, output or lifecycle clauses, and neither libraries nor symbols bind type or row parameters.

The canonical @builtin.foreign.Address is an opaque nominal of kind Type. Ordinary import, opacity and nominal identity rules apply. The builtin functions null : Unit -> Address, is_null : Address -> Bool and equal : (Address, Address) -> Bool have empty effect rows. No integer conversion, ordering, arithmetic, dereference or memory-management operation is provided. Pointer equality proves neither validity nor allocation identity. Raw Address values have no resource dependency, ownership witness or escape restriction. Ordinary modules may encapsulate them with existing data, handlers and cleanup.

The native mapping is fixed by the whole source domain and result:

Source position C mapping
Whole Unit domain No arguments.
Whole canonical Address domain One data pointer, preserving null.
Whole Bytes domain One readonly data pointer.
Flat tuple of Address/Bytes One pointer per component in source order.
Canonical Address result Data pointer, preserving null.
Unit result Actual C void; no native result is read.

Bytes results, numeric slots, String inputs, out-pointers, Unit tuple components, nested tuples, variadics, callbacks and structs by value are unsupported. An ordinary same-shaped nominal does not become Address. There is no implicit length, encoding, NUL, scalar conversion or ABI output storage.

Bytes retains its ordinary immutable managed semantics. Its backing is held through the synchronous native call. Empty Bytes supplies no readable byte and the pointer does not encode length or emptiness. Native mutation or freeing of managed backing violates the binding assumption. A function retaining or returning that pointer requires the module to keep the original Bytes alive through every subsequent native use. An Address result does not capture or infer that relation. There is no Address-to-Bytes/String or arbitrary memory read/write operation.

Each symbol supplies one ordinary effect instance with operation call : Domain -> Result. A request retains that symbol in the ordinary effect row, including when Result is Unit. Ordinary exact handlers may implement it using the usual clause, continuation and row rules. For a native program entry, the generated linked host interprets the remaining required admitted symbol effects; only those exact instances are subtracted from the entry row. Residual ordinary effects and open rows reject under the existing entry rules. Compilation supplies no executable binding. Supplied callback entries are checked against original symbols before Ash runs; a selected native invocation requires its exact entry. This association check does not establish table completeness.

A source signature and link name assert an extern "C" signature and behavior; the compiler does not establish the native assertion. Module-authored functions supply null tests, length checks, errors, lifetime interpretation and cleanup. The ordinary resource, handler, capture, scoped cleanup, work and depth rules remain unchanged. Nonbuiltin provider instantiation is unsupported; no source native-State resource declaration or compiler-interpreted foreign lifecycle is introduced by this boundary.

Effects

An ordinary effect declaration has a possibly empty ordered parameter vector and a nonempty ordered operation vector. Its parameters have the ordinary fixed kinds already admitted for nominal declarations; none has kind EffectRow. Operation spellings are unique within the declaration. Each operation type has exactly one outer pure function arrow P -> Q, where P and Q are value types formed under the effect's parameters. An operation has no local parameters, requirements, body, or independently selectable visibility. A public effect exports the whole authenticated API; a private effect remains local.

Resolution assigns one stable EffectId from the defining module and declaration order, and one stable OperationId from its owner and operation order. Static checking authenticates those identities and the ordered parameters and operation types in PHI. Equal spellings or signatures in two modules remain distinct identities.

For an operation request, substituting the target effect instance's arguments into the declared operation type produces its value domain and result. The operand is evaluated first, and the request adds that exact instance to its row.

T-Perform neither selects a handler nor names a provider. If an open operand row does not already exclude the requested instance, inferred union is ambiguous; checking may use a lacks fact already present in its expected row.

An ordinary handler targets one exact well-kinded instance and contains exactly one clause for every operation of that effect, in any source order. Each clause pattern checks against the substituted operation domain and must be irrefutable. Handling removes the target from the body row. Requirements of other identities remain, while requirements introduced by clause evaluation, including a same-instance request made directly by a clause, enter the output row.

For an operation op_i : P_i -> Q_i, the clause receives bindings from a P_i pattern and a fresh structural resume capability resume(Q_i, A, epsilon_out). Every clause checks against the handler's value type and shared output row.

T-Handle chooses the least epsilon_out satisfying the body remainder and every direct clause requirement. Effect weakening lets a clause with fewer requirements check against that shared row. Ordinary completion of the handled body passes its A value through; there is no source return clause. T-Resume checks the resumed value against the selected operation result, consumes the capability, and gives the resumed computation the handler's result contract. T-Discard consumes the same capability without resuming its captured computation. Its result is Unit, not the handler's result type; subsequent clause work still checks against the handler contract. Its inferred epsilon_close includes the effects of actions invoked by closing the owned capture after action-local and still-enclosing retained builtin cell interpretation. It does not export a captured cell's local identity merely because an action uses that cell before release. Surviving source handlers, including clause-local handlers around discard, check and discharge residual effects at their own boundaries. Discard is not universally pure.

This complete handler discharges Cell, leaving only the default allocation requirement in main's computation codomain, and evaluates to 42:

effect Cell {
    read : Unit -> Int
    write : Int -> Unit
}

main : Unit -> Int
main () = handle (perform Cell.read ()) with Cell {
    read ignored => resume 42
    write value => resume ()
}

Capability consumption is a structural dataflow judgment with states available and consumed. A clause starts in available and every normally completing path must finish in consumed. Sequential evaluation passes the outgoing state to the next expression. A match checks its scrutinee first, gives each arm the same resulting state, and requires equal outgoing states from all arms. A form with no completion occurrence otherwise preserves its incoming state. A resume first checks its value expression under the incoming state, then requires that result to remain available and changes it to consumed. discard requires available and changes it directly to consumed. In a private Store-associated clause, retain also consumes the available owner; that clause may use resume or retain but not discard. Match arms may choose different permitted completion forms if their outgoing states agree. Use in consumed is effect.resume-already-consumed. A normally completing clause left in available is effect.resume-not-consumed. Divergence before a syntactic completion remains ordinary divergence; this structural judgment does not claim termination or convert divergence into discard.

Anonymous-function bodies, recursive members, supplied local evidence methods, and nested handler clauses are barriers for an enclosing resume capability. An occurrence beyond one of those barriers is effect.resume-capture; a nested handler clause receives only its own capability. Resolution rejects resume or discard outside an operation clause as effect.resume-outside-clause and restricts retain to the nearest private clause. A capability has no source type or binder and cannot be placed in a tuple, constructor, argument, result, local binding, scheme, or stored function body. The checked Store operation moves its owned control without exposing that capability as a value.

Discard permission is distinct from duplication permission. Ordinary values and their stored closure captures are duplicable, subject to the resource lifetime rules below. The hidden continuation capability is nonduplicable and nonescaping. Discard closes exactly the selected owned capture. Each live clause boundary inside it contributes its owned capture recursively at that boundary's structural position, and is consumed once. A consumed capability adds no further capture. Non-owning registration or handle associations do not authorize taking an enclosing owner. Required completion outside the owned closure must remain reachable in untouched control.

Capture inference distinguishes stored values from latent requests. A helper can store only ordinary values yet request an operation while its caller or an internal clause has a live owner. For each possible request, inference follows control through the nearest matching exact handler, including caller continuations. A handler removes requests from its body, but its clauses bypass that handler. A handler installed inside a live clause does not capture the outer owner for requests confined to its own body. Resuming restores the selected captured segment and its handlers; it does not replay the prefix before capture. Discard must also preserve completion of owners outside the abandoned segment whose scheduled work it skips.

Known functions, aliases, closures, recursive groups and imported functions retain inferred control summaries. Possible paths join conservatively, without merging unrelated exact effect identities. Generic type parameters may later coincide; a proof cannot assume they remain distinct. Handler matching after specialization must retain that possibility. Recursive analysis must finish before publishing a permission. An unknown higher-order callee or open row rejects discard when the relevant request's obligations cannot be proved safely closable; this uncertainty alone does not reject resource-free resume-only code. There are no source capture annotations or capture-polymorphic function types.

An unsafe or unproved discard has type-phase reason effect.discard-unsafe, with its primary label on discard and causal request/call and live-owner labels where known. Ordinary syntax, resolution, typing and structural usage errors precede this capture check.

Constructing an answer or losing a ready-queue entry neither creates nor removes work. Recursive call groups use a finite ascending least fixed point; an empty initial relation is not permission, and absence of a finite return is not a termination claim. Unknown calls and joins include their possible returns and changes. Synchronous typed hooks

A hook API is an ordinary effect declaration with exactly one operation named publish, whose domain and result are structurally equal under the declaration's own parameters. Qualification precedes use-site substitution: Convert<A, B> declaring publish : A -> B does not qualify even at Convert<Int, Int>. Equal newtype representations do not establish equal payload types. Hook APIs retain ordinary effect identities, parameter kinds and visibility; their parameters cannot have kind EffectRow.

For an exact qualifying instance H, let P be its instantiated payload type. hook H { body } supplies an identity handler for H. register H transformer { body } checks an ordinary transformer from P to P, evaluates that expression before acquisition, and retains it for the scope. The body's result type A is independent of P.

The following rules use the scope-discharge relation above and existing partial row union. epsilon_init describes evaluating the transformer expression; epsilon_callback describes calling its resulting function. Their union is subject to the existing least-row and expected-row constraints, not a new row-union mechanism.

hook-scope-typing

The registration's generated clause forwards H, calls the transformer on the forwarded result, and resumes with the transformed result. Its forwarded and latent requirements remain in the outward row even if the body never publishes. An unused callback does not execute. A root removes only its target, not subscriber effects or another exact instance. Closed absent-target bodies and open tails already known to lack the target are admitted; an unconstrained tail remains ambiguous. Ordinary handle still requires an explicitly present target in its body's least row.

The generated handler runs inside a registration completion owner. Selecting its clause captures that handler and publisher-side frames, not its own owner. Callback requests therefore use handlers surrounding the registration, not handlers installed only around publication in its body. The callback's saved ordinary values and lexical type/row instantiation retain their usual meaning. Creating an ordinary closure under a handler does not store that handler.

Registration owners require completion even for pure callbacks and unused bodies. Capture and resume preserve that obligation. Checked discard can close a registration inside its owned abandoned control without invoking its transformer or remaining publication callbacks. Subscriber-local discard must preserve required completion outside that owned closure. Skipping an outside owner or its scheduled resume remains effect.discard-unsafe. Subscribers receive no surrounding resume capability.

Stored-dependency inference follows actual callback results, not merely their types. A transformer can return a function with a new cell dependency while retaining type P -> P; that result is permitted while its resource owner surrounds the restored recipient, but cannot escape it. Callback captures, tuples, selected evidence and imported factories obey the same rules as other stored values. Forwarding checks the original payload against every crossed owner before later transformers run. A later transformer that erases a dependency cannot authorize an earlier unsafe transfer, including through an empty identity root.

Dependency and completion inference preserve that possibility; generic parameters are not fresh acquisition brands. An ordinary closure that requests a static hook identity does not retain the active chain, but actual stored resource dependencies remain subject to escape checking.

Malformed syntax and unknown targets retain their earlier-phase diagnostics. Kind, ordinary type/row and structural continuation errors precede hook API qualification. An otherwise well-formed non-hook target reports type.hook-api at the target. Callback mismatches use ordinary type errors identifying the registration's payload contract. Interfaces and constrained schemes

An interface has a nonempty ordered vector of fixed-kinded parameters and a nonempty ordered method list. An omitted parameter annotation means Type. The interface may declare exactly one total determination edge. A determination edge is total: its nonempty, disjoint sides preserve declaration order and together name every interface parameter exactly once. The left side supplies determinant positions; the right side is the dependent complement. A dependent may occupy any declaration position.

Each method may have an explicit ordered list of fixed-kinded local parameters; an omitted method-parameter kind means Type. Its value type has kind Type, contains exactly its listed local parameters as its free variables outside the interface parameter set, and has Function as its outermost constructor. With no edge, every interface parameter must occur in each method value type. With an edge, every determinant parameter must occur; a dependent parameter may occur anywhere or nowhere. This occurrence rule is relational and does not make a dependent an associated result. Interface declaration order fixes the method positions used by checked evidence, and written method-parameter order fixes each method scheme's binder order.

The following judgments check an interface method and then the complete interface. free_type_variables and occurs compare resolved binder identities, not spellings. The equation method_type = domain -> codomain decomposes only the outermost constructor.

interface-well-formedness

Resolved declaration checking supplies an empty OMEGA. XI contains all accessible authenticated nominal kinds. IOTA contains authenticated imported interfaces and pre-frozen canonical parameter and determinant records for all local interfaces before the first local type-bearing declaration is checked. WF-Interface authenticates the complete record. Only an entirely accepted interface enters later checking.

After admission, a method occurrence consults MU by MethodId. It freshens the whole interface vector in declaration order and then every method parameter at the same fixed kinds. It applies one simultaneous substitution to the value type. The complete interface argument vector creates one evidence obligation; method arguments create none. The exact MethodId, ordered method arguments, checked occurrence type, and selection remain private pending state until whole-module inference closure.

Evidence improvement and selection see the complete obligation. Neither operation inspects, chooses, infers, or refines method_arguments. An unresolved determinant argument is constraint.ambiguous when the owning evidence scope closes. An otherwise unresolved method argument remains type.ambiguous at whole-module inference closure. No kind inference, higher-order matching, reversal of a determination edge, or inference of a method-local argument follows from method instantiation.

A global signature carries an ordered requirement list after its complete value type. When the declaration has an explicit binder list, that list must be an ordered bijection with all free variables in the value type and requirements, and its order becomes scheme order. An extra explicit binder is resolve.unused-type-parameter; a free variable absent from a complete list is resolve.unknown-type; and duplicate explicit binders are resolve.duplicate-type-parameter.

When the declaration omits the binder list, free uppercase variables become outer parameters in first-occurrence order: ordinary type and effect-row-tail occurrences in the value type share that order, followed by first occurrences found only in requirements. A name occurring only in ordinary type positions has kind Type; one occurring only as an effect-row tail has kind EffectRow; using the same name in both roles is invalid. In either form, a requirement without a determination edge requires every free variable in its complete application to occur in the value type. For a determined interface, every free variable in the determinant key slice must occur in the value type; a dependent-only binder may remain quantified in the constrained scheme. Determination never propagates between requirements. Here requirement_key is the determinant slice for a determined interface and the whole ordered application otherwise.

Requirements in one signature are compared in source order. Identity-equal complete applications are constraint.duplicate-requirement. Identity-equal interfaces and keys with different dependent tuples are constraint.determination-conflict. A public global may require only public interfaces. A private global may also require a private interface declared in its own module.

The judgment below constructs the checked constrained scheme for either an equational or operational global signature. requirement_key is the complete application for a no-edge interface and only its determinant slice otherwise; dependent-only variables remain quantified.

Requirements remain explicit on module-level signatures. Body checking never infers a requirement and adds it to a checked global or export summary. Equational and operational presentations with the same value type and requirements produce the same constrained scheme. The checked scheme retains the ordered (TypeVariableId, Kind) records rather than a second authoritative kind representation.

A method with an absent parameter list and another free variable, or a method that omits any required interface parameter, is interface.method-parameter. The absent-list check precedes any deferred invalid application-kind failure. Present-list kind failures belong to kind checking. After kind checking succeeds, the required-parameter check precedes outer decomposition; a method whose outermost constructor is not Function is interface.method-not-function. Duplicate complete requirements are constraint.duplicate-requirement; equal determined keys with unequal dependent tuples are constraint.determination-conflict; an undetermined key variable is constraint.undetermined-parameter; and a public signature that exposes a private interface is constraint.private-interface.

Implementations

An implementation head fixes one complete interface application. Constraint satisfaction and checked evidence

Evidence selection uses exact nominal identities. A newtype representation supplies no interface evidence for its owner: an implementation for the representation does not satisfy a goal for the newtype, and wrapping or unwrapping does not copy, lift, or select evidence.

Instantiating a constrained term creates one evidence obligation for each requirement in source order. A method occurrence creates one obligation with a complete application. Ordinary kind-aware bidirectional unification runs before interface improvement.

Before improvement mutates inference state, the checker takes one fixed snapshot of the determined obligations whose complete determinant keys contain no unsolved inference variable. It visits only those obligations, once, in source order. For each, the first applicable source is:

  1. an abstract requirement with the same interface identity and identity-equal zonked key;
  2. the exact current implementation with that key;
  3. the lexical source with an identity-equal key in the occurrence's original scope; or
  4. the unique visible implementation whose independently freshened key kind-preservingly first-order matches the known key.

The source supplies its complete dependent tuple. Improvement is mandatory when a source exists, even when ordinary typing already fixed every dependent. The checker transactionally unifies the whole supplied tuple with the pending application. A disagreement is constraint.determination-conflict and publishes no partial inference solution. Improvement never guesses or refines a key, reverses an edge, inspects prerequisites, constructs evidence, records a selection, repeats to saturation, or unlocks an obligation outside the fixed snapshot. It creates no cross-obligation or cross-requirement propagation.

After improvement, the owning closure begins root selection only when the complete goal is zonked and contains no inference variable. Snapshot eligibility gates only pending determined occurrence roots at their owning closure. Such a root must have belonged to the fixed snapshot. An unresolved key, a known key with no source and an unresolved dependent, or a pending determined root outside the snapshot is constraint.ambiguous. An eligible inference-free complete root with no matching evidence source is constraint.unsatisfied. A pending root for an interface without an edge does not participate in the snapshot and retains the predecessor full-application gate.

After that root gate succeeds, the evidence-selection judgment below carries no snapshot context. A prerequisite generated by concrete selection has already been substituted to a complete application. It uses ordinary full-application selection and full-application active-cycle detection without snapshot membership.

In particular, lexical R<N, Int> conflicts with a pending root R<N, Bool> during mandatory improvement. A recursively generated complete prerequisite R<N, Bool> instead skips that different complete lexical application and may use concrete evidence for Bool. Lexical evidence adds no key barrier to recursive complete-goal selection.

A concrete implementation candidate is freshened independently with its declared binder kinds. First-order matching may substitute only that candidate's head parameters, must preserve their kinds, and matches the complete application. Matching cannot solve or refine a variable in the goal, synthesize a type lambda, or use higher-order unification.

Selection receives the ordered abstract requirements of the current global or implementation, an optional current implementation, the occurrence's lexical sources, the effective implementation environment, an active-goal set, and one resolved complete interface application. It does not receive the determination snapshot; the owning closure has already applied that gate to the pending root. Selection considers sources in this order:

  1. An identity-equal complete abstract requirement from the current definition.
  2. Exact current-implementation evidence for an implementation method's rigid complete head.
  3. Identity-equal complete lexical evidence in the occurrence's original scope.
  4. The unique matching concrete implementation in the effective environment.

Abstract and exact-current evidence therefore precede lexical evidence, which precedes a matching generic concrete implementation. Exact current evidence uses the current implementation's already-abstract prerequisite evidence; it does not freshly instantiate the implementation or select its prerequisites again. The general concrete branch excludes the current implementation. A concrete match may substitute only that implementation's bound head parameters. It selects prerequisites recursively in declaration order.

The rules below describe successful selection. earlier_source_absent means that the preceding entries in the ordered search above did not apply. select_all(abstracts, current, lexical, effective, active, goals) applies this same selection judgment to goals in order with the supplied abstract, current, lexical, effective, and active contexts. It returns the corresponding ordered evidence sequence and never consults the determination snapshot.

Newtype declaration and constructor records, representation types and substitutions, summary and linked facts, conversion nodes, generated binders and functions, transform copies, and Core validation facts charge their existing owning syntax, type-work, graph-wide, Core-construction, or Core-validation ledgers. Every proportional allocation or traversal charges before publication. Lexical nominal and constructor names, canonical local facts, scope nodes, and independent validator indices charge their owning ledger before allocation or publication. Outward escape inspection charges the existing iterative type and row traversal, including preceding binding types affected by inference. Failure publishes no partial lexical registry or checked module; lexical scope restoration and disposal remain iterative, and a fresh budget permits retry of the same logical input. Local identities add no runtime resource ledger. The module type-work ledger also owns newtype representation substitution and graph construction and traversal. Each discovered representation occurrence, retained edge or owner-index entry, pending-stack entry, and visited or active entry charges before retention or traversal. This is not interface constraint work. Exhaustion is internal.resource.type-work; it publishes no checked module or summary. The partial graph is released iteratively, and the same logical input may be retried with a replenished type-work budget. Interface, implementation, evidence, and linked-authentication traversal or comparison charge the graph-wide constraint budget; retaining a structural type, substitution, kind, or binder-kind record additionally charges the applicable type-work ledger. A kind node, unary application node, or binder-kind record is charged before its owning visit or retention. Retaining a record also charges the type and kind nodes it copies. Comparing a kind pair charges one comparison unit in the traversal's owning ledger. A failed operation publishes no partial checked fact or summary.

These ledgers are bounded compiler-resource policy. They do not add runtime kind values or evaluator work, alter newtype erasure or effect evaluation, or make a resource ceiling part of Ash value semantics.

Ash has no kind polymorphism, general higher-rank source values, explicit source term type application, type lambdas, higher-order unification, broad application-shaped local generalization, subtyping, implicit conversions, explicit structural recursive-type operators, or polymorphic recursion. Unauthenticated nested Core schemes remain invalid. Interfaces add no associated declarations, associated-output projections or equations, multiple or partial edges, neutral parameters, reverse or injective determination, specialization, priority, default or negative implementations, inferred global requirements, first-class dictionaries, runtime implementation lookup, or interface-specific Core mechanism. Ordinary data declarations may refer to themselves and to other nominal declarations in the same module; newtype representations retain the narrower acyclic rule above. Recursive global visibility does not cross a module boundary. The interface evidence family is not effect-handler or provider authority, proof or proposition evidence, common universal evidence, or an existential package. An effect row is a computation requirement, and a lexical handler interprets only its exact effect instance; neither is inferred from interface determination.
