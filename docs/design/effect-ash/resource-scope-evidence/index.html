Safe non-foreign resource scope

Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

This informative report records the safe-resource checkpoint retained on integration/effect-ash-foundations by unsigned local merge b8a5398, above integration baseline 387c4ef. Implementation, independent reviews, full verification, transition cleanup and verified local integration are complete. The milestone closure report records integration into main and final verification status.

Retained boundary

The accepted scope is one mutable integer cell per acquisition, reusable access while live, scope-owned release and rejection of resource-dependent escape. It adds no general ownership language, cleanup callback, foreign resource or escaping continuation. The specification defines the implemented semantics; this report records evidence, not rules.

Unsigned local checkpoints retain corrected effect instantiation (8810a44), the sealed API and syntax (0ae5203), acquisition typing and Core authority (64647d8), and stored dependencies and scope completion (a841d46). The complete runtime, interaction, specification and verification checkpoint is fff611c. It retains the accepted proposal, task and execution plan in Git; cleanup commit ca3922c removes those completed transition documents from the active tree. Merge b8a5398 retains that exact product tree. No remote push, tag or main integration is part of this work.

Stored dependencies and request-carried completion obligations remain separate. Finite value relationships preserve selected fields, known calls, recursive activations and imported factories. Owner-relative payload checking does not reject an outer dependency merely because it crosses an unrelated inner scope. Resource analysis runs without discard as well as with it. Final Core derives these properties from actual linked structure rather than trusting a source permission or transformed summary.

Runtime ownership and resource bounds

The explicit machine's resource boundary owns the mutable integer. Runtime handles contain only private activation keys. A lexical instantiation binds the validated static identity to that activation, including through type and row substitutions; neither source types nor validated Core contain an execution-created inference variable. An Effect metadata negative independently rejects such a variable at the type-scope boundary.

Live-cell usage equals active resource frames plus resource frames owned by captured continuations. Acquisition increments it once after all preparation; normal release decrements it once. Capture and resume move frames without changing the count. Discard preflights actual retained live owners before consuming a capture. Static proof, not runtime body inspection, accounts for required completion outside the discarded segment. Final observation rejects nonzero resource or captured-control accounting.

Machine tests cover exact two-live capacity, one-short failure, fresh retries, capacity reuse after release, and a captured outer cell still counting while an inner cell is acquired. Failed context preparation and malformed key, operation or operand checks publish no partial acquisition or mutation. A copied closure retaining an unused handle entry does not retain payload ownership or consume released capacity.

A durable fresh-process test executes 24 nested source acquisitions on a 256 KiB stack. Owning tests also exercise 32,000-frame normal completion and failed capture disposal. Compiler tests cover exact work, one-short failures, fresh retries, wide scans and deep iterative disposal. Internal type-work accounting is not the milestone's notional work-unit scale; the production type-work ceiling remains 327,680.

Resource-free Pure execution adds no resource registry, resource frame or live cell. The fixed Effect carrier and saved lexical instantiation do not create a machine-global provider lookup, global substitution or general store API.

Downstream reassessment

The implementation keeps provider introduction distinct from ordinary interface selection and future proof evidence. Static identities, dynamic activation keys, stored dependencies and release ownership are separate. Future existential packaging would need an explicit ownership-transfer and elimination contract; this slice permits no escaping package and claims no such transfer. Hooks and reliable cleanup would need their own exit and failure semantics, rather than reinterpreting discard as cleanup. Fresh semantic review finds no demonstrated contradiction from proof, existential or hook pressure and no additional machinery justified for this checkpoint. This is not a promise of zero future refactoring.
