# Phase 170 expansion origin sidecar boundary

## Status

Implemented for TASK-1741.

## Decision

Phase 170 keeps expansion origin metadata as a **surface-side sidecar** on `ExpandedSurfaceModule`, not as Core provenance and not as embedded metadata on every surface expression.

The boundary is intentionally narrow:

- `ExpandedSurfaceModule::origins` records only nodes generated by parsed-surface expansion.
- Each entry maps the generated node span to a `SurfaceOrigin` value.
- Parser-original source nodes are not enumerated in the sidecar; their ordinary `Span` remains the source anchor.
- Core lowering consumes the expanded module exactly as before and does not claim full origin/provenance threading.

## Implemented carrier

```text
ExpandedSurfaceModule {
  module: ModuleFile,
  diagnostics: Vec<ExpansionDiagnostic>,
  origins: Vec<ExpandedSurfaceOrigin>,
}

ExpandedSurfaceOrigin {
  generated_span: Span,
  origin: SurfaceOrigin,
}
```

The sidecar currently records operator-section expansion products:

| Expansion product | Recorded origin | Notes |
|---|---|---|
| Built-in operator section, e.g. `(+)`, `(x +)`, `(+ y)` | `SurfaceOrigin::OperatorSection { section_span, operator_span }` | Preserves the original section span and raw operator span. |
| Local notation section, e.g. `(<+>)`, `(x <+>)` | `SurfaceOrigin::NotationExpansion { notation_span, target }` | Preserves the declaration span and rendered target callable path. |

## Why surface-side only?

Phase 169/170 expansion produces ordinary surface expressions before Core lowering. Threading the same metadata into Core would require a broader API decision:

- Core AST node identity is not currently keyed by stable source node IDs.
- Multiple generated surface nodes may lower into one Core node or vice versa in future desugarings.
- Runtime provenance has a different meaning from expansion origin; generated-source metadata must not be mistaken for capability/effect/provenance evidence.

Therefore Phase 170 records enough information for diagnostics and future source maps without changing Core public APIs.

## Semantics

Origin sidecars are diagnostic metadata only.

They do **not**:

- grant authority;
- change type checking;
- change effect rows;
- change contract semantics;
- participate in import/export summaries;
- provide runtime provenance.

They may be used by future diagnostics to explain that a generated node came from an operator section or notation declaration.

## Invariants

1. `origins` contains entries only for generated expansion products.
2. `generated_span` is the span of the generated top-level surface expression that replaced the original surface-only node.
3. Built-in operator-section entries retain the original operator token span.
4. Notation entries retain the notation declaration span and callable target spelling.
5. Successful expansion still leaves no raw `Expr::OperatorSection` nodes in the expanded module.
6. Failed expansion still reports unresolved operator sections at the original section/operator spelling.
7. Core lowering remains fail-closed for hand-constructed `ExpandedSurfaceModule` values that contain raw sections.

## Remaining deferral

Full Core-origin threading remains deferred. A later phase should introduce a real source-map design if Core/runtime diagnostics need generated-node ancestry after lowering. That design should include stable node identity, multi-node expansion/lowering mappings, and clear separation from runtime provenance.
