This report records implementation and comparison evidence for Modular Ash's passive-static-module increment. It does not define Ash semantics. The normative specification owns the current language. The retained module design note and dialect-milestone note explain the design pressure and future direction.

Causal semantic model

The loader starts from one entry source and configured named roots. It resolves relative and absolute imports, canonicalizes every admitted source, assigns one compilation-local ModuleId to that source, and retains all roots that own it. Every relative descendant must remain within every retained owner. The loader admits one canonical source once, rejects cycles, and orders every dependency before its dependents.

Resolution allocates term, nominal, constructor, and type-variable identities under the defining module identity. Complete imports bind public namespaces under an alias. Targeted imports bind selected public identities without changing them. Private declarations do not enter an importer scope. A public opaque nominal exports its name but not constructors. A public transparent nominal exports its complete constructor family. A private nominal identity may occur in public schemes without acquiring an exported source name.

Each dependency publishes an immutable body-free export summary only after its complete body checks. A dependent resolves and checks from that summary rather than the dependency's private scope or body. Imported rank-1 schemes instantiate without re-inference or re-generalization. Hidden identities remain equal wherever compatible public schemes carry the same module-qualified identity.

After all modules check, linking combines their defining registries and lowers each nonempty module's globals to one existing Core recursive group. Dependency groups surround dependent groups. The innermost body applies the entry module's local monomorphic main : Unit -> R to unit, where R is closed. Independent validation authenticates the whole linked program and its module-to-source provenance relation before the existing evaluator runs it. Paths, imports, aliases, summaries, visibility, and opacity have no Core node or runtime value.

The entry.main-open-result reason is a defensive driver boundary. A successfully checked source scheme is closed: every source type parameter is bound by its outer forall, and a polymorphic main fails before its domain or result is admitted. A source-level open-result fixture would contradict that checker invariant. The direct driver::tests::entry_result_closure_walks_every_nested_type test retains the closure predicate without manufacturing invalid checked source evidence.

Expensive source and edge maxima are not duplicated as end-to-end fixtures. Exact unit-accounting tests prove those two graph boundaries, while public loader tests cover path budgets, repeated canonical edges, deterministic failure selection, and deep graph stack safety. Syntax, type, coverage, Core, and validation limits additionally have graph-wide witnesses.

At the passive-module checkpoint, ResolvedModuleProgram.entry and the module field of each ResolvedModuleGroup had no current reader after construction. Interface-era linking and linked evidence validation now consume the entry identity to authenticate the selected entry's exact module closure and consume group module identities to authenticate group ownership, local and imported implementation routes, binders, and declarations. Both fields are therefore retained facts, not current cleanup candidates.

Diagnostics, resources, and ownership

Module loading retains stable reason families for unknown roots, missing files, path escape, import cycles, and graph resources. Resolution distinguishes duplicate aliases, unavailable exports, import conflicts, and opaque constructors. Entry checking distinguishes missing, polymorphic, wrong-domain, and defensive open-result failures. Cross-module diagnostics retain the importing occurrence as their primary cause. Cross-module type diagnostics also retain the exported declaration that supplied the imported type. Diagnostic-only nominal spellings preserve declaration visibility separately from importer nameability, so an unselected public type is not described as a private declaration.

One cumulative syntax budget spans every admitted source. Loading charges source, edge, path-segment, and retained owner-fact limits before keeping their proportional graph state. Resolution charges imported namespace and nominal metadata to its graph-wide type budget. Checking retains a separate graph-wide type budget and one graph-wide coverage budget, including irrefutability checks. Core construction and independent validation apply their cumulative limits to the whole linked program. Pending loader work counts only active traversal ownership, not every edge ever visited. Deep loading, validation, evaluation, rendering, and destruction use explicit work stacks at their admitted boundaries.

Canonical sources, module graphs, Core arenas, and heaps own identity domains. Alternate paths do not create semantic duplicates. Core handles and runtime locations remain numeric rather than Rust ownership cycles. Linking all loaded definitions preserves one ordinary lexical environment chain; it does not add module initialization or dynamic lifetime management.

Transferable findings

  • A module needs one stable identity for its canonical source, independent of alias, root, and route. Overlapping roots add access constraints rather than route-specific identities.
  • Export summaries must carry hidden nominal identity without carrying private source nameability. This lets public APIs compose smart-constructor-style carriers without exposing representation.
  • Opaque and hidden are distinct access states. Opaque types support new downstream global interfaces; hidden carriers support only inferred local composition through compatible public schemes.
  • A body-free summary is a checked dependency boundary, not a source module signature. Interfaces and impl can build on it only through a separate semantic proposal.
  • Module structure can erase after resolution and checking authenticate every reference. Byte-identical Core and runtime value inventories demonstrate that static modularity does not require a module Core node.
  • Resource accounting must span the whole admitted graph. Resetting syntax, type, or coverage work at each module, or retaining owner relations without a cumulative charge, would make the bound route- and partition-dependent.
  • Entry-result closure is guaranteed by the checked rank-1 scheme invariant; the driver guard is defensive rather than a source-reachable rejection.
  • Retained design notes need explicit retrospective status after their proposal lands. A historical note that keeps saying current Ash is Mini-Ash would cross the repository's authority boundary even when its original analysis is useful.

Downstream pressure and exclusions

At this passive-module checkpoint, the next planned increment was interface and impl design against real module boundaries. Ash interfaces are Rust-trait- or Haskell-type-class-like typed relationships, not module signatures. DN-0023 later selected method-only interfaces, scoped coherence, implicit source evidence, and explicit flattened Core evidence. That increment is now implemented and specified; associated types and specialization remain later pressure. It did not reinterpret compiler-generated export summaries as source declarations.

The passive-module increment documented here intentionally excludes individual constructor exports, import re-exports, parent traversal, module cycles, cross-module recursive groups, package manifests or acquisition, persistent compiled modules, separate object linking, initialization, runtime module values, dynamic loading, providers, registration, effects, dead-code elimination, a core-versus-library migration, interfaces, impl, and a selectable current-tree Mini-Ash dialect.

The historical comparison excludes changed source-root admission and does not constrain later core-versus-library refactoring to keep Mini-Ash syntax runnable in the evolving compiler.
