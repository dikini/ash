DN-0037: Ash-Authored Foreign-Library Interfaces

Development design notes · ash-lang 9a8b73b

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

Accepted and implemented

Ash-authored foreign declarations, pointer/void calls and generated evaluator hosts are accepted and implemented on main. The specification defines the language contract. AD-0013 defines the build architecture.

Agreed ffi-ash milestone

ffi-ash names the current implemented dialect on main. It includes the earlier module, interface, diagnostic and effect features, plus generic cells, lexical regions, retained control, library scheduling and the fixed two-worker network. The feature inventory records the complete current boundary and execution support. The name adds no compiler mode. The signed annotated ffi-ash tag freezes the official checkpoint described by the closure report.

The current foreign scope is the pointer/void boundary above. The earlier copying SQLite, native-buffer and Arena libraries used the retired foreign policy API and are absent from current Main. Their original delivery is historical; they are not current ffi-ash library capabilities or unfinished requirements of the accepted pointer/void design.

The original milestone, CP-0022 transition and original closure task retain that earlier scope and acceptance history. This current scope supersedes their description of the delivered language; it does not rewrite their records.

Question

How can Ash modules declare native calls and supply binding policy without per-library compiler dispatch?

Objective

Authors declare the supported C signatures and link names in passive Ash modules. Ordinary Ash functions, effects, handlers and cleanup implement null checks, protocol and lifetime policy. Program builds generate typed Rust calls and link explicit native inputs.

Context

The original provider experiments supplied SQLite, scalar Arena and lifecycle observations. Their Rust manifests and native owners were replaced by the smaller passive foreign boundary. Lexical-region providers now use an ordinary fixed allocate/release pair; a foreign Address alone supplies no owner or allocation permission.

The current binding fixtures exercise pointer arguments, Bytes backing, void results, checks and cleanup. The SQLite canary calls version/source-id getters and compares returned pointers. It does not read foreign text or implement database operations.

Constraints

ABI scope

The target is x86_64-unknown-linux-gnu. Whole Unit supplies no C arguments. Whole Address or Bytes supplies one pointer; flat Address/Bytes tuples supply pointers in source order. Address results are pointers; Unit results are actual C void. Bytes is argument-only. Numeric slots, nested tuples, Unit tuple components, out-pointers, callbacks, variadics and structs by value are unsupported.

Author and compiler responsibilities

The compiler checks source signatures and exact defining identities and independently validates Core. It generates bridges and authenticates their association with original symbols. Native signature and behavior remain binding assumptions. Source handlers retain nearest-handler precedence.

Memory and execution boundary

Bytes backing remains live through its synchronous call. There is no hidden length, terminator or encoding conversion. Native code must not mutate or free that backing. A module that permits a native pointer to outlive the call must retain the original Bytes for every later use. Address carries no ownership or inferred lifetime and provides no memory read/write or freeing operation.

Evidence and experiments

Slim FFI tests, source admission, native program builds and native region storage cover the implemented boundary. The library guide identifies the ordinary binding fixtures and direct SQLite getter canary.

Historical provider experiments and checked-host studies retain their original results. Their retired APIs are not current execution paths.

Not implemented

Full SQLite bindings, foreign text readback, richer ABI mappings, general borrowing, protected or isolated foreign execution, a native Ash backend, separate compiled Ash libraries and a stable Ash/Core ABI are not implemented.
