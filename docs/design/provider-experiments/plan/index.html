Provider experiment and adoption plan

Development design notes · ash-lang 67c79dd

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes

These are bounded experiment steps under DN-0036. Candidate semantics remain informative until accepted through the product workflow. This plan records experiment steps and the path to product adoption; it does not independently authorize new language semantics.

Goal and boundary

Extend the existing Ash compiler and runtime to test library-defined SQLite and scoped arena providers. Compare source descriptions, inferred and explicit contracts, type checking, Core execution, and native behavior. Develop the extensions so successful work can become part of Ash and its standard library.

The initial experiment used .worktree/provider-experiments on codex/provider-experiments. These are historical source paths; the package describes reproduction from any checkout containing the delivery. The consolidation record identifies the checked source, results and retention status. Retaining a verified bounded experiment on main does not adopt its candidate semantics or architecture.

The user's 2026-10-03 direction prioritizes completed source capabilities over additional internal test granularity. The historical immediate integration target was S-01: an Ash library and client execute a real SQLite session through the public driver, with checked Core and observed completion. The shared instance bridge supplied that execution boundary; each prerequisite was assessed by the boundary it removed. Later targets in that historical sequence were the remaining SQLite, arena and borrowing cases, then authoring and adoption evidence. The current bounded SQLite/scalar Arena results are recorded in the consolidation checkpoint; broader borrowing and payload work remains unfinished.

The plan covers the copying SQLite bridge, a fixed-capacity scoped arena, and their first borrowing comparison. Arena owner transport, foreign callback ABI, concurrency, native-owner reference counting, tracing, and processes remain outside these slices. A semantic gap returns to the design documents before implementation continues.

DN-0037 records a separate program for Ash-authored foreign-library interfaces. These experiments can supply evidence for that program. Its requirements do not expand this plan's native-call profile, steps or completion criteria.

Existing implementation and planned changes

Current syntax selects only cell or native_buffer in a resource expression. Their provider authority is compiler-defined and sealed. Current capture and completion rules already constrain scoped handles. The experiment tests how to generalize those boundaries for library-defined provision and typed arena objects while preserving existing behavior.

Use the current pipeline throughout:

Existing files Experimental responsibility
src/lexer/, src/parser/grammar.rs, src/parser/expression.rs, src/parser/project.rs, src/parser/cst.rs, src/surface.rs Extend existing parsing and projection for the selected surface additions.
src/module.rs, src/resolve.rs, src/resolved.rs Resolve resource type definitions, associated providers, foreign declarations, fresh binders, imports, and public contracts.
src/types.rs, src/kind.rs, src/elaborate.rs, src/evidence_validation.rs Check authority, dependencies, effects, foreign signatures, and module evidence; elaborate the selected contract.

src/core/effect.rs, src/core/dialect.rs, src/core/validate.rs, src/core/transform.rs Extend shared typed Core, independent validation, and transforms together.
src/eval/machine.rs, src/eval/disposal.rs, src/eval/value.rs Execute acquisition, contracted calls, arena access, and completion through the existing Effect machine.

Root Cargo.toml, Cargo.lock Add only necessary native dependencies and adapter membership. Keep one workspace.

These are extension points, not a requirement to edit every listed file. Each slice identifies its actual changes from the selected semantic delta. Reuse existing effects, handlers, resource completion, and data representations where their contracts suffice; explain any new primitive or retained Core metadata.

The main crate forbids unsafe Rust. Follow the existing native-buffer boundary when isolating foreign calls: private pointers, explicit ABI and layout assumptions, and audited native operations behind a safe Rust API. Add a small adapter crate to the root workspace only if needed for that boundary. Its role is foreign calls and native storage primitives. All Ash parsing, checking, validation, and execution remain in the existing implementation. Rust borrowing alone does not verify Ash source.

Complete owner row argument follow-on

The selected complete owner row arguments extend DN-0036 experimental P-1 after independent contract and prose approval. Selection remains informative wherever the experimental implementation is retained. It does not define current Ash, establish product adoption or supply a formal proof. The earlier module-publication baseline was Type-only. Common Batch 0 integrates the complete argument migration, and Batch 3 moving-source evidence executes the formal open-row callback. The finite per-request capture witness and required row/control cases pass connected common verification. The original-branch merge and its fresh final gate are recorded separately. Execution records the current consolidation status; earlier receipts retain their named checkpoint scope. The callback exclusion above means foreign callback ABI; this pressure case executes an ordinary synchronous Ash function application within a provider clause.

Follow-on evidence must cover the complete tagged syntax and saturated resource/effect/interface applications, declaration-independent owner signatures, inherited owner binder roles, exact row-bearing identity and simultaneous substitution. Check preceding-scope actuals before fresh position-zero identity, nested row dependencies, occurs/lacks rules and identity escape. Preserve row-free initializer inference and the native state/ABI vector.

The positive fixture must execute the clause callback, then resume pure MissingRow. Its client performs H and forwards the callback through the sealed method: actual body row is closed {E,H}, epsilon={H}, D={|Delta}, with existing Delta lacks H. Derive Omega={H|Delta}, K empty and rho=Omega without adding Delta lacks E<C,{|Delta}>. The derivation supplies the comparison contract; the later public callback receipt is executed evidence for that topology. Exercise generic open and closed specializations, eligible local generalization, actual captures, surviving interpreters and linked execution.

Run the amendment's negative cases at parsing, resolution, static checking, summary authentication, specialization and independent ordinary Core validation. Include wrong tags/arity, unsaturated mixed owners, invalid binder roles, nested occurs cycles, incompatible lacks, fresh-identity escape, erased callback or native demand, forged origins and conflicting association records. Verify public dependency closure, targeted aliases/reexports and diamond imports with body-free client checking and separately authenticated executable template linkage. Specialization must derive real epsilon and c, solve every affected handler/resume/descendant, and retain no unresolved recipe in ordinary Core. No new runtime reduction rule follows from type metadata or ordinary application.

The same-sigma/same-epsilon different-c source witness is a separate mandatory obligation. The finite public witness has passing moving-source evidence; it is not a general mathematical proof. The open-D callback case does not replace it. Do not weaken capture, discard, completion or principal-row rules to admit either case. A separate native-request clause variant must preserve its known direct native demand until exact admitted interpretation discharges it.

Independent reviews approve bounded selection and the required common checks pass. The original-branch merge and verification evidence are recorded separately. Later adoption follows Step 7: an accepted semantic proposal, any justified architectural decision and authorized tasks precede product implementation, tests and specification changes. Allocate those artifacts only at that later stage. Candidate representation choices and parser diagnostics remain implementation preparation, not adopted architecture.

  2. Extend the existing parser and resolver for the selected resource type definition, provider association, instance form, and foreign descriptions.   4. Extend existing typed Core, its validator, and transforms for the selected representation. Use the test pattern in tests/native_buffer_core.rs to validate linked modules and transformed Core. Mutate an owner, operation instance, primitive signature, result relation, and origin separately.

Step 4: implement the scoped arena through the same mechanism

  1. Specify capacity units, alignment, arithmetic overflow, zero-sized values, initialization failure, cursor rollback, and release obligations before adding allocation tests for M-01. Specify allocation operand/result types and handler coverage for every admitted payload type before heterogeneous cases. Current effect operations have no operation-local type binders; a generic allocation method alone cannot establish a handler for all its exact instances.
  2. Implement stable backing storage and typed allocation through the provider mechanism from the SQLite slice. Extend existing value/heap representation only where required; keep native addresses private.
  3. Publish typed access only after complete initialization. Failed allocation preserves earlier objects and the specified cursor state. Object bindings and aliases do not own separate storage release.
  4. Extend Ash checking and capture analysis for M-02 through M-05: immutable aliases, closures, nested owner dependencies, safe outer projections, independent copies, scratch scopes, and rejected owner transport.
  5. Exercise M-06 through the existing continuation and disposal machinery. Preserve owner and access obligations across capture and resume; complete them in the specified order on normal return and admitted owned discard.
  6. Compare explicit allocation with construction directed to a scoped provider. Measure friction, annotations, copying, and retained storage without assuming nearest-region construction is the accepted rule.

Exit evidence connects Ash type checking to native storage lifetime for the admitted objects and control paths. A Rust lifetime or merely enclosing lexical block cannot substitute for Ash dependency checks. Do not execute stale native pointers as rejection tests.

Step 5: compare retained storage and temporary views

  1. Define access validity, conflicting operations, branch joins, and captured obligations for X-01 through X-04 before extending the implementation.
  2. Compare copied input with arena-backed retained input. Relinquish retention through rebind, clearing bindings, or finalization according to the contract. Show that reset alone does not discharge it.
  3. Reject arena completion and incompatible mutation while retention remains. Obtain a row view and reject step, reset, conversion, or finalization that would invalidate active access. Accept an independent copy followed by those operations. Owner lifetime alone does not authorize the view.
  4. Exercise handlers with reachable aliases while a conflicting borrow is captured. Capture/resume must preserve the obligation; temporary inactivity must not grant conflicting access.
  5. Compare derived Core transitions, runtime state, native behavior, and combined discard order. State which access facts erase after checking and which remain for execution or validation.

If the candidate rejects a required useful case, preserve that finding and compare alternatives. Do not silently copy in the borrowing variant.

Create results.md, blueprint.md, and tooling.md here after observations exist. For each case record admission, inferred and explicit information, Core/native agreement, diagnostics, completion, assumptions, and measured costs.

Compare provider assembly styles against the same cases. The result assessment uses DN-0036's success criteria:

Result Branch outcome
Successful supported design Retain useful implementation and proceed to product adoption below.
Failed design Do not merge the experiment branch. Record counterexamples and reasons; disposal is optional.
Inconclusive or partial result State the supported fragment and remaining questions. Do not merge unresolved behavior; refine or plan the next bounded comparison.

Experiment completion means its questions have answers. Retention of a verified bounded experimental fragment requires attributable evidence and explicit limitations. Product adoption additionally requires a successful design and the adoption work below. Retention alone does not complete this broader plan.

Step 7: bring successful work into Ash and its standard library

  1. Produce the adoption report required by DN-0036. Map each proposed general mechanism to evidence from both experiments or state its tested scope. Identify current behavior, semantic delta, trust assumptions, compatibility, supported targets, and remaining limits.
  2. Prepare the change proposal for language semantics and architectural decisions for converged non-language choices. Retain successful code on this branch or another explicitly experimental retained checkpoint while those contracts are reviewed; rewriting it from scratch is not a prerequisite for adoption.
  3. Following acceptance, create product tasks and detailed execution plans for coherent checkpoints. Map existing experimental code to each checkpoint's requirements: retain conforming parts, revise gaps, and remove failed candidate machinery from the proposed product tree.
  4. Specify surface grammar, binding and import rules, static checking, elaboration, and Core operational transitions with the retained implementation and tests. Update the affected spec/ files in the same product checkpoint. Include failure, capture, resume, discard, and completion derivations rather than only the successful native call.
  5. Place reusable provider, arena, view, conversion, and completion APIs in Ash library modules. Decide standard-library organization through the adoption review. Keep SQLite policy in its library, with a decision on optional standard-library inclusion or separate distribution. Keep both examples testing the public mechanism after adoption.
  6. Compare with existing cell/native-buffer mechanisms and simplify only where evidence supports it. Preserve existing Pure and Effect behavior and add compatibility checks. Document supported native builds, authoring workflow, developer tools, costs, errors, and explicit foreign assumptions.
  7. Run the full product verification and required review. Adopt the successful implementation as product behavior only when the accepted contract, implementation, specification, library documentation and evidence agree. Current language semantics derive from spec/; experimental retention on main does not substitute for this adoption workflow.

An unsuccessful experiment remains unmerged. Useful code need not be discarded; retention does not waive the successful-design and product-verification gates.

Verification and pause conditions

Prefer end-to-end and integration tests through the public source pipeline. Every new test should cover a required experimental observation, a concrete integration behavior or an observed defect that existing coverage does not catch. Add a focused internal regression when needed to reproduce or isolate a bug, or to verify a required boundary that integration cannot observe. Do not add tests merely for each helper, field or implementation branch. Combine related scenarios when their observations remain attributable.

Batch connected implementation changes and run the affected integration and regression suites at useful checkpoints. Broaden verification for a completed capability, a shared change with unresolved regression risk, or an observed failure that warrants it. Avoid repeating broad gates after small edits when affected checks suffice. Required contract evidence, independent validation, review and final verification still apply. Report completed behavior and the next blocking boundary first; test counts are supporting evidence.

cargo xtask verify

For applicable proof changes, follow the adopted proof-tooling workflow and proof-navigation guide. Use validated module receipts with their compiler, source, import, option and report pins. Batch related changes, keep compiler jobs serial by default, and coordinate builds and language-server use with other tasks within the host's RAM and CPU limits. Use one Rust workspace and one open Lean file at a time; stop language servers before heavy builds. Record the tools actually exposed in the task. LSP feedback and cache receipts alone do not establish proof acceptance. Retain the reviewed frozen integration gate, including source, compiler, dependency, warning, report and axiom checks, alongside the Rust verification above.

Documentation checks cover authority labels, case links, Markdown, and formal notation. Current baseline observations are in the package README. No experimental test pass is claimed by this plan.

Pause a slice to revise its contracts when execution disagrees with a required case, checking needs an unstated assumption, or native behavior contradicts the model. Report setup failure separately. Preserve the copying baseline when a borrowing candidate fails. Passing checks alone cannot make a failed design eligible for merge.
