Combining effects and scopes

We can now give the list calculation one complete contract. Each nonzero item earns its points plus a requested bonus. Zero stops processing. The result reports the completed or partial score, the number of items visited, and how many times the processing scope closed.

The calculation uses features already introduced separately: a policy effect, a scoped counter, a stopping handler, and a cleanup action. We will derive its responsibilities from the earlier pure calculation, then trace a normal run and an early stop through the same code.

Keep the scoring rule visible

The pure comparison in 00-pure-calculation.ash passes the bonus directly. It uses the data declarations from the sibling scoring.ash shown next:

import scoring as Scoring

sum_scores : (Scoring.Scores, Int, Int) -> Scoring.Outcome
sum_scores (Scoring.End, total, bonus) = Scoring.Finished total
sum_scores (Scoring.Item(value, rest), total, bonus) = match value == 0 {
    true => Scoring.Stopped total
    false => sum_scores (rest, total + value + bonus, bonus)
}

main : Unit -> Scoring.Outcome
main () = sum_scores (Scoring.Item(20, Scoring.Item(22, Scoring.End)), 0, 2)

For each nonzero item, add its value and the bonus to the accumulator. At zero, return Stopped total; at End, return Finished total. Trace the two items with bonus 2 and predict the outcome. Run from this lesson’s src directory, where the sibling module already supplies the data declarations:

$ ash 00-pure-calculation.ash
Finished(46) : Outcome

The two contributions are 20 + 2 and 22 + 2. Their total reaches End, which constructs Finished(46).

The effectful version keeps that arithmetic and stopping point. It changes how the bonus is obtained, makes visits observable, and gives scope completion its own action.

Separate the traversal from its interpretations

Replace the bonus argument with a public request that each entry can answer. To count visits without passing cell access into the traversal, add a private Visit request before each item. Keep the stop request from Stopping a calculation at zero. A surrounding run function will interpret visits and stops, while a cleanup action records the processing scope’s completion.

scoring.ash contains those parts and the data declarations used above:

import @builtin.cell as Cell

pub type Scores = End
    | Item(Int, Scores)
pub type Outcome = Finished(Int)
    | Stopped(Int)

pub effect Bonus {
    amount : Unit -> Int
}
effect Visit {
    item : Unit -> Unit
}
effect Stop {
    at_zero : Int -> Unit
}

sum_scores : (Scores, Int) -> Int ! {Bonus, Stop, Visit}
sum_scores (End, total) = total
sum_scores (Item(value, rest), total) = {
    let ignored = perform Visit.item ()
    let ignored = match value == 0 {
        true => perform Stop.at_zero total
        false => ()
    }
    let bonus = perform Bonus.amount ()
    sum_scores (rest, total + value + bonus)
}

pub run : Scores -> (Outcome, Int, Int) ! {Bonus}
run values = resource cell<V> visited = 0 {
    resource cell<C> closed = 0 {
        let on_close : Unit -> Unit ! {Cell.Ops<C>} = fn(ignored) {
            Cell.write (closed, (Cell.read closed) + 1)
        }
        let outcome = handle (cleanup on_close {
            handle (Finished (sum_scores (values, 0))) with Visit {
                item ignored => {
                    let ignored = Cell.write (visited, (Cell.read visited) + 1)
                    resume ()
                }
            }
        }) with Stop {
            at_zero partial => {
                let ignored = discard
                Stopped partial
            }
        }
        (outcome, Cell.read visited, Cell.read closed)
    }
}

Follow sum_scores before studying run. It requests a visit at the start of each item. If the value is zero, it requests a stop with the current total. Otherwise it requests the bonus and makes the recursive call with the updated total. It receives no cell handle: a visit is a request, while counting visits is the surrounding handler’s responsibility.

run acquires two distinct cells. visited counts processed items, including a zero marker. closed records how many times the cleanup action runs. The local Visit handler increments the first cell and resumes with Unit. The Stop handler discards the remaining traversal and returns Stopped partial. Normal traversal returns Finished instead.

The cleanup action increments closed once. Its owner surrounds the traversal and the visit handler. Both cell owners surround the stop handler, so their access remains live when discard invokes the action. The returned tuple contains an ordinary outcome and two copied integers; it exports no handles.

Run the completed calculation

01-finished.ash sits beside the module and supplies a bonus of two:

import scoring as Scoring

main : Unit -> (Scoring.Outcome, Int, Int)
main () = {
    let values = Scoring.Item(20, Scoring.Item(22, Scoring.End))
    handle (Scoring.run values) with Scoring.Bonus {
        amount ignored => resume 2
    }
}

Predict each report field separately. Compute the score from item contributions, count the visit requests, and identify when the cleanup runs. Remember that resuming a bonus request continues after it without repeating the preceding visit:

$ ash 01-finished.ash
(Finished(46), 2, 1) : (Outcome, Int, Int)

The two items earn 22 and 24, giving the pure version’s score of 46. Each was visited once, and normal completion invoked on_close once. The other two fields expose the visit and completion behavior we added. Importing the module does not initialize those cells; each call to run executes its own acquisitions.

Read the outward contracts from the inside out:

Boundary Requirements still needed outside it
sum_scores Bonus, Stop, and Visit
The visit handler Bonus, Stop, and access to visited
The cleanup and stop handler Bonus and access to the two live cells
The two resource scopes Bonus
The entry’s bonus handler None

Cleanup’s cell access contributes to the effects of closing, including when closing happens during discard. The resource scopes supply those exact cell interpreters. Bonus remains public because the entry chooses its policy; Stop and Visit remain private implementation choices.

Stop before applying another bonus

02-stopped.ash changes only the input list:

import scoring as Scoring

main : Unit -> (Scoring.Outcome, Int, Int)
main () = {
    let values = Scoring.Item(20, Scoring.Item(0, Scoring.Item(99, Scoring.End)))
    handle (Scoring.run values) with Scoring.Bonus {
        amount ignored => resume 2
    }
}

Trace the visit, zero test, and bonus request in that order. Predict the partial score at the stop request, the visit count including the marker, and the cleanup count. Which later item and pending constructor will be abandoned?

$ ash 02-stopped.ash
(Stopped(22), 2, 1) : (Outcome, Int, Int)

The first item earns 20 + 2. The zero marker is visited next, then requests a stop with total 22 before requesting any bonus. Discard skips 99 and the pending Finished construction, but invokes the owned cleanup once. The clause supplies Stopped(22) beside visit count 2 and closing count 1.

The cleanup requires only the still-live closed cell. It does not need to restore the captured visit handler or continue the abandoned traversal. The effect, resource, and cleanup rules govern these separate obligations.

Change policy without changing scope ownership

03-different-policy.ash uses the original input and supplies a bonus of five:

import scoring as Scoring

main : Unit -> (Scoring.Outcome, Int, Int)
main () = {
    let values = Scoring.Item(20, Scoring.Item(22, Scoring.End))
    handle (Scoring.run values) with Scoring.Bonus {
        amount ignored => resume 5
    }
}

Predict the score from the new bonus. Then consider whether either the visit requests or scope completion changed, and predict those counts independently:

$ ash 03-different-policy.ash
(Finished(52), 2, 1) : (Outcome, Int, Int)

Only the policy answer changed. The score becomes 25 + 27, while the visit and cleanup counts retain their meanings.

05-empty-input.ash starts the same run with no items:

import scoring as Scoring

main : Unit -> (Scoring.Outcome, Int, Int)
main () = {
    let values = Scoring.End
    handle (Scoring.run values) with Scoring.Bonus {
        amount ignored => resume 2
    }
}

At End, which requests does the traversal actually make? Predict all three fields, keeping an entered cleanup scope’s obligation separate from whether the traversal makes a request:

$ ash 05-empty-input.ash
(Finished(0), 0, 1) : (Outcome, Int, Int)

The traversal returns its initial total 0 without visits or bonus requests. The cleanup still increments closed, giving (Finished(0), 0, 1). Its obligation belongs to entering its scope. The run contract still records Bonus for other inputs, and the entry supplies its handler even here.

The entry must still supply the public policy

The private handlers and resources do not answer Bonus. 04-unhandled-policy.ash records the remaining requirement on main instead of handling it:

import scoring as Scoring

main : Unit -> (Scoring.Outcome, Int, Int) ! {Scoring.Bonus}
main () = {
    let values = Scoring.Item(20, Scoring.Item(22, Scoring.End))
    Scoring.run values
}

Follow the contract table outward. Which requirement remains on main, and who could answer it if the entry has no caller supplying effects?

$ ash --message-format human --locale en 04-unhandled-policy.ash
Calling `main` must require no effects from its caller.
  --> /path/to/ash-doc/content/effects/combining-effects-and-scopes/src/04-unhandled-policy.ash:3:1
3 | main : Unit -> (Scoring.Outcome, Int, Int) ! {Scoring.Bonus}
  | ^ This is the local `main` declaration.
reason: entry.main-effects

The label points at the entry declaration whose row still contains Bonus. The entry requirement leaves no ordinary effect for an outside caller to answer. Admitted native effects can receive a checked interpretation from the tool; the ordinary Bonus effect still needs our handler. Restore it from 01-finished.ash to answer that remaining request. The module’s private handlers and resources fulfill their own requirements and leave this policy to the entry.

Practice: account for every field

Start each task in a fresh scratch directory outside this lesson’s src tree. Copy its named entry and the sibling scoring.ash together, so the entry’s import finds your copy. Run the copied entry from that directory.

Change the values and bonus in 01-finished.ash. Predict the score, visit count, and cleanup count separately.

Move the zero marker in 02-stopped.ash. Does it still contribute a bonus and a visit? Which suffix is abandoned?

Call Scoring.run twice under a bonus handler in 01-finished.ash, returning both reports. Does the second run start with fresh counts? Predict before running.

In your copied scoring.ash for 02-stopped.ash, move the visit request below the zero check. How does the stopped report change while the scoring rule stays intact? Predict the new report.

A complete explanation identifies where each request is answered, which work resumes or stops, and which owners remain responsible for completion. The result types and rows describe the outward contracts; the scope structure explains how the program satisfies them. Hooks and buffers can serve other problems without being added to this calculation merely to use every feature.
