Abstracting key order

The preceding entries supply Trees.compare_natural to each tree operation they call. Each operation receives it as compare and passes that parameter through recursion. This value tells lookup, insert, and lookup_counted how to compare keys, but repeating it also makes every caller carry knowledge that all three operations already require.

An Ash interface can move that requirement out of the source argument list. The operation declares where Order<K>, and checking must find evidence for that obligation at each use. The algorithm still calls the same comparison equations and enters the same tree branch. What changes is the boundary: comparison arrives through evidence selected during checking instead of through a value argument written by the caller.

Name the ordering capability

The shared module begins with the same transparent tree, ordering, option, and unary-natural representations as the preceding case. It then declares the one-method interface Order<A> and an implementation for Natural.

pub type Tree<K, V> =
    Empty
    | Node(Tree<K, V>, K, V, Tree<K, V>)

pub type Ordering =
    Less
    | Equal
    | Greater

pub type Option<A> =
    None
    | Some(A)

pub type Natural =
    Zero
    | Next(Natural)

pub interface Order<A> {
    compare : A -> A -> Ordering
}

pub impl Order<Natural> {
    compare Zero Zero = Equal
    compare Zero Next(right) = Less
    compare Next(left) Zero = Greater
    compare Next(left) Next(right) = compare left right
}

pub lookup : K -> Tree<K, V> -> Option<V> where Order<K>
lookup query Empty = None
lookup query Node(left, key, value, right) = match compare query key {
    Less => lookup query left
    Equal => Some(value)
    Greater => lookup query right
}

pub insert : K -> V -> Tree<K, V> -> Tree<K, V> where Order<K>
insert key value Empty = Node(Empty, key, value, Empty)
insert key value Node(left, current_key, current_value, right) = match compare key current_key {
    Less => Node(insert key value left, current_key, current_value, right)
    Equal => Node(left, current_key, value, right)
    Greater => Node(left, current_key, current_value, insert key value right)
}

pub lookup_counted : K -> Tree<K, V> -> (Option<V>, Int) where Order<K>
lookup_counted query Empty = (None, 0)
lookup_counted query Node(left, key, value, right) = match compare query key {
    Less => {
        let (found, later_comparisons) = lookup_counted query left
        (found, later_comparisons + 1)
    }
    Equal => (Some(value), 1)
    Greater => {
        let (found, later_comparisons) = lookup_counted query right
        (found, later_comparisons + 1)
    }
}

maximum : Natural -> Natural -> Natural
maximum Zero right = right
maximum left Zero = left
maximum Next(left) Next(right) = Next(maximum left right)

pub height : Tree<K, V> -> Natural
height Empty = Zero
height Node(left, ignored_key, ignored_value, right) = Next(maximum (height left) (height right))

This module has no entry contract of its own. Each of the four entry commands below imports it, so every run loads and checks this complete source before it checks the entry.

The pinned interface grammar makes Order<A> a method-only declaration. Its parameter occurs in compare : A -> A -> Ordering, and the method’s outer type constructor is a function arrow, as required by the static interface rules. An interface is not an ordinary value type. It names a checking requirement whose evidence supplies the method when a constrained occurrence is used.

The four implementation equations preserve the previous Natural comparison: Zero precedes every Next value, every Next value follows Zero, and two Next values compare their payloads. The implementation must be pub because only public facts can be selected by a dependent. Under the pinned public declaration rules, a private implementation remains available only in its defining module, while pub impl publishes a body-free fact in this module’s summary. There is no implementation name or value for an importer to call.

Each tree signature states its requirement after the complete value type:

lookup : K -> Tree<K, V> -> Option<V> where Order<K>
insert : K -> V -> Tree<K, V> -> Tree<K, V> where Order<K>
lookup_counted : K -> Tree<K, V> -> (Option<V>, Int) where Order<K>

The where clause is not another function argument and is not part of the result type. Ash keeps requirements explicit on global signatures instead of inferring them from bodies, as specified by interfaces and constrained schemes. Inside each Node equation, compare creates an Order<K> obligation. The recursive lookup, insert, or lookup_counted occurrence creates the same obligation.

While checking one of these constrained globals, its declared requirement is available as abstract evidence. Abstract evidence is considered before a concrete implementation, so both the method occurrence and the recursive global occurrence reuse the same declared Order<K> evidence. The pinned global rules keep recursive self-occurrences at the same rigid type arguments, and the selection order accounts for that abstract reuse.

The final Natural implementation equation is recursive for a different reason. While checking compare Next(left) Next(right), its compare left right occurrence uses exact current-implementation evidence for Order<Natural>. It does not start a new search for a concrete implementation. That current-evidence rule belongs to implementation-method checking and the same ordered evidence selection.

Select Natural order at an imported call

The first entry constructs the same valid three-node tree as before, but its two calls no longer mention Trees.compare_natural.

import ordered_trees as Trees
import ordered_trees (impl Order)

main : Unit -> ((Trees.Option<Int>, Int), (Trees.Option<Int>, Int))
main () = {
    let one = Trees.Next(Trees.Zero)
    let two = Trees.Next(one)
    let three = Trees.Next(two)
    let valid = Trees.Node(
        Trees.Node(Trees.Empty, one, 10, Trees.Empty),
        two,
        20,
        Trees.Node(Trees.Empty, three, 30, Trees.Empty)
    )
    (
        Trees.lookup_counted three valid,
        Trees.lookup_counted Trees.Zero valid
    )
}

The two import lines use independent channels. The complete import binds the public names beneath Trees, but selects no implementations. The impl Order item binds no name; it makes the dependency’s public Order implementation facts available for evidence selection in this entry. The pinned import rules define that separation. This private selector neither re-exports the facts nor creates ambient evidence for another module.

Follow the first call through checking. Ordinary typing determines both its query key and its tree key as Trees.Natural. Instantiating the imported constrained global therefore creates an Order<Trees.Natural> obligation. The selected public Natural implementation is the unique matching concrete candidate. The static constraint rules select only after ordinary typing has fixed the obligation’s type argument.

Predict the paths. Query three compares Greater at root two and Equal at the right child. Query Zero compares Less at root two and Less at the left child before reaching Empty. Both paths visit two nodes.

Run the entry from content/cases:

ash abstracting-key-order/src/01-lookup.ash
((Some(30), 2), (None, 2)) : ((Option<Int>, Int), (Option<Int>, Int))

The accepted line is byte-for-byte the preceding case’s result. The first pair contains the found value Some(30) and two visited Node forms; the second contains None and the same visit count. At each visited node, lookup_counted makes one top-level compare method application. Its count does not include recursive applications inside the Natural implementation.

For finite unary values, let |Zero| = 0 and |Next(n)| = |n| + 1. A completed Natural comparison has C(q, k) = min(|q|, |k|) + 1 method applications, including its terminal equation. The successful path therefore performs C(three, two) + C(three, three) = 3 + 4 = 7 internal comparison applications. The miss performs C(Zero, two) + C(Zero, one) = 1 + 1 = 2. Selected evidence changes how the method arrives, not which equations these finite inputs enter.

The exact structural result and type follow the pinned observation rules. The tool’s successful-output contract gives one standard-output line, empty standard error, and status 0.

Preserve replacement and expose malformed data

The next entry also removes only the explicit comparator arguments. Its sequential bindings retain the original tree, derive a replacement, and then construct a malformed tree directly.

import ordered_trees as Trees
import ordered_trees (impl Order)

main : Unit -> (Trees.Option<Int>, Trees.Option<Int>, Trees.Option<Int>)
main () = {
    let one = Trees.Next(Trees.Zero)
    let two = Trees.Next(one)
    let with_two = Trees.insert two 20 Trees.Empty
    let original = Trees.insert one 10 with_two
    let replaced = Trees.insert one 99 original
    let malformed = Trees.Node(
        Trees.Node(Trees.Empty, two, 20, Trees.Empty),
        one,
        10,
        Trees.Empty
    )
    (
        Trees.lookup one original,
        Trees.lookup one replaced,
        Trees.lookup two malformed
    )
}

Predict Some(10) from original and Some(99) from replaced. On an Equal insertion, the library retains the stored representative key and both branches while changing only the value. The older binding still denotes the earlier value.

The malformed tree places two in the left branch of one. Lookup compares two as Greater than the root and enters the empty right branch, so predict None even though the key occurs structurally.

Run the complete entry:

ash abstracting-key-order/src/02-replace-and-malformed.ash
(Some(10), Some(99), None) : (Option<Int>, Option<Int>, Option<Int>)

The three observations confirm replacement, retention of the older tree, and the malformed miss. Tree<K, V> remains a public transparent type, so an importer may use Trees.Node directly under the pinned public, private, and opaque declaration rules. Neither the nominal type nor Order<K> certifies descendant placement.

Observe the same unbalanced insertion

Ascending keys still make every insertion choose the right branch.

import ordered_trees as Trees
import ordered_trees (impl Order)

main : Unit -> (Trees.Tree<Trees.Natural, Int>, Trees.Natural, (Trees.Option<Int>, Int))
main () = {
    let one = Trees.Next(Trees.Zero)
    let two = Trees.Next(one)
    let three = Trees.Next(two)
    let after_one = Trees.insert one 10 Trees.Empty
    let after_two = Trees.insert two 20 after_one
    let after_three = Trees.insert three 30 after_two
    (
        after_three,
        Trees.height after_three,
        Trees.lookup_counted three after_three
    )
}

Predict a three-node right chain, unary height 3, and a lookup that visits all three nodes.

ash abstracting-key-order/src/03-ascending.ash
(Node(Empty, Next(Zero), 10, Node(Empty, Next(Next(Zero)), 20, Node(Empty, Next(Next(Next(Zero))), 30, Empty))), Next(Next(Next(Zero))), (Some(30), 3)) : (Tree<Natural, Int>, Natural, (Option<Int>, Int))

The tree, height, value, and visit count are again unchanged: ascending insertion can still produce a right chain with h = n. An interface requirement supplies comparison evidence; it adds no balancing rule or logarithmic-height guarantee.

height does not require Order<K> because it never compares keys. At each node it evaluates both recursive heights and then invokes the private maximum helper on the unary results. Those helper calls and constructed Next forms remain separate source work from lookup’s visited-node count and Natural comparison work.

Separate output from evidence lowering

These three runs establish that each complete program checks, evaluates, and produces the displayed value and type. They do not expose the chosen implementation identity, distinguish abstract from concrete selection, or show the generated Core program. Those conclusions come from the pinned specification and retained implementation tests, not from successful CLI output.

After linked evidence validation, a constrained global lowers to an ordinary Core function with type parameters first, then one function binder for each flattened evidence method, then the source value function. At a constrained call, type application comes first, evidence applications follow, and source value applications come last. Abstract selections lower to evidence parameters; concrete selections lower to occurrences of the selected implementation-method binders. These are the pinned interface-evidence lowering rules.

Three exact retained tests exercise or inspect compiler stages that a CLI result cannot reveal:

  • cross_module_constraint_lowers_to_method_evidence inspects the evidence binder and concrete method application before the source argument;
  • recursive_constrained_global_reuses_its_declared_abstract_evidence inspects the abstract selections on a method and recursive global occurrence; and
  • generic_exact_current_self_carries_abstract_prerequisite_evidence exercises recursive exact-current evidence in an implementation method.

The tests support the specified checking and lowering account. They do not add language behavior or make Core structure observable to an Ash program.

Once the selected relationships have lowered, their interface, implementation, and requirement identities erase. The evaluator receives ordinary functions, binder lookups, and applications under the pinned generated-evidence rules. There is no runtime interface value, implementation registry, registration step, implementation lookup, or interface-specific dispatch.

Generated evidence functions and applications can still perform ordinary Core work. They are outside the program’s named counts for visited nodes, top-level compare calls at nodes, and recursive Natural compare calls. The observations therefore establish no zero-overhead result, identical Core, elapsed-time comparison, or machine-cost comparison with explicit parameter passing.

Observe a missing implementation

Now change the key representation instead of the calling syntax. This complete entry constructs one Int-key node and calls the same constrained global.

import ordered_trees as Trees
import ordered_trees (impl Order)

main : Unit -> Trees.Option<Int>
main () = {
    let tree = Trees.Node(Trees.Empty, 1, 10, Trees.Empty)
    Trees.lookup 1 tree
}

The selector makes the dependency’s public Order<Natural> fact available; it does not invent or transitively discover another implementation. Ordinary typing determines K = Int, so the call creates an Order<Int> obligation. main declares no abstract requirement, it is not an implementation method with exact current evidence, and the selected facts provide no Order<Int>. Predict rejection before evaluation.

The Order<Int> obligation belongs to the Trees.lookup occurrence. The message labels that occurrence and says no available evidence satisfies the requirement. The related labels trace it through lookup’s constrained signature and the client’s import to the Order interface. The 1 key fixes this call’s requirement to Order<Int>, while the selected implementation supplies only Order<Natural>.

Use Natural keys, as in the accepted entries, to match the selected fact. Keeping integer keys would instead require a public Order<Int> implementation selected by this client. The pinned selection rules require evidence for the complete application. This failure is classified as constraint.unsatisfied; checking stops before evaluation can begin.

Retain the algorithm’s premises

Moving comparison into selected evidence does not make its laws part of Order<A>. Fix one implementation whose comparisons required by an argument return and whose results satisfy these premises:

  • Equal is the chosen equivalence between keys;
  • reversing a strict comparison reverses Less and Greater;
  • strict comparison is transitive; and
  • equivalent keys have the same ordering relationship to every other key.

For that implementation, Empty is valid. A finite Node(left, key, value, right) is valid when both subtrees are valid, every key anywhere in left compares with key as Less, and every key anywhere in right compares with key as Greater. The interface checks none of these global descendant properties.

For a finite valid input tree, when every comparison on the entered insertion path returns, a completed insertion preserves the invariant under those premises. Less and Greater rebuild the node around the one recursively changed branch. Equal retains the stored representative key and both branches. This is a proof obligation about this program, not a property that Ash derives from where Order<K>.

For a completed lookup on a finite tree whose query and visited keys k_1 through k_m are finite unary Naturals, let C(query, k_i) count completed compare method applications for that pair, including the terminal equation. Let h be the greatest number of Node forms on a root-to-Empty path. The exact comparison sub-work is:

sum from i = 1 to m of C(query, k_i)

The surrounding branch selection, result construction, recursive lookup, and count bookkeeping contribute O(m) named source operations. One-branch lookup has m <= h. Only when every visited comparison satisfies C(query, k_i) <= Cmax, with Cmax >= 1, may the combined account be summarized as O(h * Cmax). Generated evidence applications remain ordinary work outside these named counts. None of these source counts establishes elapsed time, machine instructions, arbitrary-precision integer bit cost, heap bytes, or native stack behavior.

A completed return claim also needs the finite entered path and returning comparisons on that path. A required nonreturning comparison can prevent lookup from returning. The nominal type does not prove finiteness: Ash permits constructor-guarded cyclic values under its static recursive block-group rules and dynamic recursive binding rules. A reachable cycle along the selected path may prevent return, while a cycle in an unentered branch need not affect that lookup.

This case adds no opacity, invariant enforcement, balance, deletion, mutation, iteration, or generic tree infrastructure. It also introduces no associated declarations, default methods, named implementations, inferred global requirements, runtime registries, or dynamic dispatch. The source and output make no claims about physical sharing, pointer identity, garbage collection, compiler optimization, or storage strategy.

Practice and continue

  2. Suppose the Natural implementation loses pub while the entry remains a direct dependent. Predict whether Trees.lookup_counted three valid can select that implementation, and identify the source occurrence that owns the resulting obligation.
  3. In a copy of the first entry, replace the Natural query and tree keys with Int values while retaining the constrained lookup. Predict the output message, source labels, and status before running it.
