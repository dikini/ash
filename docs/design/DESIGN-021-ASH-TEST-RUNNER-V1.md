# DESIGN-021: Ash Test Runner V1

## Status: Draft

## Overview

Introduce a first-class Ash test runner integrated into the Ash CLI. The v1 goal is not to solve the full long-term testing story, but to establish a reliable execution substrate for authored Ash tests and explicitly synthesized metadata-driven tests.

The runner must be able to:
- discover and run Ash tests
- isolate failures and panics so one bad test does not stop the suite
- support multiple test kinds through one result model
- integrate with `ash` CLI workflows and existing runtime/typecheck infrastructure
- treat contracts, policies, and obligations as first-class metadata sources for synthesized tests, while keeping those synthesized tests explicit, labeled, opt-in, and complementary to authored tests rather than silently replacing them

V1 is deliberately execution-focused. It enables unit, integration, e2e, property, and small-world test execution. It does not attempt to land the entire future ecosystem of shrinking, mutation testing, coverage analysis, fuzz orchestration, or formal proof integration.

## Problem Statement

Ash already has substantial Rust-side testing across parser, typechecker, engine, interpreter, runtime verification, policies, obligations, and pure functions, but there is no Ash-native test runner that can execute authored Ash test programs or metadata-driven test suites as first-class citizens.

This leaves several gaps:
- no canonical `ash test` command
- no shared result envelope for authored and synthesized Ash tests
- no panic-capturing test boundary that treats panic as a test outcome instead of a suite abort
- no common execution substrate for unit/integration/e2e/property/small-world Ash tests
- no explicit place where contracts, policies, and obligations can be turned into opt-in synthesized tests
- no agreed syntax/structure for Ash test metadata in the codebase

The immediate need is a test runner that can execute tests safely and report results honestly. The richer testing ecosystem can then layer on top.

## Goals

1. Add an `ash test` command to the Ash CLI.
2. Define one canonical test result model shared across all test kinds.
3. Ensure per-test panic/failure isolation so one test cannot abort the whole suite.
4. Support these v1 test kinds:
   - unit
   - integration
   - e2e
   - property
   - small-world
5. Support both authored tests and synthesized tests.
6. Make synthesized tests from contracts, policies, and obligations explicit, labeled, and opt-in.
7. Define a practical metadata syntax/structure for tests in the codebase.
8. Keep the design compatible with future shrinking, richer fixture systems, and broader synthesis.

## Non-Goals

V1 does not attempt to provide:
- full shrinking/minimization comparable to mature proptest ecosystems
- coverage instrumentation
- mutation testing
- distributed test scheduling
- flaky-test quarantine systems
- long-running fuzzing orchestration
- snapshot testing as a first-class Ash language concept
- automatic synthesis from every possible metadata source in the language
- proof-producing verification of metadata-derived tests

## Design Principles

### P1. Panic is a test outcome, not a suite outcome

The runner must treat panic as data. A panic in one test is captured, classified, and reported, but does not stop the rest of the suite.

### P2. One execution substrate, many test kinds

Unit, integration, e2e, property, and small-world tests should not each invent their own runner protocol. They differ in discovery, input generation, and oracles, but they share isolation, timing, capture, and reporting.

### P3. Synthesized tests are not hidden magic

Contracts, policies, and obligations may produce synthesized tests, but such tests must be:
- explicitly requested
- clearly labeled as synthesized
- reported separately from authored tests
- complementary to authored tests, not silent replacements

### P4. Contracts are executable metadata, not a substitute for authored tests

Preconditions and postconditions should help drive test generation and classification, but they do not replace authored tests that check diagnostics, traces, role interactions, output behavior, or cross-declaration semantics.

### P5. Keep the codebase structure boring and explicit

Discovery should be file- and directory-oriented in v1. Inline and more magical discovery can come later if the basic model proves sound.

## Test Taxonomy

V1 recognizes these axes.

### Axis A: Test source

- Authored
  - explicitly written by Ash developers in test files
- Synthesized
  - generated by the runner from metadata sources such as contracts, policies, and obligations

### Axis B: Test kind

- Unit
  - single function/workflow/policy/role/capability-focused
- Integration
  - multiple modules or declarations interacting together
- E2E
  - full program/workflow observable execution path
- Property
  - repeated generated inputs under a seeded generator
- Small-world
  - bounded finite-domain or bounded-state exploration

### Axis C: Oracle source

- Explicit assertions
- Contract-derived checks
- Policy-derived checks
- Obligation-derived checks
- Runtime/observable assertions

A single test run may combine these axes. For example:
- authored unit test with explicit assertions
- synthesized contract property test
- synthesized obligation small-world test
- authored e2e test whose pass criteria also include contract enforcement

## CLI Integration

### New command

Add a new CLI command:

```text
ash test [PATH]
```

### V1 sub-options

Recommended v1 options:

```text
ash test [PATH]
  --format human|json
  --filter <substring-or-pattern>
  --tag <tag>
  --kind unit|integration|e2e|property|smallworld
  --include-synthesized contracts,policies,obligations
  --only-synthesized contracts,policies,obligations
  --fail-fast
  --timeout <seconds>
  --seed <u64>
  --max-cases <n>
  --max-worlds <n>
```

### Default behavior

Default `ash test` behavior in v1:
- discover authored tests only
- do not synthesize metadata-driven tests unless explicitly requested
- run all discovered authored tests with panic isolation
- emit human-readable output by default
- return non-zero exit code if any test fails, panics, or infrastructure-errors

### Output modes

Human output should show:
- suite totals
- per-test result summary
- durations
- panic/error details
- seed information for property/small-world failures

JSON output should preserve a machine-readable canonical result schema.

## Result Model

Define one canonical result envelope for every executed test.

### Per-test outcome kinds

- `pass`
- `fail`
- `panic`
- `error`
- `skip`
- `xfail` (optional but useful even in v1)

### Suggested per-test record

```text
TestResult {
  id,
  name,
  source_kind,        // authored | synthesized
  synthesized_from,   // none | contract | policy | obligation
  test_kind,          // unit | integration | e2e | property | smallworld
  module_path,
  file_path,
  tags,
  status,
  duration_ms,
  timeout_ms,
  seed,
  case_index,
  world_index,
  panic_message,
  error_message,
  diagnostics,
  trace_ref,
  stdout_capture,
  stderr_capture,
  repro,
}
```

### Suite result

```text
TestSuiteResult {
  total,
  passed,
  failed,
  panicked,
  errored,
  skipped,
  xfailed,
  duration_ms,
  results: Vec<TestResult>,
}
```

## Isolation and Panic Capture

### Required property

Each test case runs inside an isolation boundary that captures:
- panic
- timeout
- runtime failure
- parse/load/setup errors

without aborting the rest of the suite.

### V1 execution boundary

At minimum, the Rust-side runner should:
- execute each test inside a dedicated per-test task/boundary
- wrap the execution boundary in panic capture
- attach timeout enforcement outside the test body
- seal the result record before moving on

### Classification rules

- panic during test execution -> `panic`
- timeout -> `error` or dedicated timeout-flavored `error`
- unmet explicit assertion -> `fail`
- infrastructure failure (fixture load / parse harness failure) -> `error`
- expected panic matched by test metadata -> `pass`

### Required v1 behavior

A suite with 100 tests where 10 panic must still run the remaining 90 tests.

## Contracts as Test Metadata

Contracts should be test-aware in three distinct modes.

### Mode 1: Contract-observing

The runner records whether pre/post conditions were implicated in the result, but does not synthesize tests from them.

### Mode 2: Contract-enforcing

Contracts participate in pass/fail semantics.

Examples:
- test expected success but call violated a precondition -> fail
- test expected success but ensured postcondition failed -> fail
- test explicitly expected precondition rejection -> pass when rejected

### Mode 3: Contract-derived

The runner synthesizes tests from function/workflow contracts.

Examples:
- generate valid inputs satisfying `requires`
- generate nearby invalid inputs violating `requires`
- execute and check `ensures`
- use contract information as an oracle for property tests

### Recommended v1 scope for contracts

V1 should support contract-derived synthesis for:
- pure-function contracts first
- workflow-side precondition propagation cases where contract boundaries are already lowered and available

### Important design rule

Contracts reduce duplication but do not replace authored tests. They are one oracle source among several.

## Policies as Test Metadata

Policies are strong candidates for synthesized tests because they already define decision boundaries.

### Recommended synthesized policy tests in v1

For explicit opt-in synthesis:
- canonical allow case
- canonical deny case
- approval case, where supported
- transform case, where supported
- bounded representative edge cases around policy-relevant thresholds or fields

### Policy synthesis output labeling

Every synthesized policy test must be labeled as:
- `source_kind = synthesized`
- `synthesized_from = policy`

## Obligations as Test Metadata

Obligations are an especially good fit for small-world and lifecycle-style synthesis.

### Recommended synthesized obligation tests in v1

- obligation introduced
- obligation must be discharged before completion
- obligation discharged exactly once
- obligation left open -> failure/rejection
- branch/path discipline cases
- double-discharge / missing-discharge negative cases

### Why obligations belong in v1 synthesis

Obligation behavior is finite-state and bounded enough to benefit from generated and small-world execution, even before more advanced generation infrastructure exists.

## Roles as Metadata

Roles are useful metadata, but in v1 they should be secondary to contracts, policies, and obligations.

### Recommended role-related scope in v1

Support simple, explicit authored tests and possibly light synthesized conformance checks such as:
- role includes expected capabilities
- role does not expose absent capabilities
- composed roles merge capabilities/obligations correctly

Richer role-driven synthesis can come after the contracts/policies/obligations path stabilizes.

## Test Metadata Syntax and Codebase Structure

V1 should keep discovery simple and explicit.

### Directory structure

Recommended test directories:

```text
tests/ash/unit/
tests/ash/integration/
tests/ash/e2e/
tests/ash/property/
tests/ash/smallworld/
```

This keeps discovery and ownership obvious.

### File-level metadata

Use explicit file-level metadata blocks in comments at the top of Ash test files.
The file-level metadata should identify the test kind, tags, timeout, and runner controls, while the authored test body itself should import and use the Ash test library surface introduced in Phase B.

Recommended shape:

```ash
-- @test
-- name: option.unwrap_or returns default on None
-- kind: unit
-- tags: [stdlib, option]
-- timeout_ms: 1000
-- capabilities: []
```

For authored property tests:

```ash
-- @test
-- name: map preserves Result error branch
-- kind: property
-- tags: [result, property]
-- seed: 12345
-- max_cases: 256
```

For authored small-world tests:

```ash
-- @test
-- name: obligation lifecycle over two branches
-- kind: smallworld
-- tags: [obligation, control]
-- max_worlds: 128
```

This metadata should be parsed by the runner, not treated as arbitrary comments.

### Inline metadata scope

V1 should support file-level metadata and optional declaration-level named test blocks, but not arbitrary implicit discovery from every function/workflow.

### Recommended authored test structuring inside Ash files

Use explicit test declarations rather than trying to infer which normal declarations are tests.

Recommended conceptual shape:

```ash
test "option.unwrap_or returns default on None" {
    -- body uses assertion helpers
}
```

or, if introducing `test` as syntax is too large for v1, use designated runner-recognized workflow/function entry shapes inside test files.

The key requirement is that test declarations be explicit, not inferred from ordinary declarations.

### Metadata for expected panic/failure

Recommended metadata fields:
- `expect: pass | fail | panic | error`
- `panic_contains: "..."`
- `xfail_reason: "..."`

This enables panic-aware tests without runner ambiguity.

## Synthesized Test Structuring

Synthesized tests should not appear as if they were authored declarations in the repository.

Instead, the runner should build an internal synthesized test plan with labels such as:

```text
synthesized/contract/fn_name/requires-boundary/seed-123
synthesized/policy/PolicyName/deny-case/seed-42
synthesized/obligation/RoleX/open-obligation/world-07
```

These names should appear in runner output and JSON reports.

## Property Testing in V1

V1 property testing should emphasize reproducibility over sophistication.

### Required v1 capabilities

- deterministic seed support
- bounded case count
- bounded generated size
- reproducible failure reporting
- no suite abort on failing property case

### Recommended property result reporting

On failure, report:
- seed
- case index
- generated input summary
- failure reason
- suggested reproduction command

### Explicit non-goal for v1

Advanced shrinking is not required for v1.

## Small-World Testing in V1

Small-world testing should be first-class, not hidden behind generic property testing.

### Why Ash needs it

Ash has many finite or bounded semantic domains where exhaustive or near-exhaustive exploration is more valuable than random generation:
- role/capability combinations
- policy decision surfaces
- obligation lifecycle states
- bounded control-link lifecycle cases
- small protocol/message spaces

### Required v1 capabilities

- finite-domain declarations or bounded enumerators
- max world count / max depth controls
- explicit counterexample output
- panic containment identical to other tests

## Fixture and Capability Fake Support

The runner should support deterministic fixtures and test doubles for capabilities.

### Required v1 fixture support

- fake capability providers
- scripted provider responses
- panic-producing providers
- deny/approve/transform policy fixtures
- temporary workspace/data fixtures for e2e and integration tests

This is required for authored tests and also for meaningful synthesized tests involving policies and obligations.

## Discovery of Metadata-Driven Tests

### Supported v1 synthesized sources

V1 should support explicit, opt-in synthesis from:
- contracts
- policies
- obligations

### CLI behavior

Default:
- authored tests only

Opt-in examples:

```text
ash test --include-synthesized contracts
ash test --include-synthesized contracts,policies
ash test --only-synthesized obligations
```

### Why opt-in

This prevents:
- invisible test-count explosions
- surprising runtime cost
- confusion between authored and synthesized test ownership

## Integration with Existing Ash Infrastructure

The runner should reuse existing infrastructure where possible.

### Existing relevant pieces

- CLI command structure in `ash-cli`
- parser/typechecker/engine execution paths
- lowered pure-function contract storage and runtime postcondition boundaries
- policy and obligation checking/runtime-verification infrastructure
- existing Rust-side test helper and provider-fixture patterns

### Recommended implementation layering

1. `ash-cli` provides discovery, command handling, output formatting, and exit codes.
2. engine/interpreter provide execution and runtime integration.
3. a dedicated test-runner module/crate owns test isolation, result classification, fixture wiring, and synthesized test planning.
4. Ash test stdlib/helpers provide assertion-level ergonomics.

## Suggested Implementation Phases

### Phase A: Runner substrate

- add `ash test`
- add result model
- add panic capture and timeout handling
- add authored test discovery
- add human/json reporting

### Phase B: Ash test library

Introduce a dedicated Ash-side test library phase before broad authored test execution lands. The runner alone is not enough; Ash code needs a stable assertion and test-helper surface.

This phase should provide:
- a small `std::test` (or equivalent) library surface for authored tests
- basic assertions:
  - `assert_true`
  - `assert_false`
  - `assert_eq`
  - `assert_ne`
  - `assert_matches`
  - `fail`
- panic-aware assertions:
  - `assert_panics`
  - `assert_panics_with`
- workflow/runtime-facing assertions:
  - `assert_error`
  - `assert_exit_code`
  - `assert_output_contains`
  - `assert_trace_contains`
- contract/policy/obligation-aware helpers where the semantics are already stable
- a small fixture/helper surface for authored tests to interact with fake providers and deterministic runtime setup

This phase should remain intentionally small. It provides the authored-test vocabulary and runner interop surface, not the full long-term testing standard library.

### Phase C: Authored test execution model

- add explicit Ash test declaration shape or designated test-file protocol
- bind authored test declarations to the Ash test library surface from Phase B
- support unit/integration/e2e authored tests

### Phase D: Metadata-driven synthesis

- contracts as synthesized test source
- obligations as synthesized test source
- policies as synthesized test source
- explicit labeling and opt-in CLI flags
- ensure synthesized tests can reuse the same result model while remaining visibly distinct from authored tests

### Phase E: Property + small-world execution

- seeded property execution
- bounded small-world enumeration
- reproducible failure output
- define how authored property/small-world tests use the Ash test library from Phase B without forcing all generation logic into the surface language immediately

## Acceptance Criteria for V1

V1 is complete when all of the following are true:

1. `ash test` exists and runs authored tests.
2. Per-test panic capture prevents suite abort.
3. Unit, integration, and e2e authored tests can be executed through one result model.
4. Property and small-world execution paths exist with bounded controls.
5. Contracts, policies, and obligations can be used as synthesized test sources.
6. Synthesized tests are explicit, labeled, and opt-in.
7. Test metadata syntax/structure is documented and stable enough for repository use.
8. Human and JSON output preserve the authored vs synthesized distinction.

## Open Questions

1. Should v1 introduce a new `test` declaration in the Ash surface syntax, or should it begin with test-file conventions built on existing declarations?
2. Should expected-failure (`xfail`) be part of the initial surface, or deferred until runner semantics settle?
3. How much generation syntax belongs in Ash source versus in runner-side metadata blocks for v1 property and small-world tests?
4. Which minimal assertion set belongs in Ash source versus remaining Rust-side helpers initially?

## Recommendation

Proceed with a staged implementation centered on a fail-contained test runner substrate and explicit test metadata. In v1, make contracts, policies, and obligations first-class metadata sources for synthesized tests, but keep those synthesized tests visibly separate from authored tests and opt-in at the CLI. This gives Ash a practical testing foundation without overcommitting the language or runner to premature complexity.
