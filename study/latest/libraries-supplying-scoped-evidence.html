Supplying scoped evidence

A module newtype gives a representation a meaning shared by that module’s clients. Sometimes a calculation needs a distinction only within one block. A local newtype gives the following code a nominal identity without making that identity part of the block’s outward contract.

Once that local type exists, the block may supply exact interface behavior for it. The supplied methods can use values already available there. Their availability follows the source scope, and selected methods become ordinary functions used by the checked calculation.

Consume a local distinction inside its block

01-local-value.ash introduces Points only for the remainder of main’s body:

main : Unit -> Int
main () = {
    newtype Points = Points(Int)
    let points = Points(40)
    match points {
        Points(value) => value + 2
    }
}

The representation is Int, as for the module newtype in the preceding chapter. Construction and the pattern explicitly cross that boundary. The local identity must stay out of the block’s outward type. Follow the pattern and arithmetic to predict the returned amount, then identify what type leaves the block. Run from this lesson’s src directory:

$ ash 01-local-value.ash
42 : Int

The pattern unwraps 40, and the body adds two to return 42 : Int. No Points identity occurs in that result type.

A local declaration is sequential: its nominal type and constructor enter the following scope together. It has no pub form and cannot become a recursive group member. Its identity belongs to this lexical declaration; executing the block does not allocate a fresh runtime identity or a resource owner.

A closure may retain a value without exposing its type

02-returned-closure.ash returns a calculation over a captured local value:

make_adder : Int -> Int -> Int
make_adder amount = {
    newtype Offset = Offset(Int)
    let offset = Offset(amount)
    fn(value) {
        match offset {
            Offset(saved) => saved + value
        }
    }
}

main : Unit -> Int
main () = make_adder 40 2

The result of make_adder 40 has type Int -> Int. The returned function captures offset and unwraps it when called, but its parameter and result do not expose Offset. Predict the amount retained when make_adder receives 40, then the result when that returned function receives 2. Run it:

$ ash 02-returned-closure.ash
42 : Int

The closure unwraps its saved 40 and adds its argument 2, producing 42. This is an ordinary retained value and closure. The local newtype has no release obligation. Its representation may remain in a function environment when the function’s outward type is independent of the local nominal identity.

Returning the local value itself crosses a different boundary:

main : Unit -> Int
main () = {
    let escaped = {
        newtype Token = Token(Int)
        Token(42)
    }
    0
}

Compare the inner block’s result type with the outward function type of make_adder. Which expression exposes a local identity beyond its declaration’s scope here? Predict whether leaving escaped unused changes that boundary:

$ ash --message-format human --locale en 04-identity-escape.ash
This type or effect row exposes a local nominal type outside its scope.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/04-identity-escape.ash:5:9
5 |         Token(42)
  |         ^ This type or effect row exposes a local nominal type outside its scope.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/04-identity-escape.ash:4:9
4 |         newtype Token = Token(Int)
  |         ^ This scope owns the local nominal type.
reason: type.local-nominal-escape

The escaping expression has type Token, and the related label identifies the declaration whose scope would end. The unused name escaped does not hide that outward type. Return an unwrapped integer, or an identity-free function such as make_adder’s result.

The check includes function domains and results, aggregate members, schemes, requirements, and effect rows. Returning a local value together with a function that unwraps it does not create an implicit package hiding the identity. The local nominal rules define this boundary.

Supply the exact method needed here

A local nominal can identify an exact interface application. In 03-exact-method.ash, Read<A, B> uses A to determine its result type B:

interface Read<A, B> where A -> B {
    read : A -> B
}

forward : A -> B where Read<A, B>
forward value = read value

main : Unit -> Int
main () = {
    newtype Token = Token(Int)
    let token = Token(40)
    let offset = 2
    with Read<Token, Int> {
        read (Token(value)) = value + offset
    }
    forward token
}

with Read<Token, Int> supplies one complete application, not a generic implementation head. Its read method unwraps a Token and adds the preceding offset value. The source becomes available only after every supplied method has checked; forward token is in that following remainder.

Identify the complete requirement at forward token and the preceding declaration that supplies it. Which ordinary value does the supplied method capture? Follow its calculation to predict the result before running it:

$ ash 03-exact-method.ash
42 : Int

The method unwraps 40 and adds the captured offset, which is two. At the call, the token fixes the selection key. The exact Read<Token, Int> source determines the result as Int and supplies the required method. Inside forward, its ordinary declared requirement carries that method to read. The global helper uses the supplied behavior without naming the local type.

This retains the earlier library model: a generic helper declares its requirement, and the caller supplies evidence. with adds a lexical source for one exact relation. It does not infer a new requirement or initiate local implementation search.

The application must be explicit and have no unresolved inference choices. Its key must contain an active local nominal. Here Token is the determinant; for an interface without an edge, all arguments form the key. A local nominal under another type constructor also counts, but one appearing only in a dependent result does not.

A module nominal does not establish a local key

Compare the earlier local declaration with a module-level Token:

interface Read<A, B> where A -> B {
    read : A -> B
}

forward : A -> B where Read<A, B>
forward value = read value

newtype Token = Token(Int)

main : Unit -> Int
main () = {
    with Read<Token, Int> {
        read (Token(value)) = value
    }
    forward (Token(42))
}

Identify the selection key in Read<Token, Int>, then locate the declaration that owns its nominal identity. Does that declaration supply an active local nominal? Predict which source occurrence the checker will mark:

$ ash --message-format human --locale en 05-no-local-key.ash
This evidence declaration needs an active local nominal type in its selection key: the determinant arguments, or all arguments when there is no determination edge.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/05-no-local-key.ash:12:10
12 |     with Read<Token, Int> {
   |          ^ This evidence declaration needs an active local nominal type in its selection key: the determinant arguments, or all arguments when there is no determination edge.
reason: evidence.missing-local-key

The diagnostic marks the exact application and states which positions form its key. This Token is a module nominal, not an active local declaration. Move the newtype back inside the block for the original scoped behavior. For behavior belonging to a module type, use an ordinary implementation in an owning module, following the preceding lessons.

with does not bypass module ownership or coherence rules. Abstract evidence from a function’s declared requirement and exact current-implementation evidence retain precedence over lexical evidence. Lexical evidence precedes matching concrete implementations; it does not rewrite those contracts.

Availability follows the occurrence’s source scope

The evidence source applies to the following remainder, including function bodies defined there. Compare that scope with this call’s position:

interface Read<A, B> where A -> B {
    read : A -> B
}

forward : A -> B where Read<A, B>
forward value = read value

main : Unit -> Int
main () = {
    newtype Token = Token(Int)
    let token = Token(40)
    let before = forward token
    with Read<Token, Int> {
        read (Token(value)) = value + 2
    }
    before
}

At forward token, which evidence declarations are already available? Predict whether the later with can supply this occurrence, then run the source:

$ ash --message-format human --locale en 06-before-evidence.ash
No available evidence satisfies this interface requirement.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/06-before-evidence.ash:12:18
12 |     let before = forward token
   |                  ^ No available evidence satisfies this interface requirement.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/06-before-evidence.ash:5:1
5 | forward : A -> B where Read<A, B>
  | ^ This declaration introduced the interface requirement.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/06-before-evidence.ash:1:1
1 | interface Read<A, B> where A -> B {
  | ^ This interface participates in the failing evidence selection.
2 |     read : A -> B
  | ^ This interface participates in the failing evidence selection.
3 | }
  | ^ This interface participates in the failing evidence selection.
reason: constraint.unsatisfied

The call in before is outside the following remainder. Its labels lead back to forward’s required relation. The final before expression and main’s Int result annotation fix the complete requirement to Read<Token, Int>. What remains missing is evidence available at the call’s original position. Moving the evidence declaration before that call supplies the source. The compiler preserves an occurrence’s original lexical scope even when it finishes inference later.

Supplied method bodies can capture preceding ordinary values and use preceding evidence. The new source is not available inside its own supplied bodies, so it grants no implicit recursive or sibling method selection. If a method needs a recursive helper, define an appropriately annotated local recursive function earlier, using the rules from Learn.

Separate scopes can supply different methods

Two simultaneously active sources cannot supply the same key:

interface Read<A, B> where A -> B {
    read : A -> B
}

forward : A -> B where Read<A, B>
forward value = read value

main : Unit -> Int
main () = {
    newtype Token = Token(Int)
    with Read<Token, Int> {
        read (Token(value)) = value + 1
    }
    with Read<Token, Int> {
        read (Token(value)) = value + 2
    }
    forward (Token(40))
}

Mark the remainder governed by each with. Which earlier source remains active when the checker reaches the second declaration? Compare their keys to predict which two locations the checker needs to relate:

$ ash --message-format human --locale en 07-duplicate-evidence.ash
An active evidence declaration already supplies this exact interface application.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/07-duplicate-evidence.ash:14:10
14 |     with Read<Token, Int> {
   |          ^ An active evidence declaration already supplies this exact interface application.
  --> /path/to/ash-doc/content/libraries/supplying-scoped-evidence/src/07-duplicate-evidence.ash:11:10
11 |     with Read<Token, Int> {
   |          ^ The earlier active evidence declaration is here.
reason: evidence.duplicate

The two labels identify the overlapping declarations. The second does not shadow the first. Remove one source when a single interpretation is intended. For two independent calculations with different interpretations, use disjoint blocks:

interface Read<A, B> where A -> B {
    read : A -> B
}

forward : A -> B where Read<A, B>
forward value = read value

main : Unit -> (Int, Int)
main () = {
    newtype Token = Token(Int)
    let token = Token(40)
    let first = {
        with Read<Token, Int> {
            read (Token(value)) = value + 1
        }
        forward token
    }
    let second = {
        with Read<Token, Int> {
            read (Token(value)) = value + 2
        }
        forward token
    }
    (first, second)
}

Follow each call using only the with source active in its block. Predict the pair’s values and explain why one block’s method cannot change the other:

$ ash 08-disjoint-scopes.ash
(41, 42) : (Int, Int)

The first method computes 40 + 1 and the second computes 40 + 2, giving (41, 42). Token remains in scope around both calculations, but each with applies only inside its own following remainder. Neither source becomes available to a new call after its block.

For a determined interface, simultaneously active equal keys with different dependent result types also conflict. Distinct local declarations remain distinct nominal keys even if they use the same representation.

Retain a selected method in an outward function

Lexical availability of new calls is separate from retaining a method already selected for a closure:

interface Read<A, B> where A -> B {
    read : A -> B
}

forward : A -> B where Read<A, B>
forward value = read value

make_reader : Int -> Unit -> Int
make_reader amount = {
    newtype Token = Token(Int)
    let token = Token(amount)
    let offset = 2
    with Read<Token, Int> {
        read (Token(value)) = value + offset
    }
    fn(ignored) {
        forward token
    }
}

main : Unit -> Int
main () = make_reader 40 ()

The function body occurs in the remainder after with. Use that source scope to identify the method selected for forward token, then trace the values it needs when called. Predict the result and check whether the returned Unit -> Int type exposes Token:

$ ash 09-retained-method.ash
42 : Int

The selected method adds its captured two to the token’s saved 40, producing 42. The checked closure retains the method function, its offset capture, and the local token needed for the call. Its outward type exposes only Unit -> Int.

After make_reader returns, calling this closure uses those retained ordinary functions and values. It does not search the caller’s block for evidence or export a new evidence fact that other calls can select.

The scoped evidence rules distinguish selecting in a lexical scope from retaining the selected functions. Local nominals and exact evidence add no acquisition, resource release, or permission to export resource access. Those separate obligations belong to the effects and resources path.

Practice: trace scope and capture

Start each task with a fresh copy in a scratch directory: use 03-exact-method.ash for task one, 08-disjoint-scopes.ash for task two, and 09-retained-method.ash for tasks three and four.

  1. Change the offset in 03-exact-method.ash. Predict the result and explain how forward receives behavior without knowing that local binding.
  2. In 08-disjoint-scopes.ash, make the second method multiply by two. Predict both fields before running it, then explain which source supplies each method.
  3. Construct two readers with different inputs using make_reader, then call both in main and update its result annotation. Predict the pair and which ordinary values each closure retains, then check the observation.
  4. Reason about returning the local constructor from make_reader. Write its outward function type on paper and identify any local identity it contains. Compare that boundary with the current Unit -> Int result.

In every run, the local machinery stayed invisible at the boundary: the results were plain 42 and (41, 42), the rejected sources were marked at their own occurrences, and each with governed only the code that followed it. Continue with the algorithm and effect Cases to use explicit capabilities while deriving calculations, invariants, and costs.
