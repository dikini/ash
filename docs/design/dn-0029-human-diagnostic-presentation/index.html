DN-0029: Human Diagnostic Presentation

Development design notes · ash-lang 9a8b73b

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes
  • ID: DN-0029
  • Status: exploring
  • Related: AD-0005, AD-0006, AD-0010

This design note is informative. It does not define current Ash or accept an architecture.

Question

How should Ash turn its retained semantic reasons and causal source spans into plain, source-aware, localized diagnostics without making presentation text a semantic authority or building a general tooling platform before one is needed?

Context

AD-0005 and AD-0006 require structured parser, resolution, checking, and elaboration failures independently from rendering. The current executable renders the reason, process-local source identity, byte range, and label text as a minimal stable view. It does not resolve ordinary pipeline spans to file paths, line and column positions, or excerpts.

Migration of eight recursive-algorithm teaching programs at the exact lib-ash checkpoint exposed a second loss. Each importer receives resolve.internal-state and the phrase “a dependency summary failed body-free authentication.” Summary validation first collapses many distinct invariant failures to InvalidState; the resolver then replaces that result with one generic label at the import. The result identifies the boundary crossed but neither explains the compiler's responsibility nor retains the invariant that failed.

The term “body-free authentication” names compiler representation work. A checked dependency publishes an immutable export summary containing the public and hidden facts required by importers but not executable definition bodies. Ash source neither declares nor authenticates this summary. User-facing prose therefore should discuss the imported module; compiler documentation may call the representation a checked export summary.

Constraints

  • Language validity, first-failure ownership, causal label order, exit status, and stdout behavior remain unchanged.
  • Compiler stages retain typed reasons and facts. A renderer does not infer policy or parse compiler prose.
  • Internal validation retains a cause specific enough for compiler investigation. An importing boundary may add its source context but may not replace that cause.
  • Human rendering uses source paths, one-based lines and columns, excerpts, and labels. Raw process source identities and byte ranges remain machine facts.
  • Human prose may change. Automation receives a versioned machine contract.
  • Translated templates may reorder named facts and apply grammatical selection without translating Ash identifiers, types, operators, paths, or reason codes.
  • The first retained checkpoint proves localization with complete English and Bulgarian catalogues.
  • Existing phase-specific diagnostic types remain the semantic owners. A presentation boundary must not duplicate them into a speculative universal error algebra.
  • Compile-time presentation and runtime reporting have distinct interfaces. Compile-time formatting may allocate within compiler resource limits. Runtime reporting must preserve failure and cleanup outcomes without source effects or recovery; resource reporting cannot depend on allocation.

Candidate directions

Human-first default with explicit formats

The default renderer leads with a plain explanation, shows source excerpts and causal labels, and places the stable reason code after the explanation. An explicit short format serves compact logs. A versioned JSON-lines format serves automation and editor consumers.

This direction gives learners the intended default while separating human wording from the machine contract. Existing downstream checks must migrate from parsing default prose to JSON at the same checkpoint.

Code-first human rendering

A Rust-like error[reason] heading could preserve a prominent code while adding excerpts and explanations. It reduces the visible contract change but continues to lead learner interaction with compiler taxonomy. Long interface, constraint, and internal reasons remain difficult even when the following prose is clear.

Enrich the current stable view

The current reason-first lines could gain paths, excerpts, and explanations. This is the smallest presentation change, but it preserves display text as an accidental automation protocol and keeps process-oriented structure ahead of the reader's question.

The human-first direction best separates the learner, log, and automation uses. Output selection must be explicit rather than depend on whether stderr is a terminal. Only optional color may vary with terminal capability.

Message catalogue directions

Typed named arguments and locale catalogues

A reason and label role select stable message identities. The renderer supplies named values derived from typed diagnostic facts. Locale templates may reorder those values and apply plural or grammatical selection. The catalogue owns words and sentence structure, not semantic classification, diagnostic order, source layout, or terminal styling.

This direction supports real translation without asking translators to edit Rust or copy complete English output blocks. It requires catalogue validation for missing keys, unknown arguments, invalid templates, and locale fallback.

Whole-string lookup

Looking up complete English strings is initially small, but punctuation or wording changes become message identities. It handles variable reordering and grammar poorly and encourages compiler phases to assemble sentences before translation.

Per-locale rendering code

Separate renderer code can express any grammar, but duplicates layout and control flow and requires Rust changes for ordinary translation work.

Typed named templates are favored. A bounded implementation comparison should select an existing catalogue format and Rust integration using only the required criteria: named arguments, grammatical selection, validation, embedded catalogues, deterministic fallback, and translator workflow.

Selected presentation model

Compile-time failures expose their existing typed reason, facts, and source labels through a small borrowed presentation view. The view adds responsibility (source, compiler, or environment) and safe developer details where the phase failure does not already carry them. A source catalogue resolves spans for presentation. Three renderers consume the same view:

  • human, the default, renders localized explanation and source context;
  • short renders one compact localized log line; and
  • json emits one locale-independent, schema-versioned object per diagnostic.

Declare each message identity and its typed named arguments once in compiler code. Construction checks argument names and types; catalogue tests check translation completeness and agreement with that declaration. Avoid parallel hand-maintained lists of IDs, keys and argument schemas. Catalogues contain complete messages, not translated sentence fragments. Add title, label or help messages only where they add information; do not require every diagnostic to fill every presentation slot. Source spellings remain verbatim and escaped.

The executable renders one diagnostic to a writer. A collection is an ordered loop over that operation, not a separate streaming framework. Detection sites construct facts and select messages, but never print or choose a locale. Wording edits change catalogue entries only. An ordinary new diagnostic needs its declaration, translations, construction site and tests, not renderer edits.

JSON preserves semantic reasons, named facts and label relationships such as the relevant import or declaration, alongside primary/related roles and spans. Use the same retained facts for message arguments and JSON rather than keeping parallel payloads. Presentation keys may change with wording structure and are not automatically part of the stable machine schema.

Runtime reporting is a separate interface and implementation slice. It shares output conventions where safe, not the compile-time allocation path or a safety flag. Preserve the existing primary failure, first teardown failure and cleanup status, allocation-independent resource reporting and stop-on-write-failure behavior. Any runtime localization preparation must precede execution; failure reporting cannot require catalogue initialization or formatting allocations.

Locale selection follows an explicit --locale option, then the supported process locale. C, POSIX, an absent locale, or an unsupported locale falls back to English. Tests always choose a locale explicitly. Requested locales fall back through their parent to English. The first implementation embeds catalogues in the executable and does not load arbitrary runtime catalogue files.

AD-0010 specifies defaults for unsupported locales, invalid invocations, catalogue defects and writer failures. Missing required messages are test failures, not a reason to silently substitute generic prose. Optional help may be absent. Fallback must preserve the original diagnostic and requested JSON format without recursively reporting a rendering failure.

For checked-export-summary validation, a small closed invariant family and a summary section retain the failed relationship. The design does not require one public Rust variant per conditional branch. Developer details may carry a stable check identity and safe observed facts. The importer adds its import span and module context without converting the failure to a generic resolver state.

Evidence and experiments

The bounded catalogue comparison selected Fluent, using the Rust fluent-bundle and fluent-syntax crates with unic-langid. Fluent supports named variables, selectors, and plural rules in embedded text resources. fluent-syntax lets tests compare each template's variables with the compiler-owned message declaration. The product needs no runtime resource loader, code generator, or custom template language.

Whole-string lookup does not let Bulgarian reorder named facts or select grammatical forms without multiplying lookup keys. Per-locale Rust rendering duplicates presentation control flow. ICU MessageFormat 2 did not offer a smaller established Rust integration for this checkpoint. The experiment therefore retains only the Fluent dependencies, two embedded catalogues, and catalogue validation tests.

Compare candidates with English and Bulgarian versions of:

  • a type mismatch with expected and found types;
  • a plural-sensitive coverage failure;
  • a multi-file import or opacity diagnostic;
  • the checked-export-summary internal failure; and
  • a message containing Ash identifiers, operators, and paths that must remain verbatim and escaped.

The separate compiler repair established producer validation before publication and current-language source or execution outcomes for the eight retained migration triggers. Preserve those outcomes. The diagnostic product checkpoint must additionally establish:

  • every reachable CLI failure has the selected output contract, with distinct compile-time and runtime reporting paths;
  • every English and Bulgarian message key accepts exactly its declared named arguments;
  • human layout handles tabs, Cyrillic, combining characters, wide characters, multiline spans, and labels from several files;
  • JSON preserves stable reasons, responsibility, facts, byte spans, and causal relationships and order independently from localized prose;
  • runtime resource reporting preserves its allocation and failure guarantees;
  • one end-to-end compile-time diagnostic demonstrates the message-addition and wording-update workflow before migration of all error producers; and
  • ash-doc migration checks consume JSON rather than default human text.

Intentional exclusions

The first checkpoint adds no runtime catalogue downloads, third-party catalogue overrides, editor protocol, telemetry, automatic bug submission, translation management service, interactive correction, or general rich-text UI. It does not require colors to complete the human renderer. It reuses SourceFile line data and existing phase diagnostic facts unless evidence shows one missing relationship.

Open questions

  • Which small private cause representation preserves checked-summary failures without exposing an unnecessary public taxonomy?
  • Review Bulgarian terms alongside the first concrete messages; keep recurring choices in catalogue comments rather than creating a terminology subsystem.
