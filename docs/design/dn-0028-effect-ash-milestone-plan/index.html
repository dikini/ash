Question

How should the effect-ash program in DN-0027 be turned into proposal-gated, test-driven product increments, beginning with the minimum module-newtype slice?

Planning boundary

Current Ash remains the behavior in the specification. At this note's planning checkpoint, no effect or newtype proposal was accepted and no implementation task was active. That statement records the input to this informative plan, not current artifact state. The specification, trajectory, accepted proposals, and active tasks own later state. This note therefore cannot be a task-owned execution plan. It is exact through preparation and acceptance of the first change proposal, then records checkpoint gates and likely implementation pressure at decreasing detail.

After each proposal is accepted, create one active task and one temporary task-owned execution plan with exact RED tests, production edits, verification commands, review assignments, commit boundaries, and a bounded work budget. Remove those transition artifacts after that product checkpoint closes; do not remove this note while it still explains the live milestone program.

No experiment is required by default. Add a disposable prototype only when the proposal cannot settle one named question from the current semantic model and existing evidence. State the comparison corpus and disposal rule before writing experimental code.

The module-newtype, local-newtype, and resume-required kernel product checkpoints were combined on integration/effect-ash-foundations. The local-newtype evidence records lexical identity, escape, validation, and erasure. Completion condition

The program is complete only when all of these are true on an integrated main:

  • module and local newtype, scoped exact evidence, the one-shot effect kernel, checked discard, safe resource scope, synchronous hooks, reliable cleanup, and one narrow foreign provider are current in spec/ and product code;
  • the combined source, diagnostic, linked, Core, transformation, runtime, resource, migration, and tamper corpus passes;
  • pure programs retain the pure dialect and acquire no effect, continuation, provider, hook, or resource runtime state;
  • a simplification review at safe resource scope and another at closure have removed unjustified carriers, passes, state, and syntax;
  • a bounded downstream-seam audit confirms the documented identity, authority, Core, capture, and runtime boundaries against named proof, existential, suspension, concurrency, and dynamic-loading pressure cases, records residual risk, and finds no demonstrated contradiction in current retained behavior;
  • transition artifacts have been cleaned up without confusing cleanup with integration; and
  • the trajectory, retained evidence, documentation links, and milestone claim agree with the integrated result.

Operating protocol for every retained checkpoint

Authority

  1. Reconstruct current behavior from spec/, accepted decisions, product tests, and the precise compiler/runtime seam.
  2. Draft the next unused CP-NNNN from the proposal template. Keep it proposed while any source, type, evaluation, diagnostic, limit, or erasure rule is open.
  3. Obtain explicit acceptance of the complete semantic delta and evidence obligations. Do not interpret approval of this program note as acceptance of a later proposal.
  4. Only then allocate the next unused TASK-NNNN, create its task-owned plan under docs/plans/, and activate product work.
  5. If implementation exposes absent or contradictory semantics, stop the task and return to proposal or design work.

Use one implementation agent at a time when checkpoints share product state. Parallelize independent read-only audits and report every agent's assignment, model class, and reasoning level.

First proposal: module newtype

The first proposal used CP-0012 and closed with its product checkpoint. The following matrix and implementation skeleton retain that planning input, not instructions to recreate its removed transition artifacts. Later proposals must allocate fresh IDs from current Git history.

Goal

Propose the smallest module declaration that introduces a fresh nominal type over one representation field, reuses current module visibility and identity transport, exposes wrapping and matching only where the constructor is accessible, and erases the wrapper without allocation after the typed boundary has been authenticated.

The increment must not add effects, local type declarations, runtime-fresh identity, implicit coercion, representation-derived interface evidence, local implementations, existentials, or evaluator-visible module state.

Step 2: Settle the proposal decision matrix

The proposal must answer every row before acceptance:

Question Leading direction Rejected unless new evidence requires it
Surface form A distinct newtype declaration shaped like current type, with exactly one constructor and one representation field. An attribute hidden inside ordinary type, multiple constructors, zero fields, or multiple representation fields.
Visibility Reuse private, public opaque, and public transparent declaration modes and current import/re-export identity transport. Constructor-specific visibility or a new module export channel.
Representation authority Authenticate the representation through defining-module and linked compiler facts until its last checked use; specify visibility-dependent public summary content separately. Identity Allocate one module-owned nominal declaration identity in source order; imports and re-exports preserve it. Runtime regeneration, path-based identity, or equality from representation shape.

A production heap-inspection API or an inference from trace events that do not record allocation.

Compare the smallest viable Core directions in the proposal:

  1. a dedicated typed zero-cost wrap/unwrap family validated in pure Core and erased before ordinary evaluation;
  2. an authenticated conversion certificate attached to an existing Core family, retained through independent validation and both transforms, then erased only at the validated evaluator boundary; and
  3. an ordinary constructor with an evaluator special case, retained only as a rejected comparison control because it adds evaluator-visible classification and a persistent branch.

Prefer the direction with the fewest retained nodes and no evaluator branch, provided independent Core validation can still reject forged nominal-to- representation conversions. Alternative 2 is not viable if it leaves an existing Core node with disagreeing nominal and representation types or consumes its certificate before validation. Alternative 3 would require an explicit relaxation of this slice's no-evaluator-branch boundary and new evidence; it is not a leading implementation direction. If the first two cannot be distinguished by static reasoning and a small hand-constructed tamper corpus, this note governs one bounded Core-only experiment. Its question is whether existing pure Core can authenticate and erase the conversion without a retained evaluator node. Compare independent tamper rejection, both transforms followed by revalidation, evaluator locality, allocation behavior, and retained carrier/resource cost. Dispose of all prototype code and syntax after recording the evidence unless a later accepted proposal and task adopt the representation. Do not experiment with surface syntax merely to compare spellings.

Before acceptance, confirm that new representation-conversion authority stays localized at the nominal-registry, lowering, Core-validation, and transform boundary. Record the precise replacement or extension seam through which local lexical identities can later authenticate conversions. Do not spread module provenance into the evaluator or implement the local identity class early.

Step 3: Define the pre-implementation corpus
