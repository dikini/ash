# TASK-1615: Extend serde-based serialization for new CPS IR forms

## Status: 📝 Planned

## Description

Extend the existing serde-based serialization (`serde_lexpr`) to handle new CPS IR forms introduced in Phase 160: `Value::Record`, `Value::Tuple`, `Atom::ConstructorName`, `PrimOp::RecordGet`/`TupleGet`, and `Term::Match`.

Phase 159 already established `serde_lexpr` as the serialization format for `.cps` files. All IR types derive `Serialize`/`Deserialize`. This task ensures new variants are compatible with the serde-lexpr representation and round-trip correctly through file I/O.

2. Round-trip tests: serialize → deserialize → compare produces identical IR for all new forms
3. File I/O tests: write to `.cps` file → read back → compare produces identical IR
4. Existing round-trip tests from TASK-1599 continue to pass

### Serde representation

The serde-lexpr format uses record-style S-expressions. New variants will automatically follow the existing pattern:

```lisp
;; Record value (auto-generated by serde_lexpr)
(Record (fields (((Name "x") (Int 42)) ((Name "y") (Int 2)))))

;; Tuple value
(Tuple (elems ((Int 1) (Int 2) (Int 3))))

;; Constructor name
(ConstructorName "Circle")

;; RecordGet primitive
(RecordGet (field "x"))

;; Match term
(Match (scrutinee (Var "shape")) (arms ...))
```

Note: The exact serde-lexpr output is determined by serde's derive macros. Tests verify round-trip correctness, not exact string matching.

use ash_core::cps::*;

fn test_roundtrip_record_value() {

### Step 2: Implement (Green)

**Files:** `crates/ash-core/src/cps.rs`

Ensure new variants derive `Serialize`/`Deserialize` (remove `Copy` from `PrimOp`):

```rust
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]  // Copy removed
pub enum PrimOp {
    // ... existing variants ...
    RecordGet(Name),   // tuple variant — String field, not Copy
    TupleGet(usize),   // tuple variant
    // MatchTag deliberately not added — match dispatch is Term::Match
}
```

**Note:** `Copy` is removed from `PrimOp` because `RecordGet` carries a `Name` (String). All call sites passing `PrimOp` by value must be updated (see TASK-1611).

**New field on `Value::Lam`:**

```rust
pub enum Value {
    // ... existing variants ...
    Lam {
        params: Vec<Name>,
        cont: Name,
        body: Box<Term>,
        captured_env: Env,
        rec_binding: Option<Name>, // NEW: serde-lexpr serializes as null or string
        row: EffectRow,
    },
}
```

**Serde compatibility:** `Option<Name>` serializes naturally with serde-lexpr:
- `None` → `null` (or omitted with `#[serde(skip_serializing_if = "Option::is_none")]`)
- `Some("pair")` → `"pair"`

For backward compatibility with existing `.cps` files (Phase 159 fixtures), add `#[serde(default)]` or make `rec_binding` default to `None`:

```rust
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum Value {
    Lam {
        params: Vec<Name>,
        cont: Name,
        body: Box<Term>,
        captured_env: Env,
        #[serde(default)] // deserializes missing field as None
        rec_binding: Option<Name>,
        row: EffectRow,
    },
    // ... other variants ...
}
```

This ensures existing `.cps` files without `rec_binding` still deserialize correctly.

No changes needed to `crates/ash-core/src/sexp.rs` — the generic `serde_lexpr` calls handle new variants automatically.

## Notes

- The serde-lexpr format is record-style S-expressions, not the custom `(record ...)` syntax originally planned. The exact output is determined by serde's representation.
- `Value::Lam` currently serializes `captured_env` (Env) as part of the value. This is existing Phase 159 behavior. For Phase 160, no change is needed — serde handles `Env` via its `Serialize`/`Deserialize` derives.
- If `Env` or `HandlerChain` cause serialization issues with new variants, add `#[serde(skip)]` to those fields (currently NOT done for `captured_env` in Phase 159).
- No hand-written parser/serializer code is needed — serde derives handle everything.
