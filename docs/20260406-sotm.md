# Ash state of the machine — 2026-04-06

This document captures the current practical state of Ash as of 2026-04-06.

It is organized as:

1. a one-page summary
2. a technical due diligence memo
3. a roadmap for what to build next based on current gaps

This document is derived from the more detailed audit summary in `docs/audit/20260406-summary.md`, but is written for broader consumption and decision-making.

---

# 1. One-page summary

## What Ash is now

Ash is now a real executable workflow engine for the Sharo Core workflow language.

It is no longer accurate to describe it as only a parser, only a semantics sketch, or only a prototype interpreter. As of this date, Ash can:

- load workflow source
- parse surface syntax
- lower workflows into core IR
- type-check workflows
- execute workflows through a runtime interpreter
- run workflows via the CLI
- run a narrow canonical entry-workflow path
- execute capability-driven workflows
- enforce role authority, policy decisions, and runtime constraints
- supervise spawned child workflows through control links
- retain terminal observations for spawned child completions and wait for them directly

## Short answer: can it load, compile, and execute workflows?

Yes.

More precisely, Ash currently supports a real:

- parse -> lower -> check -> execute

pipeline through `ash-engine`, `ash-parser`, `ash-typeck`, and `ash-interp`.

The CLI `ash run` path is real. It supports:

- ordinary workflow execution
- dry-run parse/check
- timeout execution
- tracing
- a canonical entry-workflow bootstrap path

## Short answer: what is the state of capabilities?

Capabilities are real and already useful.

Ash currently has:

- capability providers
- effect-aware capability execution
- role authority checks
- capability policies
- approval gating
- runtime constraint enforcement
- stream and behavior capability subsystems

Built-in support is strongest for:

- stdio
- filesystem
- custom providers supplied by embedders

The biggest notable built-in gap is:

- HTTP provider support in the engine builder is still not implemented as a working built-in path

## What is strong now

The strongest current areas appear to be:

- engine parse/check/execute pipeline
- CLI run path
- stdio/fs/custom capability provider integration
- stream receive execution
- authority / policy / constraint enforcement
- supervision via control links
- retained completion observation and wait support

## What is partial

The major areas that are real but still partial are:

- full formal/runtime story for `par`
- full retained completion payload parity
- exact cumulative semantic carrier closure
- broader provider coverage beyond current built-ins

## What is not yet done

The clearest unfinished items are:

- built-in HTTP capability support
- “all examples in the repo run unchanged”
- full semantic/runtime closure
- any claim of final hardened sandbox/security semantics

## Best current description

The most honest high-level description is:

> Ash is now a real parse/check/execute workflow runtime with governed capability use, runtime supervision, and a meaningful engine/CLI path. It is usable today for controlled/internal workflows and serious experimentation, but it is not yet complete in provider coverage, semantic closure, or security hardening.

# 2. Technical due diligence memo

## 2.1 Bottom-line technical assessment

Ash has crossed the threshold from “interesting implementation effort” into “real executable workflow system.”

It now has all of the following in place as connected runtime/engine surfaces:

- parsing from source text
- lowering to core workflow IR
- type checking against parsed surface workflow metadata
- async interpreter execution
- persistent runtime-owned state
- capability provider registration and execution
- policy and authority mediation
- stream/receive execution
- runtime supervision over spawned children
- retained completion observation and direct completion waiting

That means the project already supports meaningful end-to-end execution of workflows, not just isolated pieces.

## 2.2 Engine and execution pipeline

The central embedding API is `ash-engine::Engine`.

The current engine supports:

- `parse(source)`
- `parse_file(path)`
- `check(workflow)`
- `execute(workflow).await`
- `execute_with_input(workflow, input_bindings).await`
- `run(source).await`
- `run_file(path).await`
- `run_file_with_input(path, input_bindings).await`

This is a real staged pipeline.

The engine stores parsed surface workflow definitions so type checking can use source-level metadata instead of relying only on lowered IR. That is important because it means parsing, checking, and execution are not disconnected ad hoc subsystems.

## 2.3 CLI path

The CLI run path is also real and meaningful.

Current `ash run` behavior includes:

- reading workflow source from disk
- building an engine with default capabilities
- classifying workflow source kind
- running either the ordinary execution path or the entry bootstrap path
- supporting dry-run parse/check mode
- supporting execution timeout
- supporting tracing

This means the user-facing executable path is not speculative. There is a genuine CLI workflow.

## 2.4 Canonical entry workflow path

Ash now includes a narrow but real canonical entry-workflow path.

Current canonical expectations are:

- workflow name must be `main`
- return type must be exactly `Result<(), RuntimeError>`
- parameters must be capability-typed

The engine supports:

- `parse_entry_source`
- `parse_entry_file`
- `verify_entry_workflow`
- `bootstrap_entry_source`
- `bootstrap_entry_file`

This path also supports a narrow leading runtime `use` prelude for canonical runtime modules.

The runtime can derive a process exit code from a returned `RuntimeError` payload. That is a strong signal that the project now has a real application-entry model, not just a raw interpreter API.

## 2.5 Workflow forms currently executable

The interpreter supports a broad workflow surface, including:

Core control/data flow:

- `done`
- `ret`
- `let`
- `if`
- `seq`
- `par`
- `maybe`
- `must`
- `foreach`
- `split`

Capability / behavior / policy-sensitive forms:

- `observe`
- `act`
- `set`
- `send`
- `receive`
- `orient`
- `propose`
- `decide`
- `check`
- `oblig`
- `oblige`
- `check-obligation`
- `with`

Runtime control / supervision forms:

- `spawn`
- `kill`
- `pause`
- `resume`
- `check-health`
- `yield`
- `proxy-resume`

That is already a substantial execution surface.

## 2.6 Capability system: current maturity

The capability system is materially real.

At interpreter/runtime level, Ash has:

- a capability provider trait
- capability registries/contexts
- explicit provider lookup
- effect levels on providers
- observation and action paths
- explicit runtime failure when a provider is missing

At engine level, Ash has:

- stdio capability enablement
- filesystem capability enablement
- custom provider registration
- adaptation from engine providers into interpreter-compatible providers

This means capabilities are not merely syntactic declarations; they influence actual execution.

## 2.7 Built-in provider status

Current built-in engine support is strongest for:

- stdio
- filesystem

There is also provider code for MCP-related integration, but the important distinction is:

- code existing in providers is not the same thing as a fully polished and default-exposed built-in path

The clearest current built-in provider gap is HTTP:

- `with_http_capabilities(...)` currently returns a configuration error
- embedders are expected to use `with_custom_provider(...)` instead

So the provider model is real, but default provider coverage is still uneven.

## 2.8 Role authority, policies, and constraints

This is one of the strongest governance-oriented areas of the implementation.

Ash currently has runtime machinery for:

- role authority checks
- capability policy evaluation
- policy decisions including permit/deny/require-approval/transform
- runtime constraint enforcement against capability grants

Constraint enforcement currently covers things like:

- paths
- hosts
- ports
- permissions such as `read`, `write`, `spawn`, `kill`

That means capability use is governed by more than “provider exists.”

The actual runtime path can distinguish:

- capability missing
- capability not granted / outside authority
- policy denied
- approval required
- constraint violated

This is a meaningful governed-execution model.

## 2.9 Stream and behavior subsystems

Ash also has separate but real support for:

- behavior providers
- stream providers / stream context

This matters because workflow execution is not limited to simple provider calls.

The stream path currently supports:

- non-blocking receive
- blocking receive
- timeout receive
- wildcard fallback
- control mailbox handling
- policy enforcement for receive sources

The behavior path supports observation, setting, and change-tracking-like patterns via provider abstractions.

## 2.10 Supervision and retained completion state

The runtime supervision story is much stronger than it was earlier.

Current runtime support includes:

- control links
- reusable pause/resume/check-health behavior while targets remain live
- kill as terminal invalidation
- retained terminal completion observation
- retained completion payload slices
- direct completion waiting via wait API

Recent runtime work established:

- authoritative coarse runtime outcome classification via `RuntimeOutcomeState`
- sealed/write-once retained completion records
- preserved child result payload slices
- conservative retained effect summary
- terminal-visible retained obligations summary
- runtime-owned retained provenance summary
- `RuntimeState::wait_for_retained_completion(...)`

This is a meaningful execution/runtime capability, not just a documentation story.

## 2.11 What is still partial at the runtime/semantics layer

Some of the most important current limitations are not “missing implementation” in the basic sense, but “intentionally conservative closure.”

The runtime still explicitly does not claim:

- exact full `CompletionPayload` parity
- exact cumulative `Ω / π / T / ε̂` closure
- exact effect/provenance transport parity
- strongest possible formal correspondence for all concurrency and aggregation claims

This is the right level of honesty. The implementation now has real retained observation support, but the project is careful not to overstate what has been fully closed.

## 2.12 Production-readiness judgment

A realistic technical due diligence conclusion is:

### What looks production-usable now

- parse/check/execute engine path
- CLI run path for supported workflows
- stdio and filesystem built-in capabilities
- custom provider extension path
- authority / policy / constraint mediation
- stream receive execution
- runtime supervision and retained completion observation

### What looks usable but still needs disciplined framing

- `par` and broader formal runtime correspondence claims
- retained completion semantics beyond the retained slices now implemented
- canonical entry bootstrap path as a long-term stable product boundary

### What should not yet be represented as complete

- built-in HTTP capability path
- full provider-domain coverage
- full retained completion payload parity
- full cumulative semantic-carrier closure
- hardened sandbox/security claims

### Due diligence conclusion

Ash is now materially beyond “prototype semantics code.” It is a working workflow engine/runtime with governed capability usage. It appears suitable for controlled internal systems, technical pilots, and continued productization work. It should not yet be presented as semantically or operationally complete in every subsystem.

# 3. What to build next: roadmap based on current gaps

This roadmap is based on the current implementation state and the most obvious remaining gaps.

## 3.1 Priority framing

The next work should preserve the current contract-first approach.

Recommended ordering:

1. complete practical provider/runtime gaps that block real deployment use
2. strengthen runtime observation and semantic closure where the project already has partial but useful support
3. improve packaging/usability and example coherence
4. only then broaden or harden into more ambitious product/security claims

## 3.2 Roadmap: near-term (highest-value next steps)

### A. Built-in HTTP capability path

Why this is high priority:

- it is one of the clearest visible capability gaps
- the builder API already advertises an HTTP configuration surface
- current behavior is explicit non-support, which is good honesty but leaves a practical hole

Recommended deliverable:

- implement a working built-in HTTP capability provider in the engine builder path
- ensure it participates in the same provider/effect/policy/constraint flow as stdio/fs
- define what constraints are supported first (hosts, methods, ports, perhaps path prefixes)

Good first slice:

- GET/POST only
- host allowlist constraints
- timeout support
- predictable error mapping

### B. Canonical example corpus cleanup

Why this matters:

- the README currently has to warn that some examples are reference-oriented and not expected to run unchanged
- that creates friction for users evaluating whether Ash “really works”

Recommended deliverable:

- create a clearly curated set of canonical runnable examples
- explicitly separate:
  - runnable examples
  - reference/spec examples
  - aspirational samples

Good first slice:

- 5–10 canonical examples that are known-good through CLI run path
- each one documented as ordinary workflow vs canonical entry workflow

### C. Full provider inventory and compatibility table

Why this matters:

- capability maturity is already meaningful, but uneven
- a single documented compatibility matrix will make the system much easier to adopt

Recommended deliverable:

Document, for each provider surface:

- built-in vs custom-only
- observe/execute support
- effect class
- policy support
- constraint support
- CLI usability status

## 3.3 Roadmap: runtime/semantics strengthening

### D. Retained completion payload closure, one honest slice at a time

Why this matters:

- retained completion observation is already useful
- the runtime now has a strong base to extend without redesigning from scratch

Recommended approach:

Continue the same narrow-slice method used in TASK-406 through TASK-412.

Good next goals:

- improve exactness of effect transport where honest
- improve provenance fidelity where runtime-owned evidence exists
- preserve explicit separation between:
  - child-owned completion payloads
  - control tombstones
  - coarse runtime liveness state

Avoid:

- broad rewrite for “full parity” without identifying concrete runtime-owned evidence paths first

### E. Sharpen blocked / suspended / invalid semantics across more execution paths

Why this matters:

- `RuntimeOutcomeState` is now a strong public surface
- the next gains come from ensuring more runtime paths preserve the most precise honest classification

Recommended deliverable:

Audit all remaining execution/control/receive/provider boundaries for whether they correctly map into:

- `Active`
- `BlockedOrSuspended`
- `InvalidOrTerminated`
- `ExecutionFailure`
- `TerminalSuccess`

The goal is not a redesign, but classification consistency.

### F. `par` semantic/runtime correspondence tightening

Why this matters:

- `par` works operationally now
- the open issue is not “does it run?” but “what exactly should the runtime claim about aggregation and correspondence?”

Recommended deliverable:

- make the current runtime claims more explicit and mechanically testable
- if full helper-backed cumulative-state aggregation is still not there, keep it clearly partial
- add a concrete matrix of:
  - what `par` currently guarantees
  - what remains future semantic/runtime work

## 3.4 Roadmap: governance and safety hardening

### G. Capability constraint expansion and auditing

Why this matters:

- constraint enforcement is already one of the strongest practical governance pieces
- extending and testing it yields outsized value

Potential next slices:

- more precise network constraints
- stronger filesystem scoping semantics
- clearer operation-to-permission mapping docs
- structured audit reporting for constraint-denied operations

### H. Approval-flow operationalization

Why this matters:

- `RequiresApproval` is already a meaningful state
- making approval routing and observability more operational would strengthen Ash’s governed-runtime story

Good next steps:

- improve developer/user-facing visibility of approval-blocked states
- define a stronger end-to-end approval interaction model
- improve examples around approval-required workflows

### I. Security-claim hygiene before security marketing

Why this matters:

- Ash already has meaningful governance features
- the main risk is overstating them too early

Recommended deliverable:

Before any stronger sandbox/security positioning:

- explicitly document what the capability system does enforce
- explicitly document what it does not yet guarantee
- separate policy mediation from hardened isolation claims

## 3.5 Roadmap: usability and productization

### J. Better “what runs today” documentation

Why this matters:

- the system is now powerful enough that discoverability matters
- adoption friction often comes from uncertainty, not missing code

Recommended deliverable:

A concise user-facing guide covering:

- ordinary workflow execution
- canonical entry workflow execution
- built-in capabilities available today
- how to add a custom provider
- common failure modes (parse/type/provider/policy/constraint/runtime)

### K. End-to-end sample applications

Why this matters:

- the best way to validate current engine/runtime maturity is to ship a few believable end-to-end examples

Good candidates:

- CLI utility workflow using stdio + fs
- approval-gated workflow
- stream/receive workflow
- spawned-worker workflow with retained completion wait
- custom-provider example

### L. Provider developer experience

Why this matters:

- custom providers are already a major extension mechanism
- improving ergonomics here amplifies platform value quickly

Good next steps:

- templates for custom providers
- better docs for provider effect and naming conventions
- examples showing provider registration and workflow usage together

## 3.6 Suggested priority order

If only a few things are tackled next, the best order is probably:

1. implement built-in HTTP capability support
2. clean up and publish a canonical runnable example set
3. produce a provider/capability compatibility matrix
4. extend retained completion fidelity conservatively where runtime evidence already exists
5. tighten `RuntimeOutcomeState` classification consistency across remaining execution paths
6. sharpen `par` semantic/runtime correspondence claims
7. strengthen approval-flow and governance observability
8. improve custom-provider developer experience

## 3.7 Strategic summary of next work

The most important strategic point is this:

Ash does not need a ground-up rewrite to become substantially more useful.

It already has a real engine, runtime, capability system, and supervision model. The most valuable next steps are therefore not “start over” or “invent a new architecture,” but:

- fill obvious provider gaps
- harden and clarify current runtime surfaces
- improve docs/examples/usability
- continue closing semantic/runtime gaps using narrow, honest slices

That path preserves momentum while keeping the project’s strongest current quality: conservative, explicit claims about what is really implemented.

---

## Final assessment

Ash is now best understood as:

- a real parse/check/execute workflow engine
- with a functioning runtime and execution model
- with meaningful capability, policy, authority, and constraint support
- with strong recent progress on runtime supervision and completion observation
- but still in active convergence on provider coverage, semantic closure, and long-term hardening

That is a good place to be. The next phase should focus on converting that strong runtime core into a cleaner, more complete, and more obviously adoptable platform.
