AD-0011: Milestone Worktree Lifecycle

Development architectural decisions · ash-lang 7949b6d

Architectural decisions record non-language choices. Each document retains its recorded status and scope. Read the language specification for current language rules.

All architectural decisions
  • ID: AD-0011
  • Status: accepted
  • Related: DN-0027: Effect Ash Program Design, DN-0028: Effect Ash Milestone Plan

Decision

An unintegrated milestone has one persistent integration branch and one product checkout for sequential PR development. Reuse that checkout and its compatible Cargo target cache across branch switches. The integration branch is the continuation anchor; it does not need a second checkout while a checkpoint branch is active. main remains unchanged until the milestone's separate integration gate approves it. Parallel product builds are not part of this workflow.

After a product checkpoint closes and its tip is an ancestor of main or the milestone integration branch, switch the existing clean checkout to the next assigned branch. Delete the completed local feature branch only after proving its ancestry against the intended retaining ref and switching away from it. Git history through the retaining branch preserves the complete checkpoint commits. Keep the target directory at the same path so Cargo can reuse compatible artifacts. A fresh verification run does not require a clean cache.

Planning branches that contributed patch-equivalent work without becoming ancestors of the retained product history must not be merged merely to make them reachable. Remove their worktrees and move their refs under archive/planning/ instead. The archive ref preserves the exact commits while making clear that the branch is not a continuation point.

Keep the current active checkpoint checkout and branch until its accepted proposal, task, specification, evidence, review, verification, and transition cleanup all close. Then switch the same clean checkout to the integration branch, merge the completed checkpoint with an explicit merge commit and verify the combined result using the existing cache. The next authorized checkpoint starts from that verified integration tip in the same checkout. Do not switch branches while another owner is using frozen source or build outputs for a gate, native observation or handoff.

Build output and other ignored caches are disposable, but routine branch switches retain them. They carry no design, semantic, task, or evidence authority. Preserve required logs, receipts and native evidence separately before reclaiming superseded output. Cache cleanup requires an explicit storage need or a demonstrated cache problem; it is not a gate precondition.

Context

The Effects Ash work occupied separate planning, product, and integration worktrees. This preserved isolation during concurrent checkpoints, but closed and superseded checkouts remained registered afterward. Seven local worktrees under .worktree/ consumed about 49 GB, mostly through independent Rust target/ directories, and exposed several plausible but incorrect restart points.

The history already contains the required continuity:

  • the relational-interface checkpoint is reachable from main;
  • the module-newtype and resume-required effect-kernel checkpoints are both merged into integration/effect-ash-foundations;
  • the active local-newtype checkpoint starts from the integrated product baseline fa26025; and
  • the two earlier planning tips have patch-equivalent successors in the product branches but are not themselves ancestors of those successors.

Keeping every checkout adds disk and navigation cost without preserving more Git history. Merging obsolete planning branches would instead add misleading ancestry to the product line. Squashing or rebasing the milestone would erase the checkpoint boundaries used by retained evidence and review.

The user confirmed that current PR development is sequential and authorized branch switching with retained target caches. Recreating a checkout and cold cache for each PR repeats compilation and consumes storage without providing additional verification evidence. Separate build caches remain appropriate only for an explicitly assigned comparison or required isolation, with storage capacity checked before launch.

Consequences

  • main continues to describe current Ash; worktree cleanup does not integrate Effects Ash semantics.
  • integration/effect-ash-foundations names the only milestone continuation line between completed checkpoints.
  • .worktree/ normally contains only the active product checkpoint.
  • Completed feature branch names disappear after their exact commits become reachable through a retained branch.
  • Superseded planning history remains available under an archive namespace but is visibly excluded from active development.
  • The sequential product checkout persists across checkpoint and integration branches; compatible target artifacts survive each branch switch.
  • Reviewers inspect the same frozen checkout and evidence. A review does not require another product checkout or an independent cold build by default.
  • This decision does not authorize a merge into main, a push, a milestone tag, deletion of an unmerged tip, or cleanup of worktrees outside this repository's .worktree/ directory.

Verification

For each branch switch or cleanup operation:

  • record the exact source and destination ref names and object IDs;
  • require git status --short to be empty in every checkout being switched or removed, and release any active gate or handoff before switching;
  • prove each deleted feature tip is an ancestor of its retained branch;
  • prove each renamed planning ref resolves to the same object ID before and after the rename;
  • use git worktree remove rather than deleting a registered checkout directly;
  • confirm git worktree list --porcelain contains only the intended active checkout under .worktree/;
  • confirm main, the integration branch, and the active checkpoint retain their original object IDs during cleanup (authorized integration has its own gate);
  • keep the existing target path and cache during routine branch switches; and
  • confirm no remote ref, tag, source file, specification file, or product test changed.
