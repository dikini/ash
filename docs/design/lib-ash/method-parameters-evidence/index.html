Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes

This report records implementation evidence for the third bounded lib-ash increment: explicit fixed-kinded method-local type parameters and authenticated polymorphic method evidence. It is informative, not normative. The Ash specification alone defines the current language. Git history retains the accepted proposal, implementation task, and execution plan after those transition-only artifacts leave the current tree.

This report alone did not close the complete lib-ash milestone. At the third- increment checkpoint, multi-parameter interfaces, determination, associated outputs, defaults, the combined library corpus, and the final library simplification audit remained separate work. The later integrated relational increment closes the revised milestone without changing this report's evidence scope. This increment received no lib-ash tag.

Implemented boundary

An interface method may bind one explicit, complete, ordered list of fixed-kinded local parameters:

interface Functor<F : Type -> Type> {
    map<A, B> : (A -> B, F<A>) -> F<B>
}

The interface parameter and method parameters scope over that signature. An omitted kind is Type; an absent list binds no method parameter. Source code does not acquire implicit method binders, method requirements, forall, or expression type arguments.

Each occurrence instantiates the interface parameter followed by the method parameters. Only the interface argument creates an evidence obligation. Selection neither observes nor refines method arguments. A selection may be fixed before module inference closes, but its occurrence remains private pending state until all interface and method arguments are inference-free and the checked module publishes every occurrence atomically.

An implementation substitutes its head argument for the interface parameter and checks each method once under two rigid sequences: implementation-head parameters followed by method parameters. It retains the partition as well as the combined order. A direct recursive occurrence reuses the method's rigid arguments and cannot gain polymorphic recursion. Method-local arguments do not enter an implementation head or prerequisite goal and cannot change candidate choice.

Canonical schemes and occurrence authority

The defining resolved method-binder record is the authority for identity, spelling, kind, source origin, owner, and order. Allocation follows module declaration order, interface parameter order, method declaration order, and written method-binder order. The checked registry retains:

MethodScheme = forall method_parameters. method_value_type

The interface parameter remains owned by the surrounding interface. The method scheme does not enter the ordinary term environment and is not a source value. Every occurrence retains its exact MethodId, interface argument, ordered method arguments, checked occurrence type, and selected evidence. Import aliases, targeted renames, facades, and dependency diamonds preserve the defining identities.

The positive checking matrix covers optional and higher kinds, written order, completeness, two unrelated instantiations, inference closure, exact-current evidence, concrete evidence, generic heads and prerequisites, direct recursion, qualified and targeted imports, facades, diamonds, hidden and opaque carriers, and stable defining identity. The negative matrix keeps interface-goal ambiguity at constraint.ambiguous, method-argument ambiguity at type.ambiguous, and changed recursive instantiation at type.polymorphic-recursion.

Summaries and linked authentication

A public checked interface fact and every body-free mirror retain ordered method-binder records and the method monotype separately. Summary construction retains hidden kind and identity closure. Import admission authenticates the complete binder set, order, owner, kinds, body scope, method identity, spelling, annotation span, and provenance before the dependent checks from that summary.

After module inference closure, linked validation authenticates every frozen occurrence argument against its defining method scheme and fixed kind. It also checks the occurrence type, selected MethodId, selected ImplMethodId, implementation head substitution, prerequisite producers, combined head-versus-method binder partition, availability route, and source origin. Core synthesis receives only the capability produced by that complete check and does not select evidence again.

One body-free checked method fact must retain the exact annotation subspan in addition to the complete declaration origin. Without it, an importer cannot reconstruct the source relation authenticated by an implementation method. The linked product retains this exact implementation provenance:

  • primary carrier.ash range 81..130;
  • related carrier declaration 57..132 and method 81..130;
  • related api.ash method 42..76 and annotation 54..76; and
  • related carrier body 110..130.

Linked validation authenticates that complete cross-source relation. Core's accepted source-local provenance invariant receives the already-authenticated primary span at final implementation-method lowering; the full linked relation does not become an unauthenticated Core side table.

Authenticated Core evidence

The existing Core type abstraction, type application, function, and application forms express the increment. A polymorphic method requirement becomes one generated evidence domain:

forall definition_parameters.
    (forall method_parameters. substituted_method_value_type) ->
    ... ->
    source_value_type

A monomorphic method keeps its ordinary function evidence domain. At an abstract occurrence, Core type-applies the evidence binder to the retained method arguments before applying source arguments. Exact forwarding may pass that binder uninstantiated only to the same authenticated evidence domain.

A concrete or exact-current polymorphic selection uses one unspecialized adapter:

type-abstract method_parameters.
    type-apply implementation_method
      <implementation_head_arguments, method_parameters>
      prerequisite_evidence...

The adapter exposes exactly the selected method scheme. It does not copy or specialize the implementation body. Head arguments precede method arguments; prerequisites retain prerequisite and interface-method order. Repeated selections of one implementation at different evidence nodes or substitutions remain distinct adapters.

Minimal immutable authentication facts relate every evidence position to its definition owner, requirement and method order, MethodId, interface argument, method scheme, and selected implementation source. Independent Core validation derives the expected scheme, validates every occurrence, forwarding use and adapter, and consumes every fact exactly once. Canonical method binders compare exactly. Only a generated adapter may use one bounded capture-free, order- and kind-preserving alpha-renaming. Monotype equality and unification remain exact.

For a retained concrete implementation source, validation also compares its prerequisite rows lockstep with the selected implementation node's direct prerequisites, flattened in prerequisite declaration order and then each child's interface-method order. Both the selection node and MethodId must match, and both sequences must end together. Existing per-row producer, binder, Core application-chain, and recursive-source checks then validate the matched rows.

Identity and literal-folding transformations preserve or rebuild the complete relationship, then pass fresh independent validation. Method schemes and authentication facts may remain as inert authority in the validated program, but the evaluator does not inspect them or derive runtime state from them. Core type operations erase through the existing dynamic rules before observation. No new Core node or evaluator state is present.

Diagnostics, migration, and unavailable routes

The diagnostic matrix retains exact typed reasons, primary and related spans, causal labels, and deterministic precedence through the library and CLI. Malformed binder syntax is parser-owned. Resolution owns duplicates, an interface-parameter collision, unused binders, and unlisted names in a present complete list. Kind checking owns invalid binder and method-type kinds. Interface checking retains interface.method-parameter for another free variable under an absent list or an omitted interface parameter, before interface.method-not-function after successful kind checking.

The predecessor migration is explicit. This declaration remains invalid:

interface Project<I> {
    project : (I, A) -> A
}

Adding project<A> makes the previously rejected method valid. There is no compatibility grammar, implicit binder, inferred binder kind, or second compiler path.

Direct negative evidence keeps all twelve unavailable higher-rank routes out of the language:

  • source forall and explicit expression type application;
  • polymorphic parameter and result annotations;
  • polymorphic tuple and constructor fields;
  • scheme storage, return, and passing to an ordinary parameter;
  • implicit method binders and method-level requirements;
  • and polymorphic recursive self-use.

Exact resources and lifecycle

All proportional work charges before allocation, traversal, or publication. Syntax work uses its syntax ledger. Binder records, method schemes, occurrence arguments, substitutions, adapters, and Core types use the owning type-work ledger. Intentional exclusions and remaining pressure

This increment does not add implicit method binders, method-local kind inference, kind polymorphism, type lambdas, higher-order unification, impredicative instantiation, source forall, expression type arguments, polymorphic annotations or ordinary values, method requirements, polymorphic recursion, multi-parameter interfaces, determination, associated outputs, defaults, overrides, specialization, negative implementations, fallback selection, new implementation import forms, packages, persistent artifacts, separate object linking, dynamic loading, runtime registries, or a public authentication representation.

Later work may consume canonical method schemes, authenticated summaries, occurrence arguments, and generated adapter evidence. It requires separate semantic authority and cannot reinterpret this report as language truth. At this checkpoint, the complete lib-ash milestone remained open and untagged; the later integrated relational increment closes the revised milestone without claiming a tag.
