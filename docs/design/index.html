All design notes

Design notes record exploration, research, alternatives, experiments, tradeoffs, uncertainty, and future architectural pressure. They are informative and do not define Ash semantics or accept architecture. A note may govern a disposable prototype limited to its stated question, comparison cases, and retention conditions when code is necessary to compare candidates; the prototype remains evidence rather than product implementation.

Use the template, allocate the next DN-NNNN ID, and link related artifacts. When a non-language choice converges, record it in an architectural decision. When a language-semantic change becomes concrete, write a change proposal.

Implementation and evidence boundaries

A note's exploring or evaluating status describes its design work, not the completion of every feature it discusses. Read each claim within its scope:

  • Implemented means a specified product slice, or an accepted architectural choice present in the implementation. It does not accept the rest of a note.
  • Experimental means a bounded prototype, formal model, or comparison with stated assumptions. Retention on main does not make it product semantics.
  • Open means a candidate, unresolved question, or incomplete delivery. A delivery sketch or worked fragment does not establish the full capability.

The specification owns language truth; accepted decisions own non-language architecture. The feature inventory links product and experimental implementation evidence, while the trajectory records milestone maturity. The following summary identifies scope rather than assigning new artifact statuses or authorizing work. Detailed evidence and exclusions remain at their linked owners.

DN-0038: resource properties and mutation Scoped cells already distinguish reusable access from scope-owned release. General linear/unique usage, borrowing, disposal permissions, and mutable syntax remain candidates.

DN-0044–0046: runtime services, native execution, agent tooling Existing Core, evaluator, and diagnostics provide foundations; native execution and agent tooling are outlined in the trajectory. Selectable runtime services, a native backend, interactive native execution, LSP, and the agent semantic interface remain design work.
DN-0047: ECS and heterogeneous stores Checked source fragments validate limited current-language encodings. No ECS implementation or measured performance follows; open stores and existential packaging remain candidates.
DN-0048: parallel kernels Current Pure Core and strict evaluation supply reference obligations. Kernel extraction, a kernel IR, interaction-net translation, and SIMD/GPU lowering are not implemented by this note.

  • DN-0041: Typed Serialization and Data Pipelines — an Ash adaptation of Serde's architecture, first-class JSON/YAML/CSV/TOML/BSON contracts, owned and incremental processing, scoped storage and attributable type/runtime costs.
  • DN-0040: Floating-Point Semantics and Representation — a minimal binary64 language direction, source/Core/operational obligations, numerical conversions and format contracts, with proposed representation-cost comparisons.
  • DN-0039: Files and Filesystem Resources — scoped file access and filesystem authority, copying I/O, partial progress, fallible completion, host profiles and later arena/buffer integration.
  • DN-0038: Resource Properties and Mutable Variable Usage — separate usage, uniqueness, access, lifetime, payload and completion properties; compare Rust-like regimes, semantics, Core, proofs, surface forms and memory/performance opportunities before choosing a design.
  • DN-0037: Ash-Authored Foreign-Library Interfaces — a separate program for typed foreign contracts, generic host ABI calls, memory and linking, with Ash binding code and declarative native build inputs.
  • DN-0036: Foreign Library and Memory Provider Experiments — coordinated SQLite and scoped-arena experiments, type-checking contracts, surface syntax and Core semantics, a foreign-library authoring blueprint, tooling, and an adoption path into Ash and its standard library.
  • DN-0035: Region Memory Management and Verified Providers — nested lexical regions, statically selected library policies, immutable sharing, provider verification, and a memory-management reference corpus.
  • DN-0013: Session and Resource Protocol Stress Tests — tests for protocol, multiplicity, continuation, and handler composition machinery.
  • DN-0014: Finite Kinds and Promotion — finite nominal static domains and restricted datatype promotion.
  • DN-0017: Resource Management and Storage Policy — deterministic cleanup, plural storage policies, transfer, sharing, and cost visibility.
  • DN-0018: Runtime-Established Static Evidence — generative evidence for checked values and relationships, with possible place decomposition.
