Dynamic Semantics

Development specification · ash-lang 67c79dd

OverviewLexical StructureSyntaxName ResolutionStatic SemanticsElaborationDynamic Semantics

Ash evaluation is defined by one small-step relation over configurations CONFIG(heap, environment, control, continuation). Its Ash control transitions are deterministic relative to fixed admitted native bindings and the outcomes of their external calls; it does not determine or guarantee those outcomes. The heap is fresh for one evaluation and maps numeric locations to tuples, completed constructors, uninitialized slots for recursive data, or aliases. It also retains region-owned allocation records with pending or initialized disposition, backing locator, extent/alignment and actual residency. Tuple elements and constructor payloads are runtime values. The environment maps resolved term identities to runtime values. Effect execution also retains lexical type/row instantiation in the environment, separately from term bindings. This metadata is not a source value. The continuation records the remaining strict work, including ordered lexical handler boundaries, selected allocation views, prospective/live/closing region activations, pending initialization and saved paired completion. These extend the same configuration, not another machine. A selected operation moves one suffix of that continuation into a clause-owned captured continuation. The suffix is moved, not copied. Its clause boundary records whether the unique resume capability still owns that captured control or has consumed it. A checked private clause may instead move that control into its scoped Store; the continuation itself never becomes a source value.

Runtime values are arbitrary-precision integers, Booleans, unit, immutable byte sequences, validated UTF-8 strings, lexical functions, canonical builtin functions, internal lexical polymorphic functions, payload-constructor functions, opaque data-pointer Address values, opaque non-owning resource handles and retained keys, or heap locations. A function template is code metadata. Effect execution stores the lexical callable once when its function expression or recursive member is materialized; lookup returns that stored callable. Pure execution retains its allocation-free template lookup. A location is an internal handle, not source-level identity or observable mutation.

Pure Core type abstractions and applications erase without extending the environment or allocating heap cells. Effect execution retains lexical polymorphic functions and their validated instantiation so exact operation identities remain meaningful across generic calls. No type or kind becomes a source-inspectable value, and type/row instantiation alone allocates no ordinary heap cell. Validated newtype conversions and local nominal scopes are likewise erased static operations rather than values.

Initial configuration

Elaboration produces one validated linked Core expression: an explicit host-backed root outside dependency-ordered recursive global groups and the generated application of local main to unit, with required native interpretation. Root establishment precedes every module closure record. Host startup/control storage prepares the initial provider; no arbitrary Source computation runs without a selection and no alternate Source heap supplies fallback storage. The final outer expression has an empty row; the inner main application retains its row. Evaluation starts with that expression as control, a fresh empty heap and environment, and an empty continuation:

linked_program includes the generated root around the dependency-ordered groups and main () described in Elaboration. The second premise requires independent whole-program validation before evaluation. Neither premise performs module loading at runtime. The ordinary recursive-binding and application rules enter the linked groups and call main. Imports have no initialization step, and modules are not runtime values.

Native-binding admission checks the entries actually supplied against the original symbol facts of validated Core before Ash execution. It does not check that every possible native request has a binding; the empty supplied table satisfies this association check. When a native boundary is selected, invocation requires the entry for that exact original symbol. A missing selected entry is a terminal runtime failure after operand evaluation and boundary selection, before the callback is called. A nearer ordinary source handler requires no callback lookup. Admission performs no implicit native compilation or linking.

Region construction and close steps

Write CONFIG(H, E, c, K) for the same configuration above. H retains region allocation records and K retains selection, pending construction and completion. The following named steps refine that relation. A prospective activation is not live access; a pending record exposes no readable initialized object. Allocate and release remain the fixed ordinary pair of one successful region setup.

A successful supplied layout includes the object's complete persistent representation: tuple fields, nominal discriminant/payload, actual closure captures, and persistent Bytes/String/large-Int backing where applicable. Charging capacity while retaining that representation elsewhere is not supplied storage. Request size arithmetic is checked; alignment is nonzero and supported, and stated extent/alignment must satisfy the request. A zero-byte success grants no readable bytes and initializes only a genuinely zero-readable-storage layout; it still has its own allocation record/accounting. The backing adapter checks association/layout and creates pending storage; a raw Address or phantom R alone proves neither native validity nor initialized access.

The owner service remains available through required cleanup and release, at its original position and preceding allocation selection. It does not restore a removed public backend handler. Action-local handlers or surviving interpreters must discharge the actual backend requirements; the existing cleanup-context and running-completion restrictions still apply.

An ordinary function expression requests its record/captures once at creation. Calls retain its lexical values/type context but use the caller's selection for fresh construction. Integer results retain the conservative residency required by static admission even when their runtime representation is immediate.

Refusal uses ordinary effects: a clause may resume only with valid successful storage or, when checked, discard and return its ordinary result. Old objects and performed effects are not rolled back. Reporting uses pre-existing/surrounding storage or host entry reporting, not construction in a failed region. Internal work/control/storage exhaustion remains terminal and has no source-cleanup guarantee. At root entry, declared allocation refusal uses checked disposal and the existing host observation/reporting foundation, distinguishing it from internal exhaustion without constructing an error in the failed root. If required close fails, report that actual failure rather than a clean refusal. Physical validity, freshness/disjointness and successful reclamation remain native/module contract assumptions; returning from a broken native release does not prove its physical promise. No fallback, source unwind or quarantine protocol is introduced.

Type instantiation and erasure

In Pure execution, entering either explicit Core type operation takes one step to its retained term. Validation has already checked parameter scope, argument arity, kinds, and substitution, so evaluation does not inspect the parameters or arguments.

type-erasure-steps

The unchanged heap and environment make erasure observable only as progress in the machine. No source program can inspect a type parameter or type argument. In Pure execution, method-local type arguments erase through E-Type-Application. E-Newtype-Conversion also leaves the continuation unchanged. Independent Core validation has already authenticated the owner, direction, child and result types, representation substitution, and provenance, so evaluation does not inspect conversion metadata or consult a registry.

E-Local-Nominal-Scope likewise enters its body directly with the same heap, environment, and continuation. The owner has already been authenticated and creates no runtime identity, environment entry, frame, or registry state. A closure whose exposed computation is identity-free may retain ordinary erased representation values and execute its lexical code after this step's body returns; no runtime scope authority needs to survive with it.

Effect execution instead retains a type abstraction as a lexical polymorphic function. Independent Core validation admits ordinary function materialization, inert constructor values or variables, transparent type operations, and authenticated generated evidence adapters inside that abstraction, as described in Elaboration. Retaining these forms does not delay a source effect or source function body.

Evaluating an admitted abstraction that directly materializes a function creates its generic record once, with actual term captures and lexical metadata but its generalized parameters unbound. Authenticated deferred captures are retained without eagerly executing evidence adapter spines. Transparent aliases/variables and constructors forward without copying.

A type application evaluates its function, saves caller instantiation, substitutes ordinary type and complete row arguments under that caller context, and binds them simultaneously in an immutable view of the retained definition context. Direct-callable instantiation does not recreate the record, enter a source function body or mutate sibling views. A later call uses that lexical type/term context while fresh construction uses the caller's allocation selection. Recursive lookup returns the stored generic callable. Parameterized ordinary constructors retain their existing constructor behavior; their type application needs no effect context.

The same lexical context travels with handlers and captured control. Request selection compares exact effect instances after instantiating each side under its own context. This is neither type inference from argument values nor a machine-global mutable substitution. Types nested inside effect arguments, including higher-kinded applications and function effect rows, participate in the same validated substitution. Pure execution keeps the erasure rules above.

These Effect-only steps make retention and instantiation explicit. POLYMORPHIC retains the stored generic callable, not a type value. prepare_generic follows the admitted body shape. It materializes a direct generic function or a capture-bearing deferred record once through the selected-region path, retaining pending progress, actual captures and definition metadata with generalized parameters unbound. Forwarding an existing callable reuses its record; code-only constructors need no callable record. An authenticated deferred body remains unevaluated at creation. In POLYMORPHIC(parameters, stored, definition_environment), stored distinguishes a direct callable from an authenticated deferred body, and the retained environment includes its captured term values. direct_callable(stored) selects the first case; authenticated_deferred_body(stored) yields the second case's retained body. instantiate_view changes only immutable lexical instantiation metadata. Instantiating a deferred body instead evaluates its ordinary term computation under the bound capture environment; any genuinely new Function result materializes there in the existing prerequisite order. arguments contains the ordered ordinary type and complete row arguments. instantiate_arguments uses the saved caller context, and bind_parameters extends the definition context simultaneously without changing term bindings. constructor_value recognizes an ordinary payload-constructor function or nullary constructor value; these need no retained effect instantiation.

Generated interface evidence

Linking preserves each checked interface selection. Linked interface-evidence validation authenticates it, and Core synthesis lowers it before evaluation. Determination metadata erases before Core synthesis. Complete interface applications may survive through transforms and independent validation only in inert static authentication relationships. Their ordered arguments have already been substituted into authenticated method types, and the evaluator does not inspect those relationships or make them control or state. An abstract evidence method becomes an ordinary function parameter. A polymorphic occurrence type-applies that parameter to its retained method-local arguments; an entered Core application uses the type-instantiation behavior above. A monomorphic concrete evidence method becomes a binder occurrence for the implementation method in its defining module's recursive group. A polymorphic concrete or exact-current method retains a generated adapter over the implementation method's complete type application. Pure execution erases these operations; Effect execution preserves their validated arguments in lexical instantiation, including authenticated forwarding without executing the retained adapter spine. Effect lookup returns the once-materialized recursive callable; Pure lookup retains its allocation-free template behavior.

A supplied lexical method uses ordinary nonrecursive binding, function closure, and binder lookup. Its closure captures the preceding ordinary values required by its body. A checked closure may retain that method after the evidence block returns; a new occurrence outside the block cannot acquire its static evidence. The lexical source identity and selection scope create no runtime value, registry, scope frame, revocation check, or transition family.

The validated Core program may retain method authentication records and method schemes as static authority. A retained Core type application records its complete method arguments; Effect execution preserves their validated instantiation in lexical metadata, including when an authenticated adapter forwards an existing callable without entering that application node. The evaluator does not inspect method authentication records or method schemes. It does not turn an interface identity, selection record, implementation authorization route, method scheme, or method argument into a runtime value, term binding, heap cell, interface lookup, or interface-specific transition. Effect type applications retain instantiation as described above; this does not turn method authentication or selection into runtime authority.

For a generic implementation method, lowering uses the recorded head substitution to form an ordinary Core type application. When evaluation enters that Core node, Pure execution erases it while Effect execution preserves its validated arguments in lexical instantiation. The recorded selection route itself does not reach the evaluator. The existing strict application transitions then evaluate and apply every recursively generated prerequisite method in declaration order. The result is the lexical method closure that accepts the source value argument. At a constrained-global call, the same transitions apply its evidence functions before the surrounding source arguments because elaboration nested the applications in that order. Abstract prerequisite evidence uses ordinary environment lookup; concrete prerequisite evidence uses ordinary recursive function lookup. A genuinely new Function result from a prerequisite term application materializes at that ordered creation site.

There is no runtime interface value, dictionary, interface or implementation registry, implementation lookup, interface dispatch, registration step, or interface-specific failure mode. Polymorphic method evidence uses the dialect's ordinary function values and applications. It adds no interface-specific value, environment-entry class, frame kind, lookup class, transition class, failure reason, or runtime interface state. Evidence construction uses the dialect's ordinary type operations, local and recursive binding, binder lookup and closure materialization, and the strict application transitions below. It adds no interface-specific Core node or evaluation rule. Improvement is a static inference operation and does not become a lookup, transition, proof witness, effect handler, or existential package.

The test's fixed-program resource ceilings do not define allocation budgets, semantic limits or a bound on arbitrary prerequisite chains.

Bindings

A binding evaluates its initializer before matching the resulting value and extending the environment for its body. Its pattern binders are not in scope in the initializer. Static irrefutability makes match failure unreachable.

binding-steps

E-Let-Enter saves the lexical environment that precedes the binding. E-Let-Continue uses that environment plus the pattern bindings. Semicolons separate semantic fields; Ash source does not contain semicolons.

Recursive bindings

In Effect execution, entering a recursive group reserves its recursive identities and uninitialized data slots. It materializes direct ordinary function members once in source member order, retaining their recursive environment and selected residency, before guarded data initialization. Lookup returns stored callables. In Pure execution, the existing allocation-free templates and data locations are installed together as follows. Constructor-guarded data initializers evaluate in source order. Completing a data member stores an alias from its slot to the initializer's constructed location. Lookup of a recursive data member returns its slot without forcing the alias. Only Pure lookup materializes a lexical function from its template and the recursive environment.

recursive-binding-steps

In the Pure rules, function templates and data locations enter scope before data initialization. data_bindings maps every data member's binder identity to its preallocated location. pending separately pairs each guarded data initializer with that member's location in source order. E-Let-Rec-Initialize enters only the first initializer and saves the remaining pairs, group body, and recursive environment in a continuation. When that initializer returns its constructed location, E-Let-Rec-Store stores the alias and resumes the remaining initialization control. Repeating these two one-step rules makes every intermediate heap and control state, and therefore source order, explicit. A function-only group has an empty pending sequence and proceeds through E-Let-Rec-Body; its templates were installed by E-Let-Rec-Allocate.

Effect function materialization uses these steps in the same configuration. reserve_recursive publishes only internal recursive identities/data slots; functions lists direct function initializers in source order. The existing initialize control below runs guarded data only after all stored callables are ready. Completed materialization and pending data state survive capture/resume without replay. Abandonment accounts for unpublished construction but does not roll back previous effects or initialized records.

effect-recursive-materialization

A polymorphic function member has one outer TypeAbstraction node whose nonempty parameter sequence contains all generalized parameters. Allocation in Pure execution follows that wrapper to install the same function template; ordinary Pure evaluation still uses E-Type-Abstraction. Effect execution materializes and retains the generic record once with its lexical captures. Lookup and type application reuse that record; instantiated views do not mutate it or a sibling view.

Reaching an uninitialized cell, an alias loop, or an invalid location is an internal runtime failure. The static guardedness judgment makes those states unreachable from accepted source. These rules provide allocation for explicit recursive data; they do not add general laziness or source-visible mutation.

Application

Application evaluates the function before the argument. Once both are runtime values, a lexical function matches its domain pattern, extends its captured environment, and enters its body. Its lexical instantiation remains fixed while fresh body construction uses the caller's selected allocation context. The callable record and captures do not move or reinitialize. A payload constructor initializes a supplied nominal record with the argument as payload in Effect execution; the direct allocation rule below applies to Pure Core.

application-steps

The continuation frames make the left-to-right order explicit. A closed, well-typed program cannot apply an integer, Boolean, unit, tuple, or completed constructor value.

Tuples, constructors, and matches

Tuple elements evaluate strictly from left to right before their completed record is published. Effect construction requests the selected owner's supplied storage and initializes it locally with these retained operands; Pure Core uses its ordinary tuple cell. Effect nullary constructors use the same supplied nominal-record path. Code-only payload-constructor values allocate no closure record; generated wrappers do so only when lowered to ordinary Function. Persistent Bytes/String backing, large Int digits and actual closure captures follow the same selected-owner request, initialization and publication discipline. Known immediate values need no backing record.

Those allocation and tag-inspection rules apply to ordinary data constructors. A newtype constructor and pattern have already lowered to validated wrap and unwrap conversions. E-Newtype-Conversion enters their child without a heap cell, tag comparison, copy, frame, or new failure mode. The same erasure applies to module and local newtype. Capturing a local value uses the ordinary closure environment and adds no wrapper allocation.

A match evaluates its scrutinee exactly once. Pattern matching follows aliases only when it must inspect a tuple or constructor. It compares constructor identities, visits tuple and payload components left to right, and returns the pattern's binder-to-value map. Arms are tried in source order; only the first matching arm body evaluates. Exhaustiveness makes complete failure unreachable.

match-steps

The same matching operation selects an equational clause after its declared number of curried arguments has arrived.

Primitive operations

Primitive operands evaluate from left to right. Addition and multiplication operate on mathematical integers and cannot overflow. Integer equality is true exactly when its operands denote the same integer. The rules below use expression -> expression' as shorthand for the corresponding control and continuation transition. An operand step threads its resulting heap into the enclosing primitive evaluation; operand allocation and effects follow their ordinary rules. A primitive reduction on integer values leaves its incoming heap unchanged.

Native symbol execution

Write a_p for an Address value whose private data pointer is p, and a_null for the null Address. These are metavariables for existing opaque runtime values, not Ash constructors, literals, integers or image constants. Pointer equality here means data-pointer equality, including null; it establishes neither allocation identity nor validity. Address copies preserve the pointer and create no allocation, release or resource dependency.

Let f_null, f_is_null and f_equal denote the canonical builtin function values exported as null, is_null and equal by @builtin.foreign. Ordinary application evaluates the function and its one argument before these rules use the existing APPLY_ARGUMENT frame. tuple_fields(heap, value) follows only ordinary heap aliases and reads an ordinary tuple cell in source order; it does not inspect memory behind an Address. The three value rules leave the Ash heap and continuation below the application unchanged and perform no foreign call.

address-value-steps

The internal term NativeInterpret(body, interpretations) denotes the validated Effect Core boundary described in Elaboration. Its entries retain exact original symbols and their effect instances. NATIVE(interpretations, boundary_environment) is a lexical continuation boundary, not a source value, host token or resource owner. Entering it preserves the body environment; ordinary body completion removes only that boundary.

native-boundary-steps

A symbol request evaluates its operand with E-Perform-Operand below. Boundary selection uses the same innermost-first order as ordinary handlers and cells. In the rules below, prefix contains exactly the continuation entries nearer than the displayed native boundary. No entry in it may accept the requested instance. Thus a nearer matching source handler uses E-Request-Select instead, without looking up or invoking a native binding. An unrelated nearer boundary is crossed by the search but remains in the continuation.

entry retrieves the exact original symbol for the operation from the selected boundary, together with its handled effect instance. That instance is compared under the boundary's saved lexical instantiation, while the request uses its own saved instantiation. linked_binding(symbol) retrieves the generated host's typed bridge callback, not a C callback argument or an Ash function pointer. It is associated with that same original symbol; equal display names or operation coordinates alone do not authenticate a replacement binding.

marshal(heap, domain, operand_value) = arguments, keepalive is metanotation for the supported source-to-C mapping, not a source operation or a new memory interface. For whole Unit and (), the pointer vector and keepalive are empty. For whole Address and a_p, they are [p] and empty. For whole Bytes and bytes, they are [backing(bytes)] and [bytes]. For a flat Address/Bytes tuple, tuple_fields supplies its fields and these pointer vectors and retained Bytes values concatenate in source order. backing(bytes) denotes its existing readonly backing pointer; retaining that Bytes value keeps this backing alive. No length, terminator, encoding conversion, copying or mutable view is added. Empty Bytes promises no readable byte, and its pointer does not encode emptiness. Unsupported source domains have already been rejected statically.

The callback-outcome premise describes one synchronous external invocation, not a pure query or a retryable test. Its Bytes keepalive values remain retained from marshaling through callback return and result conversion. An Address reply preserves its pointer, including null; a C void reply becomes () without reading a C result. Both rules consume only the request frame and return to the same continuation, including every crossed and selected boundary. They create no clause owner, captured continuation, resume or discard capability.

native-request-steps

These transitions apply under the declaration's assumed native signature and readonly backing contract. The compiler does not verify foreign correctness or termination. For fixed bindings and a fixed external outcome sequence, each returning invocation determines one result and one continuation step. A callback that does not return supplies no return step; the rules promise no progress of foreign code. External effects are not represented by an additional Ash heap or foreign-world object, and Unit-returning calls may still have external effects.

Internal work/storage, binding or callback-interface failures are terminal runtime failures, not source error constructors or alternative successful transitions. Failure after an invocation does not retry it or undo its external effects. Bindings express ordinary error results and scoped cleanup in Ash; an Address result alone triggers no release. Native code must not mutate or free managed Bytes. Retained or returned backing pointers require the binding module to keep the original Bytes alive for every later native use; producing a_p does not capture or infer this relation.

No arbitrary memory read/write, Address-to-Bytes/String conversion, numeric ABI, out-pointer storage or compiler-managed foreign lifecycle is supplied. Ordinary cleanup and resource completion rules below continue to govern Ash control.

Effect handlers and completion

HANDLER(handler, instance, clauses, environment) is an ordered lexical continuation boundary. REQUEST(operation, instantiation) and RESUME(handler, owner) are ordinary strict frames for their operands. The request retains its lexical instantiation. CLAUSE(handler, owner, state) is the selected clause boundary; its state is either live(captured) or consumed. The captured value owns the selected handler boundary and all intervening continuation entries up to the request. The captured continuation is not a source value. Except for the checked Store transfer below, its owner remains in the clause until consumed.

Closing does not resume abandoned expressions or clause suffixes, invoke pending callbacks from abandoned publications, or restore captured source handlers. It never resumes abandoned control with a dummy body result. Cells release their payloads; registrations remove their entries without invoking their transformers; cleanup owners invoke their actions through ordinary application before advancing outward. Still-enclosing builtin cells remain available until their own closing positions.

Preflight validates and prepares the owned transfer before consuming the capability or releasing capture accounting. Initial failure leaves both unchanged. After source actions start, later internal failure does not roll back earlier effects, repeat actions or guarantee remaining invocations. Traversal and host disposal remain iterative for deeply nested captures. After closing and the remaining clause work, E-Clause-Return applies as after resume. A running action or unfinished CLOSE cannot itself be abandoned; outward requests may capture and resume it.

Static checking and Effect Core validation make an unmatched request, a missing owner, a second completion, an unsafe discard, or an invalid capture boundary unreachable from accepted source. If one appears after successful validation, evaluation reports an internal malformed-Core or machine failure. Ash has no source-level unhandled-operation, abort, exception, cancellation, or unwind result.

Scoped retained-control execution

A Store acquisition evaluates its Unit initializer once in the preceding environment. Successful preparation creates a fresh activation a, its opaque non-owning handle, an initially empty slot collection and its lexical identity binding. The Store boundary owns the slots and release; copying a handle or a key does not copy either owner. Failed preparation publishes no activation or handle. As with a cell, the body runs only after acquisition succeeds.

For a private handler, the Store operand is evaluated once before its body. The actual handle must name the live authenticated Store and the driver must be outside every active root for that activation. After fallible preparation, the machine registers a root completion and enters the ordinary handler with that root immediately outside it. The handler association is non-owning. The root remains until the branch's actual clause suffix, cleanup and other required completion have returned; removing the selected handler while its clause runs does not remove the root.

The following rules describe successful moves. STORE(a, S) is the unique live Store boundary for activation a; S contains its slots and active-root state. STORE_INIT saves the descriptor, body and preceding environment while the initializer runs. bind_store binds the fresh identity and handle without placing ownership in the ordinary value heap. ROOT_INIT saves the handler and its lexical environment while its Store operand is evaluated; ROOT(a) is its branch-completion marker. The handler identity is supplied by the static handler just as in E-Handle-Enter. A key k names a, a slot and a generation, without owning the slot. store_at finds the actual boundary in the continuation, and replace_store changes only that boundary's state. The helpers authenticate the selected private handler, owner, activation and interpreter context and perform all fallible preparation before the indicated commit. register_root adds one active root; spend empties the selected slot and registers the restored root; retire_root removes the matching active root. restore reinstalls the moved control in its original order. The SOME_ADAPTER frame and none_adapter control denote the ordinary result construction retained for the current consumer; they are not source values.

In E-Retain-Commit, the selected clause continues with k and its consumed owner; its suffix has not been skipped. The slot uniquely owns the captured control and its nested live or consumed owners. A failed reservation or move preparation leaves the clause's original owner intact and publishes no key. Slot reuse assigns a generation that cannot alias a previous key; exhaustion fails rather than wrapping into a live generation.

Both source continue callables evaluate their Store operand before their key. For a live generation, the machine prepares every fallible part of restoration before spending the slot. It then installs the captured segment above a fresh ROOT(a), the SOME_ADAPTER and the actual current consumer. The restored segment receives () as the checkpoint reply. When it returns an answer A, the adapter constructs Some(A) and delivers it to that consumer, including when A is an answer from a later checkpoint. It does not return to the earlier transferring clause. An absent or spent key runs the ordinary None adapter without executing captured control. Adapter allocation occurs on the selected path, after restored control returns on the live path, not during preparation. Failure before a live move commits leaves the slot intact.

A checkpoint before an inner resume moves its live nested clause owner; one after resume preserves that owner's consumed state and remaining suffix. A checkpoint in running cleanup moves its saved body value and unfinished action completion without making the action eligible for another invocation. A subsequent checkpoint may move that same running completion again. A restored branch that yields returns its fresh key to the current consumer, which may continue it again.

The Store-selected Probe<N>.quiescent returns true exactly when its active root count is zero and every slot is empty; otherwise it returns false. Driver admission is checked before ordinary nearest-handler selection, so an intercepting source handler does not authorize a branch to drive its own Store. At normal Store return, the boundary checks the same empty condition before release. A checked outer discard closes an owned Store only after its required actions and other closing control establish that condition. Empty library queues and answer constructors do not change the Store's ownership state.

Internal failure disposal follows actual owned active and stored control iteratively, without releasing an owner twice. If teardown cannot obtain its required working storage, it reports incomplete teardown and may leave residual owners unreleased. It does not promise source cleanup or roll back already performed effects. Missing owners, forged associations or a nonempty normal close after successful validation are internal failures, not source recovery branches.

Scoped cell execution

A cell scope owns one current payload root. Legacy resource cell<R> scopes retain integer payloads and their unary API. Generic Cell.Cell<R,T> scopes retain an ordinary checked value of the fixed type T; aggregate and callable values use the ordinary shared value representation. Its handle is an opaque, non-owning activation key: copying a handle, closure or environment does not copy the mutable slot or its release obligation. The ordinary value heap owns no resource boundary, including through unused closure environment entries.

Acquisition first evaluates the initializer exactly once in the preceding environment. Legacy initialization requires an integer. Generic initialization returns the checked T value before the new owner exists. The machine checks capacity and prepares the new scope, handle binding, lexical instantiation and complete Ops<R,T> authority before publishing a generic owner. Successful acquisition creates a fresh activation, distinct from every earlier successful execution, even at the same source site. Failure publishes none of the new scope or authority. It is an internal failure, not a source allocation branch.

The following legacy rules describe entry and normal release. RESOURCE_INIT retains the initializer's following body and preceding environment. CELL(a, n) owns payload n for activation a. bind_cell binds c to the non-owning handle for a and binds the rigid identity R to a in lexical instantiation; it does not place n in the value heap. The acquisition premise includes all capacity and fallible preparation, before publication.

resource-boundary-steps

Static checking ensures that the returning value does not depend on a. An inner return releases the inner cell before continuing inside its outer scope. An escaped independent snapshot retains its ordinary shared value after release. Reading a snapshot does not freeze cells reachable through it.

Requests retain their lexical type and row instantiation as described above. An activation binding travels through generic applications, returned closures, handler environments and captured control. A closure from an outer execution therefore continues to request its outer activation when called inside another execution of the same source site, including when its dependency appears only in operation metadata rather than a term capture. The machine does not infer activation from operand values or use a global substitution environment.

Request selection searches source-handler and cell boundaries in ordinary innermost-to-outermost order. A cell boundary accepts only its authenticated builtin operation at its exact activation; generic selection also checks the complete instantiated R,T arguments. Nonmatching boundaries are passed. A nearer exact source handler intercepts the request by the existing handler rules. Its interception creates neither a handle nor provider authority.

For a request selected by a legacy cell boundary, the operand handle must equal that boundary's activation. read returns a copied payload integer and leaves the scope in place. write requires the tuple (handle, integer), replaces the owned payload and returns Unit. Alias resolution and complete operand, operation and activation checks precede any mutation. Malformed operands or identity disagreement are internal failures, not source use-after-release.

For generic cells, read returns the current ordinary value and preserves shared aggregate identity; it performs no deep payload traversal. Earlier read results remain unchanged by later replacements. write takes (handle, value) and replaces the current root with that checked T value. Complete operation, type and activation authentication, paid alias resolution, proportional scalar or origin copying, and fallible reply/trace preparation precede publication or replacement. Preparation refusal leaves the root unchanged; effects already performed while evaluating the operands remain performed. The primitive invokes no user callback. Internal failure while disposing a replaced last-owned value terminates execution with incomplete teardown; it is neither a preparation refusal nor a source cleanup transition.

An exact source handler's intercepted read returns its actual reply, and an intercepted write performs no builtin replacement. Clause, other-handler and resumed-computation writes still update the slot in control order. Reading, replacing or dropping an Address payload performs no native memory operation and creates no release obligation.

An outward resource-free request may capture a cell boundary. Capture moves the owned scope into the continuation; resume moves it back in its original order. Neither movement changes live-cell usage or duplicates a payload. Completion after resumption applies E-Resource-Return normally. Checked discard closes cells inside its recursively owned capture using the same release transition, after validating the transfer. Static checking additionally proves that discard skips no required completion outside that owned closure; execution does not rescan suspended source bodies to establish that proof.

Cell capacity counts live owned payloads, including captured scopes, rather than total acquisitions. Normal or abandoned release makes capacity reusable; a later acquisition still receives a fresh key. Deep normal completion and internal failure disposal release cells, captured control and environments iteratively. Internal disposal is not a source cleanup transition. Divergence remains divergence, and no abort, destructor callback, cancellation or foreign cleanup path is added. Resource-free Pure execution allocates no resource registry, resource frame or live cell.

Synchronous hook execution

hook H { body } enters an exact identity handler for the qualifying hook API. Its publish clause resumes with the incoming payload unchanged. An inner root for exactly H cuts off the surrounding chain until that root returns; other instances retain their existing interpretation.

register H transformer { body } evaluates transformer exactly once in the preceding context. Successful preparation acquires a fresh registration activation and enters its body. A non-interpreting owner retains the callback outside the generated exact handler. The activation is distinct on every successful execution, including overlapping executions of one source site. It is not a source value or a resource identity supplied as an effect argument.

The generated handler uses the ordinary request and completion rules. Its clause forwards the incoming payload to the older chain, applies the saved callback to the returned payload by ordinary function application, and resumes with that result. For outer registration A and inner registration B, publication computes B(A(payload)). Each repeated registration participates separately. The body's result is returned unchanged after its registration is removed normally; the result need not have the hook's payload type.

Selecting B captures its handler and publisher-side control, while B's owner remains outside that capture. Its callback therefore runs under handlers surrounding its registration, not handlers installed only around publication. Its saved lexical term, type and row environment remains ordinary closure state. A nearer exact source handler can intercept publication under the existing rules; hook syntax gives no sealed interpretation authority.

A publication inside B's callback sees the then-active older prefix, not B or younger registrations held in captures. A temporary registration inside that callback affects publications only in its own body. A nested root cuts off the older prefix for its exact target. Neither operation inserts callbacks into the original publication's pending sequence, replays a completed prefix or reevaluates an initializer. Explicit recursive calls may still diverge.

Forwarding or an outward callback request can move younger registration owners, their pending callbacks and cells into captured control. Resume restores those same owners and activation keys in order, without reacquisition or duplication. Consumed clause boundaries may remain below restored handlers while their remaining clause computation completes. Registration ownership therefore does not require the owner and generated handler to remain adjacent.

Normal scope completion removes its callback entry and releases registration capacity exactly once, inner before outer. An external ordinary copy of the callback remains callable but retains no registration authority. A closure containing a request to a static hook identity uses the chain active when that closure is called, not the chain present when it was created.

Live-registration capacity counts owners in both active and captured control. Capture and resume do not change that count; normal release makes capacity reusable. Acquisition checks capacity and prepares all fallible state before publishing an activation. Stale or duplicated non-owning activation facts are rejected before invocation or mutation. The machine moves, rather than copies, owning registration frames.

Checked discard can close registration owners inside its owned capture, including recursively owned captures, without invoking abandoned publication callbacks. It cannot bypass required completion outside that closure. Subscriber-local discard remains valid when those outside owners and scheduled resumes still complete. Internal work, allocation or capacity failure disposes registrations, cells, environments and captured control iteratively. It runs no source cleanup or destructor callback and does not roll back earlier callback effects. Divergence promises no eventual deregistration.

Publication over N participating registrations performs N ordinary callback applications and their forwarding/resume steps, in addition to handler search and callback work. Added scans and retained relationships charge the existing evaluator work ledger. There is no machine-global registry, copied whole-chain snapshot, priority sort or second callback evaluator. Hook-free Pure execution allocates no registration owner or live-registration storage.

Scoped cleanup actions

A cleanup expression evaluates its action once in the preceding environment. Only after this initialization and fallible acquisition preparation succeed does it acquire an invocation obligation and enter its body. Abandonment before that acquisition owns no invocation of the action. Copying the ordinary callable does not acquire another obligation.

Normal completion saves the body value and invokes the retained action with (), using ordinary function application in the same evaluator. The action's Unit result is ignored; its completion returns the saved body value unchanged. An unused or pure body does not remove the acquired obligation. Nested actions complete in structural innermost-to-outermost order, while still-enclosing cell and registration owners remain available until their own closing positions.

Capture and resume transfer the owner without invoking or duplicating its action. Starting an action makes it ineligible for another invocation, but retains its unfinished completion. Outward requests may capture and resume this running state; they may not abandon it. Actions may acquire and complete nested scopes through the same rules.

An invocation attempt is not a proof of termination or successful native release. Internal exhaustion or termination provides no source-cleanup guarantee. Host teardown remains iterative, does not replay completed actions and does not roll back effects already performed.

Typed failure reporting

Recoverable cleanup failure uses ordinary source effects and data. An explicit CloseResult<E> with alternatives Closed and CloseFailed(E) can feed a reportClose adapter: Closed returns unit; CloseFailed(error) performs CleanupFailure<E>.report error, whose result is unit. The adapter does not retry. These names denote source declarations, not privileged runtime forms.

A surrounding collector retains Report<A, E>, containing the body value A and a Failures<E> list. On each report it resumes with (), then prepends that error to the returned list. This preserves emission order while allowing all remaining actions to finish. A collector that aborts by skipping a running action or close operation is not admitted.

The body value may be Outcome<T, P>: its primary failure P is preserved separately from cleanup errors E. Success is preserved too; the first cleanup error is the primary cleanup failure, followed by later errors. With no cleanup errors, the collector retains the body outcome unchanged. Different cleanup error types require an explicit sum or independently collected report effects, not implicit boxing or a common error domain. Ignored failure constructors have no automatic reporting meaning.

The complete tool example retains primary 7 and cleanup errors 22, 11, yielding 72211. The corresponding normal return retains Success 42 with the same error order. Reporting does not relax stored-payload dependency checks, promise native release, or convert internal failure into a source outcome.

Observation

Successful evaluation retains root backing through result observation and required completion. The existing host observation foundation retains the observed root storage after successful ownership transfer and releases it with its last observation owner; no closed custom region remains live and no value is relocated. This is distinct from source region access or a source finalizer. The result value remains paired with its heap. The observation pairs that value with the closed result type established for main. Observation renders tuples and constructors structurally. A constructor with a tuple payload renders its components as constructor fields. A location already on the active rendering path renders as <cycle>. Removing a location from the active path after its subtree means shared acyclic data renders in full at each occurrence. Function values render as <function>. Address values render as <address> without disclosing or dereferencing the pointer.

Successful observation retains no live resource scope, registration owner, cleanup obligation or captured continuation. The observed heap may retain copied values and unused non-owning handle entries, but owns no released cell payload. No live Store slot or branch-completion owner survives successful observation.

A completed newtype value renders exactly as its representation value because no wrapper or constructor tag reaches the heap. The observation's separately retained closed result type still renders the nominal newtype spelling and its applied type arguments. Nested ordinary data in a representation keeps its ordinary structural rendering and allocation. Observation performs no runtime nominal-registry lookup and adds no special newtype value case.

Evaluation reports uninitialized access, alias loops, invalid locations, an impossible complete-pattern failure, malformed effect control, and runtime capacity exhaustion as structured internal runtime failures. They are not source-language error outcomes.

Derived multi-step notation

Binding and shadowing: V-003

main : Unit -> Int
main () = {
    let value = 1
    let value = value + 1
    value
}

Elaboration gives the two value binders distinct identities. The first E-Let-Continue extends the environment for the second initializer. E-Add-Values produces 2, and the second continuation extends the result environment with that integer value. Thus main () evaluates to 2.

Primitive precedence: V-001

main : Unit -> Int
main () = 1 + 2 * 3

Precedence produces 1 + (2 * 3). Because the left addition operand is already a value, E-Add-Right carries the E-Multiply-Values step to obtain 1 + 6. E-Add-Values then produces 7.

Application: V-002

increment : Int -> Int
increment value = value + 1

main : Unit -> Int
main () = increment 41

The module's increment and main globals elaborate as one two-member recursive binding. E-Let-Rec-Allocate installs both function templates without allocating a data slot. The empty initialization sequence enters the generated entry application through E-Let-Rec-Body. The common entry E-Beta enters the body of main; looking up increment then materializes its closure. A second E-Beta extends that closure's captured environment with the integer value 41, and E-Add-Values produces 42.

Lexical capture: V-004

main : Unit -> Int
main () = {
    let offset = 40
    let add_offset : Int -> Int = fn(value) {
        value + offset
    }
    add_offset 2
}

The first E-Let-Continue binds the integer value 40 directly. The function captures that lexical environment, and the second binding stores the closure value directly. E-Beta extends the captured environment with the integer value 2; E-Add-Values then produces 42. This is lexical rather than dynamic scope.

Nested application: V-008

increment : Int -> Int
increment value = value + 1

fn double(value : Int) -> Int {
    value * 2
}

main : Unit -> Int
main () = double (increment 20)

The three globals elaborate as one recursive group. Allocation installs the increment, double, and main function templates in the recursive environment; it allocates no data slots. After the common entry E-Beta enters the body of main, strict application frames evaluate increment 20 before applying double: E-Beta enters 20 + 1, then E-Add-Values produces 21. The outer E-Beta enters 21 * 2, and E-Multiply-Values produces 42.

Forwarding and deep resume: EFFECT-001

effect Ask {
    ask : Int -> Int
}

effect Mark {
    mark : Int -> Int
}

main : Unit -> Int
main () = handle (
    handle ({
        let answered = perform Ask.ask 1
        perform Mark.mark answered
    }) with Mark {
        mark value => resume (value + 10)
    }
) with Ask {
    ask value => {
        let continued = resume (value + 1)
        continued + 100
    }
}

The two E-Handle-Enter steps activate Ask outside Mark. The Ask.ask request crosses the nonmatching Mark boundary, so E-Request-Select moves that boundary with the selected Ask boundary and enters the Ask clause with both absent. E-Resume-Restore reinstalls Ask around the captured remainder and restores Mark inside it. The resumed Mark.mark 2 request therefore selects Mark; its clause resumes with 12. E-Clause-Return first returns from the Mark clause and then from the Ask clause after the final addition, producing 112. The executable trace asserts this exact selection, restoration, request, resume, and clause-return order.
