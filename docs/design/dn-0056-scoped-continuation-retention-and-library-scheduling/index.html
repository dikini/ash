DN-0056: Scoped Continuation Retention and Library Scheduling

Development design notes · ash-lang 9a8b73b

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes
  • ID: DN-0056
  • Status: accepted
  • Related: DN-0033, DN-0051, DN-0038, DN-0053, DN-0055, AD-0007, AD-0008

Accepted and implemented

Scoped continuation retention and library scheduling are accepted and implemented on main as part of ffi-ash. Stores own retained control; keys are non-owning; restoration is one-shot; active branch suffixes and cleanup count as unfinished work. Admission checks support and interpreter identity. Normal-return analysis and fresh Store-selected Probe facts govern release.

Scheduling.ash implements coroutine selection, drain and cooperative FIFO scheduling. The gas safe-point example and scheduling tests implement explicit charged yielding. The fixed two-worker host and copied FIFO channels are also implemented under AD-0017. Work/Ack accounting and its error paths are ordinary Ash library code.

The specification defines the accepted control contract. Retained product evidence records the models, implementation, tests and Main integration.

Worker migration, shared Stores, general cancellation, automatic checkpoint insertion and source proof-plan integration are not implemented. The former protocol-specific compiler checker and one-way completion checker are retired. Their derivations below are historical; the current compiler does not certify Work/Ack bookkeeping or per-message processing completion.

Question

Can existing resource scopes and cleanup express the lifetime and completion gate of an executor-owned continuation store? What additional typed Core machinery is necessary to retain and restore control, while leaving scheduling and optional checkpoint policies in libraries?

The comparison must still express coroutines, cooperative multitasking, and preemption at safe points. It must account for nested handlers, work after resume, suspended cleanup, and a parent that waits for P while Q continues. Kernel-thread composition must preserve local ownership with pinned workers as its baseline. Migration is a separate ownership-transfer extension.

Findings

  • Resource ownership supplies the lifetime envelope. Cleanup can invoke a library drain loop before the store and its support are released. A separate task scope or runtime scheduling loop is not required by this derivation.
  • Cleanup alone proves neither quiescence nor eventual completion. Its ordinary Unit -> Unit callback type cannot certify that the callback drained retained control. A finite-execution induction proves quiescence on normal return for the simple recursive drain below. The implemented finite analysis uses recursive normal-return summaries and authenticated, fresh probe facts, without a new gate primitive.
  • At the start of this study, Ash could not put its hidden continuation capability in storage. The retained local extension transfers owned control into a Store and restores it to an admitted current consumer without exposing that capability as a source value.
  • Branch authority, external support, exact interpretation, and completion must be checked through these transitions. Existing analyses provide the basis; they do not already establish concurrent isolation.
  • All three execution styles can use the same mechanism. They differ in who requests suspension and who chooses the next continuation. Safe-point preemption additionally depends on checkpoint coverage and admitted foreign boundaries; it is not arbitrary instruction interruption.
  • Several pinned kernel-thread workers can each own a local executor and store. Parallelism then occurs across workers, with synchronization at admitted channels and host boundaries. Migration and shared-store scheduling require separate ownership, interpretation, and completion contracts.
  • For two workers joined by a one-way FIFO, stable end-of-input links channel delivery to local completion. Network quiescence additionally requires both endpoint owners to finish and all remaining backing users to settle. Existing cleanup supplies release ordering; the channel protocol facts remain new.
  • Bidirectional feedback needs causal completion accounting before endpoint shutdown. Closed root admission and discharged application obligations can establish stable application quiescence while passive receive loops remain suspended. Endpoint and backing settlement then complete network cleanup. Candidate protocol facts and recursive summaries check library orchestration against verified or admitted ledger and transport laws. The local store-state analysis cannot infer arbitrary accounting representation invariants. This derivation requires no new gate Core construct.
  • A private functional ledger gives a concrete representation for registration, retirement, and emptiness proofs by induction. Subject to checked proof integration and the source driver/control obligations, its bookkeeping laws need no native admission. Transport and backing behavior remain external contracts; the derivation below is not a mechanically checked implementation.
  • Untrusted proof plans and restricted induction are a candidate integration mechanism. The validator reconstructs claims against actual Core, checks transition preservation and current-state flow, and revalidates after transformations. No general proof search or executable proof primitive is required; the restricted checking rules still need a soundness argument.

The local Store and scheduling findings are implemented. The restricted proof integration and wider ownership extensions are not implemented.

Context

Current handler execution moves the selected continuation segment, including the selected handler, into one clause-owned capture. Resumption restores that segment without replaying its preceding computation. When it returns, the original clause suffix runs. The static rules require exactly one resume or checked discard on each normally completing clause path. The hidden capability cannot enter an ordinary closure, argument, result, or queue.

Capture analysis follows latent requests through helpers and caller control. A checkpoint helper can therefore request an effect while its caller is in a handler clause without obtaining that clause's hidden capability. Handler placement still determines the captured extent. A selected handler and crossed boundaries are absent while its clause runs; a request there searches outward.

Current resource rules separate duplicable access from scope-owned release. They track dependencies through values, closures, evidence, operation metadata, and actual calls. Captured resource owners keep their completion obligations. Current integer cells and native buffers do not supply an owning continuation store or a general source-defined resource facility.

Current cleanup initializes an ordinary callback before entering its body, saves the body's result, and invokes the callback once before returning that result. Starting the callback consumes invocation eligibility while preserving unfinished completion. A running cleanup can be captured and resumed but cannot be abandoned. It may use still-enclosing resources.

Effect Core already has Resource, Cleanup, Handler, Request, and clause-scoped completion operations. Its independent validator reconstructs actual dependencies and completion relationships after transforms. Adding a library name or a matching callback type does not authenticate an ownership contract.

The bounded inbox in DN-0033 is the closest prior candidate: fix continuation ports, support, interpretation, and completion at an owning destination. Its sequential proof evidence does not establish retained execution. DN-0051 records broader task, wait, cancellation, and parallel execution questions. This note tests a smaller mechanism without adopting a primitive task model.

The implemented generic cell in DN-0053 stores reusable, discardable ordinary values. It explicitly excludes restricted payload ownership. Replacing its payload type with a continuation does not establish the transfer or completion rules required here.

Constraints

The first fragment has one local executor, two isolated sequential computations P and Q, and an enclosing network owner. A retention store has its own lexical identity N. There is no simultaneous execution or worker migration. The kernel-thread baseline composes several such local executors, with one owning worker per store. Computations on different workers may execute in parallel; their local stores remain exclusive and their continuations pinned.

  • Start fresh computations by ordinary function calls under admitted handler roots. Do not clone the caller's continuation or assume a Task Core node.
  • Give each ordinary resource authority to one concurrent process. Suspension does not relinquish that authority. Read-only grants and polarized endpoints may permit access according to their own checked contracts.
  • Keep storage lifetime, access authority, completion ownership, and scheduling separate. Lexical visibility alone establishes none of the required sharing.
  • Begin communication comparisons with one dedicated buffered channel carrying copied, resource-free messages. The bidirectional case adds a second channel in the opposite direction. Endpoints partition authority; each backing store has one owner. Channel ordering and readiness remain library/provider work.
  • Keep every required owner and interpreter valid through the last admitted use and cleanup. Source results and operation operands retain existing escape checks; a locator must not launder a younger resource dependency.
  • Begin with resumption-based completion. No queue operation implicitly cancels work, disposes a running cleanup, or supplies a dummy result.
  • Keep scheduling, admission limits, gas accounting, readiness, and queue policy in libraries. No fairness, deadlock freedom, termination, latency, or performance guarantee follows from safe retention alone.
  • Treat source sugar, macros, compiler insertion, general continuation packaging, and arbitrary foreign-stack suspension separately. Pinned worker composition needs the host and channel contracts below; continuation migration and direct shared-store scheduling remain separate extensions.

Resource and cleanup composition

The following is schematic composition, not executable current Ash syntax. External support surrounds the store. Cleanup's callback is created after store acquisition and before the body; it captures ordinary store access, never a hidden resume capability.

external support {
    resource RetainedStore<N> store = empty {
        cleanup (fn () => drain(store, policy)) {
            p = run_segment(store, P)
            q = run_segment(store, Q)
            wait_for_P(store, p, q)
            R_after_P()
        }
    }
}

R can continue after P while Q remains retained. Only exit from the store's enclosing lifetime requires its remaining work to complete. A library can also wait for both computations, or let R proceed after launching both, while keeping the same enclosing owner. Launch parent and lifetime owner are distinct roles.

On normal body return, existing cleanup saves R's result and invokes drain once. The drain loops in ordinary library code. It returns only after the store has no retained work or other required completion. Cleanup then returns the saved result, followed by resource release. The runtime need not repeatedly invoke a scheduler callback or choose any queue entry itself.

The library loop can have this shape, where probe observes the owning store, not merely a ready queue:

drain(store, policy) =
    match probe(store) {
        Quiescent => ()
        Pending => {
            advance(store, policy)
            drain(store, policy)
        }
    }

advance may select and restore ready control. A wider asynchronous library could also wait for admitted notifications. An empty ready queue is not proof of quiescence when blocked computations or unsettled operations still exist. The initial ready-checkpoint fragment needs no external notification protocol.

Cleanup invokes the whole drain once; repeated advance calls are ordinary calls inside that invocation. If a branch yields during drain, its fresh slot keeps the drain pending. A running branch cleanup can do the same. Disabling retention merely because draining has begun would break this case.

Outer abandonment requires its own proof. Existing discard can invoke an armed cleanup in its owned closure, but the extended analysis must prove that the store's drain and every restored computation retain their required interpreter context. Otherwise that discard is rejected. Host failure disposal is not a substitute for completing the drain.

Quiescence proof for the recursive drain

Existing cleanup guarantees invocation and preservation of unfinished completion. The recursive drain above has this partial-correctness contract:

normal return of drain(N) implies Quiescent(N)

For the first local fragment, define W(N) as outstanding branch work: retained captures, active restored control, and unfinished branch cleanup or close work. Quiescent(N) means W(N) is empty. The store owner and the drain's own running cleanup completion are outside W(N). Including that cleanup in the observed work would make the condition circular: it completes only after drain returns. A wider asynchronous contract must also account for unsettled operations.

The proof has four premises:

  1. probe(N) reports the genuine owning store state. Its Quiescent result establishes that W(N) is empty, rather than that a ready queue is empty.
  2. The executor has exclusive control. No other producer can create work between that observation and return. Probing occurs between Continue calls, after active restored control has returned to the driver.
  3. advance(N) preserves ownership, authority, and completion invariants. Admitted control cannot bypass the recursive suffix and publish an ordinary return from drain. Divergence and suspension remain possible.
  4. Neither return arm creates work after its established quiescence fact. In particular, the recursive call is followed only by its ordinary return.

Induct on the height of a finite normally returning evaluation of drain:

  • In the Quiescent arm, the genuine observation establishes the postcondition. No later operation changes the work state before the arm returns.
  • In the Pending arm, a normal return requires advance and then the recursive drain to return. The recursive evaluation is a smaller subderivation, so the induction hypothesis establishes Quiescent(N) at its return. The enclosing call performs no later operation that invalidates the fact.

This proves the stated implication under the premises. It requires no decreasing work count: advance may resume P and cause it to yield into a fresh slot. If this continues forever, drain never returns. The proof establishes no termination, fairness, or eventual release guarantee.

Composition with cleanup and resource release

On a normal path, existing cleanup invokes drain once and retains its own completion until drain returns. The resulting order is:

W(N) becomes empty
    -> drain returns
    -> the drain's cleanup completion finishes
    -> the store releases

The store's admission check must establish that every normal path to release passes through this cleanup, or otherwise establishes the same quiescence postcondition. No new runtime gate or scheduling loop is needed for this case. Outer abandonment still needs the interpreter and completion proof described above; normal-return partial correctness alone does not admit that path.

Required analysis extension

The local Store analysis is implemented. It tracks normal returns, recursive call summaries and current authenticated Probe observations, including branch suffixes and cleanup. The static rules and C3 correspondence record the delivered analysis. Ordinary constructors do not certify arbitrary resource contents. The later protocol-aware analysis is retired.

Store-state and normal-return summaries

For each relevant store identity N, distinguish two states:

E = W(N) is empty
W = W(N) is nonempty

Uncertainty is the set {E, W}. These states do not count work or include the drain's own running cleanup. Identity and alias relationships come from the resource analysis; a function or variable name does not identify an acquisition.

A function's summary, under its admitted interpretation context, is a relation between input state, observable result case, and state at normal return:

R_f subset-of InputState x ResultCase x OutputState

For a Unit drain, the result has one case. A summary establishing quiescence permits (E, Unit, E) and (W, Unit, E), with no output W. A missing input case means the analysis has found no possible normal return for that input; the summary never promises termination.

The result case is necessary for an observation. The genuine store probe has this admitted relationship:

R_probe = {
    (E, Quiescent, E),
    (W, Pending,   W)
}

A match on its result can establish E in the Quiescent arm. Ordinary construction of that same result case does not establish the relationship. For the minimal analysis, retain finite cases needed by the store protocol; other result information can be conservatively merged.

Recursive inference

Analyse each recursive call group together, using relations for normal returns:

  1. Initialize summaries for members of that group to the empty relation: no finite returns have yet been discovered through recursive calls.
  2. Analyse each actual body using current group summaries, admitted operation contracts, and already checked summaries for other callees.
  3. Add newly discovered possible return triples and repeat until the relations stop changing. For the fixed finite state and result abstractions, this is an ascending computation of a least fixed point.
  4. Publish a completion guarantee only after convergence, when every possible normal output for the relevant inputs is E.

In the simple drain, the first iteration discovers the direct (E, Unit, E) return. Later iterations discover returning paths through advance and the recursive call. Even if advance may leave either E or W, each discovered recursive return ends in E. No iteration introduces an output W.

The finite-execution induction above justifies adding returns by unfolding recursive calls. A recursive cycle without a returning path contributes no normal return, rather than a termination guarantee. Unknown external callees must have conservative possible-return behavior; they cannot inherit the empty initialization used for the recursive group being solved. A pending arm that executes advance; () introduces a possible W output and fails the check.

Relations compose through calls and sequential control. Matches retain the correlation between an actual result case and store state. Joining control paths unions possible returns, so an unsafe returning path cannot disappear because another arm establishes E. Aliases and specialization must preserve the correct store identity; unknown possible aliases require conservative invalidation.

Probe authentication

The probe relationship belongs to the admitted owning store provider. It must be justified by its trusted or verified implementation, like the store's ownership-transfer contract. An ordinary source declaration cannot assert it.

At a request, analysis authenticates the acquisition and activation relation, sealed provider evidence, exact operation identity and arguments, and the interpreter actually selected. An authenticated operation declaration alone does not suffice: current source handlers retain precedence over a builtin interpreter.

  • If the genuine store interpreter is selected, apply its observation contract.
  • If a source handler intercepts the request, analyse that handler's complete behavior. Its result type grants no automatic quiescence fact.
  • A forwarding wrapper may retain the relationship if its actual control, including work after resume, establishes the same result/state summary.

The analysis therefore follows existing exact handler selection and lexical instantiation. Generic identities may coincide after specialization; a proof cannot assume them distinct. The authenticated contract is about the owning store's work, not merely a same-typed counter or ready queue.

A helper making an outward probe request cannot export an unconditional guarantee for every caller. Its summary must retain interpretation requirements or deferred requests, checked against actual handler selection at use. If that selection is uncertain, include all possible interpreter behavior rather than assuming the genuine store provider. Imports preserve these conditions.

Observation freshness

The fact supplied by an observation is conditional and belongs to its returned value at that point in execution:

result is Quiescent implies N is E

Ordinary aliases and code proved to preserve N can preserve that relationship. An operation that may change N's work state invalidates the old relationship and any current E fact. So does a call that may change an alias of N, or loss of the exclusive-control assumption needed for stability. Such a call must leave both states possible unless another checked summary establishes a stronger fact.

For example, this observation cannot certify quiescence after advance:

result = probe(store)
advance(store)
match result {
    Quiescent => ()
    Pending => ...
}

The value remains ordinary usable data, but its implication about the current store state has expired. Copying the value cannot renew that implication. A fresh probe or a verified drain can establish a new fact.

These are static provenance and validity facts. This derivation needs no runtime epoch, source refinement type, or first-class proof token. Slot generations for one-shot restoration remain a separate store mechanism. Effects alone do not establish preservation; use actual inferred call and control relationships, including handled requests and callable dependencies.

Actual return paths and independent validation

Compute summaries at actual normal returns, after all intervening handler and cleanup control. A syntax walk that sees a tail call is insufficient. A handler suffix after resume, or cleanup that creates new work after drain returns, can change the enclosing expression's output state back to W or uncertainty.

For example, this enclosing expression does not inherit drain's guarantee:

cleanup (fn () => create_work(store)) {
    drain(store)
}

The resource admission obligation is that every reachable normal predecessor of release(N) establishes E. A verified recursive drain is one way to establish that fact, rather than a mandatory function name or syntactic wrapper. Existing cleanup supplies invocation and protected completion; extended analysis checks the actual callback's postcondition and its preservation up to release.

For example, this same-typed callback fails that obligation:

bad_drain(store, policy) =
    match probe(store) {
        Quiescent => ()
        Pending => {
            advance(store, policy)
            ()
        }
    }

Its pending arm returns without establishing quiescence. Creating work after a successful recursive drain would likewise invalidate the postcondition.

The independent Core validator must reconstruct return summaries, probe interpretation, and freshness from actual linked control. Imported summaries remain authenticated to their definitions and hidden identities; they cannot replace linked reconstruction. Callback substitution and Core transforms must re-establish the proof, including handler and cleanup suffixes. Normal-return quiescence does not by itself prove the separate abandonment obligations.

The extension consists of the store-state domain, result-case relationships, freshness invalidation, recursive normal-return summaries, an authenticated probe contract, and the check at the existing resource-release boundary. These are new semantic analysis rules. An arbitrary Unit cleanup remains insufficient, but no new gate node or runtime scheduling loop is required by this derivation. The owning store and transfer/restore semantics themselves remain the extensions identified elsewhere in this note.

Candidate typed Core contract

One store activation fixes input Unit, answer A, resumed row rho, and required external interpretation I. Key<N> is an ordinary opaque locator qualified by the store activation and a slot generation. It carries no independent ownership. A library answer can be Finished | Suspended(Key<N>, Reason).

Let DELTA track structural capability states, sigma summarize possible captured control, and chiN denote the store's exact resource effects. These are analysis facts, not general source linear types or first-class continuation values.

Retention refers to the selected checkpoint clause's hidden owner c. The rule consumes that capability by moving its capture into the store. It does not run the retained computation, so its immediate row is the store operation's row.

Admit(N, sigma) checks every reachable capture represented by sigma:

  1. Its owned closure includes all nested live clause captures and resource or cleanup owners at their structural positions. Transfer neither duplicates them nor moves N's own owning boundary into N.
  2. Dependencies outside that closure remain protected through completion. Actual values, evidence, operation identities, saved results, and callable captures all contribute. External support can surround the store or have a separately proved completion order under the network owner.
  3. Exact interpretation remains available at the admitted consumer. A matching type or effect row cannot justify replacing a missing provider or handler.
  4. Branch resource authority remains compatible with all other live control, including suspended captures and executor code. Fresh root admission must check ordinary function captures too; retention alone cannot establish this.
  5. Finishing the transferring clause skips no required completion outside the moved closure. All user handler suffixes belonging to the branch lie inside its suspension boundary, or have separately protected completion.
  6. The answer and outward payloads obey existing escape restrictions.

Only the selected checkpoint owner becomes consumed. Nested source owners keep their available or consumed state. Retention preparation precedes the committed move; capacity failure cannot publish an ownerless or duplicated capture.

Restoration accepts a key and unit reply. It requires executor authority and an actual consumer context satisfying I. Its row includes execution of the retained computation, including future checkpoints and cleanup.

On a live generation, the store marks the slot spent and moves its capture C into active control. Restoration plugs C above an ordinary Some return adapter and the current consumer D. Its answer goes to D, not into the finished original checkpoint clause. A spent generation returns None without executing C. Slot consumption does not mean branch completion.

The store owns the opaque control and responsibility for its completion. This does not grant executor code ordinary access to branch resources. Private checkpoint-handler associations with N are administrative, non-owning links; they do not copy the store owner or grant P and Q shared mutable store authority. Admitting those links requires the store protocol, not a general exception to ordinary cell dependency-cycle checks.

The store's lifetime and closing contract can use existing Resource and Cleanup structure. New validation must account for owned control in slots, active restorations, the drain's quiescence proof, escape, and abandonment. The derivation does not require separate Closing, Drive, or Task Core constructs. It also does not establish that adding only two node variants to today's Core would be sufficient.

Root placement and a checkpoint helper

A private handler surrounds all branch-local source work, including handler clauses, suffixes after resume, and cleanup. N and the executor's drain lie outside that capture boundary. Its clause transfers the current capture and returns Suspended(key, reason) through ordinary library control. It has no unfinished source suffix that must survive after that return.

Checkpoint is an ordinary operation request with reply type Unit. The helper below uses ordinary application, bindings, and conditional control. It returns updated gas so a local binding does not lose the accounting update.

check(policy, gas, site_cost) =
    (gas1, decision) = policy.charge(gas, site_cost)
    if decision == Yield:
        checkpoint(BudgetEmpty)
    gas1

Its latent row includes the exact checkpoint instance and the policy's effects. The false path captures nothing dynamically; the static row still includes the possible request. Restoration continues after the request, without charging the same site again. Gas, refill, site costs, and decisions are library data and policy. No Gas, Poll, or conditional-checkpoint Core node follows.

An outer private handler can capture a helper called from an unrelated handler clause. A selected handler cannot handle a request from its own clause unless another matching boundary is installed. An inner local checkpoint handler also limits capture to its own boundary; it cannot be assumed to suspend the whole branch. The helper never captures or invokes its caller's hidden resume.

P and Q through handler and cleanup suspension

Suppose N owns slots kP and kQ. Restoring kP spends that generation and leaves kQ unchanged. The retained P control before a source clause's resume includes the clause boundary with its live nested capture. After resume returns, the boundary is consumed and the completed nested control is absent. A later checkpoint preserves whichever state actually exists; it cannot reactivate the consumed source owner.

For a checkpoint during cleanup, the retained P segment includes the saved result, the running cleanup completion owner, and the cleanup suffix. Starting cleanup has already consumed invocation eligibility. Retention invokes nothing and acknowledges no completion. The executor can run Q under its independent authority, then restore P to execute only the remaining cleanup suffix.

If P yields while N's drain is running, P's capture stops at its private root. The drain's own running-cleanup completion remains outside that capture. The checkpoint clause returns to the current Continue consumer in the drain, which keeps running. Capturing N or transferring that drain into its own store would create an invalid ownership/completion dependency and must reject.

Copied channel messages become receiver-owned ordinary data. P's local resources do not move to Q through scheduling or through those messages. The channel implementation must supply the synchronization its endpoint protocol requires; the owning store does not imply synchronization on every local object. Multicore notification, visibility, and transport need separate rules.

Execution styles

Style Suspension request Selection policy
Coroutines Explicit yield/adapter. Caller or coroutine library.
Cooperative multitasking Library yield/wait. Executor library.
Safe-point preemption Enabled policy guard. Executor library.

Coroutines retain and restore direct-style control. The unit-reply fragment can exchange copied data through channels; other reply ports require a separately fixed homogeneous contract. Cooperative multitasking starts fresh roots through ordinary calls and overlaps their retained lifetimes. Waiting adapters still need readiness and settlement contracts.

For the third case, the program need not explicitly choose to yield at each site: a producer can supply guarded checkpoints at safe points. Optionality means that a producer or library can omit or disable them. A concrete enabled checkpoint must pass ordinary typing and the retention admission checks. Macro expansion and compiler insertion are separate producers of the same typed Core; neither is a prerequisite for defining the contract.

Site legality and coverage are separate obligations. A valid checkpoint does not prove that every loop, recursion cycle, or foreign call reaches one within a bounded cost. Gas reaching zero only causes a yield when a check is reached. There is no fairness or bounded-latency claim without additional coverage, cost, scheduling, and host assumptions.

Coroutine abandonment and task cancellation are also separate. A resumption-only store can hold a coroutine until it completes, but cannot implement arbitrary drop-to-cancel semantics without an admitted disposal or cancellation protocol. Session types can constrain channel progress; they do not establish network-wide deadlock freedom in the presence of joins and other waits by themselves.

Kernel-thread baseline: pinned workers

Kernel threads supply execution for library executors. The baseline gives each worker exclusive control of its own store and keeps its computations on that worker. Pinning here does not require CPU affinity. This host composition is implemented for the fixed two-worker network under AD-0017.

The following tree shows ownership and placement, rather than Ash syntax:

network owner
    kernel thread K1
        executor E1, store N1: P and Q
    kernel thread K2
        executor E2, store N2: U and V

polarized channels connect the workers

P and Q interleave on K1; U and V interleave on K2. Different workers can execute simultaneously. The kernel chooses runnable kernel threads, while each library executor chooses its next Ash continuation. See the host scheduling boundary in Linux scheduling documentation.

Kernel preemption pauses the worker's existing execution state. It performs no Ash capture, ownership transfer, cleanup invocation, or completion transition. The worker later continues with the same authority. Ash safe points are needed when detaching language control for library scheduling, rather than when the kernel preserves the carrier thread's execution. Kernel preemption of K1 does not select Q inside E1: P must return or suspend for E1 to choose Q.

All three execution styles remain available within each worker. Coroutine selection, cooperative yielding, and optional gas-guarded safe-point preemption use the same local retention contract. OS scheduling supplies the independent outer level of preemption and parallel execution.

Worker entry and channel boundaries

An admitted thread entry can invoke an ordinary function to run its executor. Admission checks the function's transitive captures, storage, handlers, provider state, resource authority, and cleanup support. A simple initial arrangement constructs worker-local resources on that worker and exchanges copied messages through polarized endpoints. Shared read-only data also needs a valid lifetime and a representation admitted for concurrent access.

Only E1 claims, retains, or restores N1's slots. Other workers publish messages or notifications through an admitted channel; E1 processes them itself. A notification may identify a continuation without granting its sender authority to resume it. Sharing the host address space grants no Ash resource authority.

The channel/provider contract must establish publication and receiver visibility, safe waiter registration, stale-notification handling, and backing protection through the last possible access. The baseline does not require synchronization on ordinary worker-local store operations. It does require synchronization at these cross-thread boundaries and for any runtime representation actually shared between workers. The implemented copied-byte transport uses synchronized FIFO state, generation-checked watches and readiness rechecks. Region transfer and shared ordinary graphs are not implemented.

A blocking host call occupies its worker, preventing that executor from running its other computations until the call returns. A general blocking-work adapter that submits work to another thread and restores a local waiter is not implemented. Active Ash and native stacks are not transferred between workers.

Local quiescence and network completion

The recursive drain proof applies to each local store while its exclusive-control and observation-stability premises hold. Notifications for existing pending computations do not erase those computations' work obligations. If an external producer can admit fresh work, a local empty observation does not establish that the scope can release before that producer is settled.

A candidate network completion protocol must therefore:

  1. Close fresh-work admission for the scope being drained.
  2. Allow its existing computations to finish, including repeated retention.
  3. Account for operations, notifications, and handoffs that can still create work or access the scope's support.
  4. Drain each owned store and establish stable completion of its owned scope.
  5. Release shared support only after the relevant completion acknowledgements and channel obligations have settled.

These are additional protocol obligations, not a general network termination proof. The one-way FIFO and bidirectional derivations below specialize these requirements. Closing fresh root admission must still allow existing work to create accounted descendants until application quiescence is established. An acknowledgement must be justified by the admitted completion protocol; ordinary data labelled Done is insufficient. A transient E snapshot from each worker cannot replace that protocol. Results must not export closed store handles or dependency-bearing keys.

Completion of an owned Ash scope need not terminate its carrier thread. A persistent pool can keep a worker alive after reporting scope completion. If the network owner also owns the threads, their completion is another obligation.

Network-wide quiescence for two pinned workers

Take one buffered FIFO channel C. Worker A owns the send polarity; worker B owns the receive polarity; enclosing network owner R owns the channel backing. There is no external producer or transfer of endpoint authority in this fragment. Messages are copied, resource-free values. The chosen closing policy processes all accepted messages; copied payloads alone do not imply that policy.

The following is a conditional normal-completion derivation using admitted channel and worker contracts. It establishes neither a channel implementation nor a general distributed termination algorithm.

In-flight message accounting

The message's passage must remain accounted for throughout these phases:

Phase Required accounting
Send preparation A's active operation and access to C.
Accepted, unpublished C's pending-publication obligation.
Published, queued C's owned queue entry.
Receiving or copying Receive operation and its backing access.
Processing incomplete B's active or retained work, including cleanup.

Before a send can report acceptance, the provider must account for its pending publication and protect the copied payload. Publication moves that obligation into queued state. Receipt cannot forget the queued work before receiver control accounts for its processing. Backing access remains protected until copying is complete. No transition may leave an interval in which neither side accounts for unfinished work or access.

In the sequential receive loop below, B's existing continuation covers receipt and handling. Separate dispatch would need to register the receiver work before retiring the delivery obligation. The value itself remains ordinary duplicable data; the provider's delivery and backing obligations are not duplicated by copying it.

For the proof, let I(C) denote accepted but unpublished sends, Q(C) queued entries, and U(C) remaining provider operations or notifications that may access the backing. Active or suspended message handling belongs to B's local work. These are semantic sets, not a requirement for central atomic counters. The provider must establish their coverage and publication/visibility relationships.

Completing the send polarity

A's completion ordering is:

finish admitted computations that can send, including cleanup
    -> drain A's local store
    -> finish_send(tx)
    -> complete A's owned scope

Normal return of finish_send establishes that no more sends can be accepted through this polarity and that every earlier accepted send remains accounted for. Any publication still pending belongs to C's protected provider state. An operation retaining access to A-local memory must finish before A's scope can complete; acceptance cannot silently leave an unprotected borrow behind.

The implementation may settle publication before finish_send returns or leave an accounted publication for the provider to finish. In either case, completing the send polarity does not release C's backing or discard queued messages. The sealed send authority cannot reopen the same channel activation.

Stable end-of-input and receiver completion

B can use this ordinary recursive receive loop:

receive_loop(rx) =
    match receive(rx) {
        Message(m) => {
            handle(m)
            receive_loop(rx)
        }
        End => ()
    }

The admitted receive contract must establish:

receive(C) returns End
    implies the send polarity is sealed
        and I(C) is empty
        and all earlier queued messages have been received

A FIFO implementation can justify this with an ordered end marker or a final publication watermark, provided it cannot overtake an accepted publication. A temporarily empty queue while sending remains possible supplies no End fact. An ordinary payload labelled End does not supply it either.

This observation is stable: the finished send authority cannot create later input in this activation. The compiler need not prove the queue algorithm or watermark arithmetic from an ordinary method type; those laws belong to the admitted provider contract. Actual handler selection and result authentication remain necessary, as for the store probe.

The receive loop returns through End, after preceding sequential handlers return. That does not establish that all B-owned work is finished. Any separately admitted work, handler suffixes, and cleanup must also complete through B's local drain before its endpoint and scope report completion. The receiver endpoint's closing contract must account for genuine input completion; a local empty store alone cannot justify early receiver completion under this drain policy.

Joint completion condition and backing settlement

Define three distinct facts:

DoneA = A's admitted work and cleanup completed
        and its send endpoint completed

DoneB = B observed genuine end-of-input
        and B's admitted work and cleanup completed
        and its receive endpoint completed

SettledC = no remaining operation or notification can access C's backing

A sufficient network condition is:

NetworkQuiescent = no external admission remains
                   and DoneA and DoneB and SettledC

For this fixed network, admission can be closed by construction. A dynamic variant must establish that phase explicitly. Stable input completion accounts for I(C) and Q(C); endpoint and provider settlement must also account for U(C). Queue emptiness alone cannot establish that wake registrations, callbacks, or partially completed accesses have relinquished the backing.

A synchronous implementation may derive SettledC from endpoint completion. An asynchronous implementation needs its additional settlement acknowledgement. The fact concerns actual access, not the absence of currently runnable code. Completion of these scopes does not require persistent carrier threads to exit.

The normal-return summaries needed by analysis include send completion, the authenticated End case, each worker scope's completion, and provider settlement. Ordinary data labelled Done cannot establish them. A completion notification must follow an admitted protocol whose actual control proves its relationship to the completed scope. Probe freshness and interpretation checks still apply.

Cleanup ordering and premature-release trace

The network composition can retain existing resource and cleanup structure:

resource Channel<C> channel {
    cleanup (fn () => finish_network(channel, A, B)) {
        run_network_body()
    }
}

This is schematic composition. The library finish_network drives or awaits both owned scopes and settles the channel. It must establish NetworkQuiescent on normal return. The owner coordinates endpoint completion through its admitted protocol; it does not acquire the workers' ordinary resource authority.

Existing cleanup saves the body result, invokes this finishing computation once, and preserves its unfinished completion until return. Only afterward can the channel resource release and the saved result return. Channel-dependent results remain subject to ordinary escape checking. Later control cannot invalidate the completion facts before release.

Both workers must remain able to service the channel while draining. In a bounded FIFO, B may need to receive before A can finish sending. The closing order must not defer B's service until after A finishes. Scheduling progress remains a separate library and host assumption.

One possible execution exposes each premature-release hazard:

  1. A's last send is accepted; C owns its pending publication.
  2. A begins finishing; that publication remains protected and accounted for.
  3. The message becomes queued. A can complete its send polarity while C remains live for delivery.
  4. B receives the copy and yields during handling. Its retained continuation keeps receiver work unfinished even though the queue may now be empty.
  5. B resumes, finishes handling, observes End, and drains remaining cleanup.
  6. Both endpoints complete and any remaining backing users settle. R's finishing cleanup can then return, permitting C's release.

R may wait only for A and continue inside the enclosing channel lifetime while B remains unfinished. It cannot complete that enclosing lifetime on A's behalf alone. Normal-return analysis must establish the joint condition at every channel release predecessor. No new network gate Core construct follows from this derivation; endpoint phases, delivery coverage, and settlement are the additional provider and completion contracts. Outer abandonment needs its own completion and interpreter proof. Eventual completion is not established here.

Bidirectional quiescence with causal completion accounting

Now take two buffered channels, C_AB from A to B and C_BA from B to A. Each worker owns one send and one receive polarity; R owns both backing resources and their enclosing lifetime. Each worker processes messages sequentially, and handling a message may send further messages through its send endpoint. Messages still carry copied, resource-free application data. There is no endpoint migration or shared ordinary application resource authority.

The ordinary Work/Ack library implements bidirectional accounting and error handling. The protocol-specific compiler checks discussed below were superseded on 2026-10-31 and are retired. The host authenticates transport origin and kind; it does not certify honest acknowledgements or per-message processing completion. An application activation below means an ordinary invocation of message-handling code, not a new task value or Core control form.

Why local emptiness and end-of-input are insufficient

A locally idle A may receive work from B and send another message in response. Two empty-queue observations can miss an accepted publication or an intervening activation. Sealing both send polarities at that point could reject required descendant work. Conversely, waiting for both receive loops to observe End before sealing either send polarity makes shutdown circular.

The derivation therefore separates application quiescence from final worker, endpoint, and backing completion. Application quiescence establishes that no application work can still be generated. It does not require passive receive loops or all provider notifications to have completed.

Causal coverage and resource authority

R accounts for initial application work as root obligations. Every unfinished activation and every remaining independent producer must have a completion path to one of those roots. Before an activation publishes a message that creates further work, the library registers a child obligation under its existing path:

register child obligation
    -> publish message
    -> receive and process message
    -> finish local processing, cleanup, and descendants
    -> acknowledge completion

The coverage invariant is:

Every unfinished application computation, accepted application message, and remaining authority to generate application work has an outstanding completion path to R.

Call this invariant Covered(R). It is a property to establish and preserve, not an ordinary Boolean that the library may assert.

Registration precedes any visibility of the message and remains accounted for through pending publication, buffering, and receiver processing. Receipt must establish receiver responsibility before retiring transport responsibility. Suspension preserves the processing obligation, including handler suffixes and running cleanup. A failed send can retire its reservation only after establishing that no accepted or deliverable message remains.

An activation's completion entry can acknowledge its parent only after its own application code and producing cleanup have finished and all child obligations have completed. An acknowledgement in flight leaves the parent's child entry outstanding. The protocol matches each acknowledgement to a live entry and retires that entry once; stale or duplicate acknowledgements cannot discharge other work. Copied identifiers name entries but confer no accounting authority.

Completion dependencies do not transfer ordinary resource access between workers. There remains one owner of each executable continuation and its branch authority. A parent's outstanding dependency is not a second owner of the child's control. Where local application code has finished, its administrative entry can remain without retaining that code's ordinary access authority. Any support actually used by the entry remains protected by its own enclosing owner.

The causal parent is not a lexical release owner for remote processing. A remote dependency on A's local resource would need a separate authority and lifetime proof; the copied-message fragment supplies none.

The completion structure need not mirror the physical communication graph. Logical parent links can remain acyclic under R even when messages travel around a cycle. They are administrative relationships, not resource ownership from A to B and back to A. Each worker still mutates only its own store and accounting records. Polarized operations convey data and completion notifications; the proof does not require a shared atomic counter on every store operation.

A round trip while both workers remain available

Suppose R starts activation a on A. It sends m to B, creating b. B's processing of m sends n back to A, creating c. The causal paths are:

R -> a on A -> b on B -> c on A

The execution can proceed as follows:

  1. R registers a before starting its ordinary invocation on A.
  2. A registers b before publishing m. After a's local code and cleanup finish, A may return to its receive loop. Its administrative entry for a remains outstanding because b has not completed.
  3. B receives m under b's coverage, registers c, and publishes n. B may finish its local processing and continue servicing its channels while c remains outstanding. Waiting for c must not block the entire worker's executor.
  4. A receives n and processes c. This is subsequent sequential work on A, not simultaneous access by a and c to one ordinary resource. If c suspends, its continuation and authority remain owned by A's local store.
  5. If c produces no more work, it finishes code and cleanup, then acknowledges completion. B can retire c and acknowledge b after b's own local completion. A can then retire b and acknowledge a to R.

The accounting entries need not retain completed application frames. A genuinely suspended computation, such as one awaiting a reply, does retain its frames and completion responsibility until it resumes and finishes.

A reply delivered to an already-covered continuation needs a distinct handoff rule: establish coverage in that existing continuation before retiring delivery. Do not make the reply sender depend on completion of the receiving ancestor's entire activation. That would introduce an artificial completion cycle. The existing activation remains accounted for through its later work; delivery does not create another owner or reparent an ancestor beneath its descendant.

Passive service and producing cleanup

Both receive loops may still be suspended when application obligations disappear. They remain lifetime and completion obligations, but their parked existence need not count as application work if the library establishes that they can activate application code only upon receiving an already-accounted message.

This restriction does not apply automatically to arbitrary blocked user code. An independent timer, callback, producer, or retained computation that can generate application work needs a root or descendant obligation. Worker resources remain owned while service loops are suspended; classifying a loop as passive does not release its authority or permit concurrent sharing.

Cleanup that can send application messages belongs to the accounted application phase. It must finish before its producer obligation retires. Service teardown after application quiescence must be proved unable to generate application work; otherwise retain its producer obligation and run that cleanup before declaring application quiescence. No running cleanup is discarded or silently skipped.

Two-phase shutdown and stability proof

Let G(R) be the outstanding root obligations, including independent producers. Their descendant coverage is established by Covered(R). Define:

RootsClosed(R) = no further independent application work can be admitted
RootsEmpty(R) = G(R) is empty
AppQuiet(R) = Covered(R) and RootsClosed(R) and RootsEmpty(R)

The first phase establishes application quiescence:

  1. Seal fresh root admission, including admission by R or external sources. This does not seal internal sends by existing accounted computations.
  2. Continue servicing both workers, application channels, and completion notifications. Existing work may generate descendants and suspend repeatedly.
  3. Establish through the authenticated protocol that G(R) is empty.

To show stability, suppose application work could appear afterward. A new root would contradict RootsClosed. An existing producer, unfinished processing, producing cleanup, or accepted message would require an outstanding root by the coverage invariant. A passive receive loop could activate only from such an accounted message. Each possibility contradicts AppQuiet. This is stronger than combining observations taken from separate local stores.

The second phase completes service and settles backing access:

  1. Seal both application send polarities. No legitimate application sender remains, so this cannot prevent required descendant work.
  2. Let the receive loops observe genuine end-of-input and finish normally. Drive all remaining retained service control and non-producing cleanup.
  3. Complete both workers' owned scopes and all their endpoints. Settle every remaining channel operation, wake registration, and completion notification. Private control-channel support, if separate, has the same settlement duty.
  4. Return from network cleanup, permitting the enclosing backing owners to release and the saved body result to return.

Both directions must remain serviceable during this protocol, including with bounded queues. Serially blocking one worker until the other completes can prevent the messages or acknowledgements needed for completion. Scheduling and notification delivery remain separate library and host assumptions. Sealing application sends must not prematurely close the control support needed to finish the protocol and establish settlement.

A sufficient final condition is:

NetworkQuiescent(R) = AppQuiet(R)
                     and both owned worker scopes completed
                     and all endpoints completed
                     and all channel support settled

AppQuiet does not imply that the local stores are E: passive receive captures may remain until the second phase. The local recursive drain proof applies at final store completion. Application quiescence alone cannot authorize backing release while any provider or notification can still access it.

The enclosing ordinary cleanup can implement both phases. It retains its own unfinished completion until the finishing function returns. Resource nesting keeps channel support live throughout; every normal release predecessor must establish the final condition and preserve it up to release. These phases are library protocol states, not new Core gate or task constructs.

Ownership supplies responsibility and support validity; cleanup supplies invocation and the release boundary; the protocol supplies stable completion evidence. This conditional derivation requires no new gate primitive. It does not establish that today's analysis, or the local candidate analysis alone, can validate arbitrary library implementations of the protocol. The owning continuation store and transfer/restore extensions remain necessary.

An infinite exchange never reaches AppQuiet; an application deadlock may also prevent return. Eventual completion requires additional assumptions about finite application work, scheduling, delivery, and failure handling. Outer abandonment and cancellation still need separate completion and interpreter proofs.

The smallest candidate extension adds identity-indexed protocol facts to the normal-return summaries already derived for local stores. It checks library orchestration against small accounting and transport contracts. It does not infer that an arbitrary map or counter represents all unfinished work.

The protocol-specific checker is retired. This section records its historical design; it is not a requirement of the implemented ordinary Work/Ack library. Protocol facts and relational summaries

For the fixed two-worker fragment, distinguish these facts:

Fact Meaning

RootsClosed(R) Independent admission is closed and earlier work covered.
RootsEmpty(R) The actual root ledger has no outstanding obligations.

Accounting and transport operation contracts

The operation laws needed at the abstraction boundary are:

  • Child registration attaches a fresh outstanding obligation to a covered producer before publication is possible. The parent's responsibility cannot disappear while that child remains unfinished. Closing direct-child admission is permanent for that record; later registration cannot succeed.
  • Publication associates accepted work with the registered obligation. A reservation covers one accepted dispatch; copied keys cannot reuse it for another. A failed-send path can retire a reservation only after establishing that no accepted or deliverable message remains.
  • Receipt establishes covered processing before delivery responsibility ends. A reply may hand off to an already-covered continuation without creating a completion dependency back to its own ancestor.
  • A child-empty observation describes the actual children of the identified live record. Retirement matches a completed child and occurs once; stale or duplicate acknowledgements cannot discharge another obligation.
  • Root admission closure accounts for earlier accepted roots and prevents new independent admissions in that network activation.
  • Channel closure, genuine end-of-input, and settlement establish the endpoint, publication, notification, and backing properties used by the second phase.

These laws provide conservation of accounting and backing responsibility. They are contracts for operations, not new Core instructions. An operation can itself be an ordinary library function whose summary follows from smaller operations. Native publication, visibility, callback, and backing behavior needs a provider contract wherever its implementation is outside checked Core.

The ledger's representation laws also need proof or admission. Its empty probe must describe the actual outstanding records, registration must retain the required dependency, and retirement must preserve all other obligations. Ordinary method types, integer arithmetic, or a function named acknowledge cannot establish those properties.

Facts inferred from actual library control

Relative to those operation contracts, analysis can infer that:

  1. Every publication follows registration of its matching obligation in the same network; receiver dispatch uses the corresponding covered record.
  2. Retention preserves the link between an outstanding obligation and its executable continuation. Resumption finishes under the same responsibility.
  3. Local completion reporting follows all required application control, handler suffixes, and cleanup, and acknowledgement follows checked child completion.
  4. Application code has no unaccounted publication path through captured raw endpoints, closures, evidence methods, or imported helpers.
  5. Passive service and finishing code introduce no independent application producers. Producing cleanup remains within an outstanding obligation.

These are properties of actual transitive control and authority, not effect rows alone. A receive-loop name or callback type cannot certify passivity. External callbacks and timers need contracts identifying their admission and completion relationships when their behavior is not available as checked Core.

A suspension wrapper's return is not local application completion. The Suspended path keeps the record outstanding together with the retained capture. Only the path on which the application really finishes can report local completion. A result constructor named Finished supplies no proof without the inferred relationship to actual branch control. A same-typed substitution must re-establish that relationship.

Closure and freshness at both levels

For an activation record p, LocalDone(p) means its local application control and cleanup finished and admission of new direct children under p is closed. A remaining producer must already have its own outstanding obligation. Under the coverage and retirement laws:

LocalDone(p) and ChildrenEmpty(p)
    permits completion acknowledgement for p

Before local production closes, a child-empty observation may become stale when p sends another message. The same reasoning applies at the root: RootsEmpty becomes stable application quiescence only with RootsClosed and Covered. Root closure must not be assumed to preserve an earlier empty snapshot if pending admission can still register earlier accepted work. A fresh observation or a checked preservation summary is needed.

Ordinary aliases and proved state-preserving code may retain an observation's result/state relationship. A relevant mutation, unknown possible alias, or call whose preservation is unknown invalidates it. Parallel interference requires more than a local absence of writes: the admitted transitions of the other worker must preserve the invariant and any claimed stable fact. A transient local E or empty queue is not stable under message arrival.

Once AppQuiet is established, protocol-preserving steps cannot generate new application work: new roots are closed and every possible remaining producer would contradict coverage and root emptiness. Acknowledgements may settle administrative work without reopening application admission. Terminal endpoint and backing facts likewise require contracts preventing later use.

All observations still require the actual selected interpreter and matching network identity. An intercepted request or ordinary returned constructor does not inherit the genuine provider's contract. Forwarding wrappers, imports, specialization, and handler suffixes retain the earlier probe-authentication checks. Runtime key matching and generation checks remain provider obligations; these static facts introduce no first-class proof token or required runtime epoch.

Minimal library Core ledger and inductive invariant

Use a private functional representation to discharge the ledger-specific laws. The following data and algorithms are schematic Core-level descriptions, not executable source examples or a selected implementation. They give conditional paper proofs. Mechanical authentication and the previously identified continuation-retention extension remain separate work; this note authorizes neither implementation nor a prototype.

Representation and the current state stream

Each worker keeps ordinary data with these roles:

Ledger = (next: Int, records: List<Record>, pending_outputs: List<Output>)
Record = (id: Id, parent: Option<Address>, production: Phase,
          children: List<(Id, Worker)>)
Phase = Open | Closed
Id = Root | WorkId(Allocator, Int)
Address = (Worker, Id)

The distinguished root record lives on one worker and has no parent. R is still the enclosing ownership scope, not an additional required thread. All other records have a parent address. Its worker identifies the parent ledger's owner, which need not be the allocator named in the record's identifier.

Within one network activation, each allocator has a distinct fixed label and a private serial, initially zero. Allocation uses that serial and increments it without reuse, including after retirement. Current integer operations operate on mathematical integers, so this freshness argument needs no overflow case. Network activations and their dedicated channels remain distinct; copied old identifiers do not acquire authority in another activation.

Records and pending output envelopes contain ordinary metadata and copied, resource-free payloads. Actual continuations remain in their owning stores. An explicit child list makes emptiness structural; there is no separate cached count to relate to that list. This is a proof baseline, not a performance result.

The worker threads ledger state through one owning event loop:

drive(ledger) =
    event = next_event(...)
    successor = transition(ledger, event)
    drive(successor)

The driver also dispatches computation and submits pending outputs. Its proof must establish that subsequent transitions use the successor, with reservations and outputs installed before publication or application dispatch. No callback may reenter an update using the previous state. Application code receives identifiers and messages, not authority to select a ledger version for updates.

The ledger value is ordinary duplicable data, not a linear value. Privacy alone does not prove which copy is current. The actual driver must never roll back to an obsolete version or use it to certify current emptiness. These are source control obligations for this loop; no generic mutable cell is required. If an update checkpoints, its exclusive updating continuation remains retained; another update cannot start from its old input. Kernel preemption preserves that execution state without changing ledger ownership.

Collection lemmas and transition definitions

Implement lookup, insertion, update, and removal by recursion over private finite lists. For example, removal returns whether a matching entry existed:

remove(q, Nil) = (Nil, Missing)
remove(q, Cons(x, xs)) =
    if x.id == q:
        (xs, Found)
    else:
        (ys, result) = remove(q, xs)
        (Cons(x, ys), result)

Induction on the input list, assuming distinct identifiers, establishes:

lookup returns exactly the matching entry
remove(q) returns Found exactly when q was present
ids(remove(q, xs).list) = ids(xs) minus {q}
remove(q) preserves every other entry and identifier distinctness
xs is Nil exactly when ids(xs) is empty

Insertion and update have the corresponding frame property: entries other than the selected one remain unchanged. Finiteness is a representation invariant, not a consequence of the list type alone. Current recursive data rules admit cyclic data. The ledger starts with finite lists and these private functions preserve acyclicity; it accepts no arbitrary application-built list as ledger state.

Registration updates a local parent record and queues one work envelope:

register(L, p, destination, payload) =
    match lookup(p, L.records) {
        Missing => (L, Rejected)
        record with production Closed => (L, Rejected)
        record with production Open => {
            q = WorkId(this_allocator, L.next)
            successor = L with
                next incremented
                (q, destination) inserted into p.children
                Work(q, parent_address(p), payload) queued for destination
            (successor, Registered(q))
        }
    }

This is one pure state transformation. The driver makes the successor current before submitting the envelope. Receipt establishes the corresponding local record before executing its application code. The baseline permits one accepted dispatch for each work envelope; transport redelivery would need a separate deduplication proof and is not assumed here.

Local completion closes a record's production only after the actual application control, handler suffixes, and cleanup finish. A suspension wrapper returning does not qualify. Root closure instead closes fresh independent admission after earlier admissions and remaining producer authorities have been accounted for.

Local retirement is:

retire(L, p) =
    match lookup(p, L.records) {
        non-root record with production Closed and children Nil =>
            remove p and queue Ack(record.parent, p)
        otherwise => L
    }

Acknowledgement processing finds the named parent and removes the child whose identifier and destination match that completion envelope. Unknown parents, unknown children, and redundant acknowledgements leave the ledger unchanged. The destination match uses the sending peer established by the polarized endpoint. The root record remains available for observation.

These functions are private protocol implementation. Application payloads cannot be injected as completion envelopes, and application code cannot bypass the driver to close arbitrary records or publish through raw control endpoints. Those authority and emission properties need proof from the actual Core.

Local and network inductive invariants

The local representation invariant states:

  1. Record and child lists are finite, acyclic, and have distinct identifiers.
  2. Each allocator's serial is beyond every serial it has issued; none is reused.
  3. A record's parent and each child's destination remain fixed.
  4. Closed production cannot reopen or accept another direct child.
  5. The single current state stream accounts for pending outputs before they become visible, and submission does not replay an already accepted output.

The network invariant additionally relates all workers' ledgers, pending outputs, native transport state, and active or retained application control:

  1. Every unfinished application computation has its corresponding outstanding record and completion path to the root, including through suspension.
  2. Every pending or accepted work envelope has an outstanding parent dependency; receiver dispatch continues responsibility for that same obligation.
  3. Each logical non-root obligation has one parent, and every live non-root record is connected to the root through outstanding dependencies. There is at most one executing or retained owner of its application control. Registration introduces a fresh child beneath an existing record, so these logical paths have no cycles.
  4. A closed application record has finished its own control and cleanup and cannot admit another direct child. Any remaining producer has a separately registered obligation.
  5. A completion acknowledgement originates only from retirement of a closed, childless record. Its parent dependency stays outstanding until the matching acknowledgement is processed.

Completed records awaiting acknowledgement can be represented by their parent dependency and pending or in-flight acknowledgement rather than a live local record. Already processed duplicate acknowledgements are harmless redundant control traffic. The invariant does not require that traffic to keep a completed application obligation live, but its backing access still needs settlement.

These logical edges are administrative dependencies, not duplicated executable ownership or permission for one worker to access another's ordinary resources. The network invariant includes source control properties: the pure function that writes Closed cannot itself prove the caller's computation finished.

Initially, only the open root record exists. Its child list, the other workers' record lists, and all pending-output lists are empty. It represents fresh admission authority; no application branch or work envelope has started. This establishes the base case. Each legal transition must preserve the local and network invariants under the native contracts stated below.

Registration preservation proof

For a missing or closed parent, registration returns the unchanged ledger. For an open parent p, allocator freshness gives a child q that has never been issued. The insertion and update lemmas preserve identifier distinctness and all unrelated entries. Incrementing the serial preserves freshness.

The new dependency p to q and q's pending work envelope appear together in the successor. Since p already has a path to the root, q acquires one before publication or execution. No previous obligation disappears. Because q is new, adding that edge cannot create a cycle. A proof may order births by transition history; no shared runtime birth counter is needed.

The driver and transport handoff then preserve coverage from pending output through accepted publication and receiver processing. The receiver establishes its record before dispatch. This proves registration preservation relative to the current-state, dispatch, and native handoff premises, rather than from the insertion lemma alone.

Retirement and acknowledgement preservation proof

Retirement has two distinct stages:

  1. Local retirement checks Closed and children Nil. The control invariant establishes that the record's own application code and cleanup finished. Child-list emptiness and the network invariant establish that no descendant application obligation remains. Closed admission prevents new direct children. Remove the record and queue its acknowledgement in the successor; the parent dependency remains outstanding during this handoff.
  2. Matching acknowledgement processing removes that parent dependency. Source emission proves that the acknowledged subtree finished, and faithful transport relates the received envelope to that emission. The removal lemma preserves all other children and records. The logical tree loses only a completed leaf.

After local removal, repeating retirement finds no record. After dependency removal, repeating the acknowledgement finds no matching child. Neither action can discharge unrelated work, and non-reuse prevents a late acknowledgement from matching a newly allocated child with the same identifier.

The source protocol proves the relationship between acknowledgement and actual completion; transport need only preserve the submitted envelope and origin. No separate native law saying that an arbitrary Ack means completion is needed. If source code can forge that envelope or close a live computation's record, the network invariant fails even though the list operations remain correct.

Emptiness and stable application-quiescence proof

The root probe is a pure lookup and pattern match over the current state:

probe_root(L) =
    match root_record(L) {
        production Closed and children Nil => Quiet
        otherwise => Pending
    }

The collection lemma establishes that children Nil means no outstanding root dependencies. By the network invariant, every unfinished application computation or work envelope requires such a dependency. None therefore remains. Root closure prevents new independent work, and there is no remaining covered producer that could create descendant work. This establishes stable AppQuiet.

An open root with no children cannot report Quiet. An old ledger snapshot cannot certify current emptiness; the driver and freshness proof must establish the argument's relationship to current state. The observation law comes from this actual pure function and its invariant, not a native emptiness probe or an ordinary constructor named Quiet.

Passive receive loops and remaining notifications may still exist. Empty pending outputs do not prove that accepted publications or native backing users have settled. The second shutdown phase must still finish worker scopes and endpoints and establish Settled before the enclosing cleanup can return.

Proof integration and remaining native contracts

The paper argument gives concrete lemmas to validate, not an automatic capability of the candidate finite completion analysis. Checked use must authenticate:

  1. Collection and freshness lemmas against their actual Core definitions.
  2. Initialization and transition preservation of the representation invariant.
  3. The driver's current-state flow, publication ordering, and absence of stale reentrant updates.
  4. The correspondence between record closure and actual branch completion, retained control, cleanup, dispatch, and private acknowledgement emission.
  5. Composition of those results into the protocol and release summaries, with reconstruction after imports, specialization, and Core transformations.

Ordinary privacy, callback types, or source assertions cannot supply those proofs. The restricted integration mechanism below proposes checking them against Core and is not implemented. Its rule set and soundness questions are separate from the implemented ordinary protocol. A transform that changes removal, dispatch, or state flow must re-establish the affected lemmas and completion facts.

With that integration, ledger-specific admission can be removed. The remaining external contracts concern:

  • Faithful submission and delivery: native transport does not invent or alter protocol envelopes and delivers each accepted work envelope at most once. Source dispatch preserves that uniqueness. Application data cannot impersonate protocol origin.
  • Acceptance and failure: a definitely unaccepted submission has no deliverable message; acceptance transfers publication responsibility to protected native state. An uncertain outcome remains outstanding and cannot be blindly retried or retired as unaccepted.
  • Publication, receipt, and readiness: copies become visible with a continuous handoff of delivery responsibility; waiter registration and notifications do not lose required work or retain unprotected access.
  • Native closure and settlement: genuine end-of-input follows accepted work, and completed endpoints plus settlement account for every possible future callback, wake, or backing access before release.

Eventual delivery and scheduling progress are additional liveness assumptions, not consequences of the ledger proof. Internal failure still supplies no source cleanup guarantee. The previously required owning continuation store and its transfer/restore semantics remain foundational obligations. Removing admission of bookkeeping laws does not remove those extensions or make application quiescence sufficient for final resource release.

The candidate mechanism checks restricted inductive summaries using untrusted proof plans. Finiteness comes from the private representation invariant, not from the ordinary data type alone.

Initialization and current-state preservation establish that the counter does not reset or reuse an earlier value. RemoveById claim and checking rules

Bind the claim to actual Core function f, its list and status constructors, and its key projection. Let UniqueKeys name the earlier uniqueness predicate specialized to those projected keys. The contract is:

Precondition:
    Finite(xs)
    UniqueKeys(xs)

Normal-return postcondition for f(q, xs) = (ys, status):
    ys = erase(q, xs)
    status is Found exactly when q occurs among the input keys
    status is Missing exactly when q is absent from the input keys
    Finite(ys)
    UniqueKeys(ys)

Define the expected sequence mathematically:

erase(q, Nil) = Nil
erase(q, Cons(x, xs)) =
    if key(x) == q:
        xs
    else:
        Cons(x, erase(q, xs))

This is a logical definition of the claim, not an executable helper or a new Core primitive. Input uniqueness makes removal of the matching head removal of the only matching entry. Sequence equality permits different list-node allocations but preserves the same retained entries in the same order. Merely preserving their identifier set would allow a retained record's phase or parent to change. The checker can track original entry binders to establish preservation without deciding equality of arbitrary payloads.

The initial rule families are:

Rule family Established relationship
Constructor cases Actual Nil/Cons cases and bound components.
Predicate unfolding Finiteness, uniqueness, membership, and absence.
Key equality Equality or inequality from a verified comparison.
Tail induction The claim for a checked smaller input.
Result reconstruction Actual entries, sequence order, and result tag.
Checked helper calls Verified claims with established preconditions.

Each reachable branch must satisfy the contract. A proof plan cannot omit a difficult arm. Facts refer to actual binders and constructor identities, not their source spellings. An induction call must target the function being checked, pass an actual constructor tail of the finite induction input, establish its preconditions, and instantiate the remaining arguments correctly.

A tail binding alone does not establish well-founded descent: for cyclic data, the tail can lead back to the whole input. The Finite premise excludes that case. Calls on the unchanged input, unverified callees, and circular ordinary lemma dependencies cannot assume the claim being checked.

Reconstructing the removal lemma

The validator checks three cases of the actual remove body. Let tail denote the actual pattern-bound tail, independently of its binder's source name.

  1. Empty input. Nil contains no requested entry. The returned Nil and Missing establish the sequence, status, finiteness, and uniqueness clauses.
  2. Matching head. Verified comparison establishes key(x) = q. Input uniqueness establishes q's absence from tail. Returning tail therefore removes exactly the requested entry, preserves every other entry, and correctly reports Found.
  3. Nonmatching head. Verified comparison establishes key(x) != q. Constructor decomposition supplies Finite(tail), UniqueKeys(tail), and absence of key(x) from tail. The actual call on tail may use the induction hypothesis. Its returned ys is erase(q, tail) and introduces no new entry, so key(x) remains absent from ys. The actual result Cons(x, ys) preserves the original head and sequence order, retains uniqueness, and has the required status: membership of q in the original input equals membership in tail.

The reconstruction checks returned values, not just that a suitable constructor appears somewhere in the body. Replacing a retained entry with a same-key entry whose phase changed fails whole-entry preservation. Returning the wrong status fails the result/membership relationship even if the list itself is correct.

The required checker theorem is:

If the checker accepts RemoveById for the actual linked Core definition of f, every normally returning execution of f(q, xs), from a well-formed runtime input with a finite list and unique keys, satisfies the stated postcondition.

The argument must establish local rule soundness under Core evaluation and justify recursive-hypothesis use by induction on the finite input list. Symbolic constructor and branch facts must describe the actual matching semantics, including nominal identities and the actual selected branch. All callee claims and key-comparison facts used by the derivation need their own checked basis. This is a normal-return guarantee, not a network termination or scheduling guarantee. The theorem is a proof obligation, not an established result.

Current-state tracking and actual completion

Collection induction does not prove that a caller uses the current ledger. Track a fact with this schematic meaning:

Current(R, L)

A verified transition returning L1 establishes the successor relationship. Subsequent updates and observations must use that successor or a value proved equivalent to it. This call pattern therefore fails when the transition may change authoritative state:

L1 = transition(L, event)

Copies of L remain ordinary data. They do not retain a permission to update or certify the current ledger after that relationship expires. On a branch proved to leave state unchanged, the analysis can preserve the corresponding equality. This adds neither a source linear type nor a runtime version counter.

Migration as a separate ownership-transfer extension

Pinned workers already provide parallel execution. Moving a suspended computation to another worker requires a separately admitted handoff of unique execution authority and completion responsibility. It is not enabled by sending an ordinary copied Key<N1> to K2.

The migration contract must check the entire owned capture forest, including environments, nested captures, provider state, storage, saved results, and cleanup. External support must remain valid and required exact interpretation must be available at the destination. Thread-affine resources and native or cleanup requirements can prevent a move. Publication must establish receiver visibility and one consumer of the handed-off authority.

The contract must also say whether N remains the logical owner during a checked execution handoff or work is rehomed into another store. Rehoming requires rechecking fixed input/answer ports, administrative store associations, and the completion return path. In particular, Key<N1> cannot become Key<N2> by copying or changing a label. This note derives no such rehoming operation.

Work stealing can later choose among admitted transferable computations. It does not establish their transferability. Moving a whole executor domain would likewise require a contract for all of its owned control and support.

Direct concurrent access to one store by several workers is another extension. It would need synchronized claims and a concurrent observation/closing protocol; atomic slot claims alone do not preserve the single-owner quiescence proof. Neither migration nor shared-store scheduling is required by the baseline.

Each move must preserve unique ownership and completion phase. A progress result must state its library/host assumptions rather than infer termination from these safety properties.

Resource-plus-cleanup composition, Store moves and local drain checking are implemented. The counterexamples for those features are covered by the linked product tests. Wider proof integration, migration and cancellation cases remain unimplemented.

Open questions

  2. What additional authority rules would permit migration or shared Stores?
  3. Which additional interpreter contexts should a future extension admit?
  4. What additional resource payloads should extend the implemented Store operations and their scope, capacity and failure rules?
  5. Which typed checkpoint coverage contracts would justify stronger gas or latency bounds, independently of source syntax and insertion machinery?
  6. Which wait, channel, and host-operation settlement contracts are needed beyond the initial ready-checkpoint fragment? How should the two-worker FIFO provider establish publication, stable end-of-input, and backing settlement, and how should their summaries compose under independent validation?
  7. Which captures can admit migration, and how should a handoff preserve store identity, fixed ports, external interpretation, and completion responsibility? Rehoming and whole-executor movement need their own comparisons.
  8. Is the candidate protocol-fact abstraction sound and sufficiently precise for record parameters, aliases, dynamic key reuse, imported control, and parallel interference? How should it compose checked ledger lemmas with provider laws that still need admission? Relating descendant coverage, reply handoffs, passive service, and backing settlement must not assume that the local E/W domain proves representation invariants. Larger topologies, cancellation, and failing workers remain separate.
  9. Are the restricted claim schemas and induction rules sound and sufficient for the concrete ledger? Can the stated RemoveById normal-return soundness theorem be established from the local checking rules and structural induction? How should bounded normalization, plan dependencies, and transformations preserve checkability without general proof search? The candidate needs an implemented checker; its metadata and remaining claim schemas stay open.
