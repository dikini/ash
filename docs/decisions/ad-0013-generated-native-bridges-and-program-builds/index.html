AD-0013: Generated native bridges and program builds

Development architectural decisions · ash-lang 9a8b73b

Architectural decisions record non-language choices. Each document retains its recorded status and scope. Read the language specification for current language rules.

All architectural decisions
  • ID: AD-0013
  • Status: accepted
  • Related: DN-0037, DN-0042, AD-0007, AD-0008, AD-0011

Decision

Build whole Ash programs as native executables containing compiler-private checked Core, the existing evaluator and generated typed Rust bridges for passive foreign declarations. The specification defines the supported source boundary; the tool guide defines build inputs and invocation.

The target is x86_64-unknown-linux-gnu. Link static archives and ordinary shared dependencies through the native linker. Generate extern "C" pointer calls and actual void returns from the supported signatures. Do not introduce a generic ABI engine, native Ash backend, stable Core wire format, compiled Ash library format or runtime library resolver.

Compiler, library and program responsibilities

The front end checks a passive source graph and independently validates typed Core with immutable defining symbol facts. Imports preserve exact declaration, operation and signature identities without performing native initialization. Bindings supply profile, signature and native link name. Ordinary Ash functions, handlers and cleanup supply protocol, null/length checks and lifetime policy. The compiler does not verify native behavior or manage foreign ownership.

Program build takes the checked graph and explicit native inputs, emits typed Rust bridges and an evaluator host, then compiles and links an executable. Private images require the matching compiler/runtime version; no cross-version compatibility is promised. Startup independently reconstructs and validates Core and exact bridge registrations before evaluation. No live pointer is an image constant. Ordinary source handlers retain nearest-handler precedence.

Generated images support generic cells, lexical regions and retained control. They do not support Network scopes or operations. Pinned-worker programs execute through the source-native interpreter, including admitted host callbacks.

Bytes exposes one readonly pointer with managed backing retained through the synchronous call. Address preserves a data pointer without integer conversion; Unit results use actual void. Retention of a Bytes pointer beyond a call requires the module to retain the original backing, and managed backing must not be mutated or freed. No hidden length, terminator or inferred ownership is supplied.

One canonical contract and explicit phases

Keep compile, prepare and build phases explicit. Immutable checked symbol facts remain shared authority for module summaries, Core operands and generated bridge plans. Binding tables authenticate the original symbol allocation and exact signature rather than selecting by native link name alone. Independent Core validation rejects stale or transformed correspondence.

Reuse keys include exact source/dependency identities, profile, compiler version and native build inputs. Phase completion or cache reuse does not establish external binary validity. Ordinary non-native execution remains available; foreign execution requires an explicitly generated and linked host.

Native preparation and startup gas

Use input-derived cumulative work allowances at the modular compiler phase owners and for native preparation and startup. The accepted policy is:

preparation gas = 850 * (admitted source UTF8 bytes + validated main Core nodes)
resolution gas  = max(327680, 80 * (canonical loaded source UTF8 bytes, including builtins))
source gas      = 10000 * (canonical loaded source UTF8 bytes, including builtins)
final gas       = 800 * (the same canonical source UTF8 closure)
builder gas     = max(327680, 12 * (the same canonical source UTF8 closure)), per program arena
rewrite gas     = 16 * (the same canonical source UTF8 closure), per compiler arena
Core gas        = 25000 * (the same canonical source UTF8 closure)
startup gas     = 118 * (canonical image bytes + canonical expected-fact bytes)

Source checking sizes the complete canonical loaded source closure before checking. Count each loaded module once, including builtin sources, rather than import edges or aliases. Pay one unit per source and one for the census in a finite source-count-derived bootstrap, then carry that work inside 10000*S through every module, source copy, closed entry and retained provenance. This is the total allowance; the historical ten-percent deficit does not apply. Final elaboration and independent compiler Core each pay their own identical resident-length census before work begins and carry it inside their respective 800*S and 25000*S totals. Apply this at both Pure and Effect modular driver entries. Their existing remaining-credit loans debit the same cumulative meter. These totals have no historical extra ten percent.

The paid census also returns its canonical byte count for a separate 16*S rewrite meter, installed once when an empty compiler-owned arena is constructed. All rewrites in that arena consume the same meter. A fresh compiler arena inherits only the allowance, never spent work or unused Source/Final credit. Reject multiplication overflow. There is no floor, intercept, refill or extra margin. Generic builder, standalone and private-image defaults remain unchanged; resolution, constraints and other construction budgets remain separate.

Program arenas also receive a separate primary payload-construction allowance max(327680, 12*S) from that paid census. Install it before catalog precharges; each arena starts with fresh independent primary and rewrite meters. Primary construction remains excluded from the Source/Final reports. Standalone, default and private-image primary limits retain their existing capacities.

Context

The earlier foreign experiments established useful bridge and evaluator evidence but coupled it to numeric, owner, output, status, window and host policy. The smaller boundary retains generated typed calls and existing compiler/evaluator machinery while placing binding policy in ordinary Ash. Experimental lifecycle or full SQLite results do not enlarge the supported ABI.

Consequences

  • Adding a binding within the supported mapping changes Ash declarations and native inputs. A new ABI shape or target requires separately authorized work.
  • Native validity, retention and release remain binding assumptions. Address is neither a resource nor proof of allocation or lifetime.
  • Ordinary resources, cells, cleanup, handlers, work/depth limits and independent source/Core/image validation retain their existing responsibilities.
  • There is no mandatory header-checking tool, FFI-specific artifact protocol, protected approval or security receipt gate.
  • Numeric ABI, out-pointers, callbacks, structs and foreign text/memory interpretation remain unsupported gaps.

Verification

Require real pointer/void/Bytes calls, ordinary source-handler overrides, missing binding refusal, null/equality, unsupported-signature rejection and ordinary cleanup on normal, error and checked-discard paths. Exercise static/shared native inputs, repeated source-independent embedded-image startup and malformed Core/image/registration rejection without weakening validation.

The direct SQLite version/source-id getter canary is required. Non-null/equality observations do not read its text or establish full database coverage. Numeric and out-pointer requirements of open/prepare remain gaps. Inspect generated Rust for exact typed pointer/void signatures and absence of library-specific policy or a runtime C shim. Preserve normal depth-42/43 preparation and startup checks under the gas policy above. Final-head independent review and the normal full workspace gate remain required before integration and milestone closure.
