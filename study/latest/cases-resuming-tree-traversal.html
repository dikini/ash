Resuming tree traversal

Suppose a caller needs the first association in a dictionary, then wants to stop and decide whether to ask for another. Balanced lookup finds one key along a logarithmic path. Traversal has a different goal: visit every association in key order, allowing the caller to stop between visits.

Use the three associations two:20, one:10, and three:30. Inserting them into the preceding dictionary gives this tree. The following sketches describe its shape and traversal; they are not executable Ash.

          two:20
          /    \
     one:10    three:30

The first request should return one:10; a later request should return two:20, then three:30. A fourth request should say that traversal is finished. An empty dictionary should be finished on the first request.

Returning a complete in-order list would visit all n nodes and construct all n list forms before the caller receives the first association. That costs O(n) source work and new list state up front. Instead, each request can return one association and a value describing where to continue. The caller keeps that value while paused and supplies it to the next request. What information must it contain?

Represent the unfinished traversal

Recall the visitation order at a node, called in-order traversal:

visit left subtree; produce current association; visit right subtree

To find the first entry, descend from two to one. Before descending, save two:20 and its right subtree: both must be visited after the left subtree. At one, save one:10 and its empty right subtree. Reaching its empty left subtree finishes the descent. The saved entries now form a stack, with one at the front and two behind it.

A frame records four things: the pending key, its value, the right subtree still to visit, and the remaining stack. Work in its left subtree belongs before that association; the descent records it in frames ahead of this one. Generalize those fields over the dictionary’s existing K and V types. These are checked, non-executable excerpts from the defining module and the clients used below; the commands run their complete source files.

type FrameStack<K, V> =
    NoFrame
    | MoreFrame(K, V, Dictionary<K, V>, FrameStack<K, V>)

NoFrame means that no entry remains. MoreFrame puts one pending association in front of the rest. Its third field is a whole dictionary, not a list of its entries. Saving that subtree preserves the work for a later request without traversing it now.

For the example, the prepared stack has this schematic shape. one, two, and the named subtree stand for their actual values:

MoreFrame(
    one, 10, Empty,
    MoreFrame(two, 20, subtree rooted at three:30, NoFrame)
)

The outer frame is the next entry to produce. After producing it, traversal must handle its saved right subtree before the remaining frames. This is the stack invariant: the front association, then its right subtree, then the remaining stack describe exactly the unfinished in-order sequence. The type records the fields; the operations must preserve their intended order.

Wrap the stack in a public iterator type:

pub opaque type Iterator<K, V> =
    Iterator(FrameStack<K, V>)

Inside the module, Iterator exposes the frame stack to its operations. Outside it, the opaque type gives callers a name for the state while withholding its constructor. This is the same opaque-declaration boundary used for the dictionary. A caller obtains states through the public operations rather than assembling frames itself.

The saved state is ordinary immutable data. Each returned iterator is already prepared for its next request. There is no delayed expression to force: the remaining work happens when the caller explicitly invokes an operation.

Determine the operation types

Start with the caller’s two operations. Preparing a dictionary gives an iterator with the same key and value types:

pub iterator : Dictionary<K, V> -> Iterator<K, V>

Advancing it either reports completion or returns one association together with the state for the next request:

pub next : Iterator<K, V> -> Option<((K, V), Iterator<K, V>)>

Read the successful payload from the outside in. Some holds a pair whose first component is (K, V) and whose second is Iterator<K, V>. None has no payload. Keeping the later iterator is what makes another request possible; keeping the current one allows a caller to repeat the same request.

These operations need no Order<K> requirement. Insertion has already established the tree’s ordering; traversal follows its structure. It neither compares keys nor repairs a malformed ordering.

One private operation must prepare the next frame. It takes a subtree and an existing stack of later ancestors, then returns the prepared stack:

push_left : Dictionary<K, V> -> FrameStack<K, V> -> FrameStack<K, V>

The second input matters when resuming: after visiting a saved right subtree, traversal still owes the associations recorded in the remaining stack. Starting each descent with NoFrame would discard those ancestors.

Calculate preparation and one step

First express the public composition. An initial traversal has no ancestors, so prepare the whole dictionary over NoFrame and wrap the result:

iterator dictionary = Iterator(push_left dictionary NoFrame)

The wrapper does not postpone push_left. Ash evaluates arguments before application under its strict application rules, including arguments supplied to constructors. This call completes the initial left spine before returning an iterator, while leaving other subtrees unentered.

Now calculate next from its input’s two possible stack forms. An empty stack has no association to return:

next Iterator(NoFrame) = None

For a frame, the key and value are ready. Remove that frame, prepare its saved right subtree over rest, and package the association with the later iterator:

next Iterator(MoreFrame(key, value, right, rest)) = Some(
    ((key, value), Iterator(push_left right rest))
)

This equation explains the resume point: the saved right subtree comes next, then the previously saved ancestors. An empty right subtree simply exposes rest. A nonempty one contributes its own leftmost entries in front of rest.

It remains to fill in push_left. At Empty, there is no earlier association to place in front of the supplied stack:

push_left Empty stack = stack

At a node, its left subtree must come first. Save the current association and right subtree in one frame, then descend into left over that frame:

push_left Node(ignored_color, left, key, value, right) stack = {
    let later_stack = MoreFrame(key, value, right, stack)
    push_left left later_stack
}

The local later_stack names precisely what remains after the left subtree. The node’s color does not affect in-order visitation, so the pattern calls it ignored_color. The recursive call handles a smaller subtree in a finite acyclic tree; eventually its empty left edge returns the prepared stack.

Why does this preserve the order? The empty case contributes no entries. For a node, assume the recursive descent prepares its left subtree in order. Placing that preparation before the new frame gives the left entries, then the current association, then its right subtree, then the supplied stack. Those are exactly the required pieces in their required order. Combined with the two next equations, each request removes the first unfinished association and leaves the rest ready for another request.

For the three-key example, the prepared frames change as follows. This is a schematic trace, not a captured tool result. The front frame appears first:

Request Returned association Prepared frames afterward
Start No association yet one over two, with three saved by two
First next one:10 two, with its right subtree at three
Second next two:20 three, with an empty right subtree
Third next three:30 NoFrame
Fourth next None No later iterator in the result

The second request is the one that enters the saved subtree at three. Pausing before that request leaves that descent undone.

Collect a sequence to check the calculation

A client can test the repeated requests by collecting them into the familiar List<(K, V)>. This deliberately finishes traversal; it lets one observation show its order. The public names come from these imports:

import dictionaries as Dictionaries
import dictionaries (impl Order)

The first import supplies Dictionaries as a qualifier. The separate impl Order import supplies the ordering implementation used to build the dictionary. The iterator operations themselves do not require it.

The collection operation consumes an iterator and produces a list:

collect : Dictionaries.Iterator<K, V> -> Dictionaries.List<(K, V)>

Ask for one entry. None gives the empty list; Some((entry, later)) gives a list whose head is entry and whose tail collects from later:

collect current = match Dictionaries.next current {
    Dictionaries.None => Dictionaries.End
    Dictionaries.Some((entry, later)) => Dictionaries.More(entry, collect later)
}

Passing later is essential. Recursing on current would request the same entry again. The structural argument above says that each successful request removes one unfinished association, so this recursion reaches None on a finite dictionary.

A second operation converts an optional result to a completion flag:

is_finished : Dictionaries.Option<A> -> Bool
is_finished Dictionaries.None = true
is_finished Dictionaries.Some(ignored) = false

Together these observations determine the entry’s result type:

main : Unit -> (Bool, Dictionaries.List<(Dictionaries.Natural, Int)>)

The first component checks an empty dictionary; the second records the ordered sequence. Inside main, construct the three existing natural-number keys:

    let one = Dictionaries.Next(Dictionaries.Zero)
    let two = Dictionaries.Next(one)
    let three = Dictionaries.Next(two)

Prepare the empty dictionary with an explicit key and value type:

    let empty_dictionary : Dictionaries.Dictionary<Dictionaries.Natural, Int> = Dictionaries.empty ()

Supply the nonempty entries in the example’s insertion order:

    let entries = Dictionaries.More(
        (two, 20),
        Dictionaries.More(
            (one, 10),
            Dictionaries.More((three, 30), Dictionaries.End)
        )
    )

Finally build the dictionary, inspect the empty iterator, and collect the nonempty one:

    let dictionary = Dictionaries.build entries
    let empty_finished = is_finished (Dictionaries.next (Dictionaries.iterator empty_dictionary))
    (empty_finished, collect (Dictionaries.iterator dictionary))

(Next(Next(Zero)), 20)

These observations agree with the trace. Their order follows from in-order traversal and the inherited dictionary ordering invariant. The iterator made no comparison and performed no validation or sorting. A malformed value constructed inside Dictionaries could produce an out-of-order sequence.

Retain a state and resume it twice

A later iterator is an ordinary immutable value. To check that using it does not consume it, retain the state after producing one and call next on that same state twice. Each call should produce two:20 with a state ready for three:30.

The observation needs three fields: the retained iterator, the first call’s result, and the second call’s result. Each call has the same optional association-and-iterator type derived above. Unexpected records an empty initial result, which the nonempty example should not produce:

type ReplayObservation =
    Unexpected
    | Replay(
        Dictionaries.Iterator<Dictionaries.Natural, Int>,
        Dictionaries.Option<(
            (Dictionaries.Natural, Int),
            Dictionaries.Iterator<Dictionaries.Natural, Int>
        )>,
        Dictionaries.Option<(
            (Dictionaries.Natural, Int),
            Dictionaries.Iterator<Dictionaries.Natural, Int>
        )>
    )

The client uses the same two imports. Its checking operation has this type:

replay : Dictionaries.Iterator<Dictionaries.Natural, Int> -> ReplayObservation

One request obtains the state after the first association. In the successful case, save after_one in the observation and use it as both subsequent inputs:

replay start = match Dictionaries.next start {
    Dictionaries.None => Unexpected
    Dictionaries.Some((ignored_first, after_one)) => Replay(
        after_one,
        Dictionaries.next after_one,
        Dictionaries.next after_one
    )
}

ignored_first names the association that positions the experiment; the experiment observes what happens from the returned state. Both subsequent calls receive after_one, so neither uses the state returned by the other.

This client returns the observation directly:

main : Unit -> ReplayObservation

Inside main, define one, two, and three as before. This time insert in ascending order, which the balanced dictionary also turns into a root two with children one and three:

    let entries = Dictionaries.More(
        (one, 10),
        Dictionaries.More(
            (two, 20),
            Dictionaries.More((three, 30), Dictionaries.End)
        )
    )

Compose building, preparation, and the replay check:

    replay (Dictionaries.iterator (Dictionaries.build entries))

The tree shape predicts a saved frame for two retaining the subtree at three. Both subsequent calls should prepare equivalent frames for three. Run the complete client:

ash resuming-tree-traversal/src/02-retained-state.ash

The following are the three fields of the single captured Replay result, followed by its type. Its first field is the saved iterator:

Iterator(MoreFrame(Next(Next(Zero)), 20, Node(Black, Empty, Next(Next(Next(Zero))), 30, Empty), NoFrame))

The front frame contains two:20, a right subtree containing three:30, and NoFrame. That subtree remains a Node; it has not yet been converted to frames. The second field comes from the first next after_one:

Some((Next(Next(Zero)), 20), Iterator(MoreFrame(Next(Next(Next(Zero))), 30, Empty, NoFrame)))

It returns two:20 and prepares a frame for three:30. The third field comes from the second next after_one:

Some((Next(Next(Zero)), 20), Iterator(MoreFrame(Next(Next(Next(Zero))), 30, Empty, NoFrame)))

It shows the same association and prepared state. Both calls descend into the same saved right subtree and construct a frame for three; retaining state does not memoize that remaining source work. The complete result’s type is:

ReplayObservation

Iterator, MoreFrame, Node, and their fields are visible in these observations. Ash’s structural observation rules render nominal values even when their constructors are unavailable to the entry module. Constructor payload tuples appear as fields in this output, which is why the captured Some displays the association and iterator as two fields. Seeing those forms supplies no constructor binding to client source. Test that separate boundary next.

Test the source boundary in patterns and values

First try to inspect the iterator with a constructor pattern. The importer may name Dictionaries.Iterator<...>, but the Dictionaries.Iterator occurrence in this match arm should be rejected during name resolution. The type name is public, but the constructor that would expose the frame stack is withheld.

import dictionaries as Dictionaries

main : Unit -> Int
main () = {
    let dictionary : Dictionaries.Dictionary<Dictionaries.Natural, Int> = Dictionaries.empty ()
    match Dictionaries.iterator dictionary {
        Dictionaries.Iterator(ignored_stack) => 1
    }
}

Count the explicit pending work

Let d be the number of Node forms on one left-spine descent. push_left applies once at each of those d nodes and once more at the terminal Empty, for exactly:

d + 1 push_left applications
d MoreFrame constructions

Let h be the largest number of Node forms on a path from the root to Empty. Initialization descends one left spine, so d <= h. It constructs at most h explicit MoreFrame forms and one Iterator wrapper. The O(h) state bound counts only those explicit frame forms. Each frame also retains an existing key, value, saved right-subtree value, and rest-of-stack value. Much or all of the original n-node dictionary may remain transitively reachable, so the claim is not an O(h) bound on all reachable data or runtime bytes.

For a successful next, popping the first frame is one frame operation. If the saved right subtree has a d_i-node left spine, preparing the returned state pushes d_i new frames. The current node followed by that descent lies on one dictionary path, hence:

1 pop + d_i pushes
1 + d_i <= h

The call also constructs one new Iterator wrapper and one Some result. Its worst-case explicit frame work is therefore O(h). An exhausted call selects NoFrame and constructs None without pushing or popping a frame. The remaining ancestors and the newly prepared left spine form one pending tree path, so every returned state still contains at most h explicit frames.

Now count one complete linear traversal of a finite n-node dictionary. Every node enters a frame exactly once: nodes on the initial left spine enter during initialization, and every other node enters when a saved right subtree is prepared. Each of those frames later leaves exactly once when its association is produced. The totals, including initialization, are therefore:

n pushes + n pops = 2n frame operations

This exact count includes n = 0: the empty traversal moves no frame, and its final None call adds no frame move. For n > 0, distribute the 2n operations over the n produced pairs:

2n frame operations / n produced pairs = 2 frame operations per pair

The quotient gives two frame operations per pair across the complete linear chain. Dividing a sequence’s total work across its steps this way is called amortized analysis; here it yields amortized constant frame work. One individual next can still pop one frame and push d_i frames, so its worst-case work remains O(h). The complete sequence uses frame work within O(n + h).

The amortized account does not extend across arbitrary branching histories. Calling next again on an older state can repeat its saved right-subtree left-spine descent and construct the corresponding frame path again, as the replay did.

The preceding case established h <= 2 log2(n + 1) for a valid red-black dictionary under its ordering and balance premises. Inheriting those premises makes initialization and one worst-case next use logarithmic explicit frame work. The complete traversal remains linear because it still produces all n associations.

These return and traversal claims apply to finite acyclic dictionary spines reached through completed public operations and to iterator states produced from them. A defining module can construct malformed or constructor-guarded cyclic spines despite opacity under Ash’s static recursive block-group rules. An initial left-edge cycle can prevent iterator from returning. A cycle in a saved right subtree may permit earlier results and then prevent the next call that enters it from returning. The spine premise does not require acyclic keys or values: a cyclic key or value payload can be returned without traversal; later structural observation may render an active-path revisit as <cycle>.

At source level, a frame supplies existing key, value, subtree, and stack values unchanged to a new constructor application. The account counts named source applications and constructor applications only. It establishes no elapsed-time, machine-instruction, native-stack, tail-call-optimization, runtime-byte, heap-layout, pointer-identity, physical-sharing, garbage-collection, compiler-layout, or compiler-optimization property. It also introduces no mutation, laziness, hidden mutable cursor, or infinite-data claim.

Practice and continue

  1. Draw the initial MoreFrame stack for the three-entry dictionary built in 01-sequence.ash. Then draw the states returned after each successful next.
  2. Draw a valid tree whose root’s right subtree has a nonempty left branch. Predict the frames pushed after the root is produced, including their order.
  3. Starting from the fact that every node enters and leaves one frame, derive the n pushes, n pops, and 2n total without counting the final None as a frame operation.
  4. Explain why constant amortized frame work applies to one linear chain of states but not to a history that repeatedly resumes the same older state.

This iterator keeps pending work in last-in, first-out order: the leftmost unfinished association must come before its ancestors. What changes when a traversal must retain pending work in first-in, first-out order instead?
