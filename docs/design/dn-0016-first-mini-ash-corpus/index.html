DN-0016: First Mini-Ash Corpus Stratum

Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes
  • ID: DN-0016
  • Status: exploring
  • Related: DN-0002: Core Representation, DN-0003: Parser Architecture, DN-0005: Surface Function Definitions, DN-0006: Initial Type System, DN-0007: Data and Pattern Typing, DN-0008: Typed Core and Elaboration, DN-0015: Mini-Ash Phase

This design note is informative. It governs a provisional evaluation corpus and bounded experiments. It does not define current Ash, accept syntax or semantics, or accept a parser, Core, typing, or evaluation architecture.

Question

What evidence did the first Mini-Ash corpus stratum provide for the retained monomorphic pure-functional increment, and which questions remain useful for later strata?

Context

DN-0015 directs Mini-Ash research through a growing corpus. The first stratum combined primitive values, variables, immutable bindings, monomorphic functions, and applications because together they expose scope, evaluation order, typed representation, source provenance, and diagnostics. That stratum now has a retained implementation; the current specification, not this note or its evidence documents, defines its language behavior.

The corpus is split into linked evidence documents rather than placing grammar, typing, dynamics, diagnostics, and representation discussion in one note. Stable case IDs connect the documents. A case remains provisional until an accepted change proposal selects it as evidence for an implemented semantic increment. The retained V-001 through V-008 cases and their rejection boundary have completed that lifecycle. Other probes and uncased alternatives in these documents remain informative.

Constraints

  • The corpus must distinguish language questions from implementation questions.
  • Each case must connect source, static facts, dynamic behavior, and diagnostics without treating any one candidate representation as authoritative.
  • Equational and inline operational definitions remain distinct surface mechanisms with different definitional strengths. Equivalent cases may lower to the same or similar callable Core without erasing clause, match, body, provenance, diagnostic, or tooling differences prematurely.
  • Definition and application grouping follow the function type. Successive equational patterns and applications follow nested arrows; an operational comma-separated parameter tuple and its application follow one product domain.
  • Provisional grammar uses ebnf fences, and provisional typing and operational rules use sequent fences when they are inference rules. Prose must explain every formal fence.
  • The retained first-stratum boundary excludes recursion, algebraic data types, general pattern matching, polymorphism, effects, modules, mutation, and I/O. Boolean-pattern and parameter-grouping probes may cross that boundary only to expose the defining relationship between equation clauses, explicit matches, nested arrows, and product-domain operational functions.
  • Functions and any evaluation state remain inspectable data. Retained designs must not represent Ash functions or continuations as Rust closures.
  • A typed representation candidate must state and validate scope, type, and source-provenance invariants before evaluation.
  • Adding a corpus form should exercise feature-local parser, representation, typing, and evaluation components rather than require unrelated central rewrites.

Candidate directions

Shared corpus with selective probes

The leading direction defines common programs, rules, traces, errors, and representation pressure before implementing component probes. Written analysis settles a question when it exposes a clear difference. Code is reserved for Rust encoding, composition, recovery, traversal, validation, or evaluation behavior that remains uncertain.

Competing vertical interpreters

Multiple disposable end-to-end interpreters would expose boundary costs early, but they would duplicate work and make a difference harder to attribute to one component. A thin vertical trace may test an interface, but a full competing interpreter is not the default experiment.

Semantics and Core before surface syntax

Constructing terms directly would isolate typed representation and evaluation, but it would postpone parser and diagnostic pressure. Independent Core probes may construct inputs directly, while the shared corpus continues to carry provisional source and source-located failures.

Evidence package

The first-stratum index owns case identity and links the evidence slices:

  • programs define representative valid and rejected inputs;
  • grammar records one provisional surface grammar and unresolved alternatives;
  • typing records provisional declarative judgments and expected case outcomes;
  • dynamics records provisional small-step rules and representative traces;
  • diagnostics records source spans, structured reasons, recovery expectations, and rendered-message criteria;
  • representations records invariants and concrete pressure on candidate boundaries.

These documents form one comparison corpus. None has independent semantic or architectural authority.

Evidence and experiments

Each component experiment must name one question, the case IDs it uses, the candidates it compares, the distinguishing criteria, and its disposal condition. Parser, representation, typechecker, evaluator, and transformation probes may proceed independently when they do not share an unresolved choice.

The comparison records:

  • which invariants types express and validators check;
  • whether grammar and compiler changes remain local when a case adds one form;
  • precedence, ambiguity, recovery, span, and source-provenance behavior;
  • ownership, traversal, rewriting, and validation mechanics in Rust;
  • typechecking and evaluation complexity;
  • diagnostic structure, rendered clarity, and cascade control;
  • agreement between direct evaluation and the provisional reduction traces;
  • downstream extension seams and redesign risks without implementing future features.

Prototype code is disposable. Record measurements, counterexamples, and conclusions in the governing design note, then remove the code. Retaining a component requires an accepted architectural decision and an implementation task. Retaining language behavior additionally requires an accepted change proposal whose implementation, tests, executable path, and specification update land together.

The completed consistency review found no blocking disagreement in the named cases. The retained increment selected and narrowed the first-stratum boundary; its current grammar, typing, dynamics, and rejection behavior now live in the normative specification. The broader evidence corpus also records deliberately unretained probes such as product-domain operational functions, Boolean patterns, anonymous multi-parameter functions, and products above arity two. Those forms remain future design pressure and require a later semantic proposal before they can become current Ash.

The railroad and sequent renderers still need the conformance updates recorded by AD-0003. Those external tool updates do not change the canonical Markdown or block component research.

Convergence gates

  1. Review the corpus for agreement among programs, grammar, typing, dynamics, diagnostics, and representation pressure. This gate is complete.
  2. Compare component candidates against only the cases needed to answer each question. This gate is complete.
  3. Accept the specification method and converged component architectures in separate decisions. This gate is complete through AD-0004 to AD-0008.
  4. Propose and accept the first user-visible semantic increment. This gate is complete; Git retains the implemented proposal as transition evidence.
  5. Implement the accepted increment as a retained single-file executable. This gate is complete in the current specification, retained implementation and tests, and ash tool guide.

Open questions

  • How far can the retained closed pure Core dialect and its operation-family seam extend before later effects require a different composition boundary?
  • How do the retained event and tree types scale when later syntax adds layout, patterns, products, or richer recovery obligations?
  • How should the retained first-order evaluator machine represent one-shot handlers first, then any more complex continuation kinds required by later semantics and typing?
