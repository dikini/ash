DN-0036 readiness for Ash-authored foreign interfaces

Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes

This review starts design work under DN-0037, using Main 5c5fb914ff3ee729305a2d8a2df86ff348725e84 and inspected worktree evidence on 2026-10-09. It is informative evidence and a proposal brief. It selects no new syntax, accepts no compiler architecture and authorizes no implementation.

The user selected a first target: an end-to-end Ash-authored copying SQLite binding on one host ABI, with general borrowing and wider Arena graphs left for later proposals. The user also selected generated native bridges as the first execution/linking direction. This scope is a first DN-0037 checkpoint, not completion of the whole foreign-authoring program.

The later ffi-ash milestone scope selects x86_64-unknown-linux-gnu, generated Rust runtime bridges, optional separate C/header checks, whole-program checked-Core embedding, and native-buffer and minimal-arena source libraries alongside SQLite. AD-0013 records the converged build boundary. The retained CP-0022 transition is implemented on the milestone branch; Main integration remains separate. The historical evidence below keeps its original pins and limitations.

Two library cases, one common boundary

The user agreed that unfinished Arena work is not a prerequisite for continuing DN-0037. SQLite remains the first complete authoring delivery. A minimal native arena lifecycle is the second worked design case from the outset: declare configuration, opaque state, acquisition, usage and release in Ash and execute them through the same generated bridges. This case must observe native calls and ownership transitions, rather than fabricate a source result.

The common declaration and bridge model must express both libraries without SQLite-specific or arena-specific compiler dispatch. The arena case tests that configuration, access, refusal and release contracts transfer beyond SQLite. It does not require broader graph storage or completion of the unverified Arena recovery branch.

A native arena supplies storage; a region describes the scope and dependencies under which access is valid. Declaring an allocator's ABI alone does not supply region safety. The design must keep native ownership, scoped identity and access discipline distinct, so that later borrowing and containment rules can state which owner and validity interval justify an access.

General borrowing, typed arena allocation, containment and wider graphs remain follow-on semantic work. They are not first-delivery capabilities or hidden prerequisites. The proposal must document these exclusions and identify where their future contracts meet the initial scoped-access model.

Assessment

There is enough DN-0036 evidence to start a bounded proposal. There is not yet evidence for the central DN-0037 authoring claim: an author can bind a supported native library using Ash declarations and native build inputs without writing a library-specific Rust adapter, Rust manifest or C shim.

DN-0036 established the resource and evaluator side of that boundary. SQLite provides a realistic reference binding and comparison corpus. The main missing mechanisms are source-authored foreign contracts, generated ABI bridges, temporary native storage and validity rules, and native build/link integration.

Finishing all wider Arena experiments is not a prerequisite for this copying checkpoint. Their failures and missing borrowing contracts limit broader claims, and supply negative cases for the design. They should not silently expand the first proposal.

No deficit is used in those receipts, but there is little headroom in the largest phases. A native-authoring design must measure added declaration, conversion and validation work, rather than assume these programs have become cheap.

What still lives in hand-written native code

The native adapter, Rust implementation, build script and C shim identify the work that an Ash-only binding must replace or express through common primitives:

  • Raw foreign signatures and ABI representation checks, symbol requirements and linkage. The current audited target is x86_64-unknown-linux-gnu.
  • Stable NUL-terminated input buffers and explicit-length byte buffers, checked narrowing, nullable handles, output slots and partial acquisition.
  • SQLite-specific sequencing, including checking a suspect column result before another API call changes the relevant diagnostic.
  • Input copying with SQLITE_TRANSIENT. The existing shim supplies a special destructor-function-pointer sentinel; a plain scalar/opaque-pointer profile must explicitly account for it. This does not require calling back into Ash.
  • Returned column pointer/length validity, immediate independent copying, UTF-8 checks and bounded diagnostic copying.
  • Statement protocol and owner dependencies. Finalization consumes a statement even on its reported error; refused connection close retains it.
  • Native guard destruction for unpublished or quarantined state. That is separate from running source completion or inventing a successful result.

The proposed allocation of responsibilities is: author-declared ABI facts and foreign assumptions; ordinary Ash protocol, conversion and reporting policy; common checked primitives for memory/calls/ownership; and common toolchain support for building and linking. Generated glue may implement the primitives, but cannot acquire extra authority from being generated.

Starting proposal brief

The first proposal should state the user-visible result before choosing syntax:

Given supported C headers and a library binary, an author writes the selected SQLite binding and lifecycle policy in Ash, declares native requirements, and builds/runs an Ash client through common tools. No hand-written library-specific Rust manifest, Rust adapter or C shim is required.

Headers are author input. The compiler checks Ash declarations; a C parser is not a prerequisite. Header/binary matching and successful symbol resolution do not prove that native code obeys its declared memory or consumption assumptions.

Candidate initial ABI shapes are fixed-width scalar arguments/results, opaque handles, nullability, byte/string buffers, output parameters, and the required SQLite sentinel. The tested Linux x86-64 GNU profile is a sensible first candidate. General aggregate-by-value ABI, variadics, native callbacks, asynchrony, dynamic loading, owner transport and a stable Ash ABI remain outside that candidate. Static archives and ordinary link-time shared-library dependencies are native inputs; they need not imply a runtime dlopen feature.

The source design must identify separately:

  • Native dependency and symbol identity, target ABI and configuration.
  • Foreign representation, including addresses that carry bounded access rather than becoming ordinary integers or transferable ownership.
  • Call effects and explicit foreign assumptions: initialization, retention, invalidation, consumption/refusal and failure.
  • Ash-facing conversions, protocol and result types, reusing ordinary functions, effects, handlers and resource definitions where possible.
  • Checked module-summary and Core facts, including original authority and independent validation after transformations.
  • Runtime guard and temporary-storage transitions, plus observable failure behavior after a native effect has already occurred.

Data-access disciplines must be language contracts

The user requires the language to distinguish borrowing, copying and other access disciplines. The first implementation may support a small subset, but it must not erase that distinction behind a native pointer type or Rust-only adapter convention. This requirement remains when general borrowing is added later.

Treat representation, access discipline and ownership transition as separate typed facts. Two calls can have the same C signature while one copies an input and the other retains its address. Conversely, a call may borrow its input and return an independent copied result. A single per-operation "copying" flag is therefore insufficient; the contract belongs to each affected input/result and its owner or validity window.

Discipline Meaning the language must distinguish First checkpoint
Independent copy The result owns its Ash-managed contents and has no dependency on the source native storage. Copying an address, handle or embedded reference is not an independent copy. Required for admitted scalar, Bytes and String results. No promise of arbitrary graph copying.
Borrow for a synchronous call Temporary input storage stays valid during the call; the foreign callee is declared not to retain that access. Access permission and length/encoding remain explicit. Required for SQL, paths and transient input buffers.
Temporary returned access for copying Native-owned memory is read only within an admitted copy window, under the exact owner and API validity rules, then converted into independent data before the window closes. Required for selected column/diagnostic copies. This does not expose a general escaping native view.
Retained borrowed input or reusable borrowed view Access depends on a live owner and additional invalidation/mutation restrictions after the initial call. Explicitly unsupported in the first checkpoint; general borrowing needs a later contract.
Ownership consumption or transfer A native ownership transition occurs; it cannot be reproduced by copying an access value or constructing a report. Only the required guarded acquisition and finish dispositions. General source owner transport remains excluded.

The initial raw SQLite declarations must distinguish native input copying through SQLITE_TRANSIENT from retained input through SQLITE_STATIC. The former lets the temporary input buffer close after the call under the declared foreign contract; the latter must reject in this first binding rather than accidentally receive the same contract. Neither the function signature nor pointer constness establishes retention or validity.

Returned column data requires more than "borrow for one call": obtaining its pointer and querying its matching length are separate selected calls. The design must describe that finite copy window, permitted queries and invalidating operations. It must reject stepping, resetting, finalizing or other declared invalidation before copying completes. It must also prevent a window from escaping through a result, closure, evidence or captured control. A native diagnostic has its own validity and query-order contract; do not reuse the column rule merely because both contain bytes.

Public checked contracts must preserve these roles across imports and generic helpers. Core must retain enough facts to validate them independently. Runtime guards must enforce the admitted ownership/validity transitions. User-facing inspection and diagnostics should distinguish a copied value, a live temporary borrow and an unsupported retained borrow, rather than expose compiler phases.

The exact source forms and whether disciplines are expressed by constructors, declaration associations, effects or a combination remain design questions. The acceptance condition is behavioral: unsupported or invalid borrowing cannot be silently admitted as copying, and valid copying does not retain an unnecessary native dependency. Foreign adherence to the declared contract remains an explicit assumption.

Generated bridge boundary

The proposed path is checked Ash foreign declarations → target-resolved bridge plan → generated native wrappers → compiled and linked execution host → existing Ash evaluator. This does not require compiling ordinary Ash functions to native code. The host supplies the generated bindings to the generic runtime.

Each wrapper must correspond to an exact original foreign operation and its complete checked ABI signature. Generation must preserve that association through compilation, linkage and runtime registration. Symbol names alone do not authenticate bindings. Preflight checks must finish before associated resource acquisition; imports remain passive.

The native compiler checks emitted call sites against the declarations and selected target representation. This catches incompatible generated types and unsupported target shapes earlier than a descriptor-driven runtime call. It does not establish that an incorrectly declared external binary obeys the ABI, or that native code obeys retention, invalidation and consumption assumptions. A header parser is not required. AD-0013 places optional generated C/header verification in a separate authoring command, rather than the runtime call path.

The generated wrapper handles the admitted ABI boundary: scalar conversion, opaque handle representation, temporary buffers, output storage and return conversion. Ordinary Ash definitions express SQLite protocol, error mapping and lifecycle policy using checked primitives. The generator must contain no SQLite symbol dispatch or special ownership policy. Source-declared sentinel representation, including SQLITE_TRANSIENT, remains an obligation of the bounded profile rather than a reason to retain a handwritten SQLite shim.

The first semantic draft must specify four connected transitions:

  1. A foreign declaration establishes representation facts and explicit access, initialization and ownership assumptions; checking produces an immutable contract with its defining origin.
  2. Target resolution produces a bridge plan only for supported representations and native inputs. Compilation and linking produce an executable binding authenticated against that plan.
  3. A call receives admitted access and initialized storage, executes once, and records native ownership disposition even if result conversion fails.
  4. Copying closes temporary access after independent data has been admitted; acquisition publishes a guarded owner; completion consumes it or quarantines the same retained owner with its dependencies.

These are design obligations, not selected source syntax. Outstanding choices include output initialization on each outcome, partial acquisition destruction, finite pointer/length copy windows, sentinel declarations, and how build inputs and target facts are exposed through the public tools. Formal proofs remain a separate workstream.

Simplification and phase discipline

Use one canonical checked foreign contract to feed module summaries, Core operands and target binding, rather than retaining separate source, manifest, runtime and generated-glue descriptions that must be reconciled repeatedly. Which views can be shared follows their actual authority and lifetime.

The preparation-cost investigation supports encoding distinct processing states and immutable inputs in types. A candidate implementation discipline separates unchecked declarations, checked contracts, target-resolved plans and executable bindings. Transitions should consume or borrow the appropriate prior phase, making duplicate preparation and use of unfinished data difficult to express. This is a candidate architecture, not new Ash syntax or accepted implementation.

Branding data does not validate it. Reuse must be tied to exact input identity, target/configuration and dependency versions. Scope owners remain per activation. Independent Core checking must still reconstruct its obligations; transformed inputs cannot reuse authority for a different projection. Host teardown and foreign-call side effects are not cached preparation.

Prefer ordinary Ash wrappers for SQLite protocol and error mapping. Keep common memory/call primitives small and typed. Do not duplicate the compiler, create a closed-only binding engine, or require arbitrary graph Layout support to admit the copying profile.

Evidence required before acceptance and delivery

  1. Define the exact semantic delta from current spec/, including adoption or bounded replacement of experimental resource/Bytes/String behavior.
  2. Work one complete binding from declarations through resolution, typing, public summaries, Core, native binding, initialization, calls and completion. Explain every remaining trusted primitive and foreign assumption.
  3. Preserve the five complete SQLite programs, native values/copy counts, completion order, failure classifications and retained-owner observations. Pair the new path with the Rust reference path; do not weaken useful cases.
  4. Demonstrate missing/wrong symbols, unsupported target/configuration, wrong representations, invalid lengths/UTF-8, uninitialized outputs, partial acquisition, stale access and forged authority with causal diagnostics. Binary symbol presence alone cannot diagnose every falsely declared ABI. Pair copy versus retained-input declarations with the same raw signature; distinguish independent contents from copied handles and reject a native view used after its declared invalidation or escaping its copy window.
  5. Recheck independent Core and transforms, resume/discard/cleanup, finish conversion failures and dependency-ordered quarantine/destruction.
  6. Use a contrasting small native API within the same declared profile to test that generation/dispatch contains no SQLite-specific policy. It need not be another complete library implementation or broaden the ABI.
  7. Conduct the headers-plus-binary walkthrough using documented Ash tools, without compiler source knowledge or per-library hand-written host glue. Record declaration burden, generated code, copies, build/link time and compiler costs separately from native behavior and formal claims.

The next design step is to turn these roles into precise typed contracts for the selected generated-bridge route. Surface syntax should follow those choices. Only then can a complete proposed semantic transition state the resulting specification truth and required product checkpoint.
