Explicit Kinds and Higher-Kinded Parameter Evidence

Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes

This report records implementation evidence for the second bounded lib-ash increment: explicit kinds and higher-kinded declaration parameters. It is informative, not normative. The Ash specification alone defines the current language. Git history retains the accepted proposal, task, design record, and execution plans removed after the reviewed product checkpoints retained their results.

This report alone did not close the complete lib-ash milestone. At the second- increment checkpoint, method-local type parameters, multi-parameter interfaces, determination, associated outputs, defaults, the combined library corpus, and the final library simplification audit remained separate work. Later integrated increments close the revised milestone without changing this report's evidence scope. This increment received no lib-ash tag.

Implemented boundary

The kind language has Type and right-associative function kinds. Declaration binders may carry an explicit kind:

type Option<A> =
    None
    | Some(A)

keep<F : Type -> Type, A> : F<A> -> F<A>
keep value = value

Nominal, interface, global, operational, and implementation declarations retain their written binder order. A present global or implementation binder list is complete: every binder used by that declaration header must appear exactly once, and every listed binder must be used there. When the list is absent, the resolver introduces binders from free type names in first-occurrence order.

Every omitted declaration kind annotation, and every binder introduced by an omitted global or implementation binder list, is fixed to Type. Ash does not infer a kind for those binders. This is the current phase-dependent language constraint, not a commitment against a later bounded declaration-local inference rule.

The increment adds neither kind polymorphism nor type lambdas. It does not infer function kinds from application, perform higher-order unification, or introduce source forall or explicit term type application.

Canonical identities and applications

Each resolved source type binder receives a module-qualified identity whose local ordinal follows source order across nominal, interface, global, and implementation declaration families. Written binder order and implicit first-occurrence order remain owner-local authority. The regression at 8c11cd3 proves both properties when parameterized families interleave; strict Core registry validation continues to reject forged identity-to-source order.

Surface type application may retain several comma-separated arguments, but resolution folds them left into the one canonical unary form:

F<A, B>  =  Application(Application(F, A), B)

This structural application is not Core scheme instantiation. One Core TypeApplicationNode supplies all arguments to one complete outer rank-1 scheme simultaneously. Tests reject partial outer-scheme instantiation while admitting partial nominal or variable application when the surrounding kind expects the residual function kind.

Kind environments and checking

The shared total kind engine uses four fixed environments:

  • DELTA maps declaration or generated scheme binders to declared kinds;
  • OMEGA maps transient inference identities to their fixed kinds;
  • XI maps canonical nominal identities to derived or frozen kinds; and
  • IOTA maps interface identities to their canonical parameter record, including its TypeVariableId and declared Kind.

Primitive types synthesize Type. Variables and inference identities use DELTA and OMEGA. Nominals use XI. Unary application requires a function kind whose domain equals the argument kind and returns its residual codomain. Tuple and function components must have kind Type, and the complete tuple or function type also has kind Type. Ordinary value annotations require Type. An interface argument is checked against the selected interface parameter's declared kind rather than the ordinary value-type rule.

One resolved kind stage derives every local nominal kind before it checks any type-bearing declaration fact. The stage authenticates canonical binder records, constructor payloads, interface methods, globals, requirements, implementations, and declaration-order completeness before ResolvedModule construction. Checked schemes and body-free facts retain ordered identity-kind pairs.

Inference, matching, and evidence

Every fresh inference identity receives one fixed OMEGA entry before the identity appears in a type. Ordinary fresh identities have kind Type; scheme instantiation and constructor patterns copy the defining binder kind. Eligible local generalization copies fixed kinds into generated outer-scheme binders. Recursive and otherwise ineligible locals remain monomorphic.

Unification remains first-order. Before it publishes a solution it checks the candidate against the inference identity's fixed kind. It traverses both children of canonical applications and admits partial constructors without synthesizing a type lambda. Zonk and generalization preserve those fixed kinds and reject missing, duplicate, conflicting, or escaping inference facts.

Implementation matching treats goals as rigid and binds only candidate parameters. Each retained substitution must have the defining binder's kind. Overlap independently freshens both candidates. Selection admits only complete, inference-free interface goals and preserves abstract, exact-current, then concrete candidate priority. Prerequisites, selected roots, substitutions, checked methods, and occurrence evidence are authenticated again at their owning boundaries.

Summaries and linked facts

A checked dependency publishes body-free kind facts only after its complete body succeeds. Transparent nominals retain their ordered parameters and constructor family. Hidden and opaque nominals retain frozen body-free kind facts without exposing constructors or materializing private declaration rows. Imported interface, global, and implementation facts retain the exact defining identities and kinds used by checking and evidence selection.

Physical constructor schemes have one transfer lifecycle:

checked export summary -> imported fact -> disposal before linked Core

The linker does not retain a redundant constructor-scheme carrier. Linked nominal and constructor registry facts are sufficient for independent Core kind derivation after authenticated summaries have been consumed.

Linked evidence validation checks every canonical type-variable record, nominal family, interface fact, global scheme, implementation fact, selected evidence root, substitution, method, route, and occurrence before it exposes the capability used for Core synthesis. A failed check publishes no validated program.

Linked Core authority

AD-0009 accepts one private ordered owner-to-parameter fact in the shared immutable registry for each non-empty resolved global scheme. The fact contains only the stable term owner and ordered resolved parameter identities. Canonical variable records remain the only authority for kind, spelling, and source origin.

This is an implementation boundary, not language syntax or a normative storage model. The specification requires the observable validation relationship: a resolved outer abstraction must be the immediate initializer of its owning RecursiveBind member, its identities and order must equal the authenticated global scheme exactly once, and every authenticated owner must be consumed. The specification does not expose the private row type, its position index, or its physical storage.

A sequential Core Bind cannot claim resolved-global authority. Nominal parameters retain their separate ordered nominal ownership. Interface binders erase before Core. Implementation-method parameters and locally generalized binders use generated Core identities.

Generated Core identities are local to their TypeAbstractionNode, matching outer Forall, lexical body, and applications. A complete capture-free fresh substitution is valid alpha-renaming. Independent validation does not authenticate the elaborator's original generated identity, source span, or allocation ordinal as external authority.

Both identity traversal and literal folding rebuild expression nodes while sharing the immutable registry. Each result passes fresh module-aware Core validation. Kinds, schemes, abstractions, applications, and resolved-owner facts erase before evaluation. No evaluator value, frame, lookup, transition, or failure mode changes.

Migration

Every predecessor-valid omitted kind annotation and absent global or implementation binder list remains valid without source edits. Omitted binders retain Type and their prior owner-local order. Explicit Type annotations and explicit lists are compatible spellings of that boundary.

The compatibility corpus proves exact library and CLI observations for:

  • omitted nominal, interface, global, operational, and implementation kinds;
  • implicit global and implementation binder order;
  • explicit Type annotations and explicit list order;
  • contextual nominal Type beside kind Type;
  • ordinary rank-1 instantiation and higher-kinded partial application; and
  • linked modules using explicit implementation imports from the predecessor increment.

Intentional migrations replace saturated-shape assumptions with canonical application inspection and replace predecessor kind-blind failures with the structured kind reasons above. No compatibility grammar or second compiler path remains.

Tampering and negative evidence

Private mutation matrices reject each retained relationship independently:

  • canonical variable identity, spelling, origin, kind, module, and source order;
  • nominal owner, parameter order, constructor family, payload, kind, and hidden or opaque closure;
  • checked and summary interface, global, implementation, method, requirement, and selected-evidence mirrors;
  • imported fact identity, route, visibility, parameter, application, and kind;
  • resolved-global owner facts that are empty, missing, extra, duplicated, reordered, wrong-owner, wrong-position, nominal, interface-only, or left unconsumed;
  • Core abstraction, outer scheme, application arity, argument order, kind, occurrence, scope, provenance, and immediate recursive owner;
  • generated binder inconsistency, duplication, capture, shadowing, or escape; and
  • identity and literal-folding transform results, each rebuilt independently from the original validated program.

The named tamper anchors are exhaustive_summary_orders_indexes_aliases_and_owners_fail_before_local_checking, exhaustive_public_and_hidden_summary_carriers_fail_before_local_checking, and fused_constructor_scheme_authentication_rejects_every_independent_type_obligation in src/resolve/module_tests.rs; rejects_every_task8_kinded_linked_diamond_carrier_before_core, rejects_every_surviving_linked_nominal_and_constructor_mirror_before_core, linked_registry_rejects_every_resolved_global_parameter_row_mutation_before_core, and linked_registry_canonical_malformation_precedes_a_later_row_mismatch in src/evidence_validation.rs; linked_core_rejects_each_independent_registry_row_structure_mutation, linked_core_rejects_coherent_resolved_binder_owner_swap, linked_core_rejects_coherent_resolved_binder_reorder, linked_core_sequential_bind_cannot_claim_a_resolved_global_row, linked_core_rejects_each_independent_generated_binder_mutation, and linked_core_preserves_registry_graph_binder_and_abstraction_precedence in src/core/validate.rs; and rejects_registry_identity_order_spelling_and_source_forgery in tests/core_validation.rs. kind_inventory_is_closed and transient_kind_site_owners_are_source_anchored in tests/architecture.rs make the carrier inventory itself fail closed.

Intentional exclusions and remaining pressure

At this checkpoint, the complete lib-ash milestone remained open and untagged; later integrated increments close the revised milestone without claiming a tag.
