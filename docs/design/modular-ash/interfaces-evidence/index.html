Causal semantic model

Parsing and projection retain one-parameter interfaces, ordered methods, ordered global requirements, implementation heads, ordered prerequisites, and implementation equations. Resolution replaces their source spellings with module-qualified identities. It allocates an occurrence-local empty evidence slot for each resolved constrained-global or interface-method occurrence and retains the exact complete-import declaration or targeted selector used by an imported occurrence.

Checking authenticates top-level function interface shapes, constrained schemes, implementation ownership, prerequisite decrease, effective-environment non-overlap, membership, method types, and bodies. Substituting an implementation or requirement argument preserves each method's outer Function, so implementation equations and flattened evidence slots remain callable. Evidence selection then resolves each rigid obligation from lexical abstract requirements, the exact current implementation, or concrete available implementations, in that order. The owning obligation-closure boundary fills each structural slot exactly once. This includes an eligible unannotated anonymous-function initializer before local generalization, as well as constrained globals and implementation methods. Checked definitions retain the filled occurrence with their checked group through linking; no later stage joins spans or repeats selection.

A module publishes a body-free immutable summary only after all its declarations and bodies check. The summary preserves public interface and method facts, public implementation facts, stable identities, checked schemes, ordered prerequisites and method mappings, provenance, and the hidden nominal or interface closure needed to authenticate those facts. It does not transport a body, private name environment, private implementation, or an implementation imported from another module. A dependent therefore sees public implementations from its direct dependencies only, regardless of complete versus targeted import syntax.

Linking combines complete checked definitions and registries from every module. Linked interface-evidence validation authenticates the retained identities, occurrence-module availability, exact direct import edge, substitutions, prerequisite trees and termination, method order and mappings, scope, types, and provenance before Core synthesis. It does not infer, select, or repair evidence. Core synthesis then flattens every requirement or prerequisite in declaration order and, within it, every interface method in declaration order. At an occurrence, generated type applications precede evidence applications, which precede source value arguments. The existing Core validator runs after this synthesis.

Abstract evidence lowers to a lexical evidence binder. Concrete evidence lowers to the selected implementation-method binder. Generic concrete evidence first type-applies the recorded substitution and then supplies recursively lowered prerequisite terms. Implementation-method binders join the defining module's existing recursive group, so recursion, mutual recursion, global-to-method calls, and method-to-global calls use ordinary lexical recursion.

Stable identity, summaries, and availability

The semantic identity families are deliberately distinct:

  • InterfaceId combines a defining ModuleId and source declaration ordinal;
  • MethodId combines its InterfaceId and method declaration ordinal;
  • ImplId combines a defining ModuleId and source declaration ordinal;
  • ImplMethodId combines its ImplId and exact MethodId;
  • RequirementId combines a global BinderId or ImplId owner with a requirement declaration ordinal; and
  • each implementation method also has a hidden defining-module BinderId used by ordinary Core variables and recursive binding.

Aliases, targeted names, complete-import qualification, and alternate graph routes do not change these identities. Alternate direct routes deduplicate the same ImplId; they do not create an overlap with itself. A public implementation is available in its defining module and in a module with an authenticated direct dependency edge to its summary. It is not re-exported through an intermediary.

Hidden summary closure preserves identity without granting source access. A public constrained global or public implementation may use a public interface defined by a direct dependency. Its checked summary retains that foreign public interface's parameter and method shape to authenticate the public fact, but it does not re-export the interface or create a source binding for it. A private interface may constrain a private global declared in its defining module, but it can never occur in a public constrained global. Separately, a public implementation may retain a private nominal head identity while its private spelling and constructors remain unavailable to an importer. An opaque public type remains nameable, but its constructors and representation remain unavailable in an external implementation body. These carriers authenticate composition without turning a checked summary into a source module signature.

Structural evidence and validation

The structural selection is part of each checked resolved occurrence, not a side table keyed by source span. Empty slot clones have independent one-shot cells; clones of a filled slot share the same immutable flat plan. The plan records an abstract requirement identity or a concrete implementation identity, its ordered type substitution, its ordered prerequisite subplans, and its ordered implementation-method identities. Checked definitions and method groups own those occurrences across the checked-module and linked-program transitions.

The independent validator rejects a linked program before Core synthesis when any retained evidence fact is forged or inconsistent. Its checks cover:

  • source declaration ordinals and distinct identity families;
  • occurrence-module availability, public/private status, and the exact direct dependency route admitting an imported implementation;
  • selected goal and rigid implementation-head substitution;
  • prerequisite count, order, tree ownership, proper decrease, and absence of shared or cyclic corruption;
  • interface-method count and order, ImplMethodId mapping, and hidden binder uniqueness;
  • abstract requirement owner and argument;
  • linked global and implementation-method schemes, lexical type scope, nominal arity, and absence of inference or unbound forall; and
  • source and import provenance for the selected occurrence and fact.

Validation consumes the recorded plan. It neither consults source spelling to reselect evidence nor treats an import span as an implementation identity. Interface, implementation, method, and requirement identities are released only after this validation has authorized ordinary Core synthesis.

Diagnostics, provenance, and privacy

Constraint diagnostics retain the selected source occurrence as primary and a typed causal chain through its interface declaration, exact admitted import, selected implementation, and implementation method. Qualified and targeted occurrences retain the import alias or selector item actually used; another route to the same stable declaration is not substituted for it. Nested unsatisfied prerequisites and cycles retain the declaration-ordered selected implementation chain.

Diagnostic provenance is intentionally narrower than semantic summary closure. A private dependency implementation is unavailable and its source span does not enter an importer diagnostic. A public implementation available only to an intermediate direct dependent is not exposed as a transitive route. A hidden foreign-interface shape can authenticate a public fact without re-exporting the public interface, while a hidden private nominal identity does not make its spelling or constructors available. Neither closure makes implementation bodies or import paths renderable to the caller. Existing structured reason ownership and CLI rendering remain in place.

Resources and stack ownership

One driver-owned constraint-work budget spans imported summary admission, checking across the graph, linking, and linked interface-evidence validation. The implementation charges retained facts and planned work before allocation or traversal. Imported overlap follows authenticated route order. Candidate inspection is bounded even for a wide same-interface environment, and evidence construction charges nodes and ordered slots before retaining them. The linked validator continues the same budget rather than resetting it at the stage boundary.

This interface-and-constraint budget is distinct from existing inference, Core-construction, and Core-validation budgets. Resolution and checking retain their existing type-work budgets for inference and type storage. No Core node is constructed until linked interface-evidence validation succeeds. Core synthesis then uses the existing bounded Core builder, and the independently bounded Core validator checks the completed program afterward. An interface- evidence failure therefore stops before both Core-construction and Core-validation work; neither Core budget is spent to authenticate interface metadata.

Cycle detection owns semantic failure precedence over later resource exhaustion. Properly decreasing generic prerequisite chains use explicit work stacks. Evidence plans, deep substitutions, checked-body audits, selection chains, validator worklists, rejected payloads, and replacement paths have small-stack destruction witnesses. These cases make the bound graph-wide and independent of module partitioning or recursive Rust call depth.

Removing recursive nested-arrow search changes the exact checker boundaries. One interface exhausts the shared constraint budget at 36 units and succeeds at 37. An implementation-method substitution exhausts it at 76 and succeeds at 77. The 10,000-level invalid outer-method fixture exhausts its local check at 7 and reaches interface.method-not-function at 8 on a 64 KiB stack. Dropping that fixture also exercises ResolvedModule::drop and discard_resolved_interface_iteratively, so the rejected resolved type is not destroyed through recursive Rust calls.

Source syntax erases separately from semantic identity. Import spellings and interface declarations cease to be source operations after resolution, while their stable identities remain through checking and linked evidence validation. Linked evidence validation builds its registry locally, uses it to authenticate occurrences, and does not store it in the validated capability. Core synthesis borrows that capability inside an explicitly typed driver block. The block also owns the display-registry clone, type-display computation, synthesis finish, and the eager wrapper drop. The drop records the last intentional capability use; block exit is the ownership boundary before independent Core validation. Only Type, String, and UnvalidatedProgram cross it. Compiler-exhaustive destructuring checks the capability's exact ResolvedModuleProgram payload, and a driver weak-reference witness proves that only the unchecked Core program owns the resolved registry when Core validation begins. The authenticated relationships have already become ordinary Core structure, so this boundary releases checked bodies, evidence, routes, the display clone, and remaining checked interface metadata without changing Core or evaluation. The linked validator's registry and indexes already ended locally after successful authentication.

Locality and maintenance

Interface-specific semantic machinery is concentrated in these production boundaries:

  • src/interface.rs owns identities, constrained schemes, flat plans, head matching, and their local resource accounting;
  • src/resolve.rs and src/resolved.rs own namespace identity, summary closure, import availability, occurrence slots, and provenance;
  • src/elaborate.rs owns declaration and implementation checking, linking, and Core synthesis;
  • src/evidence.rs and src/evidence_audit.rs own structural selection and checked-body completeness;
  • src/evidence_validation.rs owns the independent pre-Core authenticity boundary; and
  • src/driver.rs orders linking, evidence validation, Core synthesis, Core validation, and evaluation under the graph-wide budget.

returns exactly those eight production files. Surface grammar and projection remain at the existing lexer/parser boundaries. Core and evaluator source are protected by the closed-inventory architecture guard rather than by a parallel interface dispatch subsystem.

Findings retained and released

Retained findings are:

  • stable semantic identities, rather than paths or spans, are the transferable currency across summaries, alternate routes, linking, and validation;
  • a body-free summary needs hidden checked identity closure distinct from public source nameability;
  • direct dependency edges own implementation availability, while alternate direct routes deduplicate one implementation identity and intermediaries do not re-export it;
  • occurrence-local one-shot evidence lets selection happen at its checking owner and survive without a span-keyed side table or lowering-time search;
  • an independent pre-Core validator is required because a structural plan alone cannot authenticate linked identity, route, scheme, scope, type, and provenance claims;
  • flattened lexical functions preserve method order and prerequisites without requiring a dictionary value or evaluator dispatch rule; and
  • a graph-wide resource budget must cross summary admission, checking, linking, and validation to remain independent of module partitioning.

Released alternatives are source dictionaries, span-keyed evidence maps, lowering-time reselection, implementation re-export, summaries containing bodies or private scopes, route-specific implementation identities, runtime registries, and a new interface Core or evaluator family.

Exclusions and downstream pressure

This increment does not add associated types, projections, normalization, multi-parameter or higher-kinded interfaces, default methods, specialization, priorities, negative implementations, first-class source dictionaries, named implementation values, interface objects, module signatures, inferred exported requirements, constrained main, cross-module recursion, dynamic loading, registration, discovery, a new Core node, a new evaluator rule, or dead-code elimination.

Its retained unspecialized trace and closed inventory provide a baseline for a later, separately authorized core-versus-library audit. That audit may compare an existing Core behavior with a library interface after this increment is complete and specified. This work does not begin the audit, choose a migration, or authorize specialization.
