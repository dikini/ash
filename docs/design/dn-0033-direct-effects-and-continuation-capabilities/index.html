DN-0033: Direct Effects and Continuation Capabilities

Development design notes · ash-lang 9a8b73b

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

  • Status: exploring
  • Related: DN-0031, DN-0032, DN-0009, DN-0012, DN-0013

This note proposes a direct operational foundation. It defines no current Ash semantics, accepts no architecture, and authorizes no implementation. The sequential rules below are a candidate calculus; the resource, duplication, transfer, and scheduling extensions have explicit proof obligations. No full one-shot type-safety theorem or complete inference algorithm is claimed.

The one-shot formalization develops the structural judgments and checked proofs for this note's first kernel. Its evidence status distinguishes completed lemmas from remaining obligations; the schematic predicates below are not proof assumptions.

Question

Can one expression language, an ordered stack of interpretations, and separately checked continuation capabilities explain effects, providers, resources, disposal, and hooks without computation wrappers or conversions between computation models?

The candidate uses ordinary values, lexical binding, operation requests, and handler boundaries. Sequencing pushes a frame. A request captures frames. Resumption reinstalls them. Ownership checking determines which additional actions may manipulate a capture. There is no Comp type constructor, source return operation, selectable bind, transformer stack, or cross-model lift.

The presence of Bind in current Core is compatible with this account: it is the syntax and evaluation of a sequential local binding. An optional denotational account does not define the operations of this calculus.

Context and constraints

Current semantic authority is the specification:

  • Bindings evaluate the initializer before entering the suffix, with a saved lexical environment.
  • Effects use exact parameterized identities and exhaustive, result-preserving handlers. The hidden capability must be consumed on each normally completing clause path.
  • Handler execution selects the nearest exact interpretation, moves the segment through its boundary, runs the clause outside that segment, and restores it on resume.
  • Resources separate duplicable access handles from unique scope completion authority.
  • Cleanup distinguishes armed actions from running actions and required unfinished completion.
  • Hooks use ordinary handlers and applications, with separate registration owners.

The Core dialect decision requires typed structure and independent validation. The relevant representation is PureComputation::Bind in the shared substrate, and request, handler, resume, discard, resource, registration, and cleanup nodes in Effect Core. The finite control graph in capture checking is evidence that current checking already follows control positions beyond a local operation signature; it does not establish inference for the proposed extension.

The important pressure from DN-0031 and DN-0032 is mixed control: a request can capture intervening handlers, owned scopes, and unfinished clause work. A continuation contract must constrain this entire segment. Properties of just its returned value or effect row cannot suffice.

Existing evidence transfers within its scope: exact matching and lexical instantiation in effect tests; owner movement and surviving cleanup context in cleanup interactions; callback order and registration-site context in hook tests. None proves multi-shot, escaping, or asynchronous behavior.

Candidate directions

The working candidate is a direct handler calculus with one evaluation stack per running task. The ordered interpretation stack is the projection of accepting frames from that stack; it is not a second, independently mutable registry. Suspended tasks and captures retain segments, so extended execution can have several stacks without changing the expression language.

Compare it with ordinary wrappers around current scopes. Wrappers are a useful baseline for provision composition, but cannot by themselves introduce the missing ownership and transfer rules. Indexed families of computation models remain an optional mathematical comparison, not the source or Core foundation. Do not insert model-conversion terms to make mixed handlers compose.

Syntax and binding

This is a small administrative presentation. x names an ordinary value, k names a continuation capability, i is an exact instantiated effect identity, p is a provider value, and h is a fresh dynamic handler activation. Existing functions, data, matches, and primitive operations are inherited from Core. Strict operands are displayed as values; a general operand is evaluated once with an ordinary binding at the same scope position.

The grammar separates the sequential kernel from explicit capability extensions. split, park, and suspend are candidate administrative forms, not currently executable Ash syntax. Lexical classes such as variable, value, exact_instance, provider, and contract are parameters to this grammar. The semicolon in the grammar is formal sequencing punctuation, not a proposal to add semicolons to Ash source.

Grammar source (EBNF)
expression ::= value
  | value "(" value ")"
  | "let" variable "=" expression ";" expression
  | "perform" exact_instance "." operation value
  | "handle" expression "with" provider
  | "resume" continuation value
  | "discard" continuation
  | "resource" identity "," variable "=" provision ";" expression
  | "cleanup" value ";" expression
  | "split" continuation "as" continuation "," continuation ";" expression
  | "park" continuation "in" owner
  | "suspend" ;
provider ::= "handler" exact_instance "under" contract "{" clause { clause } "}" ;
clause ::= operation variable "with" continuation "=>" expression ;

A provider is an exhaustive clause closure with its lexical values, type/row instantiation, and declared control contract. Creating it installs nothing. Installing it creates h; each request creates a fresh k. Provider code identity, exact effect instance, handler activation, and continuation identity are distinct. A provider containing restricted captured authority is itself restricted; syntax for a provider value does not imply unrestricted reuse.

For the base calculus, a handler preserves its body's result type A. A clause for op : P -> Q receives x : P and a capability whose input is Q and whose resumption result is A. Normal body return passes its value through. There is no implicit result transformer or new source return clause.

A provision establishes an access value, an exact identity substitution, an interpretation, and any completion obligations. The resource form abbreviates that protocol and its scopes; it does not make every provider allocate state. The resource's formal identity and access variable are bound only in the body. Setup executes in the preceding scope. A stateless provision can have no physical allocation and an empty completion action.

Four bindings therefore coexist without four sequencing operators:

Binding What it binds Dynamic significance
let x = e; n An evaluated value Saves and later enters the suffix
resource r,x = P; n Fresh instance and access Runs establishment and introduces obligations
handle n with p An interpretation boundary Changes exact request selection inside n
op x with k => n Operand and captured control authority Runs a clause outside the captured boundary

The contextual notation [r:E, s:F].e from DN-0032 remains useful for describing open syntax. Applying it substitutes request instances, types, access values, evidence, and dependencies together. It is not yet a first-class rank-1 Ash value. Aliasing reusable access is permitted where its contract allows it; identifying two independent owners requires a separate structural justification.

Machine state and stack

Write M = <S, eta, e, K>. eta contains lexical values and instantiation; S records resource state, continuation records, and ownership; K is a stack with its nearest frame on the left. S is mathematical bookkeeping, not a requirement for a new runtime registry or a universal user-visible state object.

The relevant frames are:

Frame Retained information
B(x,n,eta) A pending value binding and suffix
H(h,i,p) Exact accepting interpretation and provider environment
U(g) Clause completion group owning its outstanding continuation tickets
O(a,P) Resource completion authority and its protocol
F(a,action,phase) Cleanup authority: armed or running
Close(z) Required completion of an in-progress close
Finish(o,v) Required normal provision completion and its saved result

Strict applications and other Core contexts contribute their ordinary frames. For the current one-ticket fragment, U(g) corresponds to the current clause boundary with its live/consumed capability. A group is bookkeeping for explicit splitting; it does not permit copying that boundary freely.

A live continuation record is S(k) = live(g,Q,A,chi,C,support), where C is the cut stack segment, chi is its allowed control behavior, and support includes retained access, lexical instantiation, provider dependencies, and required residual interpretation. Owning edges and non-owning access edges are different. Recursively owned captures are included in the ownership closure.

The key invariant is that every live completion obligation has exactly one owning location: active control, one captured segment, a clause group, or an explicit receiving owner. Access aliases create no owning edges. Capturing a segment transfers those owning edges without duplicating them.

Sequential transitions

The following rules suppress unchanged components of S. Provider values and operands have already been evaluated. Fresh names are chosen outside the support of the current configuration. Ordinary value evaluation resolves variables and closures through eta as in Core.

Binding and installation

Binding pushes an ordinary frame. Handler entry pushes an accepting frame; normal return simply removes it. These rules determine sequencing directly.

Request and forwarding

Decompose the stack as L ++ [H(h,i,p)] ++ Kout, with no frame in L accepting the requested exact instance. This includes builtin accepting boundaries in the nearest-match test; a nearer builtin is not skipped. The displayed rule is the source-provider case. Its builtin counterpart retains the specified authenticated primitive transition.

The request boundary uses the existing structural judgments rather than one undivided admissibility predicate. SourceCut(i,K,C,Kout) identifies the exact nearest source boundary. WellFormed(K,Q,R,ambient) checks ports, support, ownership uniqueness, names, shape, delimiters and external resources. The operand-access premise checks that its resources occur in visible(Kout) ++ ambient. The selected request must also have the structural SourceAdmission.Code.request derivation for this actual cut, including its callback, owner-bound, cleanup-budget, selected-clause, retained-continuation and recursively checked clause-body premises. A separate usage check authorizes the declared one-shot actions.

The rule is a mathematical characterization of admitted execution. It does not propose deferring these premises to a fallible runtime check. The one-shot structural boundary proves that CaptureAdmission, predecessor well-formedness and ticket freshness construct a well-formed live boundary with exact owner insertion and outside payload support. It assumes the payload annotation; expression checking must derive that annotation separately. The two Fits premises are the split produced by capture_type_decomposition. Resumption is proved for the actual well-formed clause prefix. Disposal separately requires Discardable for that prefix and a fresh close owner. The source-level Code.request judgment and independent usage check remain necessary; the lower-level capture theorem does not prove all future clause executions safe.

The selected boundary and all intervening interpretations are absent while the clause runs. A direct same-instance request in that clause therefore forwards outward, unless the clause itself installs a nearer interpretation. No forward or lift primitive is necessary.

Resumption and clause return

Each ticket is one-use. Multi-shot behavior will be explicit ticket splitting, not reactivation of a consumed ticket. Kc is the entire current clause continuation, including work after resume. The live record owns a cut stack, not a copy of Kc. The rules below use the structural proof representation of the clause boundary and saved record: Kc contains the live ticket boundary, and Kc' is the same actual prefix after that ticket becomes spent.

resume-control

The actual-prefix WellFormed premise supplies Fits, support, uniqueness, names, shape and delimiters for the full clause front. structural_resume proves C ++ Kc' well formed, the exact owner permutation and absence of the consumed ticket. For transferred continuations, checking must also cover the destination interpretation context. Restored execution eventually returns through C into the clause continuation; it does not abandon the clause suffix. This is deep resumption.

Disposal

Disposal consumes a live ticket, skips its expression suffix, and executes a close plan. close(plan) walks owned obligations in structural inner-to-outer order, including recursively owned captures, with each obligation visited once. It does not traverse access aliases as ownership.

close(plan) is internal control, not an ordinary callable capturing Kc'. It finishes with unit, after which Close(z) is removed and the original clause continues. structural_discard proves this abstract-plan boundary for the actual clause prefix. The current lexical runtime separately uses the structural close certificate retained by SourceAdmission.Code.request; an abstract Discardable plan does not establish that runtime admission. Closing transitions have these requirements:

  1. Non-owning expression frames are skipped. Captured source handlers are not reinstalled, and abandoned callbacks are not run.
  2. A resource or registration owner performs its specified release/removal. Still-enclosing builtin resource interpretations remain usable until their own closing positions, as in current Ash.
  3. An armed cleanup owner changes to running before invoking its action through ordinary evaluation. Finishing the action discharges that owner.
  4. A running cleanup or unfinished Close cannot be abandoned or duplicated. It can be captured and resumed once; suspension preserves its obligation.
  5. Completion must not skip an outside owner or a scheduled resume on which an outside completion depends. Each invoked action must retain the exact required interpretation at its closing position.

Initial preparation failure leaves the capability unconsumed. Once actions start, the calculus does not promise rollback, replay, or eventual completion. Internal host failure keeps the current specification's weaker guarantee.

The annotated one-shot kernel develops this closing obligation as the structural judgments Closes and Discardable. It checks each invoked action against the materialized close suffix, rejects retained structural ticket uses in cleanup closures, and proves preservation of the annotated control invariant at discard. It also proves per-invocation interpretation correspondence. The expression layer now derives retained resource and free-ticket dependencies with substitution proofs. Residual-request inference and preservation of complete source-derived admission through arbitrary callback evaluation remain open.

The expression-bearing machine now invokes actual cleanup values and projects its transitions to the ownership kernel. Checked traces cover outward capture during cleanup and disposal that reads a retained cell before release. This establishes concrete execution and ownership accounting for those paths. The access layer proves joint ledger and expression/control support preservation for every finite execution satisfying explicit local release, capture, and disposal checks. For closed executions it excludes completed resource references in current expressions and retained frames, including dormant captures. Deriving those checks from source admission remains open. The usage-execution layer below joins continuation usage to this same admitted execution relation; the joint layer also combines types and effects for individual transitions and concrete executions.

Independent continuation capabilities

A control contract is a set of permitted actions with associated evidence, not one ordered mode label. The selected provider declares what its clause may do; the captured segment determines what it can safely support. Admission requires both. A declaration cannot confer ownership rights that the segment lacks.

Axis Permission or obligation
Resumption Consume a ticket by reinstating its segment
Duplication Split a ticket using a specified interpretation of the whole capture
Abandonment Finish without running the captured suffix
Disposal Execute the close protocol needed for that abandonment
Escape Transfer the ticket and its obligations beyond the current clause
Suspension Retain owned execution without taking an evaluation step
Overlap Permit simultaneously live branch executions to access shared support

Linear use means no implicit contraction or weakening of authority. A resume-only ticket must be resumed on a normally completing local path. A resume-or-dispose ticket admits zero or one suffix executions while its authority is still consumed explicitly. An affine source binding can elaborate an unused ticket to disposal only if a close program is admitted; it cannot silently forget cleanup. Duplicable but non-discardable authority is possible.

In the one-shot Core target, resume/dispose action flags govern the clause's explicit expressions. An admitted outer discard can recursively consume live tickets wholly owned by its capture, even when their clauses only resume. Their close obligations still have to be discharged. Resume-only syntax alone therefore does not prohibit indirect abandonment; that stronger restriction would need a separate capability and an explicit Core semantic comparison.

Suspension is not escape: a task can pause within its owner. Escape is not duplication: a transferred ticket can remain one-use. Sequential repetition does not imply overlap safety. Eventual resumption, termination, and successful native release are not consequences of any of these usage permissions.

Explicit splitting and multi-shot execution

For the first precise extension, permit pure, total certified splitting. split_capture(C,pi) supplies two segments, an ownership partition, and a consistent renaming of internal continuation, handler-activation, and owner identities. Static site identities may remain shared. The certificate pi describes the resource interpretation; it is not arbitrary Rust cloning.

Both tickets must subsequently be consumed or validly transferred. In this rule S1 is the state supplied by the splitter and S2 extends it; the original k is consumed. Runtime exhaustion is outside its source-total idealization. Effectful or fallible cloning needs an explicit establishment computation and failure ownership protocol before it can instantiate a broader split rule.

Structural admissibility is recursive:

Captured component Splitting requirement
Ordinary frame Its semantically retained values permit duplication
Handler frame Provider environment and interpretation permit repeated installation/execution
Live clause group Every outstanding ticket and its ownership graph can be split consistently
External access Its owner remains live, and the access/protocol permits repeated use
Internal resource owner A specified branch-copy protocol; default is rejection
Armed cleanup or registration An explicit duplication policy; default is rejection
Running cleanup or unfinished close Rejected

An outer retained cell can be shared by two sequential branches without copying its owner. An internal cell can instead be copied into two fresh branch instances if the provider supplies a valid snapshot protocol. Every associated handle, request identity, saved instantiation, and dependency must be renamed. Snapshotting cannot proceed if outside references would become stale or ambiguous; the certificate must rule those out. Neither choice follows merely from multi-shot permission.

Turning an internal owner into one shared owner for several branches would require a new common owning scope and final completion protocol. That is an explicit additional interpretation, not an instance of ordinary frame copying. The initial candidate supports shared owners already outside the cut and certified branch copies; it does not silently invent shared internal ownership.

Callback start also preserves Run, retaining the callback's source-selected request annotation and reusing the existing running-frame and runtime proofs. Resource and handler installation now also preserve Run: the opened body retains its bound by the new cell and caller, while handler installation keeps one residual row across the body, declarations and installed frame. Both use the same source-chosen fresh identity for the runtime step. Disposal still requires the certificate retained at capture. Context plugging and capture need further shared-witness preservation proofs.

The structural stored-segment refinement now keeps each plain context's source annotation with its caller interface and each handler's declarations with its residual row. Initial source establishes the judgment, focus stores it, and plugging preserves it using the existing context and value proofs. Actual focus and plug steps preserve the corresponding runtime invariant. The preservation connections now retain this same invariant through ordinary computation, all returned-value forms, and resource, handler and cleanup installation. One structural transport proof covers world, contract, action and handler-table changes. Resumption now retains the exact saved derivation selected by the independent resume capability and consumes one owner. Builtin cell operations retain that same invariant and reduce the requirement row. Disposal and capture still need the stronger segment connection; source admission must also establish disposal certificates at capture. The source-derived capture interfaces now revise the experimental offer rule: a used resume or disposal bound equals the declaring handler's residual row; unused bounds remain independent. The actual cut retains that shared row on the capture and caller, and the selected clause supplies compatible interfaces for a concrete live boundary. Joining that boundary to the complete source/store/runtime capture transition remains open, as does source-derived disposal admission. Core correspondence follows the proof target and does not require retaining inadequate experimental source judgments. Current Core and normative Ash semantics are unchanged by this experiment.

The closing-route separation now has both shared source checking and a connected normal interface. Its plan is effect-typed with the complete callback row, yet no outward row can preserve the callback's selected local handler after the plan removes it. Widening the closing row therefore cannot repair that fixed capture. This reuses the pure callback with a conservative annotation; it neither proves initial reachability nor rules out choosing a compatible annotation at source entry. Its selected clause only resumes. General progress and source admission of disposing captures remain open.

What independent checking means

The judgments are separate but communicate constraints:

  1. Value/row checking establishes types and exact requirements.
  2. Clause checking infers or verifies which actions it uses on its ticket.
  3. Capture checking establishes that those actions are admissible for every segment that can reach that interpretation.
  4. Completion and support checking establish that resulting ownership transfers, closing positions, and retained access remain valid.

An exported function cannot hide control-sensitive requirements behind a bare effect row. It needs a qualified summary relating operation behavior to retained authority, or checking must specialize it at each admissible installation. The syntax, inference, and separate-compilation representation of these summaries remain open. CompatibleCuts is a named proof obligation with the structural cases above, not a claimed complete local inference rule.

Worked mixed-handler derivations

The examples below use the administrative syntax and ordinary integer primitives. They are design examples, not current executable Ash programs. All providers have an Int handler result in the first two examples.

Forwarding and work after resumption

Suppose an outer provider handles E.ask by resume k 10. The inner provider's clause is:

ask x with k =>
    let y = perform E.ask x;
    let z = resume k (y + 1);
    z + 100

Evaluate handle (handle (let a = perform E.ask (); a * 2) with inner) with outer.

  1. The inner request captures [B(a,a*2), H_inner].
  2. Its clause forwards outside H_inner. The outer request captures the inner clause's pending y binding and its live clause group, through H_outer.
  3. The outer provider resumes once with 10, restoring that clause group.
  4. The inner clause resumes its original capture with 11. Its body produces 22, which returns to the binding for z in the clause.
  5. The clause returns 122.

This is a derivation of nesting and forwarding using one binding rule. If the outer provider attempted to split at step 2, the live inner ticket would also need splitting permission. Its one-shot declaration blocks that operation.

Multi-shot outside a one-shot interpretation

Let Coin.pick : Unit -> Bool. Its provider uses:

pick ignored with k =>
    split k as left,right;
    let a = resume left true;
    let b = resume right false;
    a + b

Let Ask.read : Unit -> Int be interpreted by resume k 10. Evaluate:

handle (
    handle (
        let b = perform Coin.pick ();
        let n = perform Ask.read ();
        if b then n else n + 1
    ) with ask_once
) with coin_twice

The Coin cut contains the pending suffix and the Ask interpretation. The Ask provider has an unrestricted environment, and there is no live Ask ticket yet. Splitting can therefore produce two handler activations. Each branch later creates and resumes its own one-shot Ask ticket. Results are 10 and 11, and the enclosing clause returns 21.

Thus a one-shot clause contract does not prohibit repeated installation of reusable provider code. Conversely, capturing an already live one-shot ticket, as in the preceding example, does prohibit duplicating that ticket.

State placement and replay

Use a suffix which increments a cell initially containing zero and returns its new value. The choice prefix is evaluated once; only the captured suffix repeats.

Placement at choice capture Ownership interpretation Branch results
Cell owner outside the choice boundary Shared sequential access to one live cell 1, then 2
Cell owner inside the captured segment Default unique-owner rule Split rejected
Cell owner inside, with certified fresh snapshot splitting Two cells copied from zero before either branch runs 1, then 1

These are different specified behaviors. Moving a resource boundary through the capture point changes the interpretation and is not ordinary reassociation. Even a shared external owner can reject repetition if its protocol admits only one transition; copying an access handle does not prove protocol replay safety.

Disposal and the exact interpreter

Capture an armed cleanup action whose required logging interpretation lies inside the cut. Discard does not reinstall that interpretation. The close is rejected unless the action has an admissible surviving interpretation with the required selection relationship. A same-signature or same-instance fallback does not by itself prove that an overridden interpretation may be substituted.

If an enclosing cell remains available to an inner cleanup at its closing position, the cleanup can use it and the cell closes afterward. If the cleanup has already started, neither its invocation nor the unfinished close can be discarded. These are current constraints retained by the proposed calculus.

Provision and resource composition

Provision establishment is a typed protocol. Success produces a fresh identity a, access value v, interpretation p_a, and obligation package o. Its successful entry installs ownership outside interpretation:

O(a,P) :: K                         owns establishment's completion
H(h,E<a>,p_a) :: O(a,P) :: K        additionally interprets its body's requests

The top frame is shown first. A request to that interpretation captures H, but leaves its owner outside; the provider clause can access its own state. An outward request may capture both. This decomposition is a model of roles; it does not require splitting current fused builtin frames in the implementation.

Normal return through O checks that the result retains no disallowed local access, saves the result, completes o, and returns the saved value. A selected failure result from establishment never enters the body. Particular providers define their result wrappers: current cells have internal acquisition failure, whereas native buffers expose an ordinary Outcome. A general provision must not flatten or conflate those behaviors.

Partial establishment must already own any acquired obligations through its own checked scopes. No general rollback or destructor guarantee is inferred.

More explicitly, Init(r,x,n,eta0,P) saves the resource body while the provider's establishment expression runs. Ready(a,v,p_a,o) is an internal successful protocol result, not a freely forgeable source constructor. finish(o) performs normal completion and returns unit to Finish(o,v), which then returns the saved body value; this active completion cannot be abandoned. Freshen substitutes the new exact identity throughout the body's lexical instantiation and binds its access value.

provision-control

Finish has the same non-abandonment and non-duplication restrictions as Close; an outward request can capture and resume it once. The owner notation O(a,P,o) makes the obligation package explicit; earlier O(a,P) suppresses it. An establishment failure removes Init and produces the provider's specified failure outcome without installing H or entering n. For a fused builtin boundary these abstract roles must simulate its authenticated primitive transitions, including its specified failure channel.

For open fragments with compatible, distinct formal provision contexts, define composition by syntax and substitution:

(R; x => e) followed by (S; y => n)
    := (R,S; x => let y = e; n)

This combines requirements without executing establishment. Free occurrences are embedded by capture-avoiding renaming. A frame theorem must establish that the additional context preserves exact dispatch, support, and permitted cuts. Merely mentioning no additional resource name is not sufficient: an extra boundary can change capture or closing behavior.

Dependent provision uses ordinary sequence: evaluate a result, establish the next provision from it, then enter its body. It need not fit an independent product of provision parameters. Scope fusion and moving establishment earlier remain separate contextual-equivalence theorems. Observable acquisition failure or cleanup supplies immediate counterexamples to unconditional movement.

Suspension and escape

These extend ownership transitions without adding another expression calculus. The first suspension model is cooperative: a task yields between ordinary machine steps; no source stack, owner, or interpretation is copied or released. suspend saves the same task configuration with () as its next expression. Rescheduling restores it once. A suspended required cleanup remains required. No fairness or eventual resumption follows from the suspension permission.

For escape, use explicit transfer to an existing owning scope q. The initial candidate supports an owned inbox for homogeneous tickets; it does not require returning unrestricted continuation values or adding existential source types. park k in q transfers a ticket to that inbox and returns unit. The receiving scope fixes input Q, answer A, admissible support, interpretation context, and its completion policy.

The transfer must preserve the ownership graph and make the destination responsible for resumption or admitted disposal. TransferOK checks that all external support outlives the inbox's use, no owning cycle is created, and the resumption context preserves required exact interpretation and completion.

The local clause may finish after transfer. Later the inbox moves the ticket to a checked consumer, which supplies a Q; resumed execution produces an A for that consumer. It does not return into the finished original clause.

Capturing C does not capture Kout. A dependency on an outside resource or interpretation must therefore remain protected by q or be rejected. This candidate forbids unrestricted replacement of missing interpreters at resume. Lifetime extension alone does not make an interpretation available.

For example, a scope q can surround a local handler whose pause clause parks an otherwise self-contained ticket and returns unit. After that handler call returns, a consumer still inside q takes the ticket and resumes it once. The captured local handler returns as part of the segment, while the answer goes to the consumer. Moving the consumer outside q, or closing an external cell on which the segment depends, is rejected.

General continuation packaging, answer-type polymorphism, arbitrary heap escape, and mobile reinterpretation need further type and support rules. They are not claimed by this bounded escape construction.

Hooks and asynchronous execution

Synchronous hooks

Current hook roots and registrations are an encoding in the sequential kernel. The root resumes with its payload. A registration keeps its owner outside a generated handler whose clause forwards to the older chain, applies its saved callback, and resumes with the transformed value. For outer A and inner B, the result is B(A(payload)).

The callback runs with the registration-surrounding interpretation context; publication-only inner handlers remain in captured control. A closure alone does not store a handler stack. Registration ownership and saved lexical values must not be mistaken for captured interpretation. Owned abandonment removes registrations without invoking pending transformations.

One concrete asynchronous candidate

Use a distinct asynchronous publication API with publish : Payload -> EnqueueResult, where EnqueueResult is Accepted | Closed. It cannot keep the synchronous endomorphism's result contract when publication returns before transformations finish. A future awaited API can return a result through explicit joining; it is a separate contract. Internal preparation failure remains outside this ordinary result, unless a particular provider explicitly exposes an additional failure case.

The candidate has structured task groups, registration-site interpretation, selection at publication, and drain-on-close. These are choices for comparison, not current Ash behavior or consequences of an effect row.

  1. Publication selects the current ordered subscribers and prepares delivery items. It checks payload sharing/copying and all callback support before committing the batch. Enqueue order follows registration order.
  2. The task group owns every queued item. Starting one moves its obligation from queued to running, rather than deleting the obligation.
  3. Each callback evaluates with a retained, checked registration-site interpretation context. Sharing provider closures/instances requires an explicit task-context admissibility check. Surrounding expression frames, live continuation tickets, and completion owners are not blindly copied.
  4. Publication returns Accepted after enqueueing, not after callback completion. Callback result is unit; typed failures are retained in the group's chosen report instead of becoming implicit exceptions.
  5. Deregistration stops future selection. Already selected items retain their callback and support until completion. A registration or supporting resource cannot finish closing while those items still need it.
  6. Normal group close disables new publication into the closing group and drains its selected work before releasing support. A publication attempted after this point returns Closed and enqueues nothing. The exact interpretation remains available to retained work until draining finishes.

A draining callback cannot wait for the very scope whose close is waiting for it without risking deadlock; reject known dependency cycles, and do not infer general deadlock freedom from effect typing.

An asynchronously retained handler may itself capture restricted provider state. Registration-site interpretation cannot be obtained just by saving names or effect rows. If the context cannot be retained/shared lawfully, registration is rejected or the caller must supply a different explicit task context.

The scheduler extends a state to owned queued/suspended/running tasks and selects one ready machine step. Starting work, yielding, and finishing are distinct transitions. For one work item, the order is:

select < enqueue < start < finish < release-required-support

For precision, write scheduler state as <S,T>, where T maps task identities to local configurations and lifecycle states. A local step may read/update the shared provider state S; the scheduler never executes two such steps at once in this interleaving model. Done(t) records the unit result or explicit typed report and discharges that task's work obligation only after its local owned completion has finished.

scheduler-control

Enqueue and start additionally perform the checked task-context construction described above. Their provider-specific retention proof remains an extension obligation, rather than being hidden in an assumption that closures capture dynamic handlers. Scheduler lifecycle transitions are unavailable to ordinary source code except through the chosen typed scheduling provider.

Different items can interleave even on one thread. FIFO enqueue does not imply FIFO completion. Safety proofs quantify over all admitted schedules; eventual draining additionally requires fairness, terminating callbacks, and the stated environment assumptions. Cost observes queue length and retained support separately from publication latency.

Cancellation is a separate optional protocol. Cancelling queued work must dispose its retained authority; cancelling running work needs an admitted cut. A running cleanup remains non-cancellable under the base completion rules. Detached callbacks and automatic cancellation are not part of this first model.

Fan-out creates separate callback executions, each normally once. Multi-shot replays a captured computation. If that computation includes publication, replay can enqueue another batch. An exactly-once delivery claim needs an additional identity/deduplication protocol and is not supplied by either feature.

Laws, propositions, and checking

Use three relations: alpha/definitional equality of syntax, derivability from an effect/provider theory, and contextual equivalence of execution. The last observes results, termination/divergence, specified failures, and ordered external events. Async observation additionally distinguishes blocking and allowed schedules; trace sets alone are not a chosen complete equivalence. Allocation, identities, and timing enter observations when exposed by a contract.

The basic binding equations are direct substitution/frame equations. For a value v, let x = v; e agrees with capture-avoiding e[v/x] under the same usage conditions. Reassociation of nested lets with fresh binders has the same evaluation order and corresponding pending frames. A proof for extended control must show that the corresponding frames have the same admissible cuts; it may not move a handler, resource, or cleanup boundary in the process.

The one-shot target must prove progress. Its comparison with current Core may also identify changes needed in Core: a failed correspondence proof requires a counterexample and judgment about whether the calculus is wrong, the implementation violates the specification, or the language needs a semantic improvement. The current work assesses that status and records counterexamples; it does not bring Core into alignment. Any later semantic delta requires an explicit proposal. Correspondence claims must state the resulting common fragment and observations.

The first checking boundary uses ordinary types, usage dataflow, and capture analysis. Provider equations and rewrite theorems need proof certificates, restricted decision procedures, or externally established lemmas. Existing interface evidence is not automatically evidence for these propositions. Do not promise general automatic discovery of semantic equivalence.

Duplicating a capture is a specified operation, not an equation asserting that one execution equals two. Likewise, checked effectful disposal is not silent weakening. Commutativity, idempotence, and deduplication require separate laws.

The first evidence should be formal derivations and counterexamples, before runtime representation choices. Compare the direct rules against current specification derivations for exact forwarding, deep resume, owned discard, resource activation, and synchronous registration. The user-authorized one-shot formalization is a bounded proof experiment. It tests whether structural capture, restoration, support, and closing judgments preserve recursively owned one-shot control, including outside pending consumption and running completion. It compares against the current exact-dispatch, nested-capture, resource-support, and cleanup obligations cited above. Retain checked definitions, proofs, and counterexamples as design evidence; remove abandoned encodings. The experiment authorizes no product evaluator, source syntax, or inference change. Model checking finite examples can find counterexamples but does not replace preservation or simulation proofs for the unbounded language.

Open questions

  • What minimal qualified summary permits separate compilation of control-sensitive helpers without exposing their implementation or losing useful composition?
  • Which resource protocols can supply pure total branch copying, and which need explicit effectful/fallible fork computations?
  • How should source syntax expose provider result types and continuation contracts while preserving the intended rank restrictions?
  • Can effectful disposal remain fully structural, or do some providers require an explicitly supplied surviving interpretation package?
  • What proof language and trusted boundary can check provider equations and contextual rewrite certificates?
  • Which retained interpretation contexts can be shared by async work, and how much ordering must be stated by their resource protocols?
  • Which fairness-sensitive equivalence should govern async rewrites?

These gaps limit the combined calculus. They do not require replacing direct sequencing with a monadic language or introducing transformer conversions.
