Retained-baseline resource calibration, 2026-10-08

Development design notes · ash-lang 7949b6d

Informative design work. Proposals and experiments may be incomplete or superseded. Read the language specification for current rules.

All design notes

This is isolated TASK-0035 evidence under DN-0036. It changes neither Ash semantics nor production resource policy. Further optimization is paused; the user accepts current measured physical costs for continued feature development under the provisional decision budgets below.

Finding

The retained compiler executes the realistic SQLite cases with median wall times of approximately 0.06–0.23 seconds and 22–42 MiB process peak RSS on this host. Copying and persistence exceed ordinary admission charges despite these modest observed costs. The old numerical ceilings were not calibrated against these programs. There is no evidence here that their practical execution cost requires another optimization before delivery.

Input size alone is a poor allowance predictor. A flat program with 1,546 surface nodes incurs 10,301 Source charges; copying has 1,480 nodes and 1,212,707 charges, about 118 times as many. Adding the measured complexity terms improves Source coverage but still misses copying and bound NUL. These fits cannot serve as general resource-program admission rules.

The diagnostic override reaches some unreported owners too; this round does not calibrate every existing limit.

Collection and verification

Release compilation occurred once in a connected batch, followed by one additional generated-resource test build. Measurements invoke those exact artifacts directly; build time is excluded. The same binary runs with observation on and off and the same diagnostic base allowance of 16,777,216 units; Core retains its threefold allowance of 50,331,648. The ordinary 327,680 / 983,040 constants remain unchanged.

The historical builds used two Cargo jobs, a deviation from the coordinated one-job policy. Their receipts remain unchanged. Future reproduction uses one job; no rebuild or replacement of measured artifacts is implied.

The corpus contains 44 programs: flat declaration width, nested types, prerequisite depth, public reexport width/depth, string payload size, repeated resource scopes and five unchanged realistic SQLite cases. Twenty programs train the models; 24 are held out, including all five SQLite programs.

Each full round has one warmup and three measured fresh processes per mode: 352 processes, including 264 measured and 88 warmups. The first round supplied the initial fits. A second round added finer CPU measurements of the same corpus. Both rounds completed every case with zero failures. This replay is a measurement replication, not a new independent validation set. A prior 12-case smoke batch also passed both modes.

The native runs execute exactly one named test each and retain original database values, persistence/reopen, completion and release assertions. The runner rejects zero-test success, malformed records, missing/aborted phases, changed inputs/artifacts and timeout. A connected Python self-check covers those measurement failures. Feature-off release library checking passed; format and evidence checks are recorded in the capsule. There was no full workspace gate for this isolated experiment.

The host was Linux x86-64, AMD Ryzen 7 7435HS, 16 logical CPUs; Rust 1.97.1, LLVM 22.1.6, optimized release profile. These are local desktop measurements, not cross-machine performance guarantees. Three repetitions report observed ranges, not statistical confidence bounds.

Small programs consume real CPU even when GNU time prints 0.00: flat width one consumes a median 6.5 ms of wrapper-inclusive child CPU; width 128 consumes 25.0 ms. These measurements include startup, rendering and teardown. They must not be interpreted as pure checking costs or infer asymptotic complexity from such small totals.

The flat-width/copying comparison illustrates the distinction: about 118 times the Source charge corresponds to about 7.3 times the measured whole-process CPU, or 16 times the observed Source wall time, in this round. These are different programs and costs; there is no universal conversion from a charge unit to CPU time.

Input collection traverses each finite surface module once; it does not unroll recursive calls. Actual checker timing includes every traversal, context expansion or repeated analysis the implementation executes. Runtime recursion belongs to the separately timed evaluation phase. Recursive call structure was not an independent scaling axis in this corpus, so the estimates do not characterize that dimension.

For compiler allowances, complexity means the checking work induced by source structure. Runtime algorithmic complexity is a separate axis: executing one recursive function many times need not require equivalent static unfolding. Similarly sized sources can induce different instantiation, constraint and capture-analysis costs. The present aggregate descriptors do not establish which of those dimensions explains the observed gap.

The phase timers separate compilation from evaluation. In the first full round, evaluation consumed 0.4–1.8% of pipeline time. Copying's median Source time was 96.6 ms, about 52% of its pipeline; Core was 55.5 ms, about 30%. Persistence's Source was 55.1 ms, about 26%; Core was 105.3 ms, about 49%. Persistence has half copying's Source charge but is slower overall because its Core and final-elaboration costs are larger. Source charge alone cannot rank total compiler cost.

Whole-process peak memory also needs separate interpretation. Copying's high-water RSS is already near its final peak during Source checking. Persistence rises substantially during Core validation. Cumulative visits cannot establish peak live memory or isolate temporary allocations.

Observation-on/off CPU median differences for the five SQLite programs range from approximately −0.1% to +7.2% in the precision round. Small negative differences reflect measurement variation, not negative observer cost. Both modes retain feature-enabled allowance machinery. This comparison does not measure that machinery against a separately built ordinary executable.

Budget, work and limit

The user's terminology distinguishes three roles:

  • A budget predicts how much a language structure should typically cost.
  • Work records how much processing actually occurred; CPU/time/memory record corresponding execution costs in their own units.
  • A limit controls whether checking may continue. Headroom and stopping thresholds belong to this policy, not to the typical-cost estimate.

Existing implementation names such as TypeWorkBudget refer to bounded accounting. Keep their recorded charges distinct from a new predictive budget and from executed-operation counts: their reservation component prevents calling every charged unit actual processing. The next instrumentation must separate those components before fitting a language-level work budget.

For the known witnesses, measured medians provide reference costs. They are not general budgets for other structures. The initial fitted envelopes below include cushions/headroom and were evaluated as possible allowances; they must not be relabeled typical-cost predictions.

Growth and interpretation

  • Flat Source charges increase exactly 80 units per added function across widths 1–128; final elaboration adds 84 and Core adds 105.
  • Nested type and prerequisite families have positive constant second differences over depths 8/12/16, supporting a quadratic component in this tested range. This is not an asymptotic proof.
  • Resource scope totals include a large fixed library cost. Marginal Source charges per additional scope increase from 5,956 to 6,183.5 over the measured widths; sublinear total ratios do not establish linear scaling.
  • String payload produces exactly payload_bytes + 152 Core charges in the three sampled programs. The models record but omit payload bytes, explaining that predictable held-out miss. Source and final charges stay constant.
  • Reexport depth increases resolution and checking while leaving final/Core charges unchanged in this family. One allowance formula for every phase would hide this distinction.

The data establish missing predictors, not the cause of copying's amplification. Callable composition, branching, handlers and provider operations are possible dimensions to investigate. Claims about their individual contribution require controlled families or attribution evidence.

Keep the retained baseline. The next decision should distinguish a practical CPU/memory requirement from an admission-policy requirement before selecting another optimization. Any revised source predictor must be tested against new programs, since this held-out set has now been examined.

Incremental limit evaluation

The user's follow-up proposes evaluating limits incrementally. A whole-program estimate before checking is not required. The unsuccessful fits above test one possible predictor; their failure does not prevent incremental control.

Current structural ledgers already accumulate charges as checking proceeds. The next design can evaluate whether to continue at phase or bounded-work checkpoints, and can refine an allowance as relevant source, type and constraint structure becomes known. Size and complexity then inform policy and explain observed costs without requiring a complete cost prediction at entry. A configured CPU or memory ceiling can also be checked incrementally without a size-based prediction.

The design must distinguish consumed charges, measured execution costs, discovered complexity facts and the allowance decision. In particular, it should say which discovered facts justify an adjustment and which represent work consumed. This lets us assess both expensive legitimate programs and unnecessary expansion using the same measurements. Report the reason for continuation or refusal and the selected finite overall policy.

This is a design option, not implemented control. The current observers emit phase endpoints; the collector obtains whole-process CPU/RSS after execution and enforces an external timeout. It does not periodically enforce CPU or memory limits inside a phase, nor adjust allowances during checking. Moving to incremental evaluation needs checkpoint placement, ownership, measurement overhead and failure/retry behavior to be reviewed. The specification already separates bounded compiler policy from Ash value semantics and requires retry with sufficient work to agree with a fresh run.

Budget evaluation can also be incremental. At a checkpoint, compare observed work with the budget for the same processed language structure. Record both work - budget and work / budget where the budget is positive; keep an unfinished obligation separate. The budget may change as new relevant structure is discovered. A stopping decision remains a separate limit policy.

Language-level measures

The user's next clarification sets the unit of study: language structures and their checking obligations. A program is a witness of those structures, not the definition of complexity. Surface node totals and the five SQLite programs alone cannot justify a language-wide allowance or checker design.

The follow-up measurement plan derives measures from current type instantiation, evidence selection, exact effect instances, recursive bindings and resource-dependency rules. It pairs those structures with actual implementation visits, retained structures and CPU/RSS. This separates the question "which obligations arise?" from "how much work does this checker perform to discharge them?" without assuming that every repeated obligation is redundant.

These measures may be discovered incrementally. No complete static expansion or runtime-recursion unrolling is required before checking begins. The next decision needs controlled variation of depth, branching, reuse and lexical identity, plus realistic end-to-end witnesses. The new attribution instrumentation remains planned. The bounded structural reference below is complete using existing charged ledgers; it does not implement the distinction between executed visits and reservations.

Initial rough budget procedure

The user selected a simple first procedure. The offline estimator uses one fixed form:

budget = a + b*nodes
           + c*(type_nodes*type_depth)
           + d*(resource_sites*nodes)

nodes is the measured surface structure total; type_nodes and type_depth describe surface type syntax. resource_sites counts lexical resource initialization/binding sites, not dynamic operations. These existing input descriptors are available before inference. They are rough proxies for the language obligations identified in the follow-up plan, not the new typed attribution measures that remain unimplemented.

Use the procedure as follows:

  1. Collect completed case medians with a pinned compiler and measurement boundary. Keep CPU seconds, peak RSS KiB and each ledger's charged units separate.
  2. Fit nonnegative coefficients for each response using the same four terms. Keep a single point estimate; do not add cushions or headroom to the budget.
  3. Freeze the model and input hash. For a new measured feature vector, evaluate the formula and flag values outside recorded feature ranges. Being inside every range does not establish that a new combination is well represented.
  4. Compare actual cost with prediction in the same units. Record the signed residual and actual/predicted ratio. Recalibrate explicitly when new evidence warrants it; repeated observations are not new language examples.
  5. Decide stopping limits separately. The estimator neither changes compiler allowances nor feeds expanded work back into its own budget.

The first model artifact recalibrates on all 44 completed CPU-precision cases, including the already examined former held-out cases. It fits per-case medians, not maxima. The transfer comparison describes the eight existing Ash fixtures without refitting. Those measurements were already examined; this is not blind validation. Every response fit converged. Poor predictions remain visible, with no extra feature search or family classifier.

For example, the CPU estimate is 105 ms against copying's observed 184 ms, and 175 ms against persistence's 229 ms. Predicted RSS is 25.75 MiB versus 33.57 MiB for copying, and 36.52 MiB versus 42.38 MiB for persistence. These are rough references. The fitted CPU intercept is zero, although measured startup has a real cost; small-program CPU predictions understate that fixed cost. Relative error can therefore be large even when absolute error is a few milliseconds.

Ledger predictions are much weaker: copying Source is estimated at 476,786 against 1,212,707 charged units, while many basic programs are overestimated. Neither that miss nor an excessive ledger ratio proves excessive physical compiler cost. Use CPU and memory evidence alongside the charges when deciding whether optimization is needed. This initial procedure is implemented; a general calibrated budget or revised stopping policy is not.

The original allowance-envelope fits remain unchanged. Bayesian inference and richer predictors are deferred until a practical decision needs them. Prediction beyond the observed domain still needs confirmation; see the NIST guidance on extrapolation.

Accepted current costs and decision budgets

The decision-support calibration accepts all 52 primary measured cases under provisional current-workload objectives of 300 ms CPU and 64 MiB peak RSS. No further optimization is required by these measurements. The largest observations are 259.204 ms CPU and 42.5625 MiB peak RSS.

The raw four-term coefficients and charged-unit predictions remain unchanged. A measured startup control supplies a 10 ms CPU prediction floor. Separate review tolerances are twice predicted CPU plus 10 ms and 1.5 times predicted RSS, rounded to 10 ms and 4 MiB. Point predictions, tolerances, engineering targets and compiler stopping limits remain distinct. Ordinary compiler limits are unchanged, and new program shapes still need completed measurements.

Adopted calibration and accepted deficits

The adopted offline assessment now distinguishes accepted-with-deficit: measured median or maximum costs may exceed an original review threshold or workload target by at most 10% of each exceeded baseline. Every excess reports its original baseline as a future optimization target. Larger excesses require review, and missing/out-of-range observations remain outside calibration. Predictions and baselines are unchanged.

The current 52 cases still pass without deficits; the separate reference keeps nine acceptable and five outside-calibration cases. Thirty synthetic boundary replays verify the exact rule. The accompanying Type/Core work-budget review is scope-qualified advice for Common's separate admission work, with no compiler policy or Rust change in this checkpoint.

Functional Rust SQLite reference

Five working Rust counterparts now cover copying, persistence, resume, bound-NUL refusal and forwarding. All 60 fresh compiler jobs and ten native validations passed in one bounded round. Median Rust metadata checking cost 98–135 ms CPU and 107–111 MiB peak RSS; complete native compilation cost 232–384 ms CPU at O0 and 434–830 ms at O3. The shared Rust bridge is compiled in every job, and the source size is 17.8–20.2 KB versus Ash's 8.2–13.2 KB.

The full Rust comparison reports per-case CPU, wall, RSS, source sizes, executable sizes and semantic differences. Rust lifetimes and one-shot closures approximate the overlapping resource behavior; they do not reproduce Ash's effect machinery or independent Core verification. These informational results do not reopen optimization or change compiler policy.
