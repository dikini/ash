Determining interface results

The previous lesson used one complete requirement, Functor<Box>, while each map occurrence chose its own method-local types. Some interfaces relate two arguments even when an operation reveals only one of them. A measurement operation might receive a key type while its implementation fixes a dependent interface type that never appears in the method’s value type. That dependent type need not be the type of the value the method returns.

Ash can state one forward determination edge on an interface. The edge says which known arguments may determine the remaining arguments before Ash selects implementation evidence.

Declare the forward relationship

Read the relation and one implementation in measurement.ash:

pub interface Measure<Key, Result> where Key -> Result {
    measure : Key -> Int
}

pub impl Measure<Bool, Unit> {
    measure value = 42
}

Measure has the complete ordered parameter vector <Key, Result>. The where Key -> Result clause partitions it into a nonempty determinant and its dependent complement. This arrow is a static relationship between interface arguments, not a function from Key values to Result values.

Without a determination edge, every interface parameter must occur in each method type. Here only the determinant Key is required. Result may be absent from measure : Key -> Int because a source for the known key can fill it before selection. These conditions come from Ash’s interface well-formedness rules.

The published implementation is one such source. Its head records both arguments of the complete Measure application, while the method signature states what value a call returns.

Select a source for the known key

The successful client imports the method name and independently selects the published implementation fact:

import measurement (measure, impl Measure)

main : Unit -> Int
main () = measure(true)

Identify the key fixed by true, then the dependent argument supplied by the selected implementation. Predict the method’s returned value and type separately from those interface arguments. Run from this lesson’s src directory to compare the observation:

ash 01-selected.ash

Ash reports:

42 : Int

The method body returns 42. Its Key -> Int signature promises an integer result. Result is Unit in the implementation’s interface application; that type is not the method’s returned value type.

The argument true fixes Key = Bool without guessing. The selected source with that key improves the pending obligation by filling Result = Unit. Ash can then select the complete Measure<Bool, Unit> implementation and run its measure method.

The sequence matters:

known Bool key -> determine Unit -> select Measure<Bool, Unit>

Determination changes only static evidence checking. It creates no result-type projection, runtime search, or dynamic mapping from Bool to Unit. Checked evidence still lowers to ordinary functions and erased type operations.

A known key is not enough by itself

Now leave the same method call and ordinary import in place, but omit the implementation selector:

import measurement (measure)

main : Unit -> Int
main () = measure(true)

The call and its Int result annotation have not changed. Which interface argument remains unanswered without the selected source? Predict whether the checker can reach a complete evidence requirement, then run this entry:

$ ash --message-format human --locale en 02-name-only.ash

reason: constraint.ambiguous

Ash exits with status 1 and writes this message on standard error.

The call still fixes the key to Bool, but no selected implementation source is available to determine Result. The obligation therefore remains incomplete when its evidence scope closes. This is constraint.ambiguous, not constraint.unsatisfied: Ash has not reached a complete application for which it could establish that no candidate exists. The checked-evidence rules do not invent the dependent type or infer it from an implementation that the client did not select.

In the first lesson, the missing selector left a complete Equal<Int> requirement unsatisfied. Here the key is known but the dependent argument is still unresolved. The two messages identify different stages of checking.

The diagnostic’s primary label covers the measure occurrence. Its related labels point to the client’s name import, the original method declaration, and the complete Measure interface declaration. Together they retain the path from the ambiguous call back to the relation that owns its obligation. Restoring impl Measure makes the published source available to determine the dependent argument and satisfy the resulting complete requirement.

Practice: trace completeness before selection

Start each task with fresh copies of measurement.ash and 01-selected.ash together in a scratch directory.

  1. Change the implementation key and call argument from Bool to Int. Identify which source occurrence fixes the determinant. Predict the value and type before running the entry.
  2. Keep the selector but add a second published implementation with the same Bool key and a different dependent type. Predict the checking outcome, then use its labels to explain the interface’s invariant.
  3. Change the method signature to return Result, and update the implementation body and entry result annotation to agree with that contract. Predict the value and type, then run it. Explain what the edge records when ordinary result typing also exposes the dependent argument.
  4. Remove the determination clause. Identify which interface parameter the method type mentions, predict the checking outcome, and follow its labels.

In the two runs the call itself never changed. true gave the checker its key, the selected source filled Result, and the program returned 42; without that source, the same call stopped with its obligation still incomplete. The next chapter asks how container behavior can depend on its elements, so selecting one implementation may require further evidence.
