Running cleanup

A calculation may need to record that a scope has finished, even when a handler stops its body early. cleanup action { body } gives the scope one obligation: invoke the retained action when closing it. The action is an ordinary function from Unit to Unit; the obligation belongs to the scope.

We will use a live cell as a log. Appending digit one means multiplying its current value by ten and adding one. This makes action order visible without introducing external output operations.

Preserve the body result, then observe the action

01-normal-completion.ash writes nine in its body and appends one on closing:

import @builtin.cell as Cell

main : Unit -> (Int, Int)
main () = resource cell<R> log = 0 {
    let append_one : Unit -> Unit ! {Cell.Ops<R>} = fn(ignored) {
        Cell.write (log, (Cell.read log) * 10 + 1)
    }
    let result = cleanup append_one {
        let ignored = Cell.write (log, 9)
        42
    }
    (result, Cell.read log)
}

On normal completion, cleanup saves the body’s value, invokes the action, and then returns the saved value. Predict the pair’s fields separately: what does the body return, and what does the log contain after append_one? Run from this lesson’s src directory:

$ ash 01-normal-completion.ash
(42, 91) : (Int, Int)

The body returns 42 after writing 9; the action changes the log to 9 * 10 + 1, or 91. Its Unit result is set aside, preserving the body’s 42. The cleanup evaluation rules describe these two steps. The cell owner surrounds the cleanup and the final read, so the action has live access when it runs. Its function type records that access’s operation row. Cleanup does not require its action to be pure.

Close inner scopes before outer scopes

02-nested-cleanup.ash gives each scope a different closing action:

import @builtin.cell as Cell

main : Unit -> (Int, Int)
main () = resource cell<R> log = 0 {
    let append_one : Unit -> Unit ! {Cell.Ops<R>} = fn(ignored) {
        Cell.write (log, (Cell.read log) * 10 + 1)
    }
    let append_two : Unit -> Unit ! {Cell.Ops<R>} = fn(ignored) {
        Cell.write (log, (Cell.read log) * 10 + 2)
    }
    let result = cleanup append_one {
        cleanup append_two {
            42
        }
    }
    (result, Cell.read log)
}

An inner cleanup must close before its surrounding body finishes. Trace the two actions in that order and predict the log alongside the saved body result:

$ ash 02-nested-cleanup.ash
(42, 21) : (Int, Int)

The inner action appends 2, then the outer action appends 1, producing 21. Neither changes the saved 42. Copying an action function would copy an ordinary callable value, not the scope’s obligation to invoke it.

Close owned scopes when their body is abandoned

Stopping a calculation used discard to skip a list calculation’s remaining work. 03-discard-cleanup.ash places two cleanup scopes in the waiting computation:

import @builtin.cell as Cell

effect Stop {
    now : Unit -> Unit
}

main : Unit -> (Int, Int)
main () = resource cell<R> log = 0 {
    let append_one : Unit -> Unit ! {Cell.Ops<R>} = fn(ignored) {
        Cell.write (log, (Cell.read log) * 10 + 1)
    }
    let append_two : Unit -> Unit ! {Cell.Ops<R>} = fn(ignored) {
        Cell.write (log, (Cell.read log) * 10 + 2)
    }
    let result = handle (cleanup append_one {
        cleanup append_two {
            let ignored = perform Stop.now ()
            let ignored = Cell.write (log, 999)
            42
        }
    }) with Stop {
        now ignored => {
            let ignored = discard
            7
        }
    }
    (result, Cell.read log)
}

The stop request selects the outer clause. Its discard owns the captured cleanup scopes and invokes their actions while closing that abandoned work. Separate the waiting body work from its closing obligations. Which writes belong to the body, and which belong to the owned actions? Predict the log after those actions and the result chosen by the stop clause:

$ ash 03-discard-cleanup.ash
(7, 21) : (Int, Int)

Discard skips the later write of 999 and the body result 42. It closes the inner cleanup by appending 2, then the outer by appending 1; only after that does the clause return 7. The log cell remains live outside the handler. Cleanup can use it before its own resource scope eventually releases it. Here discard itself has effects because it invokes actions that write the cell. It is not universally pure.

Do not restore a handler that abandonment removes

Cleanup actions can request source effects too. The cleanup rules check the nearest matching interpreter at the action’s closing position, including the action’s own handlers and surrounding boundaries. If discard removes the nearest handler needed there, an outer handler for the same instance cannot replace it.

04-removed-handler.ash surrounds an action with a Report handler. Locate that handler relative to the stop handler before deciding what discard removes:

effect Stop {
    now : Unit -> Unit
}

effect Report {
    closed : Int -> Unit
}

report_close : Unit -> Unit ! {Report}
report_close ignored = perform Report.closed 1

main : Unit -> Int
main () = handle {
    let ignored = perform Report.closed 0
    handle {
        handle (cleanup report_close {
            let ignored = perform Stop.now ()
            42
        }) with Report {
            closed value => resume ()
        }
    } with Stop {
        now ignored => {
            let ignored = discard
            7
        }
    }
} with Report {
    closed value => resume ()
}

There is also an outer Report handler, used by the initial report. Which Report handler is nearest to the cleanup’s closing position? Would it remain available when the stop clause discards?

In 05-surviving-handler.ash, the handler needed by the action surrounds the stop handler and remains available during discard:

import @builtin.cell as Cell

effect Stop {
    now : Unit -> Unit
}

effect Report {
    closed : Int -> Unit
}

report_close : Unit -> Unit ! {Report}
report_close ignored = perform Report.closed 1

main : Unit -> (Int, Int)
main () = resource cell<R> log = 0 {
    let result = handle {
        handle (cleanup report_close {
            let ignored = perform Stop.now ()
            42
        }) with Stop {
            now ignored => {
                let ignored = discard
                7
            }
        }
    } with Report {
        closed value => {
            let ignored = Cell.write (log, value)
            resume ()
        }
    }
    (result, Cell.read log)
}

Follow the scopes from report_close outward: which handler can interpret its report while discard closes the cleanup? Predict both the stop clause’s result and the log:

$ ash 05-surviving-handler.ash
(7, 1) : (Int, Int)

The surviving Report handler writes the reported 1 and resumes the closing action. That action finishes before the stop clause returns 7. Another way to give an action its interpretation is to place the needed handler inside the action itself. A handler placed only in the body’s interior does not automatically cover an action that runs after that body has finished. The cleanup rules define these closing-position checks.

An action already running must finish

Starting an action does not erase its remaining obligation. In 06-running-action.ash, the action itself makes the stop request:

effect Stop {
    now : Unit -> Unit
}

stop_while_closing : Unit -> Unit ! {Stop}
stop_while_closing ignored = perform Stop.now ()

main : Unit -> Int
main () = handle (cleanup stop_while_closing {
    42
}) with Stop {
    now ignored => {
        let ignored = discard
        7
    }
}

Here the body has already returned and the action has started. What required completion would the stop clause’s discard skip?

Discard would skip the rest of the action and its unfinished close operation. The labels identify that required completion and the request that captures it. Use resume () in the stop clause to let the action finish. Resumption continues that invocation; it does not start the cleanup action again.

These rules govern normal completion and checked abandonment. They do not promise source cleanup after internal termination or exhaustion, and they do not prove that a diverging action eventually returns.

Practice: predict closing order

For each task, make a fresh copy of its named program in a scratch directory outside this lesson’s src tree, then run the copy from that directory.

Exchange the two actions in 02-nested-cleanup.ash. What does the log contain? Predict before running.

Change the body result in 01-normal-completion.ash. Which tuple field changes, and which action still runs?

Replace the stop clause in 03-discard-cleanup.ash with resume (). In what order do the body write, the inner action, and the outer action run? Trace them before running.

A cleanup scope retains one action and owns its invocation. Normal return preserves the body’s value; abandonment closes the owned scopes before the clause continues. Both paths must respect the resources and handlers available at closing. Next we will use scoped handlers to transform publications through several registered functions.
