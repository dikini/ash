Preserving callback effects

A function such as apply_twice does not need to know what calculation its argument performs. It calls the supplied function twice. But its signature still has to account for any effects those calls require.

We will start with a pure callback, then pass the bonus calculation from the previous lessons. This creates a reason to make the effect row a parameter, just as Learn made an element type a parameter of a reusable definition.

Start with a pure callback

A callback is an ordinary function passed to another function to be called there. In 01-pure-callback.ash, increment is the callback:

apply_twice : (Int -> Int, Int) -> Int
apply_twice (function, value) = function (function value)

increment : Int -> Int
increment value = value + 1

main : Unit -> Int
main () = apply_twice (increment, 40)

Start with the inner call, function value, and use its result as the input to the outer call. Predict what applying increment twice does to the starting value, then run the file from this lesson’s src directory:

$ ash 01-pure-callback.ash
42 : Int

The first call turns 40 into 41. The second uses that result and produces 42. Neither call requests an effect.

The tuple parameter contains a pure function of type Int -> Int and its starting integer. apply_twice also promises a pure result computation. Those promises agree with increment.

An effectful callback needs a different contract

Now try supplying score. 02-pure-contract.ash installs a handler around the call, but leaves the pure signature of apply_twice unchanged:

effect Bonus {
    amount : Unit -> Int
}

score : Int -> Int ! {Bonus}
score points = points + (perform Bonus.amount ())

apply_twice : (Int -> Int, Int) -> Int
apply_twice (function, value) = function (function value)

main : Unit -> Int
main () = handle (apply_twice (score, 40)) with Bonus {
    amount ignored => resume 2
}

Compare score’s signature with the function component of apply_twice’s tuple parameter. Which requirement does each row describe? Keep the outer handler in view as you check whether the supplied function fits that parameter:

$ ash --message-format human --locale en 02-pure-contract.ash
This function argument must have type `(Int -> Int, Int)`, but has type `(Int -> Int ! {Bonus}, Int)`.
  --> /path/to/ash-doc/content/effects/preserving-callback-effects/src/02-pure-contract.ash:12:31
12 | main () = handle (apply_twice (score, 40)) with Bonus {
   |                               ^ This has type `(Int -> Int ! {Bonus}, Int)`.
  --> /path/to/ash-doc/content/effects/preserving-callback-effects/src/02-pure-contract.ash:8:15
8 | apply_twice : (Int -> Int, Int) -> Int
  |               ^ This function requires an argument of type `(Int -> Int, Int)`.
  --> /path/to/ash-doc/content/effects/preserving-callback-effects/src/02-pure-contract.ash:12:18
12 | main () = handle (apply_twice (score, 40)) with Bonus {
   |                  ^ This is the containing function application.
reason: type.argument

The first label identifies the supplied argument. The second points back to the tuple parameter in apply_twice’s signature, and the third identifies the whole call. Together they show where the effectful function meets a pure function requirement.

score has type Int -> Int ! {Bonus}, while the helper requires Int -> Int. The outer handler can answer a request made during a valid calculation; it does not change the helper’s required argument type. The callback contract has to describe the function being supplied.

The message names Bonus in the supplied function’s nonempty row. The callback may request a bonus; the helper’s pure callback contract permits no such request.

We could specialize apply_twice to Bonus. Instead, its body gives us a more useful contract: it needs whatever effects the supplied function needs.

Give the row a parameter

03-open-row.ash makes both the value type and the effect row parameters:

effect Bonus {
    amount : Unit -> Int
}

score : Int -> Int ! {Bonus}
score points = points + (perform Bonus.amount ())

apply_twice<A : Type, R : EffectRow> : (A -> A ! {| R}, A) -> A ! {| R}
apply_twice (function, value) = function (function value)

increment : Int -> Int
increment value = value + 1

main : Unit -> (Int, Int)
main () = {
    let pure_score = apply_twice (increment, 40)
    let bonus_score = handle (apply_twice (score, 40)) with Bonus {
        amount ignored => resume 2
    }
    (pure_score, bonus_score)
}

A : Type says that A stands for an ordinary value type. R : EffectRow says that R stands for an effect row. A row parameter is not an integer, a handler, or an ordinary type parameter. It describes which effects a computation may require.

The notation {| R} is an open row: it has no explicitly listed effect instances and has the tail R. Both occurrences of {| R} in the signature refer to the same parameter. The callback may require R, so calling apply_twice may require R too. The helper calls the callback without installing a handler or adding a separate effect.

Each use of this signed global definition instantiates its parameters. For each call in main, identify A from the callback’s input and result types, and R from its effect row. Use those substitutions to trace the callback’s two calls, then predict both results:

$ ash 03-open-row.ash
(42, 44) : (Int, Int)

In the call with increment, A is Int and R is the empty row. In the call with score, A is again Int and R is {Bonus}. Each call gets the contract its callback needs. The second call is handled; the first needs no handler.

The effectful calculation adds two to 40, then adds two to 42. Calling the callback twice still requires the row {Bonus}, not two entries for Bonus. A row records effect requirements, not request counts or execution order. The inner call in function (function value) finishes before its result is passed to the outer call; the expression determines that order.

Compare the body of apply_twice with the earlier version. Only its signature needed to change. The row parameter lets that same body describe both uses. All the polymorphic helpers here have global signatures; this explanation does not depend on generalizing local function bindings.

Add a known effect to the callback’s row

A different helper might call its callback once and then request a bonus of its own. Its result must include both requirements. In 04-known-effect.ash, add_bonus writes the known effect beside the tail:

effect Bonus {
    amount : Unit -> Int
}

add_bonus<R : EffectRow> : (Int -> Int ! {| R}, Int) -> Int ! {Bonus | R}
add_bonus (function, value) = (function value) + (perform Bonus.amount ())

increment : Int -> Int
increment value = value + 1

main : Unit -> Int
main () = handle (add_bonus (increment, 40)) with Bonus {
    amount ignored => resume 2
}

The callback has row {| R}. The helper’s result has row {Bonus | R}: the known Bonus instance together with the remaining effects represented by R. This notation also records that R excludes that exact Bonus instance. The tail is the remainder, not an unknown row that might duplicate the known member.

The addition uses the callback’s result and the helper’s own requested bonus. Follow the callback first and the request second, then predict their sum:

$ ash 04-known-effect.ash
43 : Int

Here the callback is pure, so R becomes empty. increment 40 produces 41, and the handler supplies 2 for the helper’s request. Adding them produces 43; only the helper introduces a Bonus requirement.

The tail’s exclusion also limits which callbacks this helper accepts. A callback that itself requests Bonus cannot supply that tail. We will examine that call after checking why the known member is needed in the result row.

Do not guess what an unknown tail contains

05-unknown-union.ash drops the known member from the result row:

effect Bonus {
    amount : Unit -> Int
}

add_bonus<R : EffectRow> : (Int -> Int ! {| R}, Int) -> Int ! {| R}
add_bonus (function, value) = (function value) + (perform Bonus.amount ())

increment : Int -> Int
increment value = value + 1

main : Unit -> Int
main () = handle (add_bonus (increment, 40)) with Bonus {
    amount ignored => resume 2
}

The body still combines the callback’s unknown row with a Bonus request. Compare the result signature with the preceding version. Does it establish that the tail excludes the known effect being added? Inspect the rejected expression:

$ ash --message-format human --locale en 05-unknown-union.ash
This expression combines effect rows that have no most general union.
  --> /path/to/ash-doc/content/effects/preserving-callback-effects/src/05-unknown-union.ash:6:31
6 | add_bonus (function, value) = (function value) + (perform Bonus.amount ())
  |                               ^ This expression combines effect rows that have no most general union.
reason: effect.row-union-ambiguous

The label identifies the expression combining the two requirements. This message uses the same reason code seen for the incorrect closed contract in the preceding lesson, but its explanation concerns an unknown row union. The signature neither includes Bonus explicitly nor establishes that R excludes it. Ash does not invent that exclusion to make the union work. Restore {Bonus | R} in the result signature, as in 04-known-effect.ash. That states the known requirement and the restriction on the remaining tail.

The effect-row rules govern these unions and exclusions. Known members form an unordered set: their written order does not select handlers or order requests. The type checker also needs enough information about open tails; it cannot assume facts about an unconstrained tail merely because one particular call uses a pure callback.

Respect the tail’s exclusion at a call

Now try the bonus-requesting score as the callback to add_bonus. 06-excluded-callback.ash retains the known member beside the result tail and passes score to the helper:

effect Bonus {
    amount : Unit -> Int
}

add_bonus<R : EffectRow> : (Int -> Int ! {| R}, Int) -> Int ! {Bonus | R}
add_bonus (function, value) = (function value) + (perform Bonus.amount ())

score : Int -> Int ! {Bonus}
score points = points + (perform Bonus.amount ())

main : Unit -> Int
main () = handle (add_bonus (score, 40)) with Bonus {
    amount ignored => resume 2
}

Read the row in score’s signature, then substitute it for R in the helper’s callback type. Can that substitution satisfy the exclusion recorded by {Bonus | R}? Run the file to inspect the call boundary:

$ ash --message-format human --locale en 06-excluded-callback.ash
This computation requires an effect excluded from the row tail. An effect written before a row tail cannot also occur in that tail with the same type arguments.
  --> /path/to/ash-doc/content/effects/preserving-callback-effects/src/06-excluded-callback.ash:12:29
12 | main () = handle (add_bonus (score, 40)) with Bonus {
   |                             ^ This computation requires an effect excluded from the row tail. An effect written before a row tail cannot also occur in that tail with the same type arguments.
  --> /path/to/ash-doc/content/effects/preserving-callback-effects/src/06-excluded-callback.ash:5:28
5 | add_bonus<R : EffectRow> : (Int -> Int ! {| R}, Int) -> Int ! {Bonus | R}
  |                            ^ This type is required here.
reason: effect.row-exclusion

The first label points at the supplied callback and its starting value. The related label points at the helper’s required callback type. The message explains why matching them fails: the known effect cannot also occur in the tail with the same type arguments.

score requires {Bonus}. Matching that callback against Int -> Int ! {| R} would put Bonus into R. The helper’s result row {Bonus | R} requires that R exclude that same instance, so this substitution cannot satisfy the contract.

Use the pure increment callback from 04-known-effect.ash to satisfy this contract. Its empty row fits R, leaving only the helper’s own Bonus request. If the helper is intended to share Bonus with its callback, its callback contract must include that known effect explicitly as well.

This is a restriction on substituting a row into a contract. It does not mean that a calculation can request a given effect only once: apply_twice already requested the bonus twice using one effect-row member.

Practice: preserve the callback’s contract

Use a fresh copy of 03-open-row.ash for each of the first two tasks, and a fresh copy of 04-known-effect.ash for the third. Keep the copies in this lesson’s src directory.

Rename apply_twice to apply_three_times and make it call its callback three times. Predict both results before running. Does the row need to change?

Now add a pure Boolean callback that exchanges true and false, and use the same apply_twice definition with it. Which value-type and row arguments does this use supply? Run it to check.

In 04-known-effect.ash, change the handler’s bonus and the initial points. Trace the callback first and the helper’s request second; predict the result without changing either function’s contract.

A reusable helper can leave its value type and its effect requirements open. The repeated row parameter connects what the callback needs to what the helper needs. A known member beside that tail adds a requirement and makes an exclusion explicit.

So far each successful effectful calculation has used one handler for Bonus. Next we can ask which handler receives a request when handlers are nested or when a program uses different effect instances.
